# 정보 수집 및 템플릿

> 이 파일이 해결하는 문제：문서를 작성하기 전에 수집해야 하는 프로젝트 정보 필드, 미확인 정보의 표기 규칙을 정의하고, 자리표시자 색인, 용어 대조 템플릿, 의존성 목록 템플릿과 그대로 복사할 수 있는 프로젝트 정보 수집 본문을 제공합니다.

## 1. 필수 필드（누락 시 차단）

| 필드 | 설명 | 영향 섹션 |
| --- | --- | --- |
| 프로젝트 이름 | 리포지터리 이름과 표시 이름, 둘이 일치하지 않을 때는 설명해야 함 | 전체 |
| 한 줄 포지셔닝 | 60자 이내, 프로젝트가 무엇이며 누구의 어떤 문제를 해결하는지 설명 | 제1장 |
| 리포지터리 설명（국가 언어 및 영어） | 두 언어 각각 120자 이내, 프로젝트 유형과 핵심 용도를 각각 설명 | 제1장 |
| 토픽 태그 | 소문자 영어 단어 20개를 모두 채우고 `-`로 연결, 대소문자 혼용 또는 비영어는 누락으로 간주 | 제1장 |
| 프로젝트 배경 | 착수 이유, 기존 방안의 부족한 점 | 제2장 |
| 핵심 기능 목록 | 모듈별로 그룹화, 사용자가 인지할 수 있는 동작 포함 | 제3장 |
| 기술 스택 | 언어, 프레임워크, 런타임 버전 제약 | 제6장 |
| 의존성 목록 | 이름, 버전, 라이선스, 저작권자, 출처 주소 | 제6장、NOTICE |
| 라이선스 유형 | 프로젝트 자체의 라이선스, SPDX 식별자여야 함 | 제19장 |
| 저작권자 | 개인 이름 또는 조직 전체 이름, 그리고 연도 | 제19장、NOTICE |
| 설치 및 실행 방법 | 환경 요구 사항, 명령, 예상 결과 | 제7、8장 |

## 2. 선택 필드

설정 항목 목록, API 정의, 디렉터리 구조, 성능 테스트 데이터, 호환성 매트릭스, 알려진 문제, 변경 이력, 로드맵, 기여 절차, 보안 정책, 스크린샷과 데모 주소, 외부 소재 출처.

## 3. 필드 작성 설명 및 예시

| 필드 | 작성 설명 | 예시 |
| --- | --- | --- |
| 프로젝트 이름 | 리포지터리 이름은 소문자, 숫자와 `-`를 사용하고, 표시 이름은 브랜드 표기를 사용할 수 있으며, 둘이 일치하지 않으면 이유를 명시 | 리포지터리 이름 `markdown-lint-cli`, 표시 이름 `Markdown Lint CLI` |
| 한 줄 포지셔닝 | 분류어와 한정어를 포함하고, 형용사를 나열하지 않으며, 60자 이내 | `기술 문서 팀을 위한 Markdown 규범 검사 명령줄 도구` |
| 리포지터리 설명（국가 언어 및 영어） | 국가 언어와 영어가 각각 독립된 문장을 이루고, 모두 120자 이내이며, 구호로 설명을 대체하지 않음 | `中文：检查 Markdown 文档结构的命令行工具` / `English: A CLI tool for checking Markdown document structure` |
| 토픽 태그 | 모두 소문자 영어, 단어 사이는 `-`로 연결, 20개를 모두 채우고, 언어, 형태, 용도, 생태계, 시나리오를 완전히 포괄 | `go cli markdown linter developer-tools` |
| 기술 스택 | 주 언어, 프레임워크와 런타임 버전 제약을 명시하고, 「최신 버전」이라고 쓰지 않음 | `Go >= 1.22；Cobra v1.8.x` |
| 의존성 목록 | 각 항목에 버전, 라이선스, 저작권자와 공식 주소를 포함하고, 출처가 불분명할 때는 미확인 항목으로 표기 | 부록 C의 의존성 목록 표 템플릿 참조 |
| 라이선스 유형 | SPDX 식별자를 사용하고, 「오픈소스」「자유롭게 사용 가능」 등 모호한 표현을 사용하지 않음 | `MIT` |
| 설치 및 실행 방법 | 현재 작업 디렉터리, 전체 명령과 검증 가능한 예상 출력을 제시 | 리포지터리 루트에서 `go install ./cmd/mdlint` 실행, 버전 번호 출력 |
| 미확인 항목 | 고정 표기를 사용하고, 누락 내용과 보완 책임자를 명시하며, 「잠정」으로 대체하지 않음 | `【待确认：依赖 foo 的许可证类型，责任人：张三】` |

## 4. 미확인 정보의 표기 규칙

1. 통일 형식: `【待确认：具体缺什么】`, 「잠정」「대략」「아마」 등 모호한 표현으로 대체해서는 안 됩니다.
2. 표기 위치: 본문의 해당 위치에 한 곳, 문서 말미의 「미확인 사항 정리」에 다시 한 번 나열합니다.
3. 라이선스, 저작권, 의존성 출처와 관련된 미확인 항목은 NOTICE에 반드시 명시적으로 표기하고, 항목 전체를 생략해서는 안 됩니다.
4. 미확인 사항 정리에는 번호, 필드, 누락 내용, 보완 책임자와 보완 예정 시각을 포함해야 하며, 책임자나 시각이 없는 항목은 단계 0에 진입할 수 없습니다（[실행 프로세스](./실행-프로세스.md) 참조）.

## 5. 부록 A · 자리표시자 색인

`{{项目名称}}`、`{{一句话定位}}`、`{{当前版本}}`、`{{维护状态}}`、`{{许可证 SPDX}}`、`{{著作权人}}`、`{{年份}}`、`{{分支名}}`、`{{仓库地址}}`、`{{最低运行时版本}}`

사용 규칙:

1. 이 색인은 수집 단계의 기본 필드만 나열합니다. README 전체 자리표시자와 그 설명은 [README 표준 템플릿](./README-표준-템플릿.md)의 자리표시자 대조표를 기준으로 합니다.
2. 정식 자리표시자는 통일되게 `{{纯名}}`으로 작성하고, 중괄호 안에 설명 텍스트, 백틱 또는 두 번째 자리표시자를 중첩해서는 안 됩니다. 규범 예시의 자연어 중괄호 내용은 정식 자리표시자로 간주하지 않습니다.
3. 수집 표의 자연어 필드는 자리표시자를 직접 사용하지 않으며, README를 생성할 때 대조표에 따라 해당 자리표시자로 매핑하고, 최종 문서에는 어떠한 설명적 중괄호 내용도 남겨서는 안 됩니다.

## 9. 부록 D · 복사 가능한 프로젝트 정보 수집 본문

다음 내용을 대상 프로젝트의 `项目信息采集表.md`에 복사하고, 「작성:」 뒤의 내용을 항목별로 교체합니다. 확인할 수 없는 필드는 제4절 규칙에 따라 표기하고, 제8절에서 정리합니다.

````markdown
# 프로젝트 정보 수집표

> 이 파일은 문서 생성에 필요한 정보를 한 번에 수집하는 데 사용합니다. 작성이 끝나면 수집 결과에 따라 README, NOTICE와 기타 인도 문서를 생성합니다.

## 1. 기본 정보

| 필드 | 작성 내용 |
| --- | --- |
| 리포지터리 이름 | 작성: 소문자, 숫자와 하이픈으로 구성된 리포지터리 이름 |
| 표시 이름 | 작성: 외부에 표시하는 프로젝트 이름, 리포지터리 이름과 같을 때는 「리포지터리 이름과 동일」이라고 작성 |
| 리포지터리 주소 | 작성: 전체 HTTPS 주소 |
| 대상 브랜치 | 작성: 기본 브랜치 이름 |
| 언어 코드 | 작성: 우선 언어 코드, 예: zh-CN |
| 현재 버전 | 작성: 시맨틱 버저닝 번호 또는 「미릴리스」 |
| 유지보수 상태 | 작성: 활발한 유지보수 / 저빈도 유지보수 / 아카이브됨 |
````
