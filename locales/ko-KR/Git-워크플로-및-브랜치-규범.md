# Git 워크플로 및 브랜치 규범

> 이 파일이 해결하는 문제：브랜치 모델, 명명 규칙, 풀 리퀘스트 설명 템플릿과 병합 전략을 정의하여 메인라인의 안정성, 협업의 질서, 변경의 추적 가능성을 보장합니다.

## 1. 규범 조문

1. 기본 브랜치(`main` 또는 `master`)는 반드시 보호해야 하며, 직접 push하는 것은 금지합니다(하드 룰 H7에 해당).
2. 모든 변경은 개인 브랜치 + 풀 리퀘스트를 통해 메인라인에 병합합니다.
3. 장기 브랜치와 단기 브랜치는 반드시 명확히 구분하여, 브랜치가 장기간 병합되지 않는 상황을 피해야 합니다.
4. 공용 브랜치에 `git push --force`하는 것은 금지합니다. 개인 브랜치를 재작성할 때는 `--force-with-lease`를 사용합니다(H8에 해당).
5. 이미 푸시된 공용 브랜치에 rebase/amend하는 것은 금지합니다. 병합 전에는 반드시 CI와 코드 리뷰를 통과해야 합니다.

## 2. 브랜치 모델

| 브랜치 유형 | 라이프사이클 | 생성 기준 | 병합 대상 | 명명 형식 | 예시 |
| --- | --- | --- | --- | --- | --- |
| 기본 브랜치 | 장기 | — | — | `main` | `main` |
| 기능 브랜치 | 단기, ≤2주 | `main` | `main` | `feat/<간략 설명>` | `feat/user-login` |
| 수정 브랜치 | 단기, ≤1주 | `main` | `main` | `fix/<간략 설명>` | `fix/token-expiry` |
| 문서 브랜치 | 단기 | `main` | `main` | `docs/<간략 설명>` | `docs/api-guide` |
| 릴리스 브랜치 | 중기 | `main` | `main` + tag | `release/<버전>` | `release/1.2.0` |
| 긴급 수정 | 단기, ≤24시간 | 릴리스 tag | `main` + tag | `hotfix/<간략 설명>` | `hotfix/payment-error` |

명명 규칙: 소문자 kebab-case를 사용하며, 간략 설명은 의도를 표현할 수 있어야 하고 `test`, `temp`, `wip`, `my-xxx`는 금지합니다. 요구사항과 연결할 때는 요구사항 번호를 추가합니다. 예: `feat/spacing-rule-req001`.

## 3. 풀 리퀘스트 설명 템플릿

```markdown
## 변경 목적
{{이 변경이 왜 필요한지 한 문장으로 설명, 요구사항 번호 연결}}

## 변경 내용
- {{구체적 변경 1}}
- {{구체적 변경 2}}

## 영향 범위
- 영향받는 모듈: {{모듈명}}
- 호환성 파괴 여부: {{예 / 아니오, 예인 경우 마이그레이션 설명 제시}}
- 구성 또는 데이터 마이그레이션 포함 여부: {{예 / 아니오, 예인 경우 설명}}

## 검증 방법
- 자체 테스트 명령: {{명령}}
- 추가 또는 수정한 테스트: {{TC 번호}}
- CI 실행 주소: {{URL}}

## 연관
- 요구사항: {{REQ-NNN}}
- 추적 매트릭스: {{업데이트 완료 / 업데이트 예정}}
- 문서: {{docs/api.md#섹션 / 없음}}
- Issue: {{#번호 / 없음}}

## 자체 점검
- [ ] 커밋 메시지가 규범을 준수함
- [ ] 민감 정보를 포함하지 않음
- [ ] 요구사항 추적 매트릭스를 업데이트함
- [ ] 호환성 파괴 변경을 변경 이력에 기록함
```

## 4. 필드 정의

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 브랜치 간략 설명 | 예 | kebab-case | 의도를 독립적으로 표현할 수 있어야 하며, 무의미한 단어 금지 | `spacing-rule` |
| 연관 요구사항 | 예 | `REQ-NNN` | 착수 번호와 일치 | `REQ-001` |
| 변경 목적 | 예 | 텍스트 | 「무엇을 바꿨는지」가 아니라 「왜」를 설명 | `중국어 문장 부호 오탐 수정` |
| 영향 범위 | 예 | 텍스트 | 호환성 파괴 여부를 반드시 명확히 | `아니오` |
| 자체 테스트 명령 | 예 | 명령 | 복사하여 실행 가능해야 함 | `npm test -- -t spacing` |
| 테스트 번호 | 예 | `TC-NNN` | 테스트 규범 번호와 일치 | `TC-001` |
| CI 주소 | 예 | URL | 리뷰어가 확인하기 쉽도록 | `https://github.com/.../runs/123` |
| 자체 점검 체크리스트 | 예 | 체크 | 항목별로 체크하며, 한 번에 전체 구간을 체크하는 것은 금지 | — |

## 5. 작성 설명

1. **브랜치 라이프사이클**: 2주를 초과하여 병합되지 않은 기능 브랜치는 이터레이션 회고에서 사유를 설명하고 분할하거나 종료해야 합니다.
2. **간략 설명 명명**: 변경 목적에서 핵심 명사 + 동작을 취하며, `fix2`, `new-feature` 등 모호한 이름은 사용을 금지합니다.
3. **변경 목적**: 문제와 가치를 작성합니다. 「코드 업데이트」「로직 최적화」는 부적합합니다.
4. **영향 범위**: 호환성 파괴를 체크할 경우, 반드시 동시에 변경 이력에 `BREAKING CHANGE:`를 표기해야 합니다.
5. **자체 테스트 명령**: 리뷰어가 직접 복사하여 실행하고 동일한 결론을 얻을 수 있어야 하며, 단계가 복잡한 경우 스크립트 경로를 작성합니다.
6. **추적 매트릭스**: PR 병합 전에 [요구사항 추적 매트릭스 규범](./요구사항-추적-매트릭스-규범.md)의 구현 PR과 상태 필드를 업데이트해야 합니다.
7. **force push**: 다른 사람이 리뷰하지 않은 본인 브랜치에만 `--force-with-lease`를 사용하며, 반드시 PR에서 사유를 설명해야 합니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| 브랜치명 `test`, `temp` | 의도 정보 없음 | `feat/<구체적 역량>`으로 변경 |
| PR 설명에 「버그 수정」만 작성 | 영향을 리뷰할 수 없음 | 목적, 영향, 검증 방법 보완 |
| `main`에 직접 push | H7 위반 | PR 병합으로 진행 |
| 이미 리뷰된 브랜치를 재작성한 뒤 강제 푸시 | 리뷰 결론 무효화 | 의견에 대응하는 커밋 추가 |
| 병합 후 소스 브랜치 미삭제 | 브랜치 목록 비대화 | 병합 후 즉시 삭제 |

## 6. 완전한 예시

```markdown
## 변경 목적
중국어 문장 부호가 영어 단어에 인접할 때 공백 규칙이 오탐하는 문제를 수정합니다(REQ-004).

## 변경 내용
- 규칙 엔진에 문장 부호 경계 판정 추가
- 대응 회귀 케이스 추가

## 영향 범위
- 영향받는 모듈: spacing 규칙
- 호환성 파괴 여부: 아니오
- 구성 또는 데이터 마이그레이션 포함 여부: 아니오

## 검증 방법
- 자체 테스트 명령: `npm test -- -t "중국어 문장 부호"`
- 추가 또는 수정한 테스트: TC-007-regression-142
- CI 실행 주소: https://github.com/example/markdown-lint-cli/actions/runs/128

## 연관
- 요구사항: REQ-004
- 추적 매트릭스: 업데이트 완료
- 문서: 없음
- Issue: #142

## 자체 점검
- [x] 커밋 메시지가 규범을 준수함
- [x] 민감 정보를 포함하지 않음
- [x] 요구사항 추적 매트릭스를 업데이트함
- [x] 호환성 파괴 변경을 변경 이력에 기록함(본 변경은 호환성 파괴 없음)
```
