# 감사 보고서 형식

> 이 파일이 해결하는 문제：감사 보고서의 유일한 인도 형식, 필드 요구사항과 작성 예시를 정의하여 보고서를 다른 agent 가 그대로 실행할 수 있도록 보장합니다.

보고서는 감사 단계의 유일한 산출물입니다. 각 문제는 근거, 책임 주체, 조치를 동시에 갖추어야 하며, 실행할 수 없는 결론은 보고서에 기록해서는 안 됩니다.

## 1. 보고서 뼈대

````markdown
# 푸시 감사 보고서 · {{仓库名}}

결론：{{结论}}
모드：{{模式}}
리포지터리：{{仓库名}} · {{可见性}} · {{许可证}} · 기본 브랜치 {{默认分支}}

## I. 게이트 상태
| 게이트 | 상태 | 미결 항목 |
| --- | --- | --- |
| A 보안 | {{门禁状态}} | {{未决项}} |
| B 품질 | {{门禁状态}} | {{未决项}} |
| C 홈페이지 | {{门禁状态}} | {{未决项}} |

## II. 문제 목록
| 등급 | 차원 | 문제 | 근거(경로:행 / 명령 출력) | 책임 agent | 조치 |
| --- | --- | --- | --- | --- | --- |
| {{等级}} | {{维度}} | {{问题}} | {{证据}} | {{责任agent}} | {{动作}} |

## III. 문서 매트릭스 상태
| 파일 | 상태 | 누락/수정 대기 항목 |
| --- | --- | --- |
| {{文件路径}} | {{状态}} | {{待改项}} |

## IV. 푸시 실행 체크리스트
- [ ] {{推送规则}}

## V. 통과 설명
{{放行说明}}
````

## 2. 필드 정의

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 리포지터리명 | 예 | 텍스트 | GitHub 리포지터리명과 글자 단위로 일치 | `markdown-lint-cli` |
| 결론 | 예 | 열거 | `ALLOW PUSH` 또는 `BLOCK PUSH` 만 사용하며, P0 이 남아 있으면 반드시 후자 | `BLOCK PUSH` |
| 모드 | 예 | 열거 | 비공개 임시 스크립트 리포지터리는 「간소화 감사」, 그 외는 「전체 감사」 | `전체 감사` |
| 공개 범위 | 예 | 열거 | `private` / `public`, 공개 전 라이선스를 재확인해야 함 | `private` |
| 라이선스 | 예 | SPDX 식별자 | 라이선스가 없으면 `NONE` 으로 쓰며, 이때 결론은 반드시 `BLOCK PUSH` | `MIT` |
| 기본 브랜치 | 예 | 텍스트 | 실제 브랜치명을 쓰고 가정한 `main` 을 쓰지 않음 | `main` |
| 게이트 상태 | 예 | 열거 ×3 | A/B/C 각 1행, `SKIP` 은 「미결 항목」에 사유 명시 | `FAIL` |
| 미결 항목 | 조건부 필수 | 텍스트 | 상태가 `FAIL` 또는 `SKIP` 일 때 필수이며, 차단 또는 생략 사유를 나열 | `D1 .env 검출` |
| 등급 | 예 | 열거 | `P0` 차단 / `P1` 푸시 전 수정 또는 등록 / `P2` 제안 | `P0` |
| 차원 | 예 | `D1`–`D14` | 번호는 [감사 차원 매트릭스](./감사-차원-매트릭스.md) 참조 | `D1` |
| 문제 | 예 | 텍스트 | 사실을 한 문장으로 기술하며 추측이나 감정적 표현을 쓰지 않음 | `루트 디렉터리에 .env 존재` |
| 근거 | 예 | 경로:행 또는 명령 출력 | 반드시 재검증 가능해야 하며, 입증할 수 없으면 `SKIP + 사유` 로 작성 | `.env:3` |
| 책임 agent | 예 | agent 이름 | 구체적 실행 역할을 쓰며 「관련 인원」을 쓰지 않음 | `security-auditor` |
| 조치 | 예 | 텍스트 | 바로 실행 가능한 작업이며 대상 파일을 포함 | `.env 삭제, 키 교체 및 이력 정리` |
| 파일 경로 | 예 | 텍스트 | [문서 매트릭스](./문서-매트릭스.md)의 목록에 따라 항목별로 나열 | `SECURITY.md` |
| 문서 매트릭스 상태 | 예 | 표 행별 | 파일별로 존재, 누락 또는 수정 대기를 표기 | `SECURITY.md 누락` |
| 푸시 실행 체크리스트 | 예 | 체크박스 목록 | [푸시 및 릴리스 규범](./푸시-및-릴리스-규범.md)의 규칙에 따라 항목별로 전개 | `- [ ] .gitignore 적용 확인` |
| 통과 설명 | 예 | 텍스트 | 차단 시 사유와 해제 조건을, 통과 시 충족한 하드 룰을 작성 | `P0 제로화 후 재검증 가능` |

## 3. 작성 설명

1. **결론 우선**: 먼저 P0 수를 판정한 후 결론을 작성합니다. P0 이 하나라도 남아 있으면 `ALLOW PUSH` 를 출력해서는 안 됩니다.
2. **근거 강제**: 모든 문제에는 `경로:행 번호` 또는 복사 가능한 명령 출력이 있어야 합니다. 근거 없는 결론은 `SKIP` 으로 표기하고 사유를 명시하며, `PASS` 로 쓰면 안 됩니다.
3. **역할별 책임**: 책임 agent 는 [감사 차원 매트릭스](./감사-차원-매트릭스.md)의 역할명을 사용하며, 하나의 문제에는 하나의 책임 주체가 대응합니다.
4. **조치 실행 가능성**: 조치는 대상 파일과 작업 유형을 지시해야 합니다. 「추후 처리」「자체 조정」은 무효로 간주합니다.
5. **게이트 일관성**: A/B/C 세 행의 상태는 문제 목록과 대응해야 하며, 어느 게이트든 `FAIL` 이면 결론은 반드시 `BLOCK PUSH` 입니다.
6. **문서 매트릭스 항목별**: 목록에 따라 파일별로 나열해야 하며, 「문서가 대체로 갖추어짐」만 쓰면 안 됩니다.
7. **체크리스트 전개**: 푸시 실행 체크리스트는 규칙을 항목별로 전개해야 하며, 「규범에 따라 수행」으로 대체할 수 없습니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| 근거란에 「문제가 있는 듯함」 | 경로도 출력도 없어 재검증 불가 | `파일 경로:행 번호` 또는 명령 출력 보충 |
| P0 이 남아 있는데 `ALLOW PUSH` 작성 | 하드 룰 위반 | `BLOCK PUSH` 로 변경하고 해제 조건 명시 |
| 점검할 수 없는 항목에 `PASS` 작성 | 결과 조작 | `SKIP` 으로 쓰고 미결 항목에 사유 명시 |
| 책임 주체에 「관련 인원」 | 책임 주체 불명 | 구체적 agent 이름 작성 |
| 조치에 「추후 처리」 | 실행 불가 | 대상 파일과 구체적 작업 명시 |
| 기본 브랜치를 확인하지 않고 `main` 작성 | 실제와 불일치 | `git branch` 출력을 기준으로 함 |

## 4. 완전한 예시

다음은 `BLOCK PUSH` 의 완전한 작성 예시입니다.

````markdown
# 푸시 감사 보고서 · markdown-lint-cli

결론：BLOCK PUSH
모드：전체 감사
리포지터리：markdown-lint-cli · private · NONE · 기본 브랜치 main

## I. 게이트 상태
| 게이트 | 상태 | 미결 항목 |
| --- | --- | --- |
| A 보안 | FAIL | D1 .env 검출, D2 LICENSE 없음 |
| B 품질 | SKIP | 리포지터리에 의존성이 설치되지 않아 빌드와 테스트 실행 불가 |
| C 홈페이지 | FAIL | README 에 설치 섹션과 최소 예시 누락 |

## II. 문제 목록
| 등급 | 차원 | 문제 | 근거(경로:행 / 명령 출력) | 책임 agent | 조치 |
| --- | --- | --- | --- | --- | --- |
| P0 | D1 | 루트 디렉터리에 .env 존재 | `.env:3` 에 DATABASE_URL 포함 | security-auditor | .env 삭제, 데이터베이스 자격 증명 교체 및 이력 정리 |
| P0 | D2 | 라이선스 파일 없음 | `ls LICENSE` 출력 `No such file or directory` | license-checker | 리포지터리 소유자가 라이선스를 확인한 후 LICENSE 생성 |
| P1 | D13 | README 에 설치 섹션 누락 | `README.md:1-28` 에 「설치」 제목 없음 | readme-writer | README 표준 템플릿에 따라 설치와 최소 예시 보완 작성 |

## III. 문서 매트릭스 상태
| 파일 | 상태 | 누락/수정 대기 항목 |
| --- | --- | --- |
| README.md | 수정 대기 | 설치 섹션과 최소 예시 누락 |
| LICENSE | 누락 | 소유자의 라이선스 유형 확인 대기 |
| SECURITY.md | 누락 | 아직 생성되지 않음 |

## IV. 푸시 실행 체크리스트
- [ ] git status 가 깨끗한지 확인
- [ ] 전체 시크릿 스캔 실행(이력 커밋 포함)
- [ ] 로컬에서 build, test 및 lint 통과
- [ ] 문서 매트릭스 완비

## V. 통과 설명
차단 사유: 2건의 P0(자격 증명 유출, 라이선스 없음)이 존재하며, 품질 게이트는 의존성 미설치로 판정할 수 없습니다. 해제 조건: 키 교체와 이력 정리를 완료하고, 라이선스를 확정하며, 빌드 가능한 환경에서 테스트를 재실행하고 P0 을 제로화한 후 재검증합니다.
````

`ALLOW PUSH` 일 때 다섯 번째 섹션에는 「모든 하드 룰을 충족했고 3계층 게이트가 모두 PASS 이므로 푸시를 실행할 수 있습니다.」라고 쓸 수 있습니다. 나머지 섹션은 실제 상황에 따라 작성하되 근거와 체크리스트를 생략해서는 안 됩니다.

## 5. 인도 순서

1. 루트 README 언어 내비게이션 전체 내용.
2. 완료된 각 언어 디렉터리의 README 전체 내용, 언어 코드와 파일 경로를 하나씩 나열.
3. NOTICE 파일 내용.
4. LICENSE 방안 설명(사용자가 라이선스를 지정하지 않은 경우 후보와 차이만 제시하고 직접 생성하지 않음).
5. 확인 대기 사항 집계.
6. 감사 보고서(본 보고서).
7. GitHub 푸시 안내.
