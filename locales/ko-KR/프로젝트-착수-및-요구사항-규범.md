# 프로젝트 착수 및 요구사항 규범

> 이 파일이 해결하는 문제：착수 단계의 목표 진술, 요구사항 수집과 범위 정의의 템플릿과 필드를 정의하여, 프로젝트가 처음부터 명확하고 검증 가능하며 추적 가능한 근거를 갖추도록 합니다.

## 1. 규범 조문

1. 착수 문서는 여섯 가지 질문에 답해야 합니다: 무엇인가, 왜 하는가, 어디까지 하는가, 누구에게 쓰이지 않는가, 누가 쓰고 있는가, 무엇에 제약받는가.
2. 요구사항은 「반드시 / 해야 함 / 할 수 있음」 3단계로 구분하며, 용어 약속은 [범용 작성 규범](./범용-작성-규범.md)을 참조합니다.
3. 모든 요구사항은 검증 가능해야 합니다. Given/When/Then으로 인수 조건을 제시하거나, 판정 가능한 측정 임계값을 제시합니다.
4. 모든 요구사항은 안정적인 번호와 출처를 가져야 하며, 번호 없는 요구사항 항목은 금지합니다.
5. 정보가 부족할 때는 「【待确认：字段名】」으로 표기하고, 추측으로 채워서는 안 되며, 규칙은 [정보 수집 및 템플릿](./정보-수집-및-템플릿.md)을 참조합니다.
6. 범위는 포함 항목과 제외 항목을 동시에 명시해야 하며, 비목표가 비어 있으면 범위가 정의되지 않은 것으로 간주합니다.
7. 범위 변경은 이유, 영향과 결정권자를 기록하고, [요구사항 추적 매트릭스 규범](./요구사항-추적-매트릭스-규범.md)의 변경 기록에 반영합니다.

## 2. 착수 문서 템플릿

```markdown
# 프로젝트 착수서: {{项目名称}}

문서 버전: {{v0.1}} ｜ 상태: {{草稿 / 评审中 / 已批准}} ｜ 결정권자: {{姓名}} ｜ 날짜: {{YYYY-MM-DD}}

## 한 줄 포지셔닝
{{目标用户}}에게 {{核心能力}}을 제공하여 {{当前痛点}}을 해결합니다.
（60자 이내, 「강력한」「우아한」「앞선」 등 자기 칭찬형 수식어 금지）

## 배경 및 동기
- 현황: {{当前如何运作}}
- 기존 방안의 부족한 점: {{具体缺陷 1}}；{{具体缺陷 2}}
- 기회 창구: {{时机、技术或市场变化}}
- 착수 근거: {{工单号 / 访谈记录 / 数据指标，须可溯源}}

## 목표 및 비목표
| 유형 | 항목 | 검증 가능한 결과 |
| --- | --- | --- |
| 목표 G1 | {{要达成的结果}} | {{可量化指标 + 阈值}} |
| 목표 G2 | {{要达成的结果}} | {{可量化指标 + 阈值}} |
| 비목표 N1 | {{明确不做的事}} | {{判定边界，说明为何排除}} |

## 성공 기준
| 지표 | 기준선 | 목표값 | 검증 방식 | 검증 시점 |
| --- | --- | --- | --- | --- |
| {{指标名}} | {{当前值}} | {{目标值}} | {{如何测量}} | {{何时测量}} |

## 목표 사용자
| 사용자 역할 | 전형적 시나리오 | 핵심 요구 | 현재 대체 방안 |
| --- | --- | --- | --- |
| {{角色}} | {{何时何地}} | {{要完成的任务}} | {{现用方案}} |

## 제약 조건
- 기술: {{语言、平台、兼容性等限制}}
- 시간: {{截止日期或窗口}}
- 자원: {{人力、预算、基础设施}}
- 컴플라이언스: {{许可证、隐私、行业规范}}

## 범위
- 포함: {{本期交付项}}
- 제외: {{本期明确不交付项}}
- 미확인: {{【待确认：字段名】}}

## 결정 기록
| 날짜 | 결정 | 결정권자 | 근거 |
| --- | --- | --- | --- |
```

## 3. 요구사항 항목 템플릿

```markdown
### REQ-{{三位序号}}：{{需求标题}}

- 출처: {{工单号 / 访谈 / 竞品 / 推测}}
- 우선순위: {{必须 / 应当 / 可以}}
- 연관 목표: {{G1 / G2 / …}}
- 사용자 스토리: {{角色}}로서, {{行为}}을 원합니다. 그래야 {{价值}}을 얻을 수 있습니다.
- 인수 조건:
  1. Given {{前置条件}}
     When {{操作}}
     Then {{预期结果}}
  2. Given {{边界或异常前置条件}}
     When {{操作}}
     Then {{预期结果}}
- 상태: {{待确认 / 已确认 / 已实现 / 已验证 / 已废弃}}
- 연관 추적: {{见需求追踪矩阵中的需求 ID}}
```

## 4. 필드 정의

### 4.1 착수서 필드

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 문서 버전 | 예 | 텍스트 | 시맨틱 버저닝 또는 날짜 버전 | `v0.1` |
| 상태 | 예 | 열거형 | 초안 / 리뷰 중 / 승인됨 | `리뷰 중` |
| 결정권자 | 예 | 텍스트 | 범위와 우선순위에 최종 결정권을 가진 사람 | `张三` |
| 한 줄 포지셔닝 | 예 | 텍스트 | 목표 사용자 + 핵심 역량 + 페인 포인트, 60자 이내 | 프런트엔드 개발자에게 …을 제공 |
| 착수 근거 | 예 | 텍스트 | 최소 한 건의 추적 가능한 기록, 「팀 결정」 금지 | `ISSUE-142` |
| 목표 / 비목표 | 예 | 표 | 각 목표에 검증 가능한 결과를 짝지음, 비목표 최소 한 건 | `G1：冷启动 <2s` |
| 성공 기준 | 예 | 표 | 지표에 기준선, 임계값, 측정 방식과 시점이 있어야 함 | `错误率 <0.1%` |
| 제약 조건 | 예 | 목록 | 네 가지 유형을 모두 작성하고, 없으면 「없음」이라고 작성 | `须兼容 Node 18+` |
| 미확인 | 아니요 | 목록 | 【待确认：字段名】 형식만 사용 | `【待确认：预算上限】` |

### 4.2 요구사항 항목 필드

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 번호 | 예 | `REQ-NNN` | 세 자리 일련번호, 연속, 재사용 없음, 재정렬 없음 | `REQ-007` |
| 출처 | 예 | 텍스트 | 구체적 기록까지 추적 가능 | `사용자 인터뷰 #3` |
| 우선순위 | 예 | 열거형 | 반드시 / 해야 함 / 할 수 있음 | `반드시` |
| 연관 목표 | 예 | 목록 | 착수서의 G 번호에 대응 | `G1` |
| 사용자 스토리 | 예 | 텍스트 | 역할 + 행동 + 가치 세 요소를 모두 갖춤 | …로서 …을 원합니다. 그래야 … |
| 인수 조건 | 예 | 목록 | 최소 1조의 Given/When/Then, 경계 또는 예외 포함 | 템플릿 참조 |
| 상태 | 예 | 열거형 | 다섯 상태 중 하나, 전진만 하고 후퇴 없음 | `已确认` |

## 5. 작성 설명

1. **한 줄 포지셔닝**: 「누구를 위해 + 무엇을 제공 + 무엇을 해결」 3단 구조로 작성합니다. 수식어를 지웠을 때 문장이 성립하지 않는다면 실질 정보가 부족한 것입니다.
2. **성공 기준**: 각 항목은 기준선과 임계값을 동시에 갖추어야 합니다. 「성능 향상」「더 나은 경험」은 불합격으로 판정하며, 「P95 기동 소요 시간을 3초에서 1.5초 미만으로 단축」으로 바꿔야 합니다.
3. **비목표**: 「나중에 논의」가 아니라 명확히 제외하는 범위와 판정 경계를 작성합니다. 비어 있지 않은 비목표가 없을 때는 범위가 정의되지 않은 것으로 간주합니다.
4. **요구사항 번호**: 한 번 부여되면 영구히 고정됩니다. 요구사항이 폐기되면 상태를 「폐기됨」으로 바꾸고, 번호는 회수하거나 재사용해서는 안 됩니다.
5. **인수 조건**: 정상 경로와 최소 한 건의 경계 또는 예외 경로를 포괄해야 합니다. 객관적으로 판정할 수 없는 조건(예: 「인터페이스가 아름다움」)은 검증 가능한 측정값이나 점검 항목으로 전환해야 합니다.
6. **미확인 항목**: 착수 시점에 미확인 항목이 존재할 수 있지만, 모두 나열하고 확인자를 지정해야 하며, 개발 착수 전에 해소해야 합니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| 「쓰기 좋은 도구를 만든다」 | 목표 사용자와 검증 가능한 결과가 없음 | 사용자 역할과 임계값 지표를 보완 |
| 비목표에 「없음」이라고 작성 | 범위가 정의되지 않아 쉽게 확장됨 | 이번에 명확히 제외하는 항목을 나열 |
| 요구사항에 번호가 없고 본문에 직접 서술 | 추적과 인용이 불가능 | `REQ-NNN`을 부여하고 전역에서 인용 |
| 인수 조건에 「기능 정상」이라고 작성 | 판정 불가 | Given/When/Then으로 분해 |
| 추측 내용을 확정 요구사항으로 취급 | 출처 추적 불가 | 출처를 「추측」으로 표기하고 미확인으로 전환 |

## 6. 전체 예시

```markdown
# 프로젝트 착수서: markdown-lint-cli

문서 버전: v0.1 ｜ 상태: 리뷰 중 ｜ 결정권자: 李四 ｜ 날짜: 2026-11-18

## 한 줄 포지셔닝
중국어 기술 작성자에게 명령줄 Markdown 규범 검사 도구를 제공하여, 여러 리포지터리의 문서 스타일이 일관되지 않고 자동 검증이 없는 문제를 해결합니다.

## 배경 및 동기
- 현황: 12개 리포지터리의 README를 각 유지보수자가 직접 작성하여 스타일이 통일되지 않았습니다.
- 기존 방안의 부족한 점: 범용 영어 lint 도구는 중영문 공백 규칙을 지원하지 않으며, 수동 리뷰는 평균 문서당 25분이 소요됩니다.
- 기회 창구: 팀이 오픈소스 첫 화면을 통일하는 중이며, 규범을 한 번에 적용할 필요가 있습니다.
- 착수 근거: ISSUE-142, 2026-11-10 문서 리뷰 회의록.

## 목표 및 비목표
| 유형 | 항목 | 검증 가능한 결과 |
| --- | --- | --- |
| 목표 G1 | 8종 형식 문제 자동 검사 | 샘플 문서 50편에 대한 검출률 95% 이상 |
| 목표 G2 | 1회 검사 소요 시간 제어 | 1000행 문서 검사 2초 미만 |
| 비목표 N1 | 문서 내용 윤문 미제공 | 규칙 적중 위치만 출력하고 텍스트는 재작성하지 않음 |

## 성공 기준
| 지표 | 기준선 | 목표값 | 검증 방식 | 검증 시점 |
| --- | --- | --- | --- | --- |
| 수동 리뷰 소요 시간 | 문서당 25분 | 문서당 5분 미만 | 유지보수자 5명 대조 실험 | v1.0 릴리스 전 |

### REQ-001: 중영문 혼용 공백 검사
- 출처: ISSUE-142
- 우선순위: 반드시
- 연관 목표: G1
- 사용자 스토리: 문서 유지보수자로서, 중영문 사이에 빠진 공백을 자동으로 표시하여 조판을 통일하고 싶습니다.
- 인수 조건:
  1. Given 문서에 「使用Node.js开发」이 포함됨
     When 검사를 실행
     Then 해당 행의 행 번호와 「중영문 사이 공백 누락」 안내를 출력
  2. Given 문서의 해당 위치에 이미 공백이 있음
     When 검사를 실행
     Then 해당 규칙 적중을 출력하지 않음
- 상태: 확인됨
```
