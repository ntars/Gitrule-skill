# 인시던트 대응 규범

> 이 파일이 해결하는 문제：인시던트 보고서 템플릿, 타임라인 기록, 커뮤니케이션 템플릿과 회고 필드를 정의하여 장애가 통제 가능하고 정보가 동기화되며 경험이 축적되도록 보장합니다.

## 1. 규범 조항

1. 인시던트 등급：P0 핵심 기능 사용 불가 또는 데이터 손상, P1 심각한 기능 손상으로 다수 사용자에게 영향, P2 국소 문제로 영향 제한적.
2. 대응 절차：발견 → 등급 지정 → 응급 조치 → 원인 파악 → 수정 → 공지. 원인 파악보다 응급 조치가 우선입니다.
3. 모든 P0/P1 인시던트는 회고해야 하며, 타임라인, 근본 원인, 영향, 조치와 개선 항목을 기록합니다.
4. 개선 항목은 [로드맵 규범](./로드맵-규범.md)에 포함하여 종결까지 추적합니다.
5. 회고는 시스템 개선에 초점을 맞추며 개인의 책임을 추궁하지 않습니다.
6. 시크릿 유출：즉시 교체 → 이력 정리 → 공지하며, 삭제 커밋만으로 처리해서는 안 됩니다( [보안 및 개인정보 규범](./보안-및-개인정보-규범.md) 참조).
7. 대용량 파일 오푸시：LFS 마이그레이션 또는 이력 재작성( [푸시 및 릴리스 규범](./푸시-및-릴리스-규범.md) 참조).

## 2. 인시던트 보고서 템플릿

```markdown
# 인시던트 보고서：{{INC-YYYYMMDD-NN}}

- 인시던트 등급：{{P0 / P1 / P2}}
- 발견 시각：{{YYYY-MM-DD HH:MM}}
- 복구 시각：{{YYYY-MM-DD HH:MM}}
- 지속 시간：{{N 分钟}}
- 지휘자：{{姓名}}
- 현재 상태：{{处理中 / 已恢复 / 已复盘}}

## 영향 범위
| 차원 | 설명 |
| --- | --- |
| 영향받은 기능 | {{具体功能}} |
| 영향받은 사용자 비율 | {{估算值与依据}} |
| 데이터 영향 | {{无 / 描述}} |
| 비즈니스 영향 | {{可量化的损失或阻塞}} |

## 타임라인
| 시각 | 이벤트 | 출처 | 작업자 |
| --- | --- | --- | --- |
| {{HH:MM}} | 경보 발생 | {{监控面板}} | {{姓名}} |
| {{HH:MM}} | P1 로 등급 지정 | {{判断依据}} | {{姓名}} |
| {{HH:MM}} | 롤백 수행 | {{命令 / 平台}} | {{姓名}} |
| {{HH:MM}} | 서비스 복구 | {{验证方式}} | {{姓名}} |

## 근본 원인
- 직접 원인：{{触发故障的具体事件}}
- 근본 원인：{{为何未被预防或及时检测}}
-  Amplification 요인：{{扩大影响的因素}}

## 조치와 검증
1. {{止血措施}}
2. {{修复措施}}
3. {{验证方式与结果}}

## 개선 항목
| 번호 | 조치 | 책임자 | 마감일 | 검증 방식 | 상태 |
| --- | --- | --- | --- | --- | --- |
| {{A-NN}} | {{具体动作}} | {{姓名}} | {{YYYY-MM-DD}} | {{可判定阈值}} | {{待开始}} |
```

## 3. 커뮤니케이션 템플릿

```markdown
## 인시던트 통보(최초)

- 시각：{{YYYY-MM-DD HH:MM}}
- 등급：{{P0 / P1 / P2}}
- 현상：{{用户可感知的现象，不写内部细节}}
- 영향：{{受影响范围}}
- 현재 조치：{{正在做什么}}
- 다음 업데이트 시각：{{HH:MM}}

## 인시던트 통보(복구)

- 복구 시각：{{HH:MM}}
- 복구 확인：{{验证方式与结果}}
- 잔여 영향：{{无 / 描述}}
- 후속 조치：{{复盘安排}}
```

## 4. 필드 정의

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 인시던트 번호 | 예 | `INC-YYYYMMDD-NN` | 당일 일련번호, 연속되며 재사용하지 않음 | `INC-20261118-01` |
| 인시던트 등급 | 예 | 열거 | P0 / P1 / P2 | `P1` |
| 지속 시간 | 예 | 기간 | 발견부터 복구까지의 분 수 | `42분` |
| 지휘자 | 예 | 텍스트 | 유일해야 하며 의사결정과 동기화를 담당 | `李四` |
| 영향받은 사용자 비율 | 예 | 텍스트 | 추정 근거를 제시해야 함 | `약 8%, 오류 로그 집계 근거` |
| 타임라인 | 예 | 표 | 각 노드에 시각과 출처 포함 | 템플릿 참조 |
| 근본 원인 | 예 | 텍스트 | 직접 원인과 근본 원인을 구분 | `롤백 훈련 부재` |
| 개선 항목.검증 방식 | 예 | 텍스트 | 판정 가능해야 하며 임계값 포함 | `다음 훈련에서 롤백 <5분` |
| 다음 업데이트 시각 | 예 | 시각 | 처리 중일 때 필수, 「수시 업데이트」 금지 | `18:30` |

## 5. 작성 설명

1. **등급 지정**: 영향 범위와 심각도에 따라 등급을 지정합니다. 불확실할 때는 높게 지정하고, 이후 조정하며 사유를 기록합니다.
2. **응급 조치 우선**: 먼저 서비스를 복구(롤백, 성능 저하 운영, 속도 제한)한 후 근본 원인을 파악합니다. 원인 파악이 응급 조치를 지연시켜서는 안 됩니다.
3. **타임라인**: 발생 시각 순서로 기록하며, 출처는 조회 가능해야 합니다(경보 ID, 명령, 로그 조각). 사후에 기억으로 보충 작성하는 것은 금지합니다.
4. **근본 원인**: 직접 원인은 유발 사건이고, 근본 원인은 체계적 결함입니다. 둘 다 작성해야 합니다.
5. **커뮤니케이션**: 최초 통보에는 다음 업데이트 시각을 제시해야 하며, 복구 통보에는 검증 방식과 잔여 영향을 설명해야 합니다.
6. **개선 항목**: 최대 세 건이며 로드맵에 포함하여 추적합니다. 책임자가 없는 개선 항목은 보고서에 넣을 수 없습니다.
7. **회고**: 시스템과 프로세스 개선에 초점을 맞추고 개인을 평가하지 않습니다. 책임 추궁이나 「모 누군가가 부주의했다」 같은 표현을 쓰지 않습니다.
8. **특수 인시던트**: 시크릿 유출은 H12 에 따라 처리하고, 대용량 파일 오푸시는 LFS 마이그레이션으로 처리하며, 모두 별도로 기록을 남겨야 합니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| 근본 원인을 먼저 파악한 후 응급 조치 | 장애 시간 연장 | 먼저 롤백하여 복구 |
| 타임라인을 사후에 보충 작성 | 사실 신뢰 불가 | 처리 중 즉시 기록 |
| 근본 원인에 「모 누군가가 부주의함」 | 개인에게 책임 전가, 개선 가치 없음 | 프로세스나 도구 수준까지 추궁 |
| 통보에 「최대한 빨리 수정」 | 다음 업데이트 시각 없음 | 구체적 시각 제시 |
| 개선 항목에 검증 방식 없음 | 종결 판정 불가 | 임계값과 점검 시점 보충 |

## 6. 완전한 예시

```markdown
# 인시던트 보고서：INC-20261118-01

- 인시던트 등급：P1
- 발견 시각：2026-11-18 10:12
- 복구 시각：2026-11-18 10:54
- 지속 시간：42분
- 지휘자：李四
- 현재 상태：회고 완료

## 영향 범위
| 차원 | 설명 |
| --- | --- |
| 영향받은 기능 | 규칙 점검 API 가 5xx 반환 |
| 영향받은 사용자 비율 | 약 8%, 5xx 로그 집계 근거 |
| 데이터 영향 | 없음 |
| 비즈니스 영향 | 42분 동안 점검 작업 제출 불가 |

## 근본 원인
- 직접 원인：규칙 플러그인 로드 경로가 새 설정에 의해 덮어써져 시작에 실패했습니다.
- 근본 원인：설정 변경이 사전 릴리스 검증에 포함되지 않았습니다.

## 개선 항목
| 번호 | 조치 | 책임자 | 마감일 | 검증 방식 | 상태 |
| --- | --- | --- | --- | --- | --- |
| A-01 | 설정 변경을 사전 릴리스 점검 체크리스트에 포함 | 王五 | 2026-11-25 | 다음 5회 변경 모두 점검 기록 포함 | 시작 전 |
```
