# README 섹션 규범

> 이 파일이 해결하는 문제：각 언어 디렉터리의 README에 반드시 포함해야 하는 20개 섹션, 각 섹션에 반드시 포함해야 할 내용과 포함해서는 안 되는 내용, 그리고 저작권 행의 표준 형식을 정의합니다.

## 1. 섹션 총요건

다음 20개 섹션은 모두 존재해야 하며, 순서는 고정이고 각 언어 버전은 1:1로 대응해야 합니다.

| 번호 | 섹션 | 반드시 포함 | 포함해서는 안 됨 |
| --- | --- | --- | --- |
| 1 | 프로젝트 이름과 포지셔닝 | 프로젝트명, 리포지터리 설명(`국가 언어 \| 영어` 이중 언어 병합 형식), 토픽 태그(20개를 모두 채우고 영어만 사용), 한 문장 포지셔닝, 언어 전환 링크, 현재 버전, 유지보수 상태 | 공허한 형용사；리포지터리 설명이 120자를 초과；토픽 태그의 대소문자 혼용 또는 비영어 단어 포함 |
| 2 | 프로젝트 소개 | 배경, 해결할 문제, 핵심 접근 방식, 적용 시나리오, 부적합 시나리오, 그리고 장점과 한계의 분리 나열(한계에는 영향 범위와 회피 방식을 포함해야 함) | 한 문장으로 얼버무림；장점만 나열하고 한계를 나열하지 않음 |
| 3 | 핵심 기능 | 모듈별로 그룹화한 기능 항목, 각 항목에 트리거 조건과 결과 포함 | 기능 이름만 나열 |
| 4 | 핵심 특성 | [기능 및 엔지니어링 트레이드오프 작성법](./기능-및-엔지니어링-트레이드오프-작성법.md) 구조에 따라 전개 | 근거 없는 찬사 |

| 7 | 설치와 배포 | 환경 요구사항, 설치 단계, 검증 명령, 업그레이드와 제거 방법, 컨테이너화 설명 | 단계를 건너뛰거나 검증을 생략 |

## 1.1 첫 화면 네 가지 질문과 한 문장 문안

README 첫 화면은 네 가지 질문에 답해야 하며, 순서는 고정입니다.

1. 프로젝트가 무엇을 하는가；
2. 프로젝트가 어떤 문제를 해결하는가；
3. 프로젝트에 어떤 특성이 있는가；
4. 최소 hello world 예제.

이 중 첫 번째 질문은 「한 문장 포지셔닝」에 해당하며, 세 가지를 동시에 만족해야 합니다. 프로젝트 유형을 설명하고, 수식어가 정확하며, 그대로 되풀이할 수 있어야 합니다. 성숙한 프로젝트의 공개 문안을 참조할 수 있습니다.

| 프로젝트 | 한 문장 문안 | 구조 분석 |
| --- | --- | --- |
| Angular | One framework. Mobile & desktop. | 카테고리 + 커버 범위 |
| React | A declarative, efficient, and flexible JavaScript library for building user interfaces. | 세 가지 수식어 + 카테고리 + 용도 |
| Vue | A progressive, incrementally-adoptable JavaScript framework for building UI on the web. | 두 가지 특성 + 카테고리 + 용도 |

작성 제약：

- 「강력한」「탁월한」「혁명적인」 등 정보가 없는 형용사를 사용해서는 안 됩니다.
- 카테고리 단어(라이브러리, 프레임워크, 도구, 애플리케이션)를 제시하여 독자가 한눈에 분류할 수 있게 해야 합니다.
- 특성 수식어는 세 개를 초과하지 않아야 하며, 나열만 하는 것을 피해야 합니다.
- 중국어 버전은 60자 이내, 영어 버전은 25단어 이내로 제한해야 합니다.

세 번째 질문 「어떤 특성이 있는가」는 부적합 시나리오도 함께 공개해야 합니다. 유효한 작성 예시：어떤 메시지 미들웨어가 「QoS 레벨 0만 지원하며, 레벨 1이 필요한 시나리오에는 적합하지 않음」을 설명하는 경우입니다. 무효한 작성은 장점만 나열하는 것입니다. 특성 비교는 검증 가능한 사실에 근거해야 하며, 동종 프로젝트를 폄하해서는 안 됩니다.

네 번째 질문의 hello world 예제는 두 단계 이내에 설치와 실행을 완료해야 합니다. 설치 단계가 번거로운 프로젝트는 컨테이너 이미지나 온라인 데모 환경을 제공하여, 독자가 README를 다 읽고 나서 포기하는 일을 피해야 합니다.
