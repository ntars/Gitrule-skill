# 코드 스타일 규범

> 이 파일이 해결하는 문제：코드 스타일 설정 템플릿, 명명 규약표, 주석 규칙과 작성 설명을 정의하여 스타일 이견을 줄이고 가독성과 리뷰 효율을 높입니다.

## 1. 규범 조문

1. 스타일 규칙은 자동화 도구를 기준으로 하며, 사람은 도구가 커버할 수 없는 부분만 처리합니다.
2. 포맷 설정은 리포지터리에 함께 커밋하여（예: 포맷 설정 파일） 서로 다른 환경에서 일관성을 보장해야 합니다.
3. CI는 포맷 검사를 통합해야 하며, 통과하지 못하면 병합해서는 안 됩니다（[테스트 규범](./테스트-규범.md) 참조）.
4. 매직 넘버와 하드코딩된 상수를 사용해서는 안 되며, 이름 있는 상수로 추출해야 합니다.
5. 행 끝은 LF로 통일하고, 파일은 개행으로 끝나야 합니다（차원 D3 리포지터리 위생에 대응）.

## 2. 스타일 설정 템플릿

```markdown
# 코드 스타일 약속: {{项目名称}}

설정 버전: {{v1.0}} ｜ 적용 언어 및 버전: {{如 TypeScript 5.x}} ｜ 포맷 도구: {{如 Prettier 3.x}}

## 포맷 규칙（도구 강제）
| 규칙 | 값 | 도구 설정 항목 | 협의 가능 여부 |
| --- | --- | --- | --- |
| 들여쓰기 | {{2 空格 / 4 空格 / Tab}} | {{配置项名}} | 아니요 |
| 행 너비 | {{100 字符}} | {{配置项名}} | 아니요 |
| 따옴표 | {{单引号 / 双引号}} | {{配置项名}} | 아니요 |
| 행 끝 | LF | `endOfLine: lf` | 아니요 |
| 파일 끝 개행 | 반드시 있어야 함 | 도구 기본값 | 아니요 |
| 세미콜론 | {{有 / 无}} | {{配置项名}} | 아니요 |

## 명명 규약（도구가 강제할 수 없음, 수동 리뷰）
| 대상 | 규칙 | 정례 | 반례 |
| --- | --- | --- | --- |
| 변수 | {{camelCase}} | `userName` | `UserName` |
| 상수 | {{UPPER_SNAKE_CASE}} | `MAX_RETRY` | `maxRetry` |
| 함수 | {{动词开头 camelCase}} | `parseConfig` | `configParse` |
| 클래스 / 타입 | {{PascalCase}} | `ConfigLoader` | `config_loader` |
| 파일 이름 | {{kebab-case}} | `config-loader.ts` | `ConfigLoader.ts` |
| 불리언 값 | {{is/has/can 前缀}} | `isValid` | `valid` |
| 컬렉션 | {{复数名词}} | `items` | `itemList` |

## 주석 규칙
- 반드시 주석을 작성해야 하는 상황: {{公开 API 的契约、非直观算法、绕开限制的临时方案}}
- 금지하는 주석: {{复述代码、无信息量、失效的旧注释、情绪化表述}}
- 주석 언어: {{与项目主语言一致}}
- TODO 형식: `// TODO({{负责人}}): {{事项}} — {{计划版本}}`

## 파일 구성
1. 임포트 순서: {{标准库 → 第三方 → 本地模块，组内字典序}}
2. 선언 순서: {{常量 → 类型 → 函数 → 导出}}
3. 단일 파일 행 수 상한: {{300 行，超出须拆分}}

## 예외 목록
| 시나리오 | 예외 규칙 | 승인자 | 유효 기간 |
| --- | --- | --- | --- |
| {{如生成代码}} | {{不参与格式化}} | {{姓名}} | {{至 v2.0}} |
```

## 3. 설정 필드 정의

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 설정 버전 | 예 | 텍스트 | 스타일 규칙 변경 시 증가 | `v1.0` |
| 적용 언어 및 버전 | 예 | 텍스트 | 주 버전을 명확히 하여 규칙 표류 방지 | `TypeScript 5.x` |
| 포맷 도구 | 예 | 텍스트 | lockfile의 버전과 일치 | `Prettier 3.2` |
| 규칙.값 | 예 | 열거형 / 숫자 | 유일해야 하며 「상황에 따라」 금지 | `2 空格` |
| 협의 가능 여부 | 예 | 열거형 | 아니요 / 예, 「예」로 표시하면 협의 조건을 제시해야 함 | `아니요` |
| 명명 정례 | 예 | 코드 | 프로젝트의 기존 코드에서 선택 | `parseConfig` |
| 명명 반례 | 예 | 코드 | 실제로 범하기 쉬운 작성법이어야 함 | `configParse` |
| TODO 책임자 | 예 | 텍스트 | 「팀」이라고 작성하는 것은 금지 | `张三` |
| 예외 유효 기간 | 예 | 버전 / 날짜 | 만료 시 재검토해야 함 | `v2.0까지` |

## 4. 작성 설명

1. **도구 우선**: 도구가 강제할 수 있는 규칙은 모두 포맷 설정에 작성하고 사람의 기억에 의존하지 않으며, 사람은 명명, 주석, 파일 구성만 담당합니다.
2. **행 너비 값**: 리뷰 인터페이스 너비를 고려하여 설정하며, 일반적으로 100 또는 120이고, 한 번 정하면 개별 파일에서 덮어쓸 수 없습니다.
3. **명명 정례**: 프로젝트의 기존 코드에서 실제로 존재하는 이름을 선택하고, 교과서식 자리표시자를 사용하는 것은 금지합니다.
4. **불리언 명명**: `is`/`has`/`can` 접두어는 의미와 일치해야 하며, `isReady`가 동작을 나타내서는 안 됩니다.
5. **TODO**: 반드시 책임자, 사항과 계획 버전을 포함해야 하며, 계획이 없는 TODO는 메인라인에 들어갈 수 없습니다.
6. **예외 목록**: 모든 예외에는 승인자와 유효 기간이 있어야 하며, 만료 시 재검토하지 않으면 자동으로 효력이 상실됩니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| 「코드는 최대한 간결하게」 | 판정 불가 | 함수 길이 상한 등 검사 가능한 규칙으로 변경 |
| 명명표에 규칙만 있고 반례가 없음 | 리뷰 시 대조 불가 | 실제로 범하기 쉬운 반례 보완 |
| 주석에 「여기에 예전에 버그가 있었다」 | 정보가 없고 쉽게 무효화됨 | 현재 동작과 이유를 설명하도록 변경 |
| TODO에 책임자가 없음 | 후속 관리자가 없음 | 책임자와 계획 버전 보완 |
| 예외에 유효 기간이 없음 | 영구 면제 | 유효 기간과 검토자 보완 |

## 5. 전체 예시

```markdown
# 코드 스타일 약속: markdown-lint-cli

설정 버전: v1.0 ｜ 적용 언어 및 버전: TypeScript 5.x ｜ 포맷 도구: Prettier 3.2

## 포맷 규칙（도구 강제）
| 규칙 | 값 | 도구 설정 항목 | 협의 가능 여부 |
| --- | --- | --- | --- |
| 들여쓰기 | 스페이스 2칸 | `tabWidth: 2` | 아니요 |
| 행 너비 | 100자 | `printWidth: 100` | 아니요 |
| 따옴표 | 작은따옴표 | `singleQuote: true` | 아니요 |
| 행 끝 | LF | `endOfLine: lf` | 아니요 |
| 세미콜론 | 있음 | `semi: true` | 아니요 |

## 명명 규약（수동 리뷰）
| 대상 | 규칙 | 정례 | 반례 |
| --- | --- | --- | --- |
| 함수 | 동사로 시작하는 camelCase | `parseRules` | `rulesParser` |
| 상수 | UPPER_SNAKE_CASE | `DEFAULT_RULES` | `defaultRules` |
| 파일 이름 | kebab-case | `rule-loader.ts` | `RuleLoader.ts` |

## 주석 규칙
- 반드시 주석을 작성해야 하는 상황: 규칙의 매칭 의미, 업스트림 API 동작에 대한 우회 처리.
- 금지하는 주석: 코드를 반복하는 주석, 「버그를 수정함」, 책임자 없는 TODO.
- TODO 형식: `// TODO(王五): 替换临时解析器 — v2.0`

## 예외 목록
| 시나리오 | 예외 규칙 | 승인자 | 유효 기간 |
| --- | --- | --- | --- |
| fixtures 디렉터리 | 포맷 대상에서 제외 | 李四 | v2.0까지 |
```
