# 버전 관리 규범

> 이 파일이 해결하는 문제：시맨틱 버저닝 규칙, 버전 결정 기록, 증가 근거와 연동 관계를 정의하여 버전 번호가 변경 성격을 표현하고, 도구로 파싱 가능하며, 릴리스 산출물과 일치하도록 보장합니다.

## 1. 규범 조항

1. 버전 번호는 시맨틱 버저닝을 따른다: `MAJOR.MINOR.PATCH`.
2. 버전 번호에 연도, 날짜, 빌드 번호를 의미적 주체로 포함하지 않으며, 이미 릴리스된 버전 번호를 재사용할 수 없습니다.
3. 파괴적 변경은 메이저 버전 업그레이드 시 일괄 처리하고 마이그레이션 방식을 제시해야 합니다.
4. 버전 번호는 tag와 일치하며, tag 형식은 `vMAJOR.MINOR.PATCH`이다([푸시 및 릴리스 규범](./푸시-및-릴리스-규범.md) 참조).
5. 프리릴리스 버전은 `-alpha`, `-beta`, `-rc` 접미사를 사용하며, 안정 버전 릴리스 전까지 검증을 완료해야 합니다.

## 2. 버전 번호 형식과 증가 근거

| 자리 | 증가 조건 | 트리거 커밋 유형 | 예시 |
| --- | --- | --- | --- |
| MAJOR | 하위 호환되지 않는 파괴적 변경 | `feat!:` / `fix!:` / `BREAKING CHANGE:` | `1.9.2 → 2.0.0` |
| MINOR | 하위 호환되는 신규 기능 | `feat` | `1.2.3 → 1.3.0` |
| PATCH | 하위 호환되는 결함 수정 | `fix` | `1.2.3 → 1.2.4` |

프리릴리스 형식: `vMAJOR.MINOR.PATCH-alpha.N` / `-beta.N` / `-rc.N`, 숫자는 1부터 증가하며, 안정 버전 릴리스 시 접미사를 제거합니다.

## 3. 버전 결정 기록 템플릿

```markdown
## 버전 결정: {{X.Y.Z}}

- 결정 날짜: {{YYYY-MM-DD}}
- 결정자: {{姓名}}
- 현재 버전: {{X.Y.Z}}
- 목표 버전: {{X.Y.Z}}
- 증가 자리: {{MAJOR / MINOR / PATCH}}
- 근거: {{列举触发的提交类型与变更内容}}

| 변경 | 커밋 유형 | 관련 요구사항 | 호환성 파괴 여부 |
| --- | --- | --- | --- |
| {{变更描述}} | {{feat / fix / BREAKING CHANGE}} | {{REQ-NNN}} | {{是 / 否}} |

- 파괴적 변경 처리: {{迁移指南链接 / 不适用}}
- 변경 이력 항목: {{链接}}
- tag: {{vX.Y.Z}}
- 릴리스 점검: {{已通过 / 待通过}}
```

## 4. 버전 대장 템플릿

```markdown
# 버전 대장: {{项目名称}}

| 버전 | 릴리스 날짜 | 유형 | 주요 변경 | tag | 변경 이력 | 상태 |
| --- | --- | --- | --- | --- | --- | --- |
| {{X.Y.Z}} | {{YYYY-MM-DD}} | {{主版本 / 次版本 / 修订}} | {{一句话}} | {{vX.Y.Z}} | {{链接}} | {{当前 / 历史 / 已废弃}} |
| {{X.Y.Z-rc.1}} | {{YYYY-MM-DD}} | 프리릴리스 | {{一句话}} | {{vX.Y.Z-rc.1}} | {{链接}} | superseded됨 |

상태: 현재 / 이력 / 폐기됨 / 대체됨
```

## 5. 필드 정의

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 현재 버전 | 예 | `X.Y.Z` | 최근 tag와 일치 | `1.2.3` |
| 목표 버전 | 예 | `X.Y.Z` | 한 자리만 증가 | `1.3.0` |
| 증가 자리 | 예 | 열거형 | MAJOR / MINOR / PATCH | `MINOR` |
| 근거 | 예 | 목록 | 트리거 변경을 나열, 「정기 업데이트」금지 | `TOML 지원 추가` |
| 파괴적 변경 처리 | 조건부 필수 | 링크 | MAJOR 증가 시 필수 | `[마이그레이션 가이드]` |
| 변경 이력 항목 | 예 | 링크 | 해당 버전 섹션을 가리킴 | `[1.3.0]` |
| tag | 예 | `vX.Y.Z` | 버전 번호와 일대일 대응 | `v1.3.0` |
| 릴리스 날짜 | 예 | `YYYY-MM-DD` | tag 생성 날짜를 기준으로 함 | `2026-11-20` |
| 상태 | 예 | 열거형 | 현재 / 이력 / 폐기됨 / 대체됨 | `현재` |

## 6. 작성 설명

1. **한 자리 증가**: 릴리스마다 한 자리만 증가시킨다. feat과 BREAKING CHANGE가 동시에 존재하면 가장 높은 자리(MAJOR)를 취하고, 나머지 변경은 해당 버전에 병합합니다.
2. **파괴적 변경 집중**: 여러 파괴적 변경을 같은 메이저 버전 릴리스로 병합하여 연속적인 MAJOR 증가를 피합니다.
3. **재사용 금지**: 릴리스된 버전 번호는 영구히 점유합니다. 릴리스 철회 시 PATCH를 증가시켜 수정 버전을 릴리스하고 원래 번호를 재사용하지 않는다.
4. **프리릴리스**: `alpha`는 내부 검증, `beta`는 공개 시험, `rc`는 릴리스 후보에 사용합니다. 각 단계는 모두 CI를 통과해야 합니다.
5. **일관성 확인**: 버전 번호는 tag, 변경 이력, Release Notes, 배포 기록, 버전 대장 다섯 곳에서 일치해야 합니다. 불일치 시 tag를 기준으로 나머지를 수정합니다.
6. **연동**: 증가 근거는 [커밋 메시지 규범](./커밋-메시지-규범.md)의 유형에서 온다. 대외 설명은 [변경 이력 규범](./변경-이력-규범.md)을, 업그레이드 경로는 [마이그레이션 가이드 규범](./마이그레이션-가이드-규범.md)을 참조합니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| `v2026.11` | 날짜를 의미적 주체로 사용 | `v2.1.0`으로 변경 |
| 같은 버전에서 두 자리를 여러 번 증가 | 의미 혼란 | 가장 높은 자리만 증가 |
| 철회된 버전 번호 재사용 | 산출물 구분 불가 | PATCH를 증가시켜 수정 버전 릴리스 |
| MAJOR 증가에 마이그레이션 가이드 없음 | 사용자가 업그레이드 불가 | 마이그레이션 가이드 보충 및 링크 |
| 버전 번호가 tag에만 존재 | 대장과 로그 불일치 | 다섯 곳 동기화 |

## 7. 완전한 예시

```markdown
## 버전 결정: 2.0.0

- 결정 날짜: 2026-12-01
- 결정자: 이순신
- 현재 버전: 1.9.2
- 목표 버전: 2.0.0
- 증가 자리: MAJOR
- 근거: 설정 파일 형식이 객체에서 파일 경로로 변경되어 호환되지 않는 변경에 해당함.

| 변경 | 커밋 유형 | 관련 요구사항 | 호환성 파괴 여부 |
| --- | --- | --- | --- |
| 설정 파일 경로화 | BREAKING CHANGE | REQ-021 | 예 |
| TOML 파싱 추가 | feat | REQ-001 | 아니오 |

- 파괴적 변경 처리: [마이그레이션 가이드 v2.0]
- 변경 이력 항목: [2.0.0]
- tag: v2.0.0
- 릴리스 점검: 통과
```
