# 코드 리뷰 규범

> 이 파일이 해결하는 문제：풀 리퀘스트 설명 템플릿, 리뷰 의견 템플릿, 리뷰 기록, 필드와 절차를 정의하여 병합 품질과 지식 공유를 보장합니다.

## 1. 규범 조문

1. 작성자는 PR 설명에서 변경 목적, 영향 범위와 자체 테스트 결과를 설명해야 하며, 템플릿은 [Git 워크플로 및 브랜치 규범](./Git-워크플로-및-브랜치-규범.md)을 참조합니다.
2. 리뷰어는 구체적이고 실행 가능한 의견을 제시하고, 「반드시 수정」과 「제안」을 구분해야 합니다.
3. 병합 전 최소 1명의 리뷰어 승인과 CI 전체 통과가 필요하며（하드 룰 H9에 대응）, 작성자가 자신의 PR을 직접 승인하는 것은 금지합니다.
4. 리뷰 의견에 이견이 있을 때는 유지보수자에게 상향하여 판정합니다（[행동 강령 규범](./행동-강령-규범.md) 참조）.
5. 병합 후 소스 브랜치를 삭제하여 브랜치 목록을 깔끔하게 유지합니다.

## 2. 리뷰 체크리스트

리뷰어는 항목별로 확인해야 합니다:

| # | 차원 | 점검 요점 | 판정 |
| --- | --- | --- | --- |
| 1 | 정확성 | 로직이 정확하고 경계와 예외가 처리됨 | 통과 / 수정 필요 |
| 2 | 테스트 | 변경에 대응하는 테스트가 있고 테스트가 통과함 | 통과 / 수정 필요 |
| 3 | 스타일 | [코드 스타일 규범](./코드-스타일-규범.md)을 준수 | 통과 / 수정 필요 |
| 4 | 보안 | 민감 정보 없음, 인젝션 리스크 없음, 권한 검사 정확 | 통과 / 수정 필요 |
| 5 | 문서 | 인터페이스 또는 동작 변경이 문서에 동기화됨 | 통과 / 수정 필요 |
| 6 | 범위 | 변경이 집중되어 있고 무관한 수정이 없음 | 통과 / 수정 필요 |
| 7 | 커밋 메시지 | [커밋 메시지 규범](./커밋-메시지-규범.md)을 준수 | 통과 / 수정 필요 |
| 8 | 추적 | 요구사항 추적 매트릭스가 갱신됨 | 통과 / 수정 필요 |

## 3. 리뷰 의견 템플릿

```markdown
### 의견 {{序号}}: {{一句话标题}}

- 등급: {{必须修改 / 建议 / 提问}}
- 위치: {{文件路径:行号}}
- 문제: {{描述可观察的问题，不评价人}}
- 근거: {{规范条款 / 需求编号 / 风险说明}}
- 제안: {{具体的修改方式或替代方案}}

예시:
### 의견 1: 예외 분기가 커버되지 않음
- 등급: 반드시 수정
- 위치: `src/rules/spacing.ts:42`
- 문제: 입력에 불완전한 Markdown이 포함될 때 예외가 발생하며, 규칙 적중 결과를 반환하지 않습니다.
- 근거: REQ-001 인수 조건 제2항（경계 경로）.
- 제안: 이 지점에서 파싱 예외를 잡아 「파싱 실패」로 적중을 반환하고, 경계 케이스를 한 건 보완합니다.
```

## 4. 리뷰 기록 템플릿

```markdown
## 리뷰 기록: {{PR 编号}}

리뷰어: {{姓名}} ｜ 리뷰 날짜: {{YYYY-MM-DD}} ｜ 회차: {{第 N 轮}}

| 의견 번호 | 등급 | 처리 결론 | 처리자 | 검증 방식 |
| --- | --- | --- | --- | --- |
| 1 | 반드시 수정 | 수정됨 | 작성자 | 커밋 abc1234 참조 |
| 2 | 제안 | 미채택 | 작성자 | 이유: {{说明}} |

결론: {{批准 / 需修改后再审 / 拒绝}}
- 승인 조건: 모든 「반드시 수정」 항목이 처리되고 CI 전체 통과.
- 미결 항목: {{无 / 列出}}
```

## 5. 필드 정의

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 등급 | 예 | 열거형 | 반드시 수정 / 제안 / 질문 | `반드시 수정` |
| 위치 | 예 | `경로:행번` | 행까지 정확히 지정하고 파일 이름만 작성하는 것은 금지 | `src/parser.ts:42` |
| 문제 | 예 | 텍스트 | 현상을 설명하고 작성자를 평가하지 않음 | `파싱 예외 미처리` |
| 근거 | 예 | 텍스트 | 규범 조항 또는 REQ 번호 | `REQ-001 인수 조건 2` |
| 제안 | 예 | 텍스트 | 실행 가능해야 하며 「최적화하세요」만 말하지 않음 | `예외를 잡아 적중을 반환` |
| 처리 결론 | 예 | 열거형 | 수정됨 / 미채택 / 연기 | `수정됨` |
| 검증 방식 | 예 | 텍스트 | 커밋 해시 또는 재검토 방식 | `커밋 abc1234 참조` |
| 결론 | 예 | 열거형 | 승인 / 수정 후 재리뷰 필요 / 거절 | `승인` |

## 6. 작성 설명

1. **등급 구분**: 「반드시 수정」은 병합을 차단하는 문제（정확성, 보안, 테스트 누락）를 의미하고, 「제안」은 병합에 영향을 주지 않으며, 「질문」은 작성자의 해명이 필요하지만 수정을 요구하지 않습니다.
2. **의견 표현**: 관찰 가능한 문제를 설명하고, 「여기는 형편없이 작성됨」 등 평가적 언어는 금지합니다.
3. **위치**: 행 번호까지 정확히 지정하며, 여러 파일에 걸친 문제는 각 의견에 각각 표기합니다.
4. **근거**: 추적할 수 있으면 추적하고, 규범 근거가 없을 때는 리스크나 영향을 작성하며, 「내 생각에는」은 금지합니다.
5. **처리 결론**: 「미채택」은 이유를 작성해야 하고, 「연기」는 후속 추적 위치를 명시해야 합니다.
6. **승인**: 모든 「반드시 수정」 항목이 종결되고 CI가 전체 통과함을 확인해야 하며, 작성자는 자신의 PR을 자체 승인할 수 없습니다.
7. **이견**: 리뷰어와 작성자의 의견이 일치하지 않을 때 유지보수자에게 상향하고, 판정 결론을 리뷰 기록에 작성합니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| 「여기는 안 됩니다」 | 문제, 근거, 제안이 없음 | 세 요소 보완 |
| 「성능을 좀 최적화하세요」 | 실행 불가 | 구체적 방법과 판정 지표 제시 |
| 파일 이름만 쓰고 행 번호를 쓰지 않음 | 위치 파악 어려움 | 행까지 정확히 지정 |
| 작성자가 자체 승인 | 규정 위반 | 다른 사람이 리뷰 |
| 개인 선호에 「반드시 수정」 사용 | 등급 남용 | 「제안」으로 하향 |

## 7. 전체 예시

```markdown
## 리뷰 기록: #12

리뷰어: 李四 ｜ 리뷰 날짜: 2026-11-18 ｜ 회차: 1회차

| 의견 번호 | 등급 | 처리 결론 | 처리자 | 검증 방식 |
| --- | --- | --- | --- | --- |
| 1 | 반드시 수정 | 수정됨 | 王五 | 커밋 a1b2c3d 참조 |
| 2 | 제안 | 미채택 | 王五 | 이유: 현재 QPS가 병목에 도달하지 않아 과설계를 피함 |
| 3 | 질문 | 해명됨 | 王五 | PR 본문에 설명 보완 |

결론: 승인
- 승인 조건: 모든 「반드시 수정」 항목이 처리되고 CI 전체 통과（run #128）.
- 미결 항목: 없음
```
