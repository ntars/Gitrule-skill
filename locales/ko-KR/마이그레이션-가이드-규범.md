# 마이그레이션 가이드 규범

> 이 파일이 해결하는 문제：파괴적 변경 시 마이그레이션 가이드의 구조, 내용 요소와 릴리스 시점을 정의하여, 사용자가 단계별로 구버전에서 신버전으로 원활하게 업그레이드할 수 있게 합니다.

## 1. 발동 조건

다음 중 하나라도 해당하면 마이그레이션 가이드를 제공해야 합니다.

1. 커밋 메시지에 `BREAKING CHANGE:` 또는 `feat!:` / `fix!:`가 포함된 경우([커밋 메시지 규범](./커밋-메시지-규범.md) 참조).
2. 설정 키 이름, 기본값 또는 우선순위가 변경된 경우.
3. API 시그니처, 반환 구조 또는 오류 코드가 변경된 경우.
4. 최소 런타임 버전이 상향되거나 특정 플랫폼을 더 이상 지원하지 않는 경우.
5. 디렉터리 구조 또는 파일 명명이 변경되어 사용자의 참조 경로에 영향을 주는 경우.

## 2. 파일 위치와 명명

1. 변경이 작은 마이그레이션 설명은 `CHANGELOG.md`의 해당 버전 항목에 작성합니다.
2. 변경이 크고 여러 단계의 작업을 포함하는 경우, 별도로 `docs/migration/` 디렉터리 아래에 파일을 만들고 버전별로 명명한다(예: `docs/migration/v2.md`).
3. 메이저 버전을 넘는 전체 마이그레이션 경로는 `docs/migration/README.md`에 색인을 만듭니다.
4. README에는 마이그레이션 안내와 링크만 두고 단계를 펼쳐 쓰지 않는다([문서 매트릭스](./문서-매트릭스.md) 참조).

## 3. 문서 구조

마이그레이션 가이드는 다음 순서로 구성해야 합니다.

1. **제목과 버전**: 출발 버전과 목표 버전을 표기한다(예: 「v1.x에서 v2.0으로 마이그레이션」).
2. **영향 개요**: 변경 범주와 영향 범위를 나열하고, 어떤 사용자가 반드시 마이그레이션해야 하는지 설명합니다.
3. **사전 조건**: 마이그레이션 전에 완료해야 하는 준비 사항(예: 백업, 환경 버전 업그레이드).
4. **변경 목록**: 파괴적 변경을 항목별로 나열하며, 각 항목은 「구 동작」「신 동작」「변경 이유」를 포함합니다.
5. **마이그레이션 단계**: 실행 가능한 작업을 번호로 나열하고 명령 또는 코드 예시를 제시합니다.
6. **검증 방식**: 마이그레이션 후 성공을 확인하는 방법과 검사 명령 또는 예상 출력을 제시합니다.
7. **롤백 방식**: 마이그레이션 실패 시 구버전으로 복구하는 방법.
8. **자주 묻는 질문**: 빈도가 높은 질문과 답변을 나열합니다.
9. **도움 받기**: 이슈, 토론 영역 또는 문서 사이트를 안내합니다.

### 3.1 복사 가능한 빈 템플릿

다음 템플릿은 3절의 아홉 가지 구조에 항목별로 대응하며, 복사 후 자리표시자를 교체하면 사용할 수 있습니다.

````markdown
# {{源版本}}에서 {{目标版本}}으로 마이그레이션

> 본 가이드는 {{源版本}}에서 {{目标版本}}으로 업그레이드하는 데 필요한 모든 작업을 설명하며, {{适用使用者范围}}에 적용됩니다.

## 1. 영향 개요

| 변경 범주 | 구체적 내용 | 영향 범위 | 마이그레이션 필수 여부 |
| --- | --- | --- | --- |
| {{变更类别}} | {{变更内容}} | {{受影响的使用者场景}} | {{是否必须迁移}} |

## 2. 사전 조건

- {{前置准备}}
- {{检查项与确认命令}}

## 3. 변경 목록

### {{变更项名称}}

- 구 동작: {{旧版本行为}}
- 신 동작: {{新版本行为}}
- 변경 이유: {{变更原因}}

마이그레이션 전:

```{{代码语言}}
{{旧配置或旧代码}}
```

마이그레이션 후:

```{{代码语言}}
{{新配置或新代码}}
```

## 4. 마이그레이션 단계

1. {{迁移步骤}}
2. {{迁移步骤}}
3. {{人工处理步骤}}

## 5. 검증 방식

```bash
{{可独立运行的检查命令}}
```

예상 출력: {{预期结果}}

## 6. 롤백 방식

1. {{恢复旧版本的操作}}
2. {{恢复旧配置的操作}}

## 7. 자주 묻는 질문

### {{问题}}

답: {{解答}}

## 8. 도움 받기

- 문제 피드백: {{issue 地址}}
- 토론 영역: {{讨论区地址}}
- 관련 문서: {{文档链接}}
````

자리표시자 대조:

| 자리표시자 | 필수 | 작성 요점 |
| --- | --- | --- |
| `{{源版本}}` / `{{目标版本}}` | 예 | 목표 tag와 일치해야 하며, 형식은 `vX.Y.Z` |
| `{{适用使用者范围}}` | 예 | 어떤 사용자가 반드시 마이그레이션해야 하는지 명시하여 모호한 표현을 피함 |
| `{{变更类别}}` | 예 | 설정, API, 런타임, 디렉터리 네 가지 중 최소 한 가지 |
| `{{是否必须迁移}}` | 예 | 해당 변경이 사용자의 마이그레이션 수행을 요구하는지 명시 |
| `{{旧行为}}` / `{{新行为}}` | 예 | 항목별로 대조하며 한쪽만 쓰지 않음 |
| `{{代码语言}}` | 예 | 코드 블록 언어 식별자(예: `yaml`, `json`, `js`) |
| `{{前置准备}}` | 예 | 마이그레이션 전에 완료해야 하는 백업과 환경 검사 |
| `{{迁移步骤}}` | 예 | 각 단계는 그대로 실행 가능해야 하며 명령 또는 코드를 포함 |
| `{{人工处理步骤}}` | 예 | 자동 마이그레이션이 불가능한 단계는 여기에 명시적으로 표기 |
| `{{检查命令}}` / `{{预期结果}}` | 예 | 명령은 독립 실행 가능해야 하고 결과는 판정 가능해야 함 |
| `{{回滚方式}}` | 예 | 생략할 수 없으며, 7절 금지 사항 참조 |

## 4. 내용 요건

### 4.1 변경 대조 예시

```markdown
### 설정 항목 `timeout`을 `timeoutMs`로 개명

- 구 동작: 설정 파일에서 `timeout: 5000`을 사용하며, 단위는 초입니다.
- 신 동작: `timeoutMs: 5000`으로 변경하며, 단위는 밀리초입니다.
- 변경 이유: 시간 단위를 통일하여 API 파라미터와의 불일치를 방지합니다.

마이그레이션 전:

```yaml
timeout: 5
```

마이그레이션 후:

```yaml
timeoutMs: 5000
```

### 4.2 작성 요건

1. 각 단계에 그대로 실행 가능한 명령 또는 코드를 제시하며, 「설정을 수정한다」라고만 서술해서는 안 됩니다.
2. 마이그레이션 전과 후의 대조를 제시하여 항목별 확인이 가능하게 합니다.
3. 자동 마이그레이션이 불가능하고 사람이 처리해야 하는 단계를 명확히 표기합니다.
4. 영향 범위는 구체적이어야 하며, 「일부 사용자에게 영향을 줄 수 있음」과 같은 모호한 표현을 피합니다.
5. 검증 명령은 독립적으로 실행 가능해야 하며 예상 출력을 포함합니다.

## 5. 릴리스 시점과 연동

1. 마이그레이션 가이드는 파괴적 변경을 포함하는 버전과 동시에 릴리스되어야 하며, 지연되어서는 안 됩니다.
2. `CHANGELOG.md`의 해당 항목은 마이그레이션 가이드를 링크해야 한다([변경 이력 규범](./변경-이력-규범.md) 참조).
3. PR 템플릿의 파괴적 변경 블록은 마이그레이션 방식을 작성하도록 안내해야 한다([이슈 및 PR 템플릿 규범](./이슈-및-PR-템플릿-규범.md) 참조).
4. 버전 번호는 시맨틱 버저닝을 따르며, 파괴적 변경은 메이저 버전을 증가시켜야 한다([버전 관리 규범](./버전-관리-규범.md) 참조).
5. README는 눈에 띄는 위치에서 구버전 사용자에게 마이그레이션 가이드를 읽도록 안내합니다.

## 6. 폐기와 유지 전략

1. 마이그레이션 가이드는 장기적으로 유지해야 하며, 신버전 릴리스 후 삭제해서는 안 됩니다.
2. 구버전 문서는 「더 이상 유지관리하지 않음」으로 표기할 수 있으나, 진입점은 유지해야 합니다.
3. 여러 메이저 버전을 넘는 업그레이드는 단계별 경로를 제공해야 하며, 모든 변경을 한 번에 넘도록 요구해서는 안 됩니다.

## 7. 금지 사항

1. 「파괴적 변경이 있으니 직접 조정하십시오」라고만 쓰는 것은 금지합니다.
2. 롤백 방식을 생략하는 것은 금지합니다.
3. 마이그레이션 단계에 실행 불가능한 의사 코드를 사용하는 것은 금지합니다.
4. 이전 버전의 마이그레이션 가이드를 삭제하는 것은 금지합니다.
