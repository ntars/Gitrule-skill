# 요구사항 추적 매트릭스 규범

> 이 파일이 해결하는 문제：요구사항에서 설계, 구현, 테스트, 릴리스까지의 양방향 추적 매트릭스 템플릿과 필드를 정의하여, 라이프사이클 각 단계의 산출물이 상호 참조에서 일관되고 변경 영향이 평가 가능하며 커버리지 공백을 발견할 수 있도록 보장합니다.

## 1. 규범 조문

1. 모든 「반드시」 등급 요구사항은 추적 매트릭스에서 한 행을 차지하고, 착수부터 릴리스까지의 전 링크 산출물을 기록해야 합니다.
2. 추적 관계는 양방향으로 조회 가능해야 합니다. 정방향은 요구사항에서 하위 산출물을 조회하고, 역방향은 산출물에서 상위 요구사항을 조회합니다.
3. 하나의 요구사항이 여러 산출물에 대응할 때는 쉼표로 구분된 번호 목록을 사용하며, 번호는 해당 문서의 정의와 완전히 일치해야 합니다.
4. 요구사항 변경은 매트릭스에 흔적을 남기고 변경 이유, 영향 범위와 결정권자를 기록해야 하며, 원래 값을 직접 덮어써서는 안 됩니다.
5. 매트릭스는 매 릴리스 전에 확인해야 하며, 종결되지 않은 「반드시」 등급 요구사항이 있으면 릴리스해서는 안 됩니다.
6. 커버리지 통계 기준: 요구사항 커버리지 = 릴리스된 「반드시」 등급 요구사항 수 / 「반드시」 등급 요구사항 총수.

## 2. 추적 매트릭스 템플릿

```markdown

| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| REQ-001 | {{标题}} | 반드시 | G1 | ADR-0002 | docs/api.md#check | #12 | TC-001, TC-002 | v1.0.0 | 검증됨 |
| REQ-002 | {{标题}} | 해야 함 | G2 | — | — | #15 | TC-005 | — | 구현됨 |
| REQ-003 | {{标题}} | 반드시 | G1 | ADR-0003 | docs/architecture.md#flow | — | — | — | 구현 대기 |

상태: 미확인 / 확인됨 / 구현 대기 / 구현됨 / 검증됨 / 릴리스됨 / 폐기됨
```

## 5. 필드 정의

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 요구사항 ID | 예 | `REQ-NNN` | [프로젝트 착수 및 요구사항 규범](./프로젝트-착수-및-요구사항-규범.md) 번호와 일치 | `REQ-001` |
| 우선순위 | 예 | 열거형 | 반드시 / 해야 함 / 할 수 있음 | `반드시` |
| 착수 목표 | 예 | `G-N` | 착수서의 목표 번호에 대응 | `G1` |
| 아키텍처 결정 | 아니요 | `ADR-NNNN` | 아키텍처 결정이 없으면 「—」라고 작성하고 비워 두지 않음 | `ADR-0002` |
| 설계 문서 | 아니요 | `경로#앵커` | 섹션 앵커까지 정확히 지정 | `docs/api.md#check` |
| 구현 PR | 아니요 | `#숫자` | PR 번호이며 커밋 해시가 아님 | `#12` |
| 테스트 케이스 | 예 | `TC-NNN` 목록 | 최소 한 건, 케이스가 없으면 이유 설명 | `TC-001` |
| 릴리스 버전 | 아니요 | `vX.Y.Z` | tag와 일치 | `v1.0.0` |
| 상태 | 예 | 열거형 | 일곱 상태 중 하나, 폐기 외에는 전진만 함 | `검증됨` |
| 변경 기록.영향 범위 | 예 | 텍스트 | 영향을 받는 ADR, PR, TC를 나열 | `ADR-0002, TC-001` |

## 6. 작성 설명

1. **번호 일치**: 매트릭스의 요구사항 ID, ADR 번호, TC 번호는 원본 문서와 글자 단위로 일치해야 하며, 약칭이나 별칭을 사용해서는 안 됩니다.
2. **빈 값 규범**: 해당 없음은 「—」, 아직 생성되지 않음은 「보완 예정」이라고 작성합니다. 두 가지는 의미가 다르므로 혼용해서는 안 됩니다.
3. **역방향 색인**: 정방향 매트릭스를 갱신할 때마다 역방향 색인을 동기화합니다. 둘이 일치하지 않을 때는 정방향 매트릭스를 기준으로 하고 즉시 수정합니다.
4. **변경 흔적**: 어떤 필드든 수정하기 전에 변경 기록에 한 행을 추가하고 원래 값과 새 값을 작성합니다. 직접 덮어쓰는 것은 금지합니다.
5. **릴리스 확인**: 릴리스 전에 「반드시」 등급 요구사항이 테스트 케이스와 릴리스 버전을 갖추었는지 항목별로 점검하며, 어느 하나라도 빠지면 릴리스를 차단합니다.
6. **폐기된 요구사항**: 행을 유지하고 삭제하지 않으며, 상태를 「폐기됨」으로 바꾸고 변경 기록에 폐기 이유를 작성합니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| 테스트 케이스 필드를 비워 둠 | 커버리지 공백이 보이지 않음 | 「보완 예정」을 채우고 릴리스 전에 해소 |
| PR 필드에 커밋 해시를 기입 | 리뷰 기록을 찾을 수 없음 | PR 번호로 변경 |
| 변경 시 값을 바로 수정 | 영향 추적 불가 | 먼저 변경 기록을 추가 |
| 상태를 「검증됨」에서 「구현됨」으로 후퇴 | 전진만 하는 원칙 위반 | 결함을 새로 열고 별도 추적 행 생성 |
| 정방향과 역방향 색인이 불일치 | 참조 불일치 | 릴리스 전에 정방향을 기준으로 동기화 |
