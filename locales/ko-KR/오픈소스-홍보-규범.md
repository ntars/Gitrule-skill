# 오픈소스 홍보 규범

> 이 파일이 해결하는 문제：오픈소스 프로젝트의 릴리스 전후 홍보 채널, 릴리스 리듬, 첫 화면 자료와 커뮤니티 운영 규범을 정의하여, 프로젝트가 사용 가능한 문서를 갖춘 상태에서 목표 사용자에 맞는 노출을 얻도록 한다.

본 파일의 채널 목록과 원칙은 phodal의 《GitHub 漫游指南》 홍보 장을 참고하였다. 해당 프로젝트는 11,362 star 규모로 이러한 방식이 중국어 오픈소스 커뮤니티에서의 적용 가능성을 검증하였다.

## 1. 기본 원칙

1. **품질이 홍보보다 우선**: 홍보는 이미 갖춘 품질을 확대할 뿐, 결여를 고치지 않는다. README, 예시, 문서, 테스트가 준비되기 전에는 홍보를 시작해서는 안 된다.
2. **프로젝트 자체가 홍보의 전부는 아님**: 코드와 README 외에도 상세 문서, 예시 프로그램과 문제 대응 메커니즘을 준비해야 한다.
3. **명확한 동기**: 홍보는 구체적 목표(초기 사용자 확보, 기여자 모집, 피드백 수집)에 봉사하며, star 수 추구를 위해 홍보해서는 안 된다.
4. **채널 적합성**: 프로젝트 기술 스택과 목표 사용자에 따라 채널을 선택하고, 무차별 살포를 피한다.
5. **정직한 제시**: star 수, 다운로드 수 또는 사용 사례를 조작해서는 안 되며, 기능 비교는 검증 가능한 사실에 근거해야 한다.

## 2. 릴리스 전 준비 체크리스트

| 범주 | 요건 | 판정 근거 |
| --- | --- | --- |
| 첫 화면 | README가 네 가지 질문 검사를 통과(무엇인가/무엇을 해결하는가/특징/예시) | [README 섹션 규범](./README-섹션-규범.md) |
| 한 문장 문안 | 범주와 수식어를 명확히 하고, 독립적으로 다시 설명 가능 | 위와 동일, 1.1절 |
| 예시 | 두 단계 이내에 실행 가능한 hello world 제공 | [README 표준 템플릿](./README-표준-템플릿.md) |
| 문서 | 설치, 설정, API 문서 모두 구비 | [문서 매트릭스](./문서-매트릭스.md) |
| 라이선스 | LICENSE가 존재하고 README 표기와 일치 | [LICENSE 규범](./LICENSE-규범.md) |
| 컴플라이언스 | NOTICE가 제3자 의존성을 포괄 | [NOTICE 규범](./NOTICE-규범.md) |
| 커뮤니티 진입점 | 이슈 템플릿, 기여 가이드, 행동 강령 구비 | [기여 가이드 규범](./기여-가이드-규범.md) |
| 대응 메커니즘 | 문제 대응 담당자와 대응 기한을 명확히 함 | [인시던트 대응 규범](./인시던트-대응-규범.md) |

위 체크리스트를 완료하지 않고 홍보하는 것은 본 규범이 금지하는 행위이다.

## 3. 채널 분류

### 3.1 국제 기술 커뮤니티

| 채널 | 적용 콘텐츠 | 유의 사항 |
| --- | --- | --- |
| Hacker News | 기술 구현, 깊이 있는 엔지니어링 설계 | 제목은 담백하게 쓰고 마케팅 표현을 피함 |
| Reddit 해당 게시판 | 라이브러리, 도구, 프레임워크 | 각 게시판의 자기 홍보 규칙 준수 |
| Lobsters | 시스템 프로그래밍, 엔지니어링 실무 | 커뮤니티가 마케팅에 민감함 |
| 기술 주간지(JavaScript Weekly 등) | 라이브러리와 도구 | 간결한 프로젝트 요약 제공 |
| 공식 블로그와 문서 사이트 | 심층 소개와 버전 설명 | 다른 채널의 착지점 역할 |

### 3.3 프로젝트 자체 채널

1. 프로젝트 README의 커뮤니티 진입점(Discussions, Discord);
2. 프로젝트 전용 소셜 계정으로 버전과 활동을 게시;
3. 문서 사이트와 예시 사이트를 외부 유입의 착지 페이지로 활용.

## 4. 릴리스 리듬

1. **예열기**: 2절 체크리스트를 완료하고 한 문장 문안, 스크린샷, 데모 GIF 등 자료를 준비한다.
2. **첫 발행기**: 가장 적합한 1~2개 채널에 발행하여, 같은 내용이 여러 플랫폼에서 도배되는 것을 피한다.
3. **대응기**: 첫 발행 후 72시간 이내에 높은 빈도로 대응하며 이슈와 피드백을 처리한다.
4. **이터레이션기**: 버전 릴리스 리듬에 따라 지속적으로 갱신하고, 매 릴리스에 변경 설명을 첨부한다.
5. **정착기**: 빈도가 높은 문제를 FAQ로 정리하여 문서에 환류한다.

## 5. 첫 화면 자료 요건

| 자료 | 규격 | 용도 |
| --- | --- | --- |
| 한 문장 문안 | 중국어 60자 이내 / 영어 25단어 이내. 리포지터리 Description은 「국가 언어 \| 영어」 이중 언어 병합 형식을 사용하며, [프로젝트 명명 규범](./프로젝트-명명-규범.md) 5절 참조 | 리포지터리 Description, 소셜 요약 |
| 스크린샷 | 라이트/다크 테마 두 버전, 너비 제어 | README 첫 화면 |
| 데모 GIF | 압축 후 용량 제어, 핵심 흐름 시연 | README 데모 섹션 |
| 로고 | SVG 형식, 라이트/다크 두 버전 포함 | 첫 화면과 소셜 카드 |
| 기능 비교 표 | 검증 가능한 사실에 근거하고, 적용되지 않는 상황 포함 | README 또는 문서 사이트 |

자료는 버전과 함께 동기화하여 갱신해야 하며, 구버전 인터페이스가 표시되지 않도록 한다.

## 6. 커뮤니티 운영

1. 최초 기여자에게 명확한 진입점을 제공한다(예: `good first issue` 라벨).
2. 문제 대응은 기록을 남겨야 하며, 중복 문제가 반복적으로 발생하지 않도록 한다.
3. 행동 강령은 모든 커뮤니티 채널에 적용되며, [행동 강령 규범](./행동-강령-규범.md)을 참조한다.
4. 기여자 감사는 한곳에 모아 두고, 본문 곳곳에 흩어 놓지 않는다.
5. star 유도, 상호 좋아요 등의 방식으로 허위 관심을 얻어서는 안 된다.

## 7. 금지 사항

1. 품질 체크리스트가 완료되지 않은 상태에서 홍보하는 것은 금지한다.
2. 프로젝트 데이터와 사용 사례를 조작하거나 과장하는 것은 금지한다.
3. 같은 내용을 여러 채널에서 반복 도배하는 것은 금지한다.
4. 자사 이미지를 높이기 위해 동종 프로젝트를 폄하하는 것은 금지한다.
5. 유도 수단으로 star 수를 얻는 것은 금지한다.
