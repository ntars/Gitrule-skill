# 오픈소스 컴플라이언스 규범

> 이 파일이 해결하는 문제：오픈소스 컴플라이언스의 수집 범위, 의존성 목록 필드, 수집 방법, 라이선스 호환성 판단, 수정 표기와 자료 인용 규칙을 정의하여 고지가 완전하고 검증 가능하도록 보장합니다.

## 1. 수집 범위

네 가지 출처를 포괄해야 합니다. 직접 의존성, 간접 및 전이 의존성, 빌드와 개발 도구 체인, 자료 자원(아이콘, 폰트, 이미지, 오디오, 데이터셋, 알고리즘 출처).

## 2. 의존성 목록 필드

| 필드 | 요구사항 |
| --- | --- |
| 컴포넌트 이름 | 공식 리포지터리와 일치 |
| 버전 | 실제로 고정된 버전, 범위 표현식이 아님 |
| 인용 방식 | 직접 의존성 또는 간접 의존성 |
| 저작권자 | 공식 선언된 저작권자 전체 이름 |
| 라이선스 | SPDX 식별자, 다중 라이선스는 결합 방식을 명시 |
| 공식 주소 | 리포지터리 또는 홈페이지 전체 URL |
| 본 프로젝트 용도 | 구체적 호출 위치 또는 기능 |
| 수정 여부 | 예 또는 아니요 |
| 수정 설명 | 수정 파일, 수정 내용, 수정 사유, 미수정이면 「없음」으로 기재 |
| 라이선스 원문 위치 | 프로젝트 내 경로 또는 파일 링크 |

의존성 목록 표 템플릿은 [정보 수집 및 템플릿](./정보-수집-및-템플릿.md) 참조.

## 3. 수집 방법

기술 스택에 따라 해당 명령으로 의존성 트리를 생성한 후 라이선스와 저작권 정보를 항목별로 보완합니다. `npm ls --all`, `pip freeze`, `go mod graph`, `cargo tree`, `mvn dependency:tree`, `gradle dependencies`, `composer show --tree`. 라이선스 스캔은 `license-checker`, `pip-licenses`, `cargo-license` 등의 도구를 사용할 수 있으며, 스캔 결과는 반드시 사람이 재검토해야 하고 도구 출력을 그대로 최종 결론으로 삼아서는 안 됩니다.

## 4. 라이선스 호환성

1. 프로젝트 라이선스와 각 의존성 라이선스의 호환성을 판단해야 하며, GPL, AGPL, LGPL, MPL 의 전염 범위를 중점 확인합니다.
2. Apache-2.0 의존성은 해당 NOTICE 파일 요구사항이 충족되었는지 확인해야 합니다.
3. 자료 유형 라이선스(예: SIL OFL 폰트, CC 계열)는 저작자 표시와 전파 요구사항을 별도로 확인해야 합니다.
4. 호환성을 판단할 수 없을 때는 「【확인 대기: 라이선스 호환성】」으로 표기하고 의문 사유를 설명합니다.
5. 프로젝트가 계층 라이선스를 채택할 때는 계층별로 판단해야 합니다. 어떤 의존성이 어느 계층에 쓰이는지에 따라 그 계층의 라이선스로 호환성을 판정하며, 주 라이선스로 저장소 전체를 대표시켜서는 안 됩니다. 계층 배치와 확인 절차는 [LICENSE 규범](./LICENSE-규범.md)을 참고합니다.
6. 동일한 의존성이 여러 라이선스 계층에 걸칠 때는 그 의존성의 실제 사용 범위를 표기하고, 가장 엄격한 적용 계층으로 판정합니다.

## 5. 타인 코드 수정 표기

1. 파일 헤더에 원본 저작권 표시와 라이선스 표시를 유지합니다.
2. NOTICE 에 수정 파일 경로, 수정 내용 요약, 수정 날짜를 명시합니다.
3. README 의 해당 섹션에도 동기화하여 설명합니다.

## 6. 인용과 자료

1. 타인의 문서나 코드 조각을 인용할 때는 출처 주소, 저자, 라이선스를 명시해야 합니다.
2. 이미지, 아이콘, 폰트는 출처와 라이선스를 기록해야 하며, 누락 시 확인 대기로 표기하고 그대로 사용해서는 안 됩니다.
3. 출처가 불분명한 자료를 사용해서는 안 됩니다.
