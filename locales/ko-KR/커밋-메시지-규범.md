# 커밋 메시지 규범

> 이 파일이 해결하는 문제：Conventional Commits의 필드, 형식, 작성 설명과 예시를 정의하여 이력을 읽을 수 있게 하고 변경 이력과 버전 번호를 자동 생성할 수 있도록 보장합니다.

## 1. 형식

```text
<类型>[可选作用域][可选 !]: <描述>

[可选正文]

[可选脚注]
```

## 2. 유형

전체 열 가지 유형은 다음과 같으며, 일반적인 오픈소스 프로젝트의 커밋 시나리오를 포괄합니다:

| 유형 | 의미 |
| --- | --- |
| `feat` | 신규 기능 추가 |
| `fix` | 결함 수정 |
| `docs` | 문서 변경 |
| `style` | 로직을 바꾸지 않는 형식 조정(공백, 포매팅, 세미콜론 누락 등) |
| `refactor` | 리팩터링, 신규 기능도 결함 수정도 아님 |
| `perf` | 성능 최적화 코드 변경 |
| `test` | 누락된 테스트 추가 또는 기존 테스트 정정 |
| `build` | 빌드 시스템 또는 외부 의존성에 영향을 주는 변경(예: npm, gulp) |
| `ci` | 지속적 통합 구성과 스크립트의 변경(예: GitHub Actions, CircleCI) |
| `chore` | 빌드, 의존성, 툴체인 등 잡무 |

### 2.1 팀 작성 방식의 대조와 선택

협업 방식이 다르면 세 가지 흔한 작성 방식이 존재하며, 프로젝트는 착수 시 하나를 선택하여 전 팀이 통일해야 합니다:

| 작성 방식 | 형식 | 적용 | 한계 |
| --- | --- | --- | --- |
| 업무 방식 | `[작업 카드 번호] 작성자: 수정 내용` | 칸반, 페어 프로그래밍을 사용하는 팀 | 작업 카드 번호 체계에 의존하므로 카드 번호가 없으면 적용 불가 |
| 일반 방식 | `[분류] 컴포넌트(선택): 수정 내용` | 업무 모듈별로 이력을 필터링해야 하는 팀 | 팀의 분류표 합의가 필요하여 추가 비용 발생 |
| 오픈소스 방식 | `<type>(<scope>): <subject>` | 오픈소스 라이브러리와 애플리케이션, CHANGELOG 자동 생성 필요 | 유형과 스코프가 많아 학습 비용이 높음 |

본 프로젝트는 오픈소스 방식을 통일 적용합니다(즉 Conventional Commits). 이유: 기계가 판독할 수 있어 변경 이력과 버전 번호를 자동 생성할 수 있습니다. 업무 방식과 일반 방식은 비공개 팀에서만 합의에 따라 사용하며, 대외 리포지터리에 혼입해서는 안 됩니다.

## 3. 필드 정의

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 유형 | 예 | 열거 | 열 가지 중 하나, 임의 창작 금지 | `feat` |
| 스코프 | 아니오 | 텍스트 | 모듈명, 소문자 짧은 단어, 공백 없음 | `parser` |
| 호환성 파괴 표시 | 아니오 | `!` | 유형 또는 스코프 뒤, 콜론 앞에 위치 | `feat!:` |
| 설명 | 예 | 텍스트 | 명령형, 소문자 시작, ≤72자, 끝에 마침표 없음 | `add TOML config support` |
| 본문 | 아니오 | 텍스트 | 동기와 구현을 설명하며, 설명과 한 줄 띄움 | `Allow the parser to read TOML...` |
| 각주 | 아니오 | 텍스트 | `BREAKING CHANGE:` 또는 `Refs: #N` | `BREAKING CHANGE: ...` |
| 연관 요구사항 | 아니오 | `REQ-NNN` | 본문 또는 각주에 작성하여 추적 용이 | `Refs: REQ-001` |

## 4. 작성 설명

1. **설명**: 명령형(add, fix, remove)을 사용하여 「무엇을 했는지」를 쓰고 「수정했다」고 쓰지 않습니다. 중국어 프로젝트는 중국어 설명을 쓸 수 있으나 전체 리포지터리가 통일해야 합니다.
2. **스코프**: 파일명이 아닌 모듈명을 취합니다. 여러 모듈에 걸친 변경은 스코프를 생략하며 `all`이나 `global`을 쓰지 않습니다.
3. **본문**: 설명만으로 동기를 밝히기 부족할 때만 작성합니다. 설명을 반복하지 않고 과정을 나열하지 않습니다.
4. **호환성 파괴 변경**: `feat!:` / `fix!:`와 `BREAKING CHANGE:` 각주 중 하나를 선택하거나 함께 사용합니다. 둘이 나타나면 반드시 동시에 [변경 이력 규범](./변경-이력-규범.md)과 [마이그레이션 가이드 규범](./마이그레이션-가이드-규범.md)에 기록해야 합니다.
5. **원자성**: 한 번의 커밋은 한 가지만 수행합니다. 포매팅과 로직 변경은 두 번의 커밋으로 나눕니다.
6. **보안**: 키, 토큰, 개인정보, 내부 주소를 포함해서는 안 됩니다. 커밋 전에 키 스캔으로 점검합니다([보안 및 개인정보 규범](./보안-및-개인정보-규범.md) 참조).
7. **버전 연동**: `feat`는 마이너 버전 증가, `fix`는 패치 버전 증가, `BREAKING CHANGE`는 메이저 버전 증가를 유발합니다. 자세한 내용은 [버전 관리 규범](./버전-관리-규범.md)을 참조합니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| `wip`, `update`, `fix bug` | 정보량이 없어 H10 위반 | 대상과 행위를 명시 |
| `feat: Added new feature.` | 명령형이 아니고 대문자 시작이며 마침표 있음 | `feat: add config loader` |
| `feat(전체): 최적화` | 스코프가 유효하지 않고 설명이 모호 | 구체적 모듈명을 쓰고 변경 사항을 명시 |
| 한 번의 커밋에 포매팅과 기능 변경 포함 | 원자성 파괴 | `style:`과 `feat:` 두 번의 커밋으로 분리 |
| 커밋 메시지에 내부망 주소 포함 | 정보 유출 | 제거하고 키 스캔 진행 |

## 5. 완전한 예시

```text
feat(parser): add support for TOML config

Allow the parser to read TOML configuration files in addition to YAML.
Refs: REQ-001

BREAKING CHANGE: the `config` option now accepts a file path instead of an object.
```

각 필드의 의미: `feat`는 유형, `parser`는 스코프, 콜론 뒤는 간단한 설명입니다. 본문은 동기와 구현을 설명하고, 각주는 요구사항을 연결합니다. 끝의 각주는 호환성 파괴 변경을 선언하고 마이그레이션 방향을 제시합니다.

수정 유형 예시:

```text
fix(spacing): avoid false positives before Chinese punctuation

The spacing rule previously flagged strings such as 「使用Node.js，」 because
the punctuation check ran after whitespace normalization.

Refs: REQ-004, #142
```
