# SECURITY 템플릿

> 이 파일이 해결하는 문제：프로젝트가 SECURITY.md 를 생성할 수 있도록 그대로 복사 가능한 보안 정책 템플릿을 제공하며, 지원 버전, 취약점 신고 채널, 대응 절차와 공개 원칙을 명확히 합니다. 함께 제공되는 작성 설명은 신고 채널 선택과 민감 정보 처리를 다룹니다.

## 1. 사용 설명

1. 3절 「템플릿 본문」 전체 내용을 복사하여 프로젝트 루트 디렉터리에 `SECURITY.md` 로 새로 만듭니다.
2. 4절에 따라 자리표시자를 교체합니다. 신고 채널은 반드시 실제로 도달 가능하고 공격 면을 공개적으로 노출하지 않는 주소여야 합니다.
3. 5절의 시나리오 변형에 따라 잘라냅니다. 다중 버전을 유지하지 않는 프로젝트는 지원 버전 표에서 구 버전 행을 삭제합니다.
4. 보안 규칙과 민감 정보 요구사항은 [보안 및 개인정보 규범](./보안-및-개인정보-규범.md) 참조, 커뮤니티 거버넌스 차원은 [감사 차원 매트릭스](./감사-차원-매트릭스.md) 참조.

## 2. 맞춤 설정 원칙

- **비공개 채널 우선**: 취약점 신고는 비공개 채널로 진행하며, 신고자에게 공개 이슈에서 세부 사항을 공개하도록 요구하는 것은 금지합니다.
- **기한 명확화**: 최초 응답과 수정의 시간 범위를 제시하여 무기한 약속을 피합니다.
- **정보 최소화**: 신고자에게 재현에 필요한 최소 정보만 제공하도록 요구하며, 실제 운영 데이터 제출은 금지합니다.
- **법률 일치**: 공개 원칙은 적용 법률 및 플랫폼 정책과 일치해야 하며, 규제 산업의 경우 법무 검토를 거쳐야 합니다.

## 3. 템플릿 본문

```markdown
# 보안 정책

> 이 파일은 {{项目名称}} 의 보안 지원 범위와 취약점 신고 방식을 설명하며, 보안 연구자, 기여자와 사용자에게 적용됩니다.

## 지원 버전

| 버전 | 보안 보고 접수 여부 |
| --- | --- |
| {{当前版本}} | 예 |
| {{上一版本}} | {{是否接受}} |
| 이전 버전 | 아니요 |

## 신고 채널

공개 이슈, 토론 게시판 또는 소셜 채널을 통해 보안 취약점을 신고하지 마십시오. 다음 비공개 채널로 제출해 주십시오.

- 보안 이메일：{{真实可达的安全邮箱}}
- 비공개 신고 입구：{{私有漏洞报告地址}}

위 채널이 없으면 {{备用私有联系方式}} 로 유지관리자에게 연락해 주십시오.

## 보고 내용

처리 효율을 높이기 위해 가능한 한 다음을 제공해 주십시오.

- 영향받은 버전과 컴포넌트
- 취약점 유형과 잠재적 영향
- 최소 재현 절차 또는 개념 증명
- 권장 수정 방향(선택 사항)

실제 운영 데이터, 시크릿 또는 개인 식별 정보를 제출하지 마십시오.

## 대응 절차

| 단계 | 시간 범위 | 설명 |
| --- | --- | --- |
| 접수 확인 | {{首次响应时限}} | 유지관리자가 보고서 접수를 확인 |
| 1차 평가 | {{评估时限}} | 보안 문제 해당 여부와 영향 범위 판단 |
| 수정과 검증 | {{修复时限}} | 수정 완료 및 검증, 복잡한 문제는 별도 협의 |
| 공개 릴리스 | 수정 완료 후 {{发布延迟}} | 보안 공지와 수정 버전 릴리스 |

## 공개 원칙

- 유지관리자는 수정이 릴리스될 때까지 신고자 신원과 보고 내용을 비밀로 유지합니다.
- 유지관리자의 동의 없이 신고자는 수정 릴리스 전에 취약점 세부 사항을 공개해서는 안 됩니다.
- 수정 릴리스 후 유지관리자는 보안 공지에서 신고자에게 감사를 표합니다(신고자 동의 시).
- 선의의, 본 정책을 준수하는 보안 연구는 책임을 묻지 않습니다.

## 예외와 면책

본 정책은 어떠한 보안 보장에 대한 약속도 구성하지 않으며, 프로젝트 내용은 「현상 그대로」 제공됩니다. 자세한 내용은 [면책 조항](./면책-조항.md)과 [LICENSE](./LICENSE)를 참조하십시오.
```

## 4. 자리표시자 대조표와 필드 정의

| 자리표시자 | 필수 | 필드 정의 | 작성 예시 |
| --- | --- | --- | --- |
| `{{项目名称}}` | 예 | 프로젝트 대외 명칭 | `FooBar` |
| `{{当前版本}}` | 예 | 현재 유지관리 중인 최신 버전 또는 `main` | `v2.3.0` |
| `{{上一版本}}` | 아니요 | 여전히 유지관리 중인 이전 버전 | `v2.2.x` |
| `{{是否接受}}` | 예 | 해당 버전의 보안 보고 접수 여부 | `예` |
| `{{真实可达的安全邮箱}}` | 예 | 보안 보고 전용 이메일 | `security@example.com` |
| `{{私有漏洞报告地址}}` | 예 | 비공개 보고 입구 | `https://github.com/owner/repo/security/advisories/new` |
| `{{备用私有联系方式}}` | 아니요 | 주 채널 사용 불가 시 대체 수단 | `유지관리자 계정을 통한 비공개 메시지` |
| `{{首次响应时限}}` | 예 | 보고 접수 확인의 시간 범위 | `영업일 3일` |
| `{{评估时限}}` | 예 | 1차 평가 완료의 시간 범위 | `영업일 7일` |
| `{{修复时限}}` | 예 | 수정 완료의 시간 범위 | `30일` |
| `{{发布延迟}}` | 예 | 수정 후 공개 릴리스까지의 간격 | `7일` |

## 5. 작성 설명과 시나리오 변형

| 시나리오 | 반드시 유지할 섹션 | 잘라낼 수 있는 섹션 | 조정 요점 |
| --- | --- | --- | --- |
| 단일 버전 프로젝트 | 신고 채널, 보고 내용, 대응 절차, 공개 원칙 | 지원 버전 표에서 구 버전 행 삭제 | 현재 버전을 `main` 또는 최신 tag 로 기재 |
| 다중 버전 유지 | 전체 | 없음 | 여전히 보고를 접수하는 버전을 행별로 나열 |
| 개인 프로젝트 | 전체 | 지원 버전은 간소화 가능 | 비공개 채널은 장기 보유 이메일 사용 |
| 기업 프로젝트 | 전체 | 없음 | 기한은 내부 보안 제도와 일치해야 하며 법무 검토를 거침 |
| 규제 산업 | 전체 | 없음 | 컴플라이언스 통보 의무와 데이터 보존 요구사항 추가 |

흔한 오류 대조:

| 잘못된 작성 | 결과 | 올바른 작성 |
| --- | --- | --- |
| 「Issue 에 취약점을 보고해 주십시오」 | 세부 사항이 공개되어 위험 확대 | 비공개 채널 사용 |
| 「최대한 빨리 처리하겠습니다」 | 명확한 기대치 없음, 신고자가 판단 불가 | 단계별로 시간 범위 제시 |
| 기한을 「24시간 내 수정」으로 작성 | 과도한 약속으로 이행 불가 | 합리적 범위를 쓰고 복잡한 문제는 별도 협의 명시 |
| 마스킹을 요구하지 않음 | 신고자가 실제 운영 데이터를 제출할 수 있음 | 실제 데이터와 시크릿 제출을 명확히 금지 |

## 6. 완전한 예시

다음은 신고 채널 단락을 작성한 예시이며, 형식 참고용입니다.

```markdown
## 신고 채널

공개 이슈, 토론 게시판 또는 소셜 채널을 통해 보안 취약점을 신고하지 마십시오. 다음 비공개 채널로 제출해 주십시오.

- 보안 이메일：security@example.com
- 비공개 신고 입구：https://github.com/example/democli/security/advisories/new

실제 운영 데이터, 시크릿 또는 개인 식별 정보를 제출하지 마십시오.
```
