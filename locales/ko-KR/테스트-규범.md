# 테스트 규범

> 이 파일이 해결하는 문제：테스트 계층, 테스트 계획과 케이스의 템플릿, 필드, 커버리지 기준과 실행 표준을 정의하여, 모든 요구사항이 검증 가능하고 모든 변경이 회귀 가능하도록 보장합니다.

## 1. 규범 조문

1. 테스트는 단위, 통합, 엔드투엔드 세 계층으로 나뉘며, 각 계층은 테스트 대상과 테스트하지 않는 범위를 명시해야 하고, 중복 커버리지를 피합니다.
2. 모든 「반드시」 등급 요구사항에는 최소 한 건의 테스트 케이스가 대응해야 하며, 추적 관계는 [요구사항 추적 매트릭스 규범](./요구사항-추적-매트릭스-규범.md)을 참조합니다.
3. 결함 수정은 먼저 회귀 케이스를 보완한 후 코드를 변경해야 하며, 회귀 케이스는 원래 결함을 재현할 수 있어야 합니다.
4. 커버리지 임계값은 프로젝트에서 설정하여 CI에 반영하며, 정해진 임계값보다 낮아서는 안 됩니다（하드 룰 H9에 대응）.
5. 테스트는 반복 가능해야 하고 외부 상태에 의존하지 않아야 하며, 외부 서비스에 의존하는 경우 격리하거나 mock을 사용해야 합니다.
6. 테스트 이름은 테스트 대상 동작과 예상 결과를 표현해야 하며, 테스트, lint, format, 타입 검사는 CI에서 자동 실행되고 모두 통과해야 병합할 수 있습니다（[코드 리뷰 규범](./코드-리뷰-규범.md) 참조）.

## 2. 테스트 계층

| 계층 | 테스트 대상 | 커버해야 함 | 커버하지 않음 | 대표 도구 |
| --- | --- | --- | --- | --- |
| 단위 테스트 | 함수, 순수 로직 모듈 | 핵심 로직, 경계 조건, 예외 분기 | 모듈 간 협업, 외부 I/O | 언어 내장 runner |
| 통합 테스트 | 모듈 간 협업 | 핵심 호출 체인, 어댑터, 영속화 상호작용 | 전체 사용자 흐름 | 테스트 컨테이너 / mock server |
| 엔드투엔드 테스트 | 전체 사용자 시나리오 | 주요 사용 경로, 핵심 비즈니스 폐쇄 루프 | 분기 전수 조사, 성능 부하 테스트 | 브라우저 / CLI 드라이버 |

## 3. 테스트 계획 템플릿

```markdown
# 테스트 계획: {{项目名称}} {{版本号}}

버전: {{v1.0}} ｜ 대응 요구사항 범위: {{REQ-001 ~ REQ-020}} ｜ 책임자: {{姓名}}

## 테스트 범위
- 포함: {{模块 / 需求编号列表}}
- 제외: {{不在本期验证的范围及原因}}
- 연관 착수 성공 기준: {{G1 / G2}}

## 계층 전략
| 계층 | 테스트 대상 | 커버리지 목표 | 도구 | 실행 시점 |
| --- | --- | --- | --- | --- |
| 단위 | {{对象}} | {{覆盖率阈值}} | {{工具}} | 매 커밋 |
| 통합 | {{对象}} | {{关键链路清单}} | {{工具}} | 매 병합 |
| 엔드투엔드 | {{场景}} | {{主要路径清单}} | {{工具}} | 매 릴리스 |

## 환경 및 데이터
- 환경: {{操作系统 / 运行时版本 / 依赖服务版本}}
- 테스트 데이터: {{构造方式；禁止使用生产敏感数据}}
- 외부 의존성: {{需 mock 的服务及隔离方式}}

## 진입 및 종료
- 진입: {{进入测试的前置条件，如开发自测通过}}
- 종료: {{通过率 100%、无 P0/P1 缺陷、覆盖率达标}}
- 중단 조건: {{阻塞性问题清单}}

## 리스크 및 트레이드오프
- 미테스트 범위 및 이유: {{例如第三方付费接口以 mock 替代}}
- 알려진 리스크: {{例如并发场景仅做 10 路验证}}
```

## 4. 테스트 케이스 템플릿

```markdown
### TC-{{三位序号}}：{{用例标题}}

- 연관 요구사항: {{REQ-001}}
- 계층: {{单元 / 集成 / 端到端}}
- 우선순위: {{P0 / P1 / P2}}
- 유형: {{正常 / 边界 / 异常}}
- 사전 조건: {{环境与数据准备}}
- 단계 및 예상:
  | 단계 | 조작 | 예상 결과 |
  | --- | --- | --- |
  | 1 | {{操作}} | {{可判定的结果}} |
  | 2 | {{操作}} | {{可判定的结果}} |
- 정리: {{恢复环境的操作；无则写「无」}}
```

## 5. 필드 정의

### 5.1 테스트 계획 필드

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 대응 요구사항 범위 | 예 | 목록 | REQ 번호 구간 사용 | `REQ-001 ~ REQ-020` |
| 제외 범위 | 예 | 텍스트 | 테스트하지 않는 이유를 명시 | `付费接口 미테스트: 테스트 계정 없음` |
| 커버리지 목표 | 예 | 임계값 | 커버리지는 숫자 백분율이어야 함 | `행 커버리지 ≥80%` |
| 실행 시점 | 예 | 열거형 | 커밋 / 병합 / 릴리스 | `매 병합` |
| 테스트 데이터 | 예 | 텍스트 | 구성 방식을 선언하고 실제 민감 데이터 금지 | `fixture로 생성` |
| 종료 조건 | 예 | 텍스트 | 판정 가능하고 결함 등급 임계값 포함 | `미종결 P0/P1 결함 없음` |

### 5.2 테스트 케이스 필드

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 번호 | 예 | `TC-NNN` | 연속, 재사용 없음 | `TC-007` |
| 연관 요구사항 | 예 | 목록 | 최소 한 건의 REQ 번호 | `REQ-001` |
| 우선순위 | 예 | 열거형 | P0 / P1 / P2 | `P0` |
| 유형 | 예 | 열거형 | 정상 / 경계 / 예외 | `경계` |
| 단계 및 예상 | 예 | 표 | 각 단계에 판정 가능한 예상이 있어야 함 | 템플릿 참조 |
| 정리 | 예 | 텍스트 | 정리가 없으면 「없음」이라고 작성하고 비워 두지 않음 | `없음` |

### 5.3 커버리지 기준

| 기준 | 정의 | 적용 계층 | 권장 임계값 |
| --- | --- | --- | --- |
| 행 커버리지 | 실행된 문장 수 / 전체 문장 수 | 단위 | 80% 이상 |
| 분기 커버리지 | 실행된 분기 수 / 전체 분기 수 | 단위 | 70% 이상 |
| 요구사항 커버리지 | 테스트 케이스가 있는 「반드시」 등급 요구사항 수 / 「반드시」 등급 요구사항 총수 | 전체 계층 | 100% |
| 경로 커버리지 | 검증된 주요 경로 수 / 식별된 주요 경로 총수 | 엔드투엔드 | 100% |

기준 설명: 커버리지는 미테스트 영역을 발견하는 수단이며 품질 목표 그 자체가 아닙니다. 높은 커버리지가 단언 품질을 대체하지 않으며, 단언은 코드를 실행하는 것만이 아니라 동작을 검증해야 합니다.

## 6. 작성 설명

1. **연관 요구사항**: REQ 번호를 기입해야 하며, 연결할 수 없는 케이스는 탐색적 테스트 기록으로 옮기고 정식 케이스 집합에 포함하지 않습니다.
2. **예상 결과**: 판정 가능해야 합니다. 「올바른 결과 반환」은 불합격이며, 「상태 코드 200을 반환하고 `name` 필드가 비어 있지 않음」은 합격입니다.
3. **유형 분포**: 모든 「반드시」 등급 요구사항에는 최소 한 건의 정상 케이스와 한 건의 경계 또는 예외 케이스를 배치합니다.
4. **정리**: 파일, 데이터베이스, 전역 상태와 관련된 케이스는 반드시 정리 단계를 작성해야 하며, 정리를 작성하지 않으면 케이스가 불완전한 것으로 간주합니다.
5. **회귀 케이스**: 결함 수정은 결함 번호를 접두어로 하여 이름을 붙입니다. 예: `TC-007-regression-142`.
6. **격리**: 케이스 사이에 실행 순서 의존이 있어서는 안 되며, 상태를 공유해야 하는 경우 사전 조건에서 재구성합니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| 예상에 「기능 정상」이라고 작성 | 판정 불가 | 구체적인 반환값 또는 상태 작성 |
| 케이스에 연관 요구사항 없음 | 추적 체인 끊김 | REQ 번호 보완 |
| 정상 경로만 테스트 | 경계 결함 누락 | 예외 및 경계 케이스 보완 |
| 케이스가 이전 케이스의 실행 결과에 의존 | 반복 실행 불가 | 사전 조건에서 상태 재구성 |
| 운영 데이터로 테스트 | 개인정보 및 컴플라이언스 리스크 | fixture로 변경 |

## 7. 전체 예시

```markdown
# 테스트 계획: markdown-lint-cli v1.0

버전: v1.0 ｜ 대응 요구사항 범위: REQ-001 ~ REQ-014 ｜ 책임자: 王五

## 테스트 범위
- 포함: 규칙 엔진, CLI 매개변수 파싱, 보고서 출력（REQ-001 ~ REQ-014）
- 제외: 에디터 플러그인 통합（v1.1로 연기, 대응 요구사항 없음）
- 연관 착수 성공 기준: G1、G2

## 계층 전략
| 계층 | 테스트 대상 | 커버리지 목표 | 도구 | 실행 시점 |
| --- | --- | --- | --- | --- |
| 단위 | 규칙 함수 | 행 커버리지 85% 이상 | 언어 내장 runner | 매 커밋 |
| 통합 | CLI → 규칙 엔진 → 보고서 | 핵심 링크 3건 | 테스트 컨테이너 | 매 병합 |
| 엔드투엔드 | 실제 리포지터리 일괄 검사 | 주요 경로 2건 | shell 드라이버 | 매 릴리스 |

### TC-001: 중영문 사이 공백 누락 검출
- 연관 요구사항: REQ-001
- 계층: 단위
- 우선순위: P0
- 유형: 경계
- 사전 조건: `spacing` 규칙 로드
- 단계 및 예상:
  | 단계 | 조작 | 예상 결과 |
  | --- | --- | --- |
  | 1 | 「使用Node.js开发」 입력 | 적중 1건 반환, 행 번호 1 |
  | 2 | 「使用 Node.js 开发」 입력 | 적중 0건 반환 |
- 정리: 없음
```
