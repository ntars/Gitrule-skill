# LICENSE 규범

> 이 파일이 해결하는 문제：프로젝트 라이선스의 SPDX 표기, LICENSE 전문 요구사항, 저작권 행 위치, GitHub 감지 메커니즘, 계층 라이선스의 파일 배치와 확인 절차, 그리고 확인 없이 기재해서는 안 되는 규칙을 정의합니다.

## 1. 기본 규칙

1. 프로젝트 라이선스는 SPDX 식별자로 README에 명확히 기재하고, 해당 LICENSE 파일을 제공해야 합니다.
2. LICENSE 파일은 해당 라이선스의 공식 영문 전문이어야 하며, 조항을 삭제하거나 변경해서는 안 됩니다. 문구를 바꾸거나 문단을 재배열하거나 Markdown으로 다시 조판하면 모두 자동 감지가 실패합니다.
3. 저작권 행은 파일 머리말 또는 README 제19장에 두며, 형식은 [README 섹션 규범](./README-섹션-규범.md)을 참고합니다.

## 2. GitHub 감지 메커니즘

GitHub은 오픈소스 도구 licensee로 저장소의 라이선스를 판정합니다. 그 결과가 저장소 페이지의 배지, API의 license 필드, 그리고 license 키워드 검색에서 검색되는지를 좌우합니다. 규칙은 다음과 같습니다.

1. 스캔하는 위치는 두 곳뿐입니다. 프로젝트 루트 디렉터리와 최상위 `LICENSES/` 디렉터리입니다. `locales/`, `docs/` 같은 하위 디렉터리에 있는 같은 이름의 파일은 판정에 참여하지 않습니다.
2. 루트 디렉터리는 파일명으로 점수를 매기고 높은 점수가 우선합니다. `LICENSE`는 1.00, `LICENSE.md`는 0.95, `COPYING`은 0.90, `LICENSE-MIT`처럼 접미사가 붙은 형태는 0.70입니다.
3. 최상위 `LICENSES/` 디렉터리 안의 파일은 파일명이 SPDX 식별자 형식이고 확장자가 `.txt`, `.md`, `.markdown`, `.html`이면 1.00, 그 밖에는 0.00입니다.
4. 파일 내용은 해당 라이선스의 공식 전문과 고도로 일치해야 합니다. 「이 프로젝트는 특정 라이선스를 사용한다」는 선언만 담은 파일은 감지되지 않으며, 감지되더라도 비표준 값이 됩니다.
5. 서로 다른 여러 라이선스가 감지되면 프로젝트 수준 결과가 특정 라이선스를 반환하지 않을 수 있고, 저장소 페이지에는 `View license` 또는 `Other`로 표시됩니다.
6. README의 자연어 선언은 판정에 참여하지 않습니다. 「이 프로젝트는 MIT 라이선스다」라고 적어도 MIT로 감지되지 않습니다.

따라서 **README의 선언과 LICENSE 파일은 두 개의 독립된 메커니즘이며, 둘 다 갖추어야 합니다.** 또한 루트 디렉터리에 여러 라이선스 파일이 있으면 최종적으로 어느 것이 보고되는지는 파일명 점수와 내용 일치도에 함께 좌우되어 예측할 수 없습니다. 실측에서 듀얼 라이선스 저장소는 둘 중 하나만 보고되었습니다.

## 3. 계층 라이선스의 파일 배치

계층 라이선스는 저장소의 서로 다른 부분에 서로 다른 라이선스를 적용하는 것을 말합니다. 예를 들어 코드는 MIT, 문서는 CC BY 4.0을 씁니다. 이때 다음 순서로 배치를 정합니다.

| 방안 | 루트에 두는 것 | 자동 감지 결과 | 적용 조건 |
| --- | --- | --- | --- |
| 단층(기본) | `LICENSE` 한 부 | 해당 라이선스로 안정적으로 감지 | 각 계층의 라이선스가 같거나, 차이가 사용자 의무에 영향을 주지 않음 |
| 계층 + 설명 | `LICENSE`에 주 라이선스, 별도 `LICENSING.md` | 루트 `LICENSE`의 라이선스로 안정적으로 감지 | 계층화가 필요하고 배지의 명확성도 지켜야 함 |
| 계층 + REUSE | 최상위 `LICENSES/`에 각 라이선스 전문 | 비표준 값으로 퇴화할 수 있음 | 하위 사용자가 REUSE 준수를 명시적으로 요구할 때만 |

절충 지점：

1. 루트에 여러 개의 라이선스 파일을 동시에 두지 마십시오. 실측에서 듀얼 라이선스 저장소는 모두 둘 중 하나만 보고되었고, 나머지 하나는 저장소 페이지와 API에서 보이지 않아 대외적으로 한 가지 라이선스만 선언한 것과 같습니다.
2. REUSE 배치는 배지의 명확성과 충돌합니다. `LICENSES/`에 여러 라이선스를 두면 다중 라이선스로 판정되어 `reuse lint` 전부 통과를 얻는 대신 자동 감지 결과가 불명확해질 수 있습니다. 둘을 동시에 완벽히 만족할 수 없으며, 프로젝트 측이 절충해야 합니다.
3. 「계층 + 설명」을 채택할 때 `LICENSING.md`라는 파일명은 `LICENSE`나 `COPYING` 패턴을 포함하지 않아 라이선스 파일로 오인되지 않으며, 루트 `LICENSE`의 감지에 영향을 주지 않습니다.
4. 어떤 배치를 고르든 README 제19장에 SPDX 표현식(예: `MIT AND CC-BY-4.0`)과 각 계층의 적용 범위를 적어야 합니다. 사람이 읽는 수준에서 정보가 유실되지 않는 유일한 위치입니다.

## 4. 계층 판단과 확인 절차

계층 라이선스는 법적 의미를 지니므로, 작성하거나 최적화하기 전에 반드시 회차를 거듭해 확인해야 하며 임의로 메워서는 안 됩니다.

1. 임의로 계층화해서는 안 됩니다. 사용자가 명확히 요구하지 않았을 때는 단층으로 처리하고, 보고서에 「계층화가 필요하다면 선택 가능한 방안과 차이는 다음과 같습니다」라고 적습니다.
2. 계층화를 제안할 때는 근거를 함께 보고해야 합니다. 각 계층이 실제로 덮는 내용 범위, 후보 라이선스와 그 의무의 차이, 하위 사용자에 대한 영향, 그리고 자동 감지 결과가 어떻게 달라지는지입니다.
3. 기록하기 전에 최소 두 번 확인합니다. 첫 번째는 계층 조합(어느 계층에 어느 라이선스인지), 두 번째는 파일 배치(루트 파일에 어느 것을 두고 `LICENSES/`를 만들지)입니다.
4. 푸시 전에 다시 확인합니다. 생성 후에는 「파일을 생성했습니다. 확인하신 뒤 직접 커밋해 주십시오」라고 분명히 알리고, 사용자를 대신해 커밋하거나 푸시해서는 안 됩니다.
5. 확인받지 않은 후보 방안은 보고서나 임시 파일에만 기록하며, `LICENSE`, `LICENSES/`, `LICENSING.md`로 기록해서는 안 됩니다.
6. 어떤 부분이 어느 계층에 속하는지 판단할 수 없을 때는 「【확인 대기: 계층 귀속】」으로 표기하고 의문 파일을 나열합니다. 기본값으로 분류해서는 안 됩니다.

## 5. 면책 조항 요구사항

라이선스 문구는 법적 효력을 지닙니다. 템플릿과 도구는 판정 규칙과 파일 배치만 제공하며 법적 조언을 구성하지 않습니다.

1. README 제19장 또는 `LICENSING.md`에 면책 조항을 포함하고, 라이선스 선택은 프로젝트 측이 스스로 확인한다는 점을 설명해야 합니다.
2. 면책 조항은 NOTICE의 면책 조항과 일치해야 하며, 한쪽에 있고 다른 쪽에 없는 상태여서는 안 됩니다.
3. 「준수 판정을 완료했다」고 주장해서는 안 되며, 「규칙에 따라 파일 배치와 SPDX 표기가 갖추어졌는지 확인했다」고만 설명할 수 있습니다.
4. 계층 라이선스의 법적 효력은 각 라이선스 원문을 따릅니다. 저장소 안의 설명 문구는 색인일 뿐이며 조항을 바꾸지 않습니다.
