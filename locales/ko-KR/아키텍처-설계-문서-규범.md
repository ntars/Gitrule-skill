# 아키텍처 설계 문서 규범

> 이 파일이 해결하는 문제：아키텍처 문서와 아키텍처 결정 기록（ADR）의 템플릿, 필드와 작성법을 정의하고, 시스템 경계, 모듈 책임, 품질 속성과 핵심 트레이드오프를 설명하며 결정의 추적 가능성을 보장합니다.

## 1. 규범 조문

1. 아키텍처 문서（`docs/architecture.md`）는 구조와 경계만 설명하고 사용 예시는 포함하지 않으며, 책임 경계는 [문서 매트릭스](./문서-매트릭스.md)를 참조합니다.
2. 모든 중대한 기술 결정에는 대응하는 ADR이 있어야 하며, ADR이 없는 결정은 기록되지 않은 결정으로 간주합니다.
3. ADR 번호는 연속적이고 영구히 고정되며, 일단 채택되면 과거를 재작성하지 않고, 상태 변경은 새 ADR을 추가하여 기록하고 「대체됨」으로 표기합니다.
4. 아키텍처 설명은 코드 구현과 일관성을 유지해야 하며, 코드와 문서가 일치하지 않을 때는 코드를 기준으로 하고 즉시 문서를 개정합니다.
5. 모든 아키텍처 결정은 하나 이상의 요구사항으로 소급할 수 있어야 하며, 추적 관계는 [요구사항 추적 매트릭스 규범](./요구사항-추적-매트릭스-규범.md)을 참조합니다.
6. 품질 속성은 검증 가능한 측정 목표를 제시해야 하며, 「고성능」「고가용성」만 작성하는 것은 금지합니다.

## 2. 아키텍처 문서 템플릿

```markdown
# 아키텍처 설계: {{项目名称}}

문서 버전: {{v1.0}} ｜ 대응 코드 버전: {{tag}} ｜ 최종 확인 날짜: {{YYYY-MM-DD}}

## 시스템 컨텍스트
- 시스템 책임: {{一句话说明系统边界内的责任}}
- 외부 참여자: {{用户、上游系统、下游系统}}
- 입출력: {{进入系统的请求与系统产出的结果}}
- 경계 밖: {{明确不由本系统承担的职责}}

## 모듈 구분
| 모듈 | 유일한 책임 | 외부 인터페이스 | 의존 모듈 | 담당하지 않음 |
| --- | --- | --- | --- | --- |
| {{模块名}} | {{仅一件事}} | {{接口名}} | {{模块名}} | {{明确排除}} |

## 핵심 데이터 흐름
1. {{触发点}} → {{模块 A}}: {{传递的数据}}
2. {{模块 A}} → {{模块 B}}: {{转换与传递}}
3. {{模块 B}} → {{结果}}: {{最终产出}}

## 기술 선정
| 영역 | 선정 | 대안 | 결정 근거 | ADR |
| --- | --- | --- | --- | --- |
| {{语言 / 框架 / 存储}} | {{采用项}} | {{未采用项}} | {{取舍理由}} | {{ADR-000N}} |

## 품질 속성
| 속성 | 목표값 | 검증 방식 | 연관 ADR |
| --- | --- | --- | --- |
| 성능 | {{P95 延迟 < X ms}} | {{压测方式}} | {{ADR-000N}} |
| 가용성 | {{月度可用性 ≥ X%}} | {{监控统计}} | {{ADR-000N}} |
| 보안 | {{敏感数据零明文落盘}} | {{审计方式}} | {{ADR-000N}} |
| 확장성 | {{横向扩容至 N 节点无需改代码}} | {{扩容演练}} | {{ADR-000N}} |

## 제약과 트레이드오프
- 기술 제약: {{语言版本、平台、兼容性}}
- 포기한 방안 및 이유: {{方案 A：原因}}
- 알려진 기술 부채: {{债务项与偿还条件}}
```

## 3. ADR 템플릿

```markdown
# ADR-{{四位序号}}：{{决策标题}}

- 상태: {{提议 / 已采纳 / 已废弃 / 被 ADR-000N 替代}}
- 날짜: {{YYYY-MM-DD}}
- 결정권자: {{姓名}}
- 연관 요구사항: {{REQ-001 / …}}

## 배경
{{面临的客观问题与约束，须可验证，不写主观偏好}}

## 결정
{{采用的方案，一句话陈述，须明确到可执行的程度}}

## 대안
| 방안 | 장점 | 단점 | 미채택 이유 |
| --- | --- | --- | --- |
| {{方案 A}} | | | |
| {{方案 B（采用）}} | | | — |

## 결과
- 긍정: {{获得的能力}}
- 부정: {{引入的成本或限制}}
- 후속 작업: {{需要跟进的事项}}

## 관련 파일
- {{架构文档中受影响的章节}}
- {{替代或被引用的 ADR}}
```

## 4. 필드 정의

### 4.1 아키텍처 문서 필드

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 대응 코드 버전 | 예 | tag | [버전 관리 규범](./버전-관리-규범.md)의 tag와 일치 | `v1.2.0` |
| 최종 확인 날짜 | 예 | 날짜 | 코드 변경 후마다 갱신해야 함 | `2026-11-18` |
| 모듈 유일한 책임 | 예 | 텍스트 | 하나의 모듈에는 한 가지만 작성 | `Markdown 규칙 파싱 및 검증` |
| 담당하지 않음 | 예 | 텍스트 | 경계를 명확히 하여 책임 표류 방지 | `텍스트 재작성은 담당하지 않음` |
| 기술 선정.결정 근거 | 예 | 텍스트 | ADR 번호를 인용해야 함 | `ADR-0002 참조` |
| 품질 속성.목표값 | 예 | 측정값 | 단위와 임계값을 포함하고 검증 가능 | `P95 < 150ms` |
| 알려진 기술 부채 | 아니요 | 목록 | 상환 트리거 조건을 명시 | `v2에서 파서 교체 예정` |

### 4.2 ADR 필드

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 번호 | 예 | `ADR-NNNN` | 네 자리 일련번호, 연속, 영구 고정 | `ADR-0002` |
| 상태 | 예 | 열거형 | 제안 / 채택됨 / 폐기됨 / 대체됨 | `채택됨` |
| 연관 요구사항 | 예 | 목록 | 착수서의 REQ 번호에 대응 | `REQ-001` |
| 배경 | 예 | 텍스트 | 객관적 제약을 서술하고 「내 생각에는」 금지 | `Node 18 호환 필요` |
| 결정 | 예 | 텍스트 | 한 문장, 실행 가능 | `remark를 파서로 채택` |
| 대안 | 예 | 표 | 최소 1개의 미채택 방안 포함 | 템플릿 참조 |
| 부정 이유 | 예 | 텍스트 | 미채택 방안마다 제시해야 함 | 템플릿 참조 |
| 결과 | 예 | 목록 | 긍정, 부정, 후속 작업 세 가지를 모두 갖춤 | 템플릿 참조 |

## 5. 작성 설명

1. **모듈 구분**: 각 행의 「유일한 책임」에 「그리고」「및」으로 연결된 두 가지 일이 나타나면 두 모듈로 분리해야 합니다.
2. **데이터 흐름**: 시간 순서로 번호를 매기고 전달되는 데이터 내용을 표시하며, 모듈 이름 화살표만 작성하는 것은 금지합니다.
3. **품질 속성**: 각 항목은 목표값, 검증 방식과 ADR 인용을 갖추어야 하며, 어느 하나라도 빠지면 불완전한 것으로 간주합니다.
4. **ADR 배경**: 문제와 제약을 작성하고 결정 자체는 작성하지 않으며, 결정은 「결정」 단락에서 한 번만 나타납니다.
5. **대안**: 방안이 하나뿐이더라도 「직접 구현을 고려했으나 유지보수 비용이 너무 높아 채택하지 않음」을 작성해야 하며, 대안이 없으면 충분히 논증되지 않은 것으로 간주합니다.
6. **상태 변경**: 원래 ADR 본문을 수정하지 않고, 새 ADR을 생성하며 원문 상태를 「ADR-000N에 의해 대체됨」으로 바꿉니다.
7. **기술 부채**: 상환 트리거 조건을 작성해야 하며, 현상만 나열하는 것은 금지합니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| 아키텍처 문서에 API 호출 예시를 넣음 | [API 문서 규범](./API-문서-규범.md)과 책임이 중복됨 | API 문서로 옮기고 아키텍처에는 인터페이스 이름만 남김 |
| 「시스템은 고성능이어야 함」 | 임계값이 없고 검증 불가 | P95 지연 목표와 부하 테스트 방식을 제시 |
| ADR에 결정만 있고 대안이 없음 | 논증되지 않음 | 최소 1개의 미채택 방안과 이유 보완 |
| 채택된 ADR의 본문을 수정 | 과거가 재작성됨 | 새 ADR을 생성하고 대체 관계 표기 |
| 결정을 요구사항에 연결할 수 없음 | 추적 체인이 끊어짐 | 연관 REQ 번호 보완 |

## 6. 전체 예시

```markdown
# ADR-0002: remark를 Markdown 파싱 계층으로 채택

- 상태: 채택됨
- 날짜: 2026-11-18
- 결정권자: 李四
- 연관 요구사항: REQ-001、REQ-004

## 배경
GFM과 중국어 텍스트 노드 위치 지정을 지원해야 하고, 런타임 의존성은 Node 18과 호환되어야 하며, 팀이 파서를 유지보수할 수 있는 인력 상한은 분기당 0.5 인월입니다.

## 결정
remark 생태계를 유일한 Markdown 파싱 계층으로 채택하고, 규칙은 플러그인 형태로 구현합니다.

## 대안
| 방안 | 장점 | 단점 | 미채택 이유 |
| --- | --- | --- | --- |
| 자체 개발 파서 | 완전한 제어 가능 | 경계 사례를 장기간 유지보수해야 함 | 인력 상한 초과 |
| marked | 경량 | 중국어 노드 위치 지정 능력이 약함 | REQ-004 미충족 |

## 결과
- 긍정: GFM 호환성을 업스트림에서 유지보수하며, 노드 위치 지정이 인수 조건을 충족합니다.
- 부정: 플러그인 API 변경 시 업스트림 버전을 따라가야 합니다.
- 후속 작업: CI에서 remark 주 버전을 고정하고 해당 릴리스 알림을 구독합니다.
```
