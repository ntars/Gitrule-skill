# 규범 선택 가이드

> 이 파일이 해결하는 문제：프로젝트 유형, 팀 규모, 릴리스 단계에 따라 규범의 조정 근거를 제시하고, 최소 사용 가능 조합과 완전한 컴플라이언스 조합을 제공하여 「필요에 따라 활용」에 명확한 판정 기준을 부여하고 개인 판단에 의존하지 않도록 합니다.

이 파일이 조정하는 대상은 규범 전체 세트입니다. README 섹션 수준의 유형 차이는 [README 분류 적응 가이드](./README-분류-적응-가이드.md)를, 단계의 전체 매핑은 [라이프사이클 매핑 표](./라이프사이클-매핑-표.md)를 참조합니다.

## 1. 선택 원칙

1. **강제 제약은 조정할 수 없다**: [하드 룰](./하드-룰.md)과 [금지 사항](./금지-사항.md)은 모든 프로젝트, 모든 단계에서 완전히 적용됩니다.
2. **단계 게이트가 하한을 결정한다**: 어떤 단계에 진입하기 전, 해당 단계가 [라이프사이클 매핑 표](./라이프사이클-매핑-표.md)에 표기한 종료 게이트를 반드시 통과해야 하며, 대응하는 핵심 규범을 생략할 수 없습니다.
3. **유형 차이는 깊이에만 영향을 준다**: 프로젝트 유형은 어떤 규범을 강조하고 어떤 세부를 단순화할지 결정하며, 품질 게이트를 건너뛰는 근거가 되지 않는다.
4. **강등은 반드시 명시적으로 선언한다**: 비공개 임시 스크립트 리포지터리는 P0 게이트만 실행할 수 있으나, 전달물에 「강등 모드」를 표기하고 미실행 항목을 나열해야 합니다.

## 2. 조정 차원

| 차원 | 값 | 주요 영향 |
| --- | --- | --- |
| 프로젝트 유형 | 라이브러리 / SDK, 애플리케이션, 명령줄 도구, 프레임워크, 리소스 모음 | 강화할 규범과 단순화할 수 있는 세부를 결정합니다 |
| 팀 규모 | 개인, 소규모 팀, 조직 | 거버넌스와 협업 규범의 필요성을 결정합니다 |
| 릴리스 단계 | 프로토타입 검증, 최초 공개, 안정 유지보수 | 컴플라이언스와 운영 규범의 도입 시기를 결정합니다 |

세 차원이 중첩될 때는 「강제 제약 → 단계 게이트 → 릴리스 단계 → 프로젝트 유형 → 팀 규모」의 우선순위로 값을 정합니다. 낮은 우선순위 차원의 조정이 높은 우선순위 차원의 요구를 약화해서는 안 됩니다.

### 6.3 완전한 컴플라이언스 조합

모든 규범을 적용하며, 조직 차원의 프로젝트, 규제 환경 배포를 목표로 하는 프로젝트, 또는 expert / Skill / MCP / 명령줄 프로그래밍 방식 접근이 필요한 프로젝트에 사용합니다. 건수는 [중국어 간체 색인](./README.md)을 기준으로 하며, 활성화 시 [라이프사이클 매핑 표](./라이프사이클-매핑-표.md)의 단계 게이트를 항목별로 검증해야 합니다.

## 7. 충돌 처리

1. 같은 차원 내에서 충돌이 발생하면 릴리스 단계가 더 늦은 쪽의 요구를 기준으로 합니다. 프로토타입 단계의 단순화를 공개 단계까지 연장해서는 안 됩니다.
2. 서로 다른 차원에서 충돌이 발생하면 2절의 우선순위에 따라 처리하며, 강제 제약과 단계 게이트는 어떤 차원으로도 덮어쓸 수 없습니다.
3. 프로젝트에 본 가이드를 벗어나야 하는 특수한 상황이 실제로 존재하면, 전달물에 벗어난 규범, 이유, 보상 조치를 기록하고 리뷰를 제출해야 합니다.
4. 강등 모드는 외부 공개 리포지터리에 사용할 수 없으며, 라이선스 또는 보안 게이트를 건너뛰는 근거로도 사용할 수 없습니다.
