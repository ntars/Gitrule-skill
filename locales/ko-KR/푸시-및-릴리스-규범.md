# 푸시 및 릴리스 규범

> 이 파일이 해결하는 문제：푸시 전/중/후의 조치 체크리스트, tag와 릴리스 규칙, 인시던트 처리 프로세스, 그리고 완전한 GitHub 푸시 가이드와 실패 처리 매트릭스를 정의합니다.

## 1. 푸시 전

1. `git status`가 깨끗하며, 추적되지 않은 민감 파일이 없습니다.
2. `git log`에 WIP가 없고, `fix bug`가 없으며, 개인정보 유출이 없습니다.
3. `.gitignore`가 유효함을 확인하고, 산출물과 의존성이 추적되지 않았는지 확인합니다.
4. 로컬에서 build, test, lint를 통과합니다.
5. 전체 비밀 키 스캔을 실행한다(과거 커밋 포함).
6. 문서 매트릭스가 구비되어 있다([문서 매트릭스](./문서-매트릭스.md) 참조).

## 2. 푸시 동작

7. 개인 브랜치를 푸시한다: `git push -u origin feat/xxx`.
8. 메인라인은 PR로만 진행하며, 직접 push하지 않는다.
9. `push --force`를 금지합니다. 자신의 브랜치를 재작성할 때는 `--force-with-lease`를 사용합니다.
10. 이미 푸시된 공용 브랜치에 rebase/amend를 하는 것을 금지합니다.
11. 단일 파일이 >50MB이면 먼저 LFS를 거쳐 푸시합니다.
12. 최초 푸시 전에 리포지터리 공개 범위를 확인한다: 기본은 private이며, 실제로 공개가 필요할 때 public으로 전환합니다.

## 3. tag와 릴리스

13. tag 형식은 `vMAJOR.MINOR.PATCH`이며, 반드시 annotated여야 한다: `git tag -a v1.0.0 -m "release: 1.0.0"`.
14. tag는 CI가 통과하고 Release Notes가 준비된 후에만 생성합니다.
15. 파괴적 변경은 반드시 `feat!:` 또는 `BREAKING CHANGE:`를 사용하고, CHANGELOG에 마이그레이션 방식을 제시합니다.

## 4. Phase 6 · 푸시 후 (Post-Push)

- annotated tag를 생성한다;
- Release Notes를 작성한다;
- 배지와 링크의 사용 가능 여부를 검증한다;
- CI 통과를 확인한다;
- About 영역 정보가 올바른지 확인한다(description / topics / 링크 / social preview).

## 5. 인시던트 처리

16. **비밀 키가 푸시됨**: 즉시 교체 → `git filter-repo`로 정리 → 보호 브랜치 강제 푸시는 관리자 절차를 거침 → 공지.
17. **대용량 파일 오푸시**: LFS 마이그레이션 또는 이력 재작성하며, 파일만 삭제해서는 안 됩니다.

## 6. GitHub 푸시 가이드 규범

가이드는 다음 일곱 부분을 포함해야 하며, 명령은 완전한 실행 가능 버전을 제시합니다.

### 6.1 사전 안전

1. 푸시 전에 로컬 리포지터리와 원격 리포지터리를 완전히 백업해야 하며, `git clone --mirror`로 미러 백업을 생성하는 것을 권장합니다.
2. 원격 리포지터리에 협업자가 없는지, 또는 협업자에게 푸시 중지를 통지했는지 확인합니다.
3. 대상 브랜치에 강제 푸시 보호가 활성화되지 않았는지 확인합니다.

### 6.2 로컬 정리

```bash
git status
git diff --name-status HEAD
git ls-files
```

세 가지 출력을 대조하여, 커밋할 변경이 로컬 디렉터리와 일치하는지, 임시 파일, 빌드 산출물, 구버전 문서 잔여물이 없는지 확인합니다. `.gitignore`는 빌드 산출물과 로컬 설정 파일을 포함해야 합니다.

### 6.3 일관성 확인

```bash
git fetch origin
git diff --name-status HEAD origin/{{分支名}}
```

이 명령은 원격과 로컬의 파일 차이를 나열합니다. 원격에는 존재하나 로컬에서 삭제된 파일은, 로컬에서 `git rm`을 실행한 후 커밋하여 삭제 동작이 버전 이력에 들어가도록 해야 합니다.

### 6.4 커밋과 푸시

```bash
git add -A
git commit -m "docs: 重建项目文档（README、README_EN、NOTICE）"
git push --force-with-lease origin {{分支名}}
```

`--force` 대신 `--force-with-lease`를 사용하여, 원격에 다른 사람의 새 커밋이 있으면 푸시를 거부하고 다른 사람의 작업을 덮어쓰지 않는다. 원격 리포지터리를 삭제한 후 재생성하는 것은 고위험 작업이며, 개인 리포지터리이고 미러 백업이 완료된 경우에만 사용하며, 가이드에 데이터 손실 위험을 명시적으로 표기해야 합니다.

### 6.5 푸시 후 검증

```bash
git ls-remote --heads origin
gh repo view --web
```

웹 페이지에서 파일 목록, README 렌더링, 언어 전환 링크, NOTICE 링크의 유효성을 항목별로 확인합니다.

### 6.6 실패 처리 매트릭스

| 오류 유형 | 전형적 증상 | 처리 방안 | 위험 안내 |
| --- | --- | --- | --- |
| 인증 실패 | `Authentication failed`, `Permission denied (publickey)` | HTTPS를 SSH로 전환하고 키를 구성하거나, `gh auth login` 후 푸시 | 없음 |
| 네트워크 중단 | `Failed to connect`, `RPC failed` | 네트워크 변경, 프록시 구성, `git config --global http.postBuffer 524288000` 실행 | 없음 |
| 파일 초과 | `remote: error: File exceeds 100 MB` | 커밋 이력에서 대용량 파일 제거 또는 Git LFS 활성화 | 이력 재작성 후 협업자에게 재클론 통지 필요 |
| 대소문자 충돌 | 파일명 대소문자 불일치로 중복 항목 발생 | `git mv`로 수정 후 커밋 | 없음 |
| 이력 충돌 | `non-fast-forward`, `fetch first` | 우선 `git pull --rebase`; 실제로 덮어써야 할 때는 `--force-with-lease` 사용 | 다른 사람의 커밋을 덮어쓰면 복구 불가 |
| 브랜치 보호 | `protected branch hook declined` | PR 프로세스로 병합하거나, 관리자가 일시적으로 규칙 조정 | 규칙 조정은 기록해야 함 |
| 리포지터리 손상 | `fatal: not a git repository`, 객체 누락 | 재클론 후 작업 영역 변경 사항 복사 | 작업 영역을 먼저 백업해야 함 |

### 6.7 롤백

푸시 완료 후 문제를 발견하면 `git revert`로 역방향 커밋을 생성합니다. 이미 공개된 이력을 다시 강제 푸시로 덮어써서는 안 됩니다.
