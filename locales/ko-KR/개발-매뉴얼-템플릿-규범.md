# 개발 매뉴얼 템플릿 규범

> 이 파일이 해결하는 문제：「클라우드 작성, 로컬 실행」 2단계 개발 매뉴얼의 뼈대, 작업 카드 형식, 인계 프로토콜과 검수 게이트를 정의하여, 하나의 아이디어를 클라우드 모델이 모호함 없는 작업 카드로 전사하고 로컬 코딩 모델이 부분별로 릴레이 방식으로 실행할 수 있게 합니다.

## 1. 포지셔닝과 사용 절차

1. 본 규범은 「하나의 클라우드 추론 모델 + 하나의 로컬 코딩 모델」의 분업 시나리오를 대상으로 합니다. 클라우드는 모호한 아이디어를 명확한 방안으로 전사하는 일을, 로컬은 방안에 따라 결정적으로 실행하는 일을 담당합니다.
2. 사용 절차는 4단계로 고정되며 순서를 건너뛸 수 없습니다:
   - 사전 점검: 아이디어에 잘못된 전제, 논리적 비약, 정보 누락이 있는지 점검합니다. 정보가 부족하면 먼저 사용자에게 질문하며, 추측으로 채우는 것은 금지합니다.
   - 클라우드 작성: 제9절 규범에 따라 오픈소스 방안을 조사하고 매뉴얼을 작성합니다.
   - 사용자 검토: 검수 명령, 채택 기록, 금지 구역을 중점 검토합니다.
   - 로컬 실행: 기계 판독 인덱스에 따라 해당 챕터와 인계 기록을 주입하고, 부분별로 실행합니다.
3. 매뉴얼 본문에는 「등」「관련」「적절」「가급적」「필요시」와 같은 모호한 단어를 쓰는 것이 금지되며, 모든 곳에서 정확한 값을 제시하거나 의사결정 규칙을 제시해야 합니다.

## 2. 매뉴얼 뼈대

모든 개발 매뉴얼은 다음 부분을 순서 그대로 포함합니다:

| 부분 | 책임 |
| --- | --- |
| 기계 판독 인덱스 | 챕터 경로, 대응 코드 디렉터리, 검수 명령, 단계 표식의 내비게이션 표 |
| 채택 기록 | 오픈소스 공급망 기록 표, 프로젝트 전체의 단일 진실원(제11절 참조) |
| 프로젝트 헌법 | 프로젝트 전체의 불변식, 모든 부분에 주입 |
| 용어집 | 용어와 쉬운 설명, 대응 코드의 대조 |
| 모듈 챕터 | 모듈별 한 챕터, 제4절 구조에 따라 작성 |
| 릴리스 챕터 | 빌드와 배포 규범, 배포 동작은 사용자 확인 필요 |
| 홈페이지 카피 챕터 | 일반 사용자 대상 카피 규범, 로컬 모델에 주입하지 않음 |
| 변경 기록 | 날짜, 챕터, 변경 사항과 의사결정자 |

## 3. 프로젝트 헌법

프로젝트 헌법은 로컬 실행 부분마다 주입하는 불변식이며, 다음 5개 항목을 고정 포함합니다:

1. 기술 스택과 버전: 버전 번호까지 정확하게 기재합니다.
2. 디렉터리 구조 약속: 트리 다이어그램과 디렉터리별 한 문장 책임.
3. 코딩 규범: 프로젝트 유형에 따라 조정하며, 기준은 모듈화 온디맨드 로딩, 최소하고 가장 직접적인 코드, 요구되지 않은 기능 추가 금지, 주석 완비와 전문 개념을 쉬운 언어로 주석 처리하는 것입니다. UI 프로젝트는 Apple HIG를 따르며, 글꼴 단위는 px 또는 rem만 사용하고 rpx 사용은 금지합니다.
4. 전역 금지 구역: 절대 해서는 안 되는 일, 예컨대 채택 기록에 없는 의존성 도입 금지, 계약 파일 수정 금지.
5. 출력 언어 규범: 설명, 로그, 진행 상황, 오류 메시지는 중국어 간체를 사용하며, 코드, 명령, 파일 경로, 고유명사는 원문을 유지할 수 있습니다.

## 4. 모듈 챕터 구조

각 모듈 챕터는 9개 절을 고정 포함하며 순서는 바뀌지 않습니다:

| 절 | 책임 |
| --- | --- |
| 모듈 책임 | 1-3문장, 무엇을 하고 무엇을 하지 않는지 명확히 기술 |
| 의존하는 오픈소스 방안 | 이름, 용도, 채택 기록 번호 |
| 파일 목록 | 경로, 동작(신규/수정/읽기 전용), 책임. 총수 10개 이하, 초과 시 챕터 분할 |
| 인터페이스 계약 | 시그니처, 라우팅, 프로토콜 필드는 타입까지 정확하게, 완전한 입출력 예시 첨부 |
| 데이터와 상태 | 무엇을 어디에 어떤 형식으로 저장하는지. 전문 개념은 쉬운 언어로 주석 |
| 의존 관계 | 먼저 읽어야 할 파일, 호출할 파일, 절대 수정 금지 파일의 3개 목록 |
| 작업 카드 | 본 모듈을 나눈 부분, 카드별 독립 실행 |
| 본 챕터 금지 구역 | 본 모듈에서 특별히 해서는 안 되는 일 |
| 설계 비고 | 선정 이유, 포기한 방안, 사실과 추측의 구분. 로컬 모델에 주입하지 않음 |

## 5. 작업 카드 형식

한 장의 작업 카드는 로컬 세션 한 번이자 검수 명령 한 줄과 같으며, 필드는 다음과 같이 고정됩니다:

| 필드 | 요구 |
| --- | --- |
| 목표 | 한 문장, 기계 검증 가능 |
| 선행 조건 | 의존하는 이전 부분과 파일이 모두 존재 |
| 단계 | 번호를 매겨 나열, 단계별로 하나의 결정적 동작, 한 번에 완료하며 중단·추가 질문 없음 |
| 검수 명령 | 바로 복사해 실행 가능. 검수 체계가 아직 없으면 첫 카드가 먼저 검수 명령을 구축해야 함 |
| 기대 결과 | 정확한 출력, 종료 코드 또는 어서션 수 |
| 실패 처리 | 대표적인 오류별로 처리 방안을 항목별 제시. 연속 3회 실패 시 반드시 중단하고 인계 기록에 기재 |
| 인계 요구 | 인계 기록에 기재해야 할 필드 선언 |

하드 제약:

1. 한 장의 카드가 다루는 파일이 10개를 초과하면 카드를 분할하고, 한 챕터의 카드가 6장을 초과하면 챕터를 분할합니다.
2. 납품 자가 점검이 포함된 카드는 중복 코드 정리와 README, NOTICE, LICENSE 동기화 지점을 명시적으로 나열해야 합니다.
3. 파일 삭제 또는 덮어쓰기와 관련된 동작은 반드시 멈추고 인계 기록의 block 필드에 기재한 뒤 사용자 확인을 기다립니다.
4. 모호하여 검수 명령을 작성할 수 없는 작업은 카드를 작성해서는 안 되며, 별도로 「사용자 의사결정 필요」로 표기합니다.

## 6. PROGRESS 인계 프로토콜

인계 기록 파일 PROGRESS.md는 부분과 부분 사이의 유일한 진실원이며, 형식은 고정입니다:

| 필드 | 요구 |
| --- | --- |
| done | 본 카드의 목표 달성 여부 |
| files | 실제로 변경한 파일 목록 |
| decisions | 과정에서의 의사결정, 형식은 「A를 선택했는데 B 때문이다」 |
| next | 다음 카드 번호와 진입점, 파일 경로와 진입 함수까지 기재해야 하며 「계속 다듬기」처럼 쓰는 것은 금지 |
| block | 미해결 문제, 없으면 비워둠 |

1. 모든 카드 마무리 시 반드시 한 항목을 추가하며, 형식 변경은 금지입니다.
2. 로컬 실행 시 최신 항목 하나만 주입하며, 이력 항목은 주입하지 않습니다.
3. 중단 지점 복구: 「계속」 지시를 받으면 먼저 최신 항목을 읽어 중단 지점을 확인하고, next가 가리키는 진입점에서 이어서 진행합니다. 기억이나 추측으로 이미 완료한 단계를 다시 하는 것은 금지입니다.

## 7. 로컬 주입 예산

harness는 다음 표에 따라 각 부분의 컨텍스트를 조립하며, 총 예산은 24K(32K 작업 창의 75%)를 초과하지 않습니다:

| 주입 항목 | 예산 |
| --- | --- |
| 프로젝트 헌법 | 2-3K |
| 현재 작업 카드가 속한 챕터 | 2-5K |
| 인계 기록 최신 항목 | 약 0.5K |
| 인계 프롬프트 뼈대 | 약 0.3K |
| 코드와 도구 출력 | 남은 한도 |

주입하지 않는 항목: 채택 기록 전체 표(본 카드와 관련된 항목만 주입), 설계 비고, 홈페이지 카피 챕터.

## 8. 인계 프롬프트 철칙

각 부분 착수 시 고정된 오프닝을 주입하며, 철칙은 다음 6개로 고정됩니다:

1. 전 과정에서 중국어 간체로 출력하며, 코드, 명령, 경로, 고유명사는 원문을 유지할 수 있습니다.
2. 작업 카드 안의 일만 수행하며, 요구되지 않은 기능, 설정, 확장 능력을 추가하지 않습니다.
3. 지어내거나 꾸며내지 않습니다. 확실하지 않은 API 시그니처는 확실하지 않다고 직접 밝히며, 사실과 추측을 명시적으로 구분합니다.
4. 검수 명령이 실패하면 작업 카드의 실패 처리에 따라 수행하며, 검수 기준을 임의로 바꾸는 것은 금지입니다.
5. 파일 삭제, 덮어쓰기와 관련된 동작은 반드시 멈추고 사용자 확인을 기다립니다.
6. 완료 후 인계 요구에 따라 엄격히 인계 기록을 작성한 뒤 종료합니다.

## 9. 클라우드 작성 규범

클라우드 모델은 매뉴얼 작성 전에 두 가지 사전 작업을 완료한 뒤 챕터별로 작성합니다:

1. 전제 점검: 잘못된 전제, 논리적 비약, 정보 누락을 점검하며, 부족하면 먼저 사용자에게 질문합니다.
2. 오픈소스 방안 조사: 오픈소스 생태계에서 사용할 수 있는 기성 방안을 검색합니다. 먼저 조사한 뒤 작성하며, 성숙한 방안이 있으면 바퀴를 다시 만들지 않고, 결과는 채택 기록에 등록합니다.

작성 시 준수 사항:

1. 모든 모호한 단어를 없애고, 모든 곳에서 정확한 값 또는 의사결정 규칙을 제시합니다.
2. 설계 의사결정은 설계 비고에 기재하며, 선정 이유와 포기한 방안을 포함해 사용자 검토에 제출하고, 로컬 모델에는 주입하지 않습니다.
3. 로컬 모델에 주는 지시는 「프로젝트 배경을 모른다」는 전제로 작성하며, 모든 전제를 명시적으로 기술합니다.
4. 컴플라이언스 하한선: 라이선스가 불명확하면 「확인 필요」로 표기하고, 강한 copyleft 방안에는 파생 의무 안내를 표기하며, 수정한 오픈소스 코드는 원저작권과 수정 설명을 유지하고, 채택 항목은 반드시 README, README_EN, NOTICE, LICENSE를 동기화하며, 동기화 동작은 해당 작업 카드의 명시적 단계이자 검수 내용이 됩니다.
5. 문서 형식 규범은 본 리포지터리의 해당 규범을 참조하며, 매뉴얼에 규범 본문을 복사하지 않습니다.

## 10. 단계 상태와 작업 창

기계 판독 인덱스의 각 챕터는 단계 표식을 달고 있으며, 이에 따라 로컬 작업 창을 조정합니다:

| 단계 | 특징 | 작업 창 |
| --- | --- | --- |
| 그린필드 | 동결된 계약에 따라 구현을 작성 | 16-24K |
| 성장 | 모듈 간 기능, 기본 등급 | 32K |
| 유지보수 | 리팩터링과 모듈 간 문제 추적 | 48-64K, 병렬 처리는 그에 따라 감소 |

유지보수기 챕터에는 문제 추적 가이드를 추가로 첨부해야 합니다: 증상, 가능 위치, 검증 명령의 3개 열.

## 11. 채택 기록, 릴리스와 홈페이지 카피

1. 채택 기록 표의 필드는 다음으로 고정됩니다: 이름, 분류, 버전, 용도, 라이선스, 저작권자, 공식 주소, 수정 여부, 수정 설명, 고지 방식, 채택 상태. 채택 상태는 「즉시 채택 가능, 평가 필요, 현재 사용 불가」의 3개 등급으로 나뉩니다.
2. 릴리스 챕터는 빌드 스크립트, CI 매트릭스, checksum, 서명 환경 변수 템플릿을 다룹니다. 릴리스 카드의 검수 명령은 빌드 산출물 점검이며, 대외 배포 동작은 로컬 모델에 넣지 않고 사용자 확인 후 실행합니다.
3. 홈페이지 카피 챕터는 일반 사용자를 대상으로 합니다: 코드, 명령줄, 기술 용어, 빈 단어의 등장은 금지이며, 구조는 첫 화면 포지셔닝, 페인 포인트, 하이라이트, 신뢰, 다운로드, 시나리오 스토리, 자주 묻는 질문이고, 어조는 담담하고 절제되어야 합니다.

## 12. 크로스 프로젝트 참조와 검증

1. 대상 프로젝트가 본 규범을 참조할 때는 `gitrule spec`으로 전문을 읽고, 매뉴얼 뼈대를 프로젝트 내 매뉴얼의 초기 뼈대로 복사합니다. 본 규범은 프로젝트와 함께 개정하지 않으며, 프로젝트 내 매뉴얼의 진화는 프로젝트 리포지터리 안에서 폐쇄 루프를 이룹니다.
2. 문서 산출이 포함된 작업 카드는 검수 명령에 `gitrule check`를 추가하고, 다국어 프로젝트는 `gitrule xcheck`를 추가하며, 용어집 변경 후에는 `gitrule termcheck`를 실행합니다.
3. `gitrule check`의 문서 위반은 자동 수정 가능 유형에 속하며, 먼저 `gitrule optimize`를 실행한 뒤 재검사하고, 그래도 통과하지 못하면 인계 기록의 block 필드에 기재합니다.
4. Gitrule 규범은 문서와 리포지터리 규범만을 관할하며, 코드 품질은 각 프로젝트의 테스트와 검증 스크립트에 속하고, 양자는 서로를 대체하지 않습니다.
