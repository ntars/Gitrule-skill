# 의존성 관리 규범

> 이 파일이 해결하는 문제：의존성 도입 신청, 의존성 목록, 잠금과 업데이트의 템플릿과 필드를 정의하여 빌드 재현성, 의존성 추적 가능성, 라이선스 컴플라이언스를 보장합니다.

## 1. 규범 조문

1. 새로운 의존성을 도입할 때는 용도, 라이선스, 유지보수 상태를 설명해야 합니다([오픈소스 컴플라이언스 규범](./오픈소스-컴플라이언스-규범.md) 참조).
2. 라이선스가 호환되고 커뮤니티가 활발한 의존성을 우선 선택합니다. 출처가 불분명하거나 라이선스가 불분명한 의존성의 도입은 금지합니다.
3. 의존성 버전은 반드시 lockfile에 기록하고 리포지터리에 커밋하여, 깨끗한 환경에서 빌드를 재현할 수 있도록 보장해야 합니다(하드 룰 H9와 차원 D5에 해당).
4. 버전 번호는 실제로 해석된 버전을 잠가야 하며, 범위 표현식을 최종 납품물로 사용하지 않습니다.
5. 의존성 업데이트는 자동화 도구의 지원을 받아야 하며, 업데이트 후에는 반드시 CI를 통과해야 합니다. 취약점은 적시에 처리하거나 완화 조치를 기록해야 합니다.
6. 의존성 목록은 NOTICE와 일치해야 합니다([NOTICE 규범](./NOTICE-규범.md) 참조).

## 2. 의존성 도입 신청 템플릿

```markdown
## 의존성 도입 신청: {{包名}}

- 신청 번호: {{DEP-NNN}}
- 신청자: {{姓名}}
- 용도: {{一句话说明解决什么问题}}
- 자체 구현 가능 여부: {{是 / 否；是则说明为何仍引入}}
- 대안 평가: {{已评估的替代包及未选原因}}

| 필드 | 값 |
| --- | --- |
| 패키지명 | {{包名}} |
| 도입 버전 | {{精确版本号}} |
| 라이선스 | {{SPDX ID}} |
| 라이선스 호환성 | {{兼容 / 不兼容 / 需法务确认}} |
| 최근 배포일 | {{YYYY-MM-DD}} |
| 유지보수 상태 | {{活跃 / 低频 / 停滞}} |
| 주간 다운로드 수 | {{数值}} |
| 전이 의존성 수 | {{数值}} |
| 알려진 취약점 | {{无 / CVE 编号与处置}} |
| 번들 크기 영향 | {{增量 KB}} |

- 결론: {{批准 / 拒绝 / 有条件批准}}
- 승인자: {{姓名}}
```

```markdown

| --- | --- | --- | --- | --- | --- | --- |
| {{包名}} | {{^1.2.0}} | {{1.2.3}} | 직접 / 간접 | {{MIT}} | {{用途}} | {{YYYY-MM-DD}} |

## 업데이트 기록
| 날짜 | 의존성 | 버전 변화 | 사유 | 검증 결과 |
| --- | --- | --- | --- | --- |
```

## 4. 필드 정의

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 신청 번호 | 예 | `DEP-NNN` | 연속되며 재사용하지 않음 | `DEP-007` |
| 용도 | 예 | 텍스트 | 해결하는 문제를 설명하며 「개발 편의」 금지 | `TOML 구성 파싱` |
| 대안 평가 | 예 | 텍스트 | 최소 1개의 대안을 평가 | `toml-js를 평가했으나 유지보수 정체로 미선택` |
| 도입 버전 | 예 | 정확한 버전 | `^` 또는 `~` 사용 불가 | `1.2.3` |
| 잠금 버전 | 예 | 정확한 버전 | lockfile과 일치 | `1.2.3` |
| 라이선스 | 예 | SPDX ID | [LICENSE 규범](./LICENSE-규범.md)의 표기와 일치 | `MIT` |
| 유지보수 상태 | 예 | 열거 | 활발 / 저빈도 / 정체, 판정 근거 첨부 | `활발(최근 30일 내 커밋 있음)` |
| 전이 의존성 수 | 예 | 수치 | 과다할 경우 크기와 위험 영향을 설명 | `12` |
| 알려진 취약점 | 예 | 텍스트 | 없으면 「없음」이라 쓰며 비워 두지 않음 | `없음` |
| 재검토 날짜 | 예 | 날짜 | 예외 항목은 재검토 날짜를 설정 | `2026-12-31` |

## 5. 작성 설명

1. **자체 구현 평가**: 먼저 「표준 라이브러리나 기존 역량으로 구현할 수 있는가」에 답합니다. 자체 구현이 가능한데도 도입하는 경우에는 이유를 설명해야 합니다.
2. **라이선스**: SPDX ID여야 합니다. `UNLICENSED`, 사용자 정의 라이선스는 「법무 확인 필요」로 전환해야 하며 직접 도입할 수 없습니다.
3. **유지보수 상태**: 최근 배포일과 issue 응답을 근거로 하며, 「누군가 유지보수하는 것처럼 보인다」는 금지합니다.
4. **버전 잠금**: 납품 시 lockfile에는 정확히 해석된 버전이 있어야 합니다. `package.json`은 범위 표현식을 유지할 수 있으나 lockfile은 반드시 정확해야 합니다.
5. **업데이트 주기**: 자동화 업데이트를 활성화하고, 사람이 확인하여 병합합니다. 매 업데이트는 CI를 통과해야 하며 라이선스 변화를 확인해야 합니다.
6. **취약점 처리**: 안전한 버전으로 업그레이드하는 것을 우선합니다. 업그레이드할 수 없을 때는 완화 조치와 재검토 날짜를 작성하고 [인시던트 대응 규범](./인시던트-대응-규범.md)의 위험 등록에 포함합니다.
7. **목록 동기화**: 의존성을 도입하거나 제거한 후에는 의존성 목록과 NOTICE를 동시에 업데이트하며, 세 가지(lockfile, 목록, NOTICE)가 일치해야 합니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| 「라이브러리 하나로 구성 처리」 | 구체적 패키지명과 용도 없음 | 패키지명, 버전, 해결 문제 작성 |
| 라이선스를 「오픈소스」로 작성 | 호환성을 판정할 수 없음 | SPDX ID 작성 |
| lockfile 미커밋 | 빌드 재현 불가 | lockfile 커밋(H9에 해당) |
| 전이 의존성 수를 비워 둠 | 위험을 볼 수 없음 | 구체적 수치 기입 |
| 취약점에 완화 조치 미작성 | 위험 추적 불가 | 조치와 재검토 날짜 보완 |

## 6. 완전한 예시

```markdown
## 의존성 도입 신청: remark

- 신청 번호: DEP-001
- 신청자: 王五
- 용도: Markdown 파싱 계층으로서 규칙 엔진의 노드 위치 파악 요구사항을 지원합니다(REQ-001, REQ-004).
- 자체 구현 가능 여부: 아니오. 자체 구현으로는 인력 한도 내에서 GFM 경계 케이스를 포괄할 수 없습니다.
- 대안 평가: marked를 평가했으나 중국어 노드 위치 파악 역량이 부족하여 미선택했습니다.

| 필드 | 값 |
| --- | --- |
| 패키지명 | remark |
| 도입 버전 | 15.0.1 |
| 라이선스 | MIT |
| 라이선스 호환성 | 호환 |
| 최근 배포일 | 2026-11-02 |
| 유지보수 상태 | 활발(최근 30일 내 커밋 있음) |
| 주간 다운로드 수 | 4,200,000 |
| 전이 의존성 수 | 18 |
| 알려진 취약점 | 없음 |
| 번들 크기 영향 | +42 KB |

- 결론: 승인, ADR-0002와 함께 시행
- 승인자: 李四
```
