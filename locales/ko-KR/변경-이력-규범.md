# 변경 이력 규범

> 이 파일이 해결하는 문제：사용자 대상 버전 변경 기록 템플릿, 필드, 작성법을 정의하여 매 변경이 추적 가능하고, 버전이 대응되며, 업그레이드 경로를 판단할 수 있도록 보장합니다.

## 1. 규범 조항

1. 변경 이력은 Keep a Changelog 구조를 따르고, 버전 번호는 [버전 관리 규범](./버전-관리-규범.md)의 시맨틱 버저닝을 따른다.
2. 각 버전에는 릴리스 날짜가 있어야 하며, 형식은 `YYYY-MM-DD`입니다. 미릴리스 내용은 `Unreleased` 섹션에 둔다.
3. 항목은 여섯 가지로 그룹화한다: `Added` 추가 / `Changed` 변경 / `Deprecated` 폐기 / `Removed` 제거 / `Fixed` 수정 / `Security` 보안.
4. 각 변경은 사용자를 향해야 하며, 영향과 마이그레이션 방식을 설명해야 하고, 내부 리팩터링 세부는 쓰지 않는다.
5. 파괴적 변경은 `BREAKING CHANGE:`를 표기하고 마이그레이션 단계를 제시해야 한다([마이그레이션 가이드 규범](./마이그레이션-가이드-규범.md) 참조).
6. 버전 번호는 tag, Release Notes와 일치해야 하며, 파괴적 변경은 커밋 메시지의 `feat!:` 또는 `BREAKING CHANGE:`와 대응해야 합니다.

## 2. 변경 이력 템플릿

```markdown
# 변경 이력

이 파일은 모든 사용자 대상 변경을 기록합니다. 형식은 Keep a Changelog를 따르고, 버전은 시맨틱 버저닝을 따른다.

## [Unreleased]

### Added
- {{추가된 기능, 사용자에게 주는 가치 설명}}

### Changed
- {{동작 변경, 영향 범위 설명}}

### Deprecated
- {{곧 제거될 기능, 대안과 제거 버전 설명}}

### Removed
- {{제거된 기능, 마이그레이션 경로 설명}}

### Fixed
- {{결함 수정, 발생 조건 설명}}

### Security
- {{보안 수정, 영향과 업그레이드 권장 사항 설명}}

## [{{X.Y.Z}}] - {{YYYY-MM-DD}}

### {{유형}}
- {{변경 항목}}
- {{BREAKING CHANGE: 기존 동작 → 새 동작; 마이그레이션 단계는 링크 참조}}

[Unreleased]: https://github.com/{{owner}}/{{repo}}/compare/v{{X.Y.Z}}...HEAD
[{{X.Y.Z}}]: https://github.com/{{owner}}/{{repo}}/compare/v{{prev}}...v{{X.Y.Z}}
```

## 3. 항목 템플릿

```markdown
- {{동사로 시작하는 한 문장 변경 설명}}（{{관련 REQ 번호}}）
  - 영향：{{어떤 사용자 또는 시나리오가 영향받는지}}
  - 마이그레이션：{{수행해야 할 작업; 없으면 이 줄 생략}}
  - 참고：{{Issue / PR 링크}}
```

## 4. 필드 정의

| 필드 | 필수 | 유형 | 작성 요점 | 예시 |
| --- | --- | --- | --- | --- |
| 버전 번호 | 예 | `X.Y.Z` | tag와 완전히 일치, 접두사 `v`가 없어도 되나 전문에서 통일 | `1.2.0` |
| 릴리스 날짜 | 예 | `YYYY-MM-DD` | tag 생성 날짜를 기준으로 함 | `2026-11-18` |
| 그룹 유형 | 예 | 열거형 | 여섯 가지 중 하나; 해당 그룹 항목이 없으면 섹션 전체 생략 | `Fixed` |
| 변경 설명 | 예 | 텍스트 | 동사로 시작, 사용자 대상, 가치 설명 | `GFM 표 검사 추가` |
| 영향 | 조건부 필수 | 텍스트 | 동작 변경, 폐기, 제거, 파괴적 변경 시 필수 | `기존 설정 파일 이름 변경 필요` |
| 마이그레이션 | 조건부 필수 | 텍스트 | 파괴적 변경 시 필수, 마이그레이션 가이드를 가리킴 | `마이그레이션 가이드 v1.0 참조` |
| BREAKING CHANGE | 조건부 필수 | 표기 | 파괴적 변경 시 필수, 항목 서두에 배치 | `BREAKING CHANGE:` |
| 비교 링크 | 예 | URL | 각 버전 섹션마다 compare 링크를 제공해야 함 | `compare/v1.1.0...v1.2.0` |
| 관련 REQ | 아니오 | 목록 | 요구사항 추적 매트릭스와 대조하기 쉽도록 함 | `REQ-007` |

## 5. 작성 설명

1. **항목 세분성**: 하나의 변경은 사용자가 인지할 수 있는 하나의 결과를 설명합니다. 여러 결과는 여러 항목으로 나눈다.
2. **동사로 시작**: 「추가」「지원」「수정」「제거」「폐기」「조정」을 사용하고, 「업데이트했다」「몇 가지 작업을 했다」는 사용하지 않는다.
3. **금지 내용**: 날짜 없는 항목, 내부 리팩터링, 개발 계획, 로드맵 내용, 모호한 표현(「경험 최적화」「여러 문제 수정」).
4. **파괴적 변경**: `BREAKING CHANGE:` 표기, 영향 설명, 마이그레이션 단계, 마이그레이션 가이드 링크 네 가지를 모두 갖추어야 하며 하나도 빠져서는 안 됩니다.
5. **폐기 항목**: 대안과 제거 예정 버전 번호를 명시해야 합니다. 예: 「v2.0에서 제거 예정」.
6. **Unreleased**: 병합 후 즉시 등록하고, 릴리스 당일까지 쌓아 두었다가 보충하지 않는다.
7. **일관성**: 버전 번호와 릴리스 날짜는 tag, Release Notes, 배포 기록 세 곳과 일치해야 합니다. 불일치 시 tag를 기준으로 나머지 세 곳을 수정합니다.

흔한 오류:

| 잘못된 작성 | 문제 | 수정 방식 |
| --- | --- | --- |
| 「내부 모듈 구조 리팩터링」 | 내부 세부에 해당하여 사용자가 인지할 수 없음 | 삭제하거나 인지 가능한 효과로 다시 작성 |
| 「여러 문제 수정」 | 판정 불가 | 수정 내용을 항목별로 나열 |
| 파괴적 변경에 「변경 있음」만 기술 | 마이그레이션 경로 없음 | 영향, 마이그레이션 단계, 가이드 링크 보충 |
| 버전 번호가 tag와 불일치 | 버전 대응 관계 단절 | tag를 기준으로 통일 |
| compare 링크 없음 | 차이를 볼 수 없음 | GitHub compare URL 보충 |

## 6. 완전한 예시

```markdown
## [1.0.0] - 2026-11-20

### Added
- 중영문 혼용 공백 검사 규칙 추가（REQ-001）, 명령줄에서 직접 호출 지원.
- JSON 보고서 출력 추가, CI 통계 연동 용이.

### Changed
- BREAKING CHANGE: 설정 파일 이름이 `.mdlint.json`에서 `.mdlintrc.json`으로 변경. 기존 파일은 더 이상 읽히지 않음; 마이그레이션 단계는 [마이그레이션 가이드](./마이그레이션-가이드-규범.md) 참조.

### Deprecated
- `--format=table` 파라미터는 v2.0에서 제거 예정이므로 `--reporter=table`로 전환할 것.

### Fixed
- 중국어 문장부호가 영단어에 바로 인접할 때 오탐하는 문제 수정.

### Security
- 규칙 플러그인 로드 경로가 외부 입력으로 덮어쓰일 수 있는 문제 수정; 모든 사용자의 v1.0.0 업그레이드를 권장.

[1.0.0]: https://github.com/example/markdown-lint-cli/compare/v0.9.3...v1.0.0
```
