# CI 워크플로 규범

> 이 파일이 해결하는 문제：`.github/workflows/*.yml` 지속적 통합 워크플로의 트리거 조건, 작업 분할, 캐시 전략과 보안 구성을 정의하여 빌드, 테스트, 검사가 재현 가능하고 감사 가능하도록 만듭니다.

## 1. 설계 원칙

1. **단일 책임**: 각 워크플로는 한 가지 목표(빌드, 테스트, 릴리스, 문서 배포)만 담당하며, 릴리스와 테스트를 하나의 워크플로에 섞어서는 안 됩니다.
2. **빠른 피드백**: 가벼운 검사(lint, 포맷)를 앞에, 시간이 오래 걸리는 작업(전체 테스트 매트릭스)을 뒤에 둡니다.
3. **재현 가능**: 의존성 버전을 잠그고, 고정 버전의 Actions를 사용하며, 캐시는 가속에만 쓰고 결과를 바꾸지 않습니다.
4. **최소 권한**: 워크플로는 작업별로 권한을 부여하며 기본은 읽기 전용이고, 릴리스 작업만 별도로 권한을 높입니다([보안 및 개인정보 규범](./보안-및-개인정보-규범.md) 참조).

## 2. 파일 구조

### 2.1 명명과 경로

- 경로는 `.github/workflows/*.yml`로 고정합니다.
- 파일명은 소문자와 하이픈을 사용하며 책임에 따라 명명합니다. 예: `ci.yml`, `release.yml`, `docs.yml`.
- 워크플로 `name` 필드는 파일명 의미와 일치해야 합니다.

### 2.2 필수 블록

| 블록 | 역할 | 요구사항 |
| --- | --- | --- |
| `name` | 워크플로 표시 이름 | 간결하며 책임을 읽어낼 수 있어야 함 |
| `on` | 트리거 조건 | 브랜치, 경로 또는 이벤트를 명확히 |
| `permissions` | 권한 선언 | 명시적으로 선언하며 기본은 최소 |
| `jobs` | 작업 집합 | 책임별로 분할 |

### 2.3 트리거 조건 설계

| 트리거 이벤트 | 적용 | 주의 |
| --- | --- | --- |
| `push` | 메인라인과 릴리스 브랜치 | 브랜치 범위를 제한하여 전체 브랜치 트리거를 피함 |
| `pull_request` | 모든 PR | 병합 전 검사를 보장 |
| `workflow_dispatch` | 수동 트리거 | 릴리스, 롤백 등 통제된 작업에 사용 |
| `schedule` | 정기 작업 | 의존성 업데이트 점검, 야간 빌드에 사용 |
| `release` | 릴리스 후 동작 | 산출물 업로드와 공지에 사용 |

## 3. 작업 분할

권장 단계 순서:

1. **정적 분석**: 포맷, lint, 타입 검사.
2. **빌드**: 빌드 산출물을 생성하여 후속 작업이 재사용하도록 함.
3. **테스트**: 단위 테스트, 통합 테스트를 매트릭스로 병렬 실행 가능.
4. **산출물 검증**: 빌드 산출물의 크기, 서명 또는 무결성 검사.
5. **릴리스**: CI가 모두 통과하고 조건이 충족될 때만 실행([푸시 및 릴리스 규범](./푸시-및-릴리스-규범.md) 참조).

작업 간 의존성은 `needs`로 선언하여 실패 시 즉시 중단되도록 보장하며, 후속 작업이 실패 상태에서 계속 진행되어서는 안 됩니다.

## 4. 매트릭스 빌드

`strategy.matrix`를 사용하여 다중 버전, 다중 플랫폼을 포괄합니다:

```yaml
strategy:
  fail-fast: false
  matrix:
    os: [ubuntu-latest, macos-latest, windows-latest]
    node-version: [18, 20, 22]
```

요구사항:

- 버전은 프로젝트가 지원한다고 선언한 최저 및 최신 버전을 포괄합니다([호환성 설명](./README-섹션-규범.md) 제14장 참조).
- `fail-fast`를 `false`로 설정하여 각 조합이 완전히 실행되도록 하여 호환성 문제를 파악하기 쉽게 합니다.
- 매트릭스 차원은 세 개를 넘지 않도록 하여 조합 폭발을 피합니다.

## 5. 캐시 전략

| 캐시 대상 | 키 값 제안 | 주의 |
| --- | --- | --- |
| 의존성 디렉터리 | 패키지 관리자 잠금 파일 해시 | 잠금 파일이 변경되면 무효화 |
| 빌드 산출물 | 소스 코드와 구성 해시 | 빌드 입력과 일치 |
| 툴체인 | 버전 번호 | 버전 업그레이드 시 무효화 |

캐시는 가속만 할 뿐 빌드 결과를 바꾸지 않습니다. 캐시가 적중하더라도 전체 테스트는 여전히 실행해야 합니다.

## 6. 보안 구성

1. 키는 리포지터리 Secrets를 통해 주입하며, 워크플로 파일이나 로그에 기록하는 것은 금지합니다.
2. 각 워크플로는 `permissions`를 명시적으로 선언하며 기본은 `contents: read`입니다.
3. 서드파티 Action은 고정 버전 또는 커밋 해시를 참조하여 부동 태그를 피합니다.
4. PR이 Fork에서 온 경우 Secrets 주입을 금지하여 권한 상승 공격을 방지합니다.
5. 릴리스 작업은 주 검사와 분리하며, 보호된 브랜치 또는 tag에서만 트리거합니다.

## 7. 상태 배지

워크플로는 README에 상태 배지를 제공해야 하며, 형식은 다음과 같습니다:

```markdown
[![CI](https://github.com/{owner}/{repo}/actions/workflows/ci.yml/badge.svg)](https://github.com/{owner}/{repo}/actions/workflows/ci.yml)
```

배지 파라미터와 배열은 [배지 규범](./배지-규범.md)을 참조합니다.

## 8. 금지 사항

1. 워크플로에 키나 내부 주소를 하드코딩하는 것은 금지합니다.
2. `continue-on-error`를 사용하여 테스트 실패를 감추는 것은 금지합니다.
3. 동일한 조건에 서로 충돌하는 여러 트리거 규칙을 구성하는 것은 금지합니다.
4. 메인라인 검사가 통과하지 않은 상태에서 릴리스를 실행하는 것은 금지합니다.
