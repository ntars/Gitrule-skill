# README视觉排版规范

> 本文件解决什么问题：定义 README 的排版层次、段落组织、表格、截图与 GIF 的使用场景及放置位置，使文档在信息密度与视觉吸引力之间取得平衡。

本文「实测」数据来自本项目对头部开源项目 README 的抽样统计（样本 N=120）；标杆做法取自多个高星项目的首屏结构取证。

## 1. 排版层次

### 1.1 标题层级

README 须建立清晰的标题层级，遵循以下约束：

1. 全文仅保留一个一级标题（`#`），即项目名称，位于文件首行。
2. 二级标题（`##`）为主要章节，数量以 6–12 个为宜；实测中位数为 7 个。
3. 三级标题（`###`）用于章节内细分，仅在二级标题内容较长时使用。
4. 不得出现标题层级跳跃（如从 `#` 直接到 `###`）。
5. 标题文字简洁，使用名词或名词短语，末尾不加句号。

### 1.2 首屏结构顺序

首屏指读者无需滚动即可看到的内容，按以下顺序组织：

1. 居中 Logo 或项目横幅（可选）；
2. 一级标题（项目名称）；
3. 徽章行（详见 [徽章规范](./徽章规范.md)）；
4. 一句话定位（说明项目是什么、给谁用、解决什么问题）；
5. 章节导航链接行（可选，适用于长 README）；
6. 核心功能或亮点摘要。

标杆取证：`fd`、`ripgrep` 在定位后紧跟章节导航；`next.js`、`rust-lang/rust` 使用居中 Logo 与横幅开场；`vscode` 在定位后即插入产品截图。

### 1.3 段落与留白

- 每段控制在 1–4 行，避免大段密集文字。
- 段落之间空一行，保证渲染后的呼吸感。
- 关键结论前置，解释后置。
- 中文与英文、数字之间保留一个空格；中英文标点按各自语境使用。

## 2. 表格使用规范

### 2.1 使用场景

表格适用于多维度、可对比的信息。实测 36.7% 的样本使用表格，是配置说明、兼容性矩阵、命令对照的推荐形式。适用场景包括：

- 配置项说明（键名、类型、默认值、作用）；
- 平台 / 版本兼容性矩阵；
- 命令或参数对照；
- 功能对比（本项目与其他方案）；
- 路线图与状态。

### 2.2 放置位置

表格紧跟所属二级标题，前置一句引导语说明表格用途；表格后若有例外情况，另起段落补充。

### 2.3 书写要求

| 要求 | 说明 |
| --- | --- |
| 列数控制 | 3–6 列，超过 6 列考虑拆分 |
| 表头明确 | 每列给出简短 noun 表头，避免空表头 |
| 对齐一致 | 全文表格对齐方式统一 |
| 内容简短 | 单元格内不写长段落，必要时用脚注或链接展开 |
| 无空单元格 | 无内容处写明「无」或「不适用」 |

## 3. 代码块使用规范

### 3.1 使用场景

代码块用于命令、配置、API 调用与示例输出。实测 66.7% 的样本包含代码块，是「快速开始」章节的必备元素，中位数为 2 个。

### 3.2 书写要求

1. 每个代码块必须标注语言，例如 `bash`、`json`、`python`、`javascript`，便于语法高亮。
2. 命令示例给出完整可执行命令，不得省略前置步骤。
3. 需要展示结果时，另起代码块标注 `text`，并在文字中说明预期输出。
4. 代码块前后各留一行空行。
5. 单块内容控制在 20 行以内，过长示例拆分为多块或移入 `examples/` 目录并给出链接。
6. 交互式命令使用 `$` 提示符时须全篇统一。

格式示例：

```bash
npm install <package-name>
```

```text
✓ Installation complete
```

## 4. 截图与 GIF 使用规范

### 4.1 使用场景与取舍

| 元素 | 适用场景 | 注意事项 |
| --- | --- | --- |
| 静态截图 | 应用界面、运行结果、图表 | 实测使用率 63.3%，最常用 |
| GIF / 动图 | 命令行演示、交互流程、前后对比 | 文件体积大，须压缩，控制时长 |
| Logo / 横幅 | 品牌识别、首屏门面 | 提供深浅色双版本 |
| 示意图 | 架构、流程、数据流 | 须随文档版本同步更新 |

实测 63.3% 的样本包含图片。标杆取证：`fd` 使用 `doc/screencast.svg` 作为 Demo，`ripgrep` 使用搜索结果截图，`vscode` 使用产品运行截图，`rust`、`next.js` 使用深浅色自适应的 Logo 横幅。

### 4.2 放置位置

1. Logo / 横幅：文件最顶部，居中。
2. 产品截图：一句话定位之后、「快速开始」之前，用于建立直观认知。
3. GIF 演示：独立「Demo / 演示」章节，紧跟「核心功能」之后。
4. 架构示意图：放入「架构」或「设计」章节，或移入 `docs/architecture.md` 并在 README 中链接。

### 4.3 书写要求

- 每张图片必须提供 `alt` 文本，描述画面内容，不得使用 `image`、`截图` 等无意义文本。
- 图片使用相对路径引用仓库内资源，或使用稳定的绝对 URL；避免使用带时效性的临时链接。
- 需要自适应主题的图片，使用 HTML `<picture>` 配合 `prefers-color-scheme` 提供深浅双版本。
- 控制图片体积：截图优先使用 WebP 或优化后的 PNG，GIF 优先转为短视频或压缩动图。
- 图片宽度适配：使用 `width` 属性或外层容器限制，避免撑破页面。

## 5. 链接与导航

### 5.1 章节导航

README 超过 200 行时，在首屏加入导航链接行，指向主要章节：

```markdown
[安装](#安装) · [快速开始](#快速开始) · [文档](#文档) · [贡献](#参与贡献)
```

### 5.2 相对链接优先

仓库内文档、图片、许可证一律使用相对路径，保证 Fork 与离线阅读时仍可用。外部链接须为权威来源（官方文档、包管理页、CI 页面）。

## 6. 美观度与吸引力的落地清单

1. 首屏具备 Logo 或清晰标题，3 秒内传达项目定位。
2. 徽章统一样式、语义配色、数量适中。
3. 一级标题唯一，二级标题 6–12 个，层级无跳跃。
4. 至少一个可复制运行的代码示例。
5. 至少一张能体现产品价值的截图或 Demo。
6. 表格用于对比类信息，列数受控、表头清晰。
7. 所有图片有 `alt`，所有代码块有语言标注。
8. 长文档具备章节导航。
9. 深浅主题下的图片与徽章均可读。
