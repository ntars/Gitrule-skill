# 迁移指南规范

> 本文件解决什么问题：定义破坏性变更时迁移指南的结构、内容要素与发布时机，使使用者能够按步骤从旧版本平滑升级到新版本。

## 1. 触发条件

出现以下任一情况须提供迁移指南：

1. 提交信息含 `BREAKING CHANGE:` 或 `feat!:` / `fix!:`（见 [提交信息规范](./提交信息规范.md)）。
2. 配置键名、默认值或优先级发生变化。
3. API 签名、返回结构或错误码发生变化。
4. 最低运行时版本提升，或不再支持某平台。
5. 目录结构或文件命名发生变更，影响使用者引用路径。

## 2. 文件位置与命名

1. 改动较小的迁移说明写入 `CHANGELOG.md` 对应版本的条目中。
2. 改动较大、涉及多步骤操作时，单独建 `docs/migration/` 目录下的文件，按版本命名，如 `docs/migration/v2.md`。
3. 跨大版本的完整迁移路径在 `docs/migration/README.md` 中建立索引。
4. README 只放迁移提示与链接，不展开步骤（见 [文档矩阵](./文档矩阵.md)）。

## 3. 文档结构

迁移指南须按以下顺序组织：

1. **标题与版本**：标明源版本与目标版本，如「从 v1.x 迁移到 v2.0」。
2. **影响概览**：列出变更类别与影响范围，说明哪些使用者必须迁移。
3. **前置条件**：迁移前须完成的准备，如备份、环境版本升级。
4. **变更清单**：逐项列出破坏性变更，每项包含「旧行为」「新行为」「变更原因」。
5. **迁移步骤**：编号列出可执行的操作，给出命令或代码示例。
6. **验证方式**：迁移后如何确认成功，给出检查命令或预期输出。
7. **回滚方式**：迁移失败时如何恢复到旧版本。
8. **常见问题**：列出高频问题与解答。
9. **获取帮助**：指向 issue、讨论区或文档站。

### 3.1 可复制空白模板

下列模板逐项对应第 3 节的九项结构，复制后替换占位符即可使用：

````markdown
# 从 {{源版本}} 迁移到 {{目标版本}}

> 本指南说明从 {{源版本}} 升级至 {{目标版本}} 所需的全部操作，适用于 {{适用使用者范围}}。

## 1. 影响概览

| 变更类别 | 具体内容 | 影响范围 | 是否必须迁移 |
| --- | --- | --- | --- |
| {{变更类别}} | {{变更内容}} | {{受影响的使用者场景}} | {{是否必须迁移}} |

## 2. 前置条件

- {{前置准备}}
- {{检查项与确认命令}}

## 3. 变更清单

### {{变更项名称}}

- 旧行为：{{旧版本行为}}
- 新行为：{{新版本行为}}
- 变更原因：{{变更原因}}

迁移前：

```{{代码语言}}
{{旧配置或旧代码}}
```

迁移后：

```{{代码语言}}
{{新配置或新代码}}
```

## 4. 迁移步骤

1. {{迁移步骤}}
2. {{迁移步骤}}
3. {{人工处理步骤}}

## 5. 验证方式

```bash

```

预期输出：{{预期结果}}

## 6. 回滚方式

1. {{恢复旧版本的操作}}

## 7. 常见问题

### {{问题}}

答：{{解答}}

## 8. 获取帮助

- 问题反馈：{{issue 地址}}
- 讨论区：{{讨论区地址}}
- 相关文档：{{文档链接}}
````

占位符对照：

| 占位符 | 必填 | 填写要点 |
| --- | --- | --- |
| `{{源版本}}` / `{{目标版本}}` | 是 | 与目标 tag 一致，格式 `vX.Y.Z` |
| `{{适用使用者范围}}` | 是 | 写明哪些使用者必须迁移，避免含糊表述 |
| `{{变更类别}}` | 是 | 配置、API、运行时、目录四类中至少一类 |
| `{{是否必须迁移}}` | 是 | 写明该变更是否要求使用者执行迁移 |
| `{{旧行为}}` / `{{新行为}}` | 是 | 逐项对照，不得只写一侧 |
| `{{代码语言}}` | 是 | 代码块语言标识，如 `yaml`、`json`、`js` |
| `{{前置准备}}` | 是 | 迁移前须完成的备份与环境检查 |
| `{{迁移步骤}}` | 是 | 每步可直接执行，含命令或代码 |
| `{{人工处理步骤}}` | 是 | 不可自动迁移的步骤须在此显式标注 |
| `{{检查命令}}` / `{{预期结果}}` | 是 | 命令可独立运行，结果可判定 |
| `{{回滚方式}}` | 是 | 不得省略，见第 7 节禁止事项 |

## 4. 内容要求

### 4.1 变更对照示例

```markdown
### 配置项 `timeout` 更名为 `timeoutMs`

- 旧行为：在配置文件中使用 `timeout: 5000`，单位为秒。
- 新行为：改用 `timeoutMs: 5000`，单位为毫秒。
- 变更原因：统一时间单位，避免与 API 参数不一致。

迁移前：

```yaml
timeout: 5
```

迁移后：

```yaml
timeoutMs: 5000
```

### 4.2 写作要求

1. 每步给出可直接执行的命令或代码，不得只描述「修改配置」。
2. 给出迁移前与迁移后的对照，便于逐项核对。
3. 明确标注不可自动迁移、须人工处理的步骤。
4. 影响范围须具体，避免「可能影响部分用户」等含糊表述。
5. 验证命令须可独立运行，含预期输出。

## 5. 发布时机与联动

1. 迁移指南须与包含破坏性变更的版本同步发布，不得滞后。
2. `CHANGELOG.md` 对应条目须链接到迁移指南（见 [变更日志规范](./变更日志规范.md)）。
3. PR 模板的破坏性变更区块须提示填写迁移方式（见 [Issue与PR模板规范](./Issue与PR模板规范.md)）。
4. 版本号遵循语义化版本，破坏性变更须递增主版本（见 [版本管理规范](./版本管理规范.md)）。
5. README 在显著位置提示旧版本使用者阅读迁移指南。

## 6. 废弃与保留策略

1. 迁移指南须长期保留，不得在新版本发布后删除。
2. 旧版本文档可标记为「不再维护」，但须保留入口。
3. 跨多个大版本的升级须提供分步路径，不得要求一次性跨越全部变更。

## 7. 禁止事项

1. 禁止只写「有破坏性变更，请自行调整」。
2. 禁止省略回滚方式。
3. 禁止在迁移步骤中使用无法执行的伪代码。
4. 禁止删除历史版本的迁移指南。
