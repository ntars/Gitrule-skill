# CI工作流规范

> 本文件解决什么问题：定义 `.github/workflows/*.yml` 持续集成工作流的触发条件、任务拆分、缓存策略与安全配置，使构建、测试与检查可复现、可审计。

## 1. 设计原则

1. **单一职责**：每个工作流只负责一类目标（构建、测试、发布、文档部署），不得把发布与测试混在一个工作流中。
2. **快速反馈**：轻量检查（lint、格式）在前，耗时任务（完整测试矩阵）在后。
3. **可复现**：锁定依赖版本，使用固定版本的 Actions，缓存仅用于加速不改变结果。
4. **最小权限**：工作流按任务授予权限，默认只读，发布任务单独提权（见 [安全与隐私规范](./安全与隐私规范.md)）。

## 2. 文件结构

### 2.1 命名与路径

- 路径固定为 `.github/workflows/*.yml`。
- 文件名用小写与连字符，按职责命名，如 `ci.yml`、`release.yml`、`docs.yml`。
- 工作流 `name` 字段须与文件名语义一致。

### 2.2 必备区块

| 区块 | 作用 | 要求 |
| --- | --- | --- |
| `name` | 工作流显示名称 | 简明，能读出职责 |
| `on` | 触发条件 | 明确分支、路径或事件 |
| `permissions` | 权限声明 | 显式声明，默认最小 |
| `jobs` | 任务集合 | 按职责拆分 |

### 2.3 触发条件设计

| 触发事件 | 适用 | 注意 |
| --- | --- | --- |
| `push` | 主干与发布分支 | 限制分支范围，避免全分支触发 |
| `pull_request` | 所有 PR | 保证合入前检查 |
| `workflow_dispatch` | 手动触发 | 用于发布、回滚等受控操作 |
| `schedule` | 定时任务 | 用于依赖更新检查、夜间构建 |
| `release` | 发布后动作 | 用于产物上传与公告 |

## 3. 任务拆分

推荐的阶段顺序：

1. **静态检查**：格式、lint、类型检查。
2. **构建**：产出构建物，供后续任务复用。
3. **测试**：单元测试、集成测试，可按矩阵并行。
4. **产物校验**：检查构建物大小、签名或完整性。
5. **发布**：仅在 CI 全绿且条件满足时执行（见 [推送与发布规范](./推送与发布规范.md)）。

任务间通过 `needs` 声明依赖，保证失败即中断，不得让后续任务在失败状态下继续。

## 4. 矩阵构建

使用 `strategy.matrix` 覆盖多版本、多平台：

```yaml
strategy:
  fail-fast: false
  matrix:
    os: [ubuntu-latest, macos-latest, windows-latest]
    node-version: [18, 20, 22]
```

要求：

- 版本覆盖项目声明支持的最低与最新版本（见 [兼容性说明](./README章节规范.md) 第 14 章）。
- `fail-fast` 设为 `false`，使各组合完整运行，便于定位兼容性问题。
- 矩阵维度不超过三个，避免组合爆炸。

## 5. 缓存策略

| 缓存对象 | 键值建议 | 注意 |
| --- | --- | --- |
| 依赖目录 | 包管理器锁文件哈希 | 锁文件变更即失效 |
| 构建产物 | 源码与配置哈希 | 与构建输入一致 |
| 工具链 | 版本号 | 版本升级即失效 |

缓存只加速，不改变构建结果；缓存命中时仍须执行完整测试。

## 6. 安全配置

1. 密钥通过仓库 Secrets 注入，禁止写入工作流文件或日志。
2. 每个工作流显式声明 `permissions`，默认 `contents: read`。
3. 第三方 Action 引用固定版本或提交哈希，避免浮动标签。
4. PR 来自 Fork 时，禁止注入 Secrets，防止提权攻击。
5. 发布任务与主检查分离，仅在受保护分支或 tag 触发。

## 7. 状态徽章

工作流应为 README 提供状态徽章，格式为：

```markdown
[![CI](https://github.com/{owner}/{repo}/actions/workflows/ci.yml/badge.svg)](https://github.com/{owner}/{repo}/actions/workflows/ci.yml)
```

徽章参数与排列见 [徽章规范](./徽章规范.md)。

## 8. 禁止事项

1. 禁止在工作流中硬编码密钥或内部地址。
2. 禁止使用 `continue-on-error` 掩盖测试失败。
3. 禁止对同一条件配置多个相互冲突的触发规则。
4. 禁止在主干检查未通过时执行发布。
