# 架构设计文档规范

> 本文件解决什么问题：定义架构文档与架构决策记录（ADR）的模板、字段与写法，说明系统边界、模块职责、质量属性与关键取舍，并保证决策可追溯。

## 1. 规范条文

1. 架构文档（`docs/architecture.md`）只描述结构与边界，不含使用示例，职责边界见 [文档矩阵](./文档矩阵.md)。
2. 每条重大技术决策须有对应 ADR；无 ADR 的决策视为未记录决策。
3. ADR 编号连续、永久固定；一旦采纳不改写历史，状态变更通过新增 ADR 记录并标注「被替代」。
4. 架构描述须与代码实现保持一致；代码与文档不一致时以代码为准并立即修订文档。
5. 每条架构决策须能回溯到一条或多条需求，追踪关系见 [需求追踪矩阵规范](./需求追踪矩阵规范.md)。
6. 质量属性须给出可验证的度量目标，禁止仅写「高性能」「高可用」。

## 2. 架构文档模板

```markdown
# 架构设计：{{项目名称}}

文档版本：{{v1.0}} ｜ 对应代码版本：{{tag}} ｜ 最后核对日期：{{YYYY-MM-DD}}

## 系统上下文
- 系统职责：{{一句话说明系统边界内的责任}}
- 外部参与者：{{用户、上游系统、下游系统}}
- 输入输出：{{进入系统的请求与系统产出的结果}}
- 边界之外：{{明确不由本系统承担的职责}}

## 模块划分
| 模块 | 唯一职责 | 对外接口 | 依赖模块 | 不负责 |
| --- | --- | --- | --- | --- |
| {{模块名}} | {{仅一件事}} | {{接口名}} | {{模块名}} | {{明确排除}} |

## 关键数据流
1. {{触发点}} → {{模块 A}}：{{传递的数据}}
2. {{模块 A}} → {{模块 B}}：{{转换与传递}}
3. {{模块 B}} → {{结果}}：{{最终产出}}

## 技术选型
| 领域 | 选型 | 备选 | 决策依据 | ADR |
| --- | --- | --- | --- | --- |
| {{语言 / 框架 / 存储}} | {{采用项}} | {{未采用项}} | {{取舍理由}} | {{ADR-000N}} |

## 质量属性
| 属性 | 目标值 | 验证方式 | 关联 ADR |
| --- | --- | --- | --- |
| 性能 | {{P95 延迟 < X ms}} | {{压测方式}} | {{ADR-000N}} |
| 可用性 | {{月度可用性 ≥ X%}} | {{监控统计}} | {{ADR-000N}} |
| 安全 | {{敏感数据零明文落盘}} | {{审计方式}} | {{ADR-000N}} |
| 可扩展性 | {{横向扩容至 N 节点无需改代码}} | {{扩容演练}} | {{ADR-000N}} |

## 约束与取舍
- 技术约束：{{语言版本、平台、兼容性}}
- 已放弃方案及原因：{{方案 A：原因}}
- 已知技术债：{{债务项与偿还条件}}
```

## 3. ADR 模板

```markdown
# ADR-{{四位序号}}：{{决策标题}}

- 状态：{{提议 / 已采纳 / 已废弃 / 被 ADR-000N 替代}}
- 日期：{{YYYY-MM-DD}}
- 决策人：{{姓名}}
- 关联需求：{{REQ-001 / …}}

## 背景
{{面临的客观问题与约束，须可验证，不写主观偏好}}

## 决策
{{采用的方案，一句话陈述，须明确到可执行的程度}}

## 备选方案
| 方案 | 优点 | 缺点 | 未采用原因 |
| --- | --- | --- | --- |
| {{方案 A}} | | | |
| {{方案 B（采用）}} | | | — |

## 后果
- 正面：{{获得的能力}}
- 负面：{{引入的成本或限制}}
- 后续任务：{{需要跟进的事项}}

## 相关文件
- {{架构文档中受影响的章节}}
- {{替代或被引用的 ADR}}
```

## 4. 字段定义

### 4.1 架构文档字段

| 字段 | 必填 | 类型 | 填写要点 | 示例 |
| --- | --- | --- | --- | --- |
| 对应代码版本 | 是 | tag | 与 [版本管理规范](./版本管理规范.md) 的 tag 一致 | `v1.2.0` |
| 最后核对日期 | 是 | 日期 | 每次代码变更后须更新 | `2026-11-18` |
| 模块唯一职责 | 是 | 文本 | 一个模块只写一件事 | `解析并校验 Markdown 规则` |
| 不负责 | 是 | 文本 | 明确边界，防止职责漂移 | `不负责文本改写` |
| 技术选型.决策依据 | 是 | 文本 | 须引用 ADR 编号 | `见 ADR-0002` |
| 质量属性.目标值 | 是 | 度量 | 含单位与阈值，可验证 | `P95 < 150ms` |
| 已知技术债 | 否 | 列表 | 写明偿还触发条件 | `待 v2 替换解析器` |

### 4.2 ADR 字段

| 字段 | 必填 | 类型 | 填写要点 | 示例 |
| --- | --- | --- | --- | --- |
| 编号 | 是 | `ADR-NNNN` | 四位序号，连续、永久固定 | `ADR-0002` |
| 状态 | 是 | 枚举 | 提议 / 已采纳 / 已废弃 / 被替代 | `已采纳` |
| 关联需求 | 是 | 列表 | 对应立项书的 REQ 编号 | `REQ-001` |
| 背景 | 是 | 文本 | 陈述客观约束，禁止「我觉得」 | `需兼容 Node 18` |
| 决策 | 是 | 文本 | 一句话、可执行 | `采用 remark 作为解析器` |
| 备选方案 | 是 | 表格 | 至少包含 1 个未采用方案 | 见模板 |
| 否定理由 | 是 | 文本 | 每个未采用方案均须给出 | 见模板 |
| 后果 | 是 | 列表 | 正面、负面、后续任务三项齐全 | 见模板 |

## 5. 填写说明

1. **模块划分**：每行的「唯一职责」若出现「和」「以及」连接的两件事，应拆为两个模块。
2. **数据流**：按时间顺序编号，标明传递的数据内容，禁止只写模块名箭头。
3. **质量属性**：每条须有目标值、验证方式与 ADR 引用；缺任一者视为不完整。
4. **ADR 背景**：写问题与约束，不写决策本身；决策只在「决策」段出现一次。
5. **备选方案**：即使只有一种方案，也须写明「考虑过自行实现，因维护成本过高未采用」；无备选视为未充分论证。
6. **状态变更**：不修改原 ADR 正文，新建 ADR 并将原文状态改为「被 ADR-000N 替代」。
7. **技术债**：须写偿还触发条件，禁止只列现象。

常见错误：

| 错误写法 | 问题 | 修正方式 |
| --- | --- | --- |
| 架构文档里放 API 调用示例 | 与 [API文档规范](./API文档规范.md) 职责重叠 | 移到 API 文档，架构只留接口名 |
| 「系统需高性能」 | 无阈值、不可验证 | 给出 P95 延迟目标与压测方式 |
| ADR 只有决策没有备选 | 未论证 | 补至少 1 个未采用方案及原因 |
| 修改已采纳 ADR 的正文 | 历史被改写 | 新建 ADR 标注替代关系 |
| 决策无法关联需求 | 追溯链断裂 | 补关联 REQ 编号 |

## 6. 完整示例

```markdown
# ADR-0002：采用 remark 作为 Markdown 解析层

- 状态：已采纳
- 日期：2026-11-18
- 决策人：李四
- 关联需求：REQ-001、REQ-004

## 背景
需支持 GFM 与中文文本节点定位，且运行时依赖须兼容 Node 18；团队维护解析器的人力上限为 0.5 人月/季度。

## 决策
采用 remark 生态作为唯一 Markdown 解析层，规则以插件形式实现。

## 备选方案
| 方案 | 优点 | 缺点 | 未采用原因 |
| --- | --- | --- | --- |
| 自研解析器 | 完全可控 | 需长期维护边界用例 | 超出人力上限 |
| marked | 轻量 | 中文节点定位能力弱 | 不满足 REQ-004 |

## 后果
- 正面：GFM 兼容性由上游维护，节点定位满足验收条件。
- 负面：插件 API 变更需跟进上游版本。
- 后续任务：在 CI 中锁定 remark 主版本并订阅 its release 通知。
```
