# 开发手册模板规范

> 本文件解决什么问题：定义"云端编写、本地执行"两阶段开发手册的骨架、任务卡格式、交接协议与校验门禁，让同一个想法可由云端模型转写为无歧义任务卡，并由本地编码模型按部分接力执行。

## 1. 定位与使用流程

1. 本规范面向"一个云端推理模型 + 一个本地编码模型"的分工场景：云端负责把模糊想法转写为明确方案，本地负责按方案确定性执行。
2. 使用流程固定为四步，顺序不得跳过：
   - 前置核查：检查想法是否存在错误前提、逻辑跳跃或信息缺失；信息不足先向用户提问，禁止脑补。
   - 云端编写：按第 9 节规范扫描开源方案并填写手册。
   - 用户审核：重点审核验收命令、采纳记录与禁区。
   - 本地执行：按机读索引注入对应章节与交接记录，逐部分执行。
3. 手册正文中禁止出现"等""相关""适当""尽量""必要时"等含糊词；每处要么给出精确值，要么给出决策规则。

## 2. 手册骨架

每份开发手册固定包含以下部分，顺序不变：

| 部分 | 职责 |
| --- | --- |
| 机读索引 | 章节路径、对应代码目录、验收命令、阶段标记的导航表 |
| 采纳记录 | 开源供应链记录表，全项目单一真源（见第 11 节） |
| 项目宪法 | 全项目不变量，每个部分必注入 |
| 术语表 | 术语与通俗解释、对应代码的对照 |
| 模块章节 | 每模块一章，按第 4 节结构编写 |
| 发行章节 | 构建与分发规范，发布动作须用户确认 |
| 官网文案章节 | 面向普通用户的文案规范，不注入本地模型 |
| 变更记录 | 日期、章节、变更与决策人 |

## 3. 项目宪法

项目宪法为每个本地执行部分必注入的不变量，固定含五项：

1. 技术栈与版本：精确到版本号。
2. 目录结构约定：树状图加每个目录一句话职责。
3. 编码规范：按项目类型裁剪，基线为模块化按需加载、最小最直接代码、不添加非要求的功能、注释完整且专业概念用通俗语言注释；界面类项目遵循 Apple HIG，字体单位一律使用 px 或 rem，禁止使用 rpx。
4. 全局禁区：绝不许做的事，例如不引入未进采纳记录的依赖、不改契约文件。
5. 输出语言规范：说明、日志、进度与错误信息使用简体中文；代码、命令、文件路径与专有名词可保留原文。

## 4. 模块章节结构

每个模块章节固定含九节，顺序不变：

| 节 | 职责 |
| --- | --- |
| 模块职责 | 1-3 句，写清做什么、不做什么 |
| 依赖的开源方案 | 名称、用途、采纳记录编号 |
| 文件清单 | 路径、动作（新建/修改/只读）、职责；总数不超过 10 个，超出拆章 |
| 接口契约 | 签名、路由、协议字段精确到类型，附完整输入输出样例 |
| 数据与状态 | 存什么、存哪里、格式；专业概念用通俗语言注释 |
| 依赖关系 | 需要先读、会调用、绝不改三组文件列表 |
| 任务卡 | 本模块拆成的部分，每卡独立执行 |
| 本章禁区 | 本模块特别不许做的事 |
| 设计备注 | 选型理由、放弃的方案、事实与推测的区分；不注入本地模型 |

## 5. 任务卡格式

一张任务卡等于一次本地会话等于一条验收命令，固定字段如下：

| 字段 | 要求 |
| --- | --- |
| 目标 | 一句话，可机器验证 |
| 前置条件 | 依赖的上一部分与文件均已存在 |
| 步骤 | 编号列出，每步一个确定性动作，一次做完不打断不追问 |
| 验收命令 | 可直接复制执行；还没有验收体系时，第一张卡必须先搭建验收命令 |
| 期望结果 | 精确输出、退出码或断言数 |
| 失败处理 | 按典型错误逐条给出处置；连续失败 3 次必须停止并写入交接记录 |
| 交接要求 | 声明必须写入交接记录的字段 |

硬性约束：

1. 一张卡触达文件超过 10 个就拆卡；一章超过 6 张卡就拆章。
2. 凡涉及交付自检的卡，须显式列出冗余代码清理与 README、NOTICE、LICENSE 同步点。
3. 涉及删除或覆盖文件的动作一律停下，写入交接记录的 block 字段，等用户确认。
4. 含糊到写不出验收命令的任务不得填卡，单独标注"需用户决策"。

## 6. PROGRESS 交接协议

交接记录文件 PROGRESS.md 是部分与部分之间的唯一真源，格式固定：

| 字段 | 要求 |
| --- | --- |
| done | 本卡目标是否达成 |
| files | 实际改动的文件清单 |
| decisions | 过程决策，格式为"选择了 A，因为 B" |
| next | 下一张卡编号与入口，必须写到文件路径与入口函数，不许写"继续完善" |
| block | 未解决问题，无则留空 |

1. 每张卡收尾必须追加一条，格式不许改。
2. 本地执行时只注入最新一条，历史条目不注入。
3. 断点恢复：收到"继续"指令时，先读最新一条确认断点，从 next 指向的入口继续，禁止凭记忆或猜测重做已完成步骤。

## 7. 本地注入预算

harness 按下表拼装每个部分的上下文，总预算不超过 24K（32K 工作窗的 75%）：

| 注入项 | 预算 |
| --- | --- |
| 项目宪法 | 2-3K |
| 当前任务卡所属章节 | 2-5K |
| 交接记录最新一条 | 约 0.5K |
| 交接提示词骨架 | 约 0.3K |
| 代码与工具输出 | 剩余额度 |

不注入：采纳记录全表（只注入本卡涉及条目）、设计备注、官网文案章节。

## 8. 交接提示词铁律

每个部分开工时注入固定开场，铁律固定六条：

1. 全程使用简体中文输出；代码、命令、路径与专有名词可保留原文。
2. 只做任务卡内的事，不添加非要求的功能、配置或扩展能力。
3. 不臆造、不虚构；不确定的 API 签名直接说明不确定；事实与推测显式区分。
4. 验收命令失败时按任务卡的失败处理执行，不许自行更改验收标准。
5. 涉及删除、覆盖文件的动作一律停下，等用户确认。
6. 完成后严格按交接要求写交接记录，然后结束。

## 9. 云端填写规范

云端模型填写手册前先完成两项前置，再逐章填写：

1. 前提核查：检查错误前提、逻辑跳跃与信息缺失，不足先问用户。
2. 开源方案扫描：检索开源生态中可用的现成方案，先扫后填，能用成熟方案不造轮子，结果登记进采纳记录。

填写时遵守：

1. 消灭一切含糊词，每处给精确值或决策规则。
2. 设计决策写进设计备注，含选型理由与放弃的方案，供用户审核，不注入本地模型。
3. 给本地模型的指令按"它不知道项目背景"来写，所有前提显式写出。
4. 合规底线：许可证不明标"待确认"；强 copyleft 方案标注衍生义务提示；修改过的开源代码保留原始版权与修改说明；采纳项必须同步 README、README_EN、NOTICE、LICENSE，同步动作作为对应任务卡的显式步骤与验收内容。
5. 文档格式规范引用本仓库对应规范，不在手册中复制规范正文。

## 10. 阶段状态与工作窗

机读索引中每章带阶段标记，据此调整本地工作窗：

| 阶段 | 特征 | 工作窗 |
| --- | --- | --- |
| 绿地 | 按冻结契约填实现 | 16-24K |
| 增长 | 跨模块功能，默认档 | 32K |
| 维护 | 重构与跨模块排查 | 48-64K，并行相应减少 |

维护期章节须额外附排查指引：症状、可能位置、验证命令三列表。

## 11. 采纳记录、发行与官网文案

1. 采纳记录表字段固定为：名称、类别、版本、用途、许可证、版权方、官方地址、是否修改、修改说明、声明方式、采纳状态；采纳状态分"可立即采用、需评估、暂不可用"三档。
2. 发行章节覆盖构建脚本、CI 矩阵、checksum、签名环境变量模板；发行卡的验收命令是构建产物检查；对外发布动作不进本地模型，由用户确认后执行。
3. 官网文案章节面向普通用户：禁止出现代码、命令行、技术名词与空词；结构为首屏定位、痛点、亮点、信任、下载、场景故事、常见问题；语气平静克制。

## 12. 跨项目引用与校验

1. 目标项目引用本规范时，通过 `gitrule spec` 读取全文，把手册骨架复制为项目内手册的初始骨架；本规范不随项目修订，项目内手册的演进在项目仓库闭环。
2. 涉及文档产出的任务卡，验收命令追加 `gitrule check`；多语言项目追加 `gitrule xcheck`；术语表变更后执行 `gitrule termcheck`。
3. `gitrule check` 的文档违规属可自动修复类，可先执行 `gitrule optimize` 后复检，仍不通过再写入交接记录的 block 字段。
4. Gitrule 规范只管文档与仓库规范，代码质量归各项目测试与验证脚本，两者不互相替代。
