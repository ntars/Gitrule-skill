# 依赖管理规范

> 本文件解决什么问题：定义依赖引入申请、依赖清单、锁定与更新的模板与字段，保证构建可复现、依赖可追溯、许可证合规。

## 1. 规范条文

1. 引入新依赖须说明用途、许可证与维护状态（见 [开源合规规范](./开源合规规范.md)）。
2. 优先选择许可证兼容、社区活跃的依赖；禁止引入来源不明或许可证不明的依赖。
3. 依赖版本须写入 lockfile 并提交仓库，保证干净环境可复现构建（对应硬规则 H9 与维度 D5）。
4. 版本号须锁定实际解析版本，不使用范围表达式作为最终交付。
5. 依赖更新须自动化工具辅助，更新后须跑通 CI；漏洞须及时处理或记录缓解措施。
6. 依赖清单与 NOTICE 保持一致（见 [NOTICE规范](./NOTICE规范.md)）。

## 2. 依赖引入申请模板

```markdown

- 申请编号：{{DEP-NNN}}
- 申请人：{{姓名}}
- 用途：{{一句话说明解决什么问题}}
- 是否可自建：{{是 / 否；是则说明为何仍引入}}
- 替代方案评估：{{已评估的替代包及未选原因}}

| 字段 | 值 |
| --- | --- |
| 包名 | {{包名}} |
| 引入版本 | {{精确版本号}} |
| 许可证 | {{SPDX ID}} |
| 许可证兼容性 | {{兼容 / 不兼容 / 需法务确认}} |
| 最近发布时间 | {{YYYY-MM-DD}} |
| 维护状态 | {{活跃 / 低频 / 停滞}} |
| 周下载量 | {{数值}} |
| 传递依赖数量 | {{数值}} |
| 已知漏洞 | {{无 / CVE 编号与处置}} |
| 打包体积影响 | {{增量 KB}} |

- 结论：{{批准 / 拒绝 / 有条件批准}}
- 审批人：{{姓名}}
```

## 3. 依赖清单模板

```markdown
# 依赖清单：{{项目名称}}

更新时间：{{YYYY-MM-DD}} ｜ lockfile：{{路径}} ｜ 生成工具：{{工具与版本}}

| 依赖 | 引入版本 | 锁定版本 | 类型 | 许可证 | 用途 | 最后审查 |
| --- | --- | --- | --- | --- | --- | --- |
| {{包名}} | {{^1.2.0}} | {{1.2.3}} | 直接 / 间接 | {{MIT}} | {{用途}} | {{YYYY-MM-DD}} |

## 更新记录
| 日期 | 依赖 | 版本变化 | 原因 | 验证结果 |
| --- | --- | --- | --- | --- |
| {{YYYY-MM-DD}} | {{包名}} | {{1.2.2 → 1.2.3}} | {{安全修复}} | {{CI 全绿}} |

## 例外与缓解
| 依赖 | 问题 | 缓解措施 | 复核日期 |
| --- | --- | --- | --- |
| {{包名}} | {{漏洞 / 停滞}} | {{限制使用范围}} | {{YYYY-MM-DD}} |
```

## 4. 字段定义

| 字段 | 必填 | 类型 | 填写要点 | 示例 |
| --- | --- | --- | --- | --- |
| 申请编号 | 是 | `DEP-NNN` | 连续、不复用 | `DEP-007` |
| 用途 | 是 | 文本 | 说明解决的问题，禁止「方便开发」 | `解析 TOML 配置` |
| 替代方案评估 | 是 | 文本 | 至少评估 1 个替代项 | `评估过 toml-js，因维护停滞未选` |
| 引入版本 | 是 | 精确版本 | 不得使用 `^` 或 `~` | `1.2.3` |
| 锁定版本 | 是 | 精确版本 | 与 lockfile 一致 | `1.2.3` |
| 许可证 | 是 | SPDX ID | 与 [LICENSE规范](./LICENSE规范.md) 写法一致 | `MIT` |
| 维护状态 | 是 | 枚举 | 活跃 / 低频 / 停滞，附判定依据 | `活跃（近 30 天有提交）` |
| 传递依赖数量 | 是 | 数值 | 过多时须说明体积与风险影响 | `12` |
| 已知漏洞 | 是 | 文本 | 无则写「无」，不得留空 | `无` |
| 复核日期 | 是 | 日期 | 例外项须设复核日期 | `2026-12-31` |

## 5. 填写说明

1. **自建评估**：先回答「能否用标准库或现有能力实现」；能自建仍引入的须说明理由。
2. **许可证**：须为 SPDX ID；`UNLICENSED`、自定义许可须转为「需法务确认」，不得直接引入。
3. **维护状态**：以最近发布时间与 issue 响应为据，禁止「看起来有人维护」。
4. **版本锁定**：交付时 lockfile 中须为精确解析版本；`package.json` 可保留范围表达式，但 lockfile 必须精确。
5. **更新节奏**：自动化更新每开启，人工确认合并；每次更新须跑通 CI 并核对许可证变化。
6. **漏洞处理**：优先升级到安全版本；无法升级时写明缓解措施与复核日期，并进入 [事故响应规范](./事故响应规范.md) 的风险登记。
7. **清单同步**：引入或移除依赖后，同步更新依赖清单与 NOTICE，三者（lockfile、清单、NOTICE）须一致。

常见错误：

| 错误写法 | 问题 | 修正方式 |
| --- | --- | --- |
| 「用一个库处理配置」 | 无具体包名与用途 | 写包名、版本、解决问题 |
| 许可证写「开源」 | 不可判定兼容性 | 写 SPDX ID |
| lockfile 未提交 | 构建不可复现 | 提交 lockfile（对应 H9） |
| 传递依赖数量留空 | 风险不可见 | 填具体数值 |
| 漏洞不写缓解措施 | 风险无跟踪 | 补措施与复核日期 |

## 6. 完整示例

```markdown
## 依赖引入申请：remark

- 申请编号：DEP-001
- 申请人：王五
- 用途：作为 Markdown 解析层，支撑规则引擎的节点定位需求（REQ-001、REQ-004）。
- 是否可自建：否；自建无法在人力上限内覆盖 GFM 边界用例。
- 替代方案评估：评估过 marked，因中文节点定位能力不足未选。

| 字段 | 值 |
| --- | --- |
| 包名 | remark |
| 引入版本 | 15.0.1 |
| 许可证 | MIT |
| 许可证兼容性 | 兼容 |
| 最近发布时间 | 2026-11-02 |
| 维护状态 | 活跃（近 30 天有提交） |
| 周下载量 | 4,200,000 |
| 传递依赖数量 | 18 |
| 已知漏洞 | 无 |
| 打包体积影响 | +42 KB |

- 结论：批准，随 ADR-0002 一并落地
- 审批人：李四
```
