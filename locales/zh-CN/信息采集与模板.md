# 信息采集与模板

> 本文件解决什么问题：定义撰写文档前须采集的项目信息字段、未确认信息的标记规则，并提供占位符索引、术语对照模板、依赖清单模板与可直接复制的项目信息采集正文。

## 1. 必填字段（缺失即阻断）

| 字段 | 说明 | 影响章节 |
| --- | --- | --- |
| 项目名称 | 仓库名与展示名，两者不一致时须说明 | 全篇 |
| 一句话定位 | 不超过 60 字，说明项目是什么、为谁解决什么问题 | 第 1 章 |
| 仓库描述（国家语言与英语） | 两种语言各不超过 120 字符，分别说明项目类型与核心用途 | 第 1 章 |
| 话题标签 | 5–10 个小写英文词，用 `-` 连接，大小写混用视为缺项 | 第 1 章 |
| 项目背景 | 立项原因、现有方案的不足 | 第 2 章 |
| 核心功能清单 | 按模块分组，含用户可感知的行为 | 第 3 章 |
| 技术栈 | 语言、框架、运行时版本约束 | 第 6 章 |
| 依赖清单 | 名称、版本、许可证、版权方、来源地址 | 第 6 章、NOTICE |
| 许可证类型 | 项目自身许可证，须为 SPDX 标识符 | 第 19 章 |
| 著作权人 | 个人姓名或组织全称，与年份 | 第 19 章、NOTICE |
| 安装与运行方式 | 环境要求、命令、预期结果 | 第 7、8 章 |

## 2. 选填字段

配置项清单、API 定义、目录结构、性能测试数据、兼容性矩阵、已知问题、更新日志、路线图、贡献流程、安全策略、截图与演示地址、外部素材来源。

## 3. 字段填写说明与示例

| 字段 | 填写说明 | 示例 |
| --- | --- | --- |
| 项目名称 | 仓库名使用小写字母、数字与 `-`；展示名可使用品牌写法，两者不一致时注明原因 | 仓库名 `markdown-lint-cli`，展示名 `Markdown Lint CLI` |
| 一句话定位 | 包含品类词与限定词，不堆砌形容词，不超过 60 字 | `面向技术文档团队的 Markdown 规范检查命令行工具` |
| 仓库描述（国家语言与英语） | 国家语言与英语各自独立成句，均不超过 120 字符，不以口号替代描述 | `中文：检查 Markdown 文档结构的命令行工具` / `English: A CLI tool for checking Markdown document structure` |
| 话题标签 | 全部小写，词间用 `-` 连接，优先覆盖语言、形态、用途、生态 | `go cli markdown linter developer-tools` |
| 技术栈 | 写明主语言、框架与运行时版本约束，不写「最新版本」 | `Go >= 1.22；Cobra v1.8.x` |
| 依赖清单 | 每项含版本、许可证、版权方与官方地址；来源不明时按未确认项标注 | 见附录 C 的依赖清单表格模板 |
| 许可证类型 | 使用 SPDX 标识符，不使用「开源」「可自由使用」等模糊说法 | `MIT` |
| 安装与运行方式 | 给出当前工作目录、完整命令与可核对的预期输出 | 在仓库根目录执行 `go install ./cmd/mdlint`，输出版本号 |
| 未确认项 | 使用固定标记，写明缺失内容与补充责任人，不用「暂定」替代 | `【待确认：依赖 foo 的许可证类型，责任人：张三】` |

## 4. 未确认信息的标记规则

1. 统一格式：`【待确认：具体缺什么】`，不得使用「暂定」「大概」「可能」等模糊表述替代。
2. 标注位置：正文对应位置一处，文末「待确认事项汇总」再列一次。
3. 涉及许可证、版权、依赖来源的未确认项，必须在 NOTICE 中显式标注，不得省略整个条目。
4. 待确认事项汇总须包含编号、字段、缺失内容、补充责任人与计划补齐时间；无责任人或时间的条目不得进入阶段 0（见 [执行流程](./执行流程.md)）。

## 5. 附录 A · 占位符索引

`{{项目名称}}`、`{{一句话定位}}`、`{{当前版本}}`、`{{维护状态}}`、`{{许可证 SPDX}}`、`{{著作权人}}`、`{{年份}}`、`{{分支名}}`、`{{仓库地址}}`、`{{最低运行时版本}}`

使用规则：

1. 本索引仅列采集阶段的基础字段；README 全量占位符及其说明以 [README标准模板](./README标准模板.md) 的占位符对照表为准。
2. 正式占位符统一写成 `{{纯名}}`，不得在花括号内嵌套说明文字、反引号或第二个占位符；规范示例中的自然语言花括号内容不视为正式占位符。
3. 采集表中的自然语言字段不直接使用占位符；生成 README 时再按对照表映射到对应占位符，最终文档中不得留下任何说明性花括号内容。

## 9. 附录 D · 可复制项目信息采集正文

将以下内容复制到目标项目的 `项目信息采集表.md`，逐项替换「填写：」后的内容。无法确认的字段按第 4 节规则标注，并在第 8 节汇总。

````markdown
# 项目信息采集表

> 本文件用于一次性采集文档生成所需信息。填写完成后，依据采集结果生成 README、NOTICE 与其他交付文档。

## 1. 基本信息

| 字段 | 填写内容 |
| --- | --- |
| 仓库名 | 填写：小写字母、数字与连字符组成的仓库名 |
| 展示名 | 填写：对外展示的项目名称；与仓库名一致时写「同仓库名」 |
| 仓库地址 | 填写：完整 HTTPS 地址 |
| 目标分支 | 填写：默认分支名称 |
| 语言码 | 填写：优先语言码，如 zh-CN |
| 当前版本 | 填写：语义化版本号或「未发布」 |
| 维护状态 | 填写：活跃维护 / 低频维护 / 已归档 |

## 2. 定位与适用范围

| 字段 | 填写内容 |
| --- | --- |
| 一句话定位 | 填写：不超过 60 字，含品类词与限定词 |
| 仓库描述（国家语言） | 填写：不超过 120 字符 |
| 仓库描述（English） | 填写：不超过 120 字符 |
| 话题标签 | 填写：5–10 个小写英文词，用连字符连接 |
| 项目背景 | 填写：立项原因与现有方案的不足 |
| 适用场景 | 填写：逐条列出，每条含触发条件 |
| 不适用场景 | 填写：逐条列出，每条说明原因 |
| 优势 | 填写：每条附可核对依据 |
| 局限 | 填写：每条含影响范围与规避方式 |

## 3. 功能与特性

| 模块 | 用户可感知行为 | 触发条件 | 结果 | 证据或链接 |
| --- | --- | --- | --- | --- |
| 填写：模块名 | 填写：行为描述 | 填写：触发方式 | 填写：输出或状态变化 | 填写：测试、截图或文档链接 |

## 4. 技术与依赖

| 字段 | 填写内容 |
| --- | --- |
| 主语言与版本约束 | 填写：例如 `Go >= 1.22` |
| 框架与构建工具 | 填写：名称与版本约束 |
| 运行时与系统要求 | 填写：操作系统、运行时、浏览器或数据库版本 |
| 依赖清单 | 填写：依赖清单文件路径，或在本节插入附录 C 表格 |
| 外部素材 | 填写：字体、图片、图标、数据集合的来源与许可证 |

## 5. 交付与使用

| 字段 | 填写内容 |
| --- | --- |
| 环境要求 | 填写：安装前必须具备的条件 |
| 安装命令 | 填写：包含当前工作目录说明的完整命令 |
| 验证命令与预期输出 | 填写：可直接执行的命令与可核对的结果 |
| 升级与卸载方式 | 填写：命令或操作步骤 |
| 配置项清单 | 填写：键名、类型、默认值、必填、取值范围、作用 |
| API 或模块说明 | 填写：接口签名、参数、返回值、错误码、调用示例 |
| 兼容性矩阵 | 填写：明确支持与不支持的版本组合 |
| 性能数据 | 填写：测试环境、方法、指标与瓶颈；无数据则写「未提供，不得推断」 |

## 6. 风险与边界

| 字段 | 填写内容 |
| --- | --- |
| 已知问题 | 填写：描述、影响范围、临时规避方案、跟踪链接 |
| 当前限制 | 填写：明确当前版本做不到的事 |
| 未实现功能 | 填写：功能、未实现原因、计划状态 |
| 安全与隐私 | 填写：数据收集、存储、传输、权限模型、已知风险 |
| 漏洞上报渠道 | 填写：邮箱、Issue 模板或专用地址 |

## 7. 合规与责任

| 字段 | 填写内容 |
| --- | --- |
| 许可证类型 | 填写：SPDX 标识符，例如 `MIT` |
| 著作权人 | 填写：个人姓名或组织全称 |
| 著作权年份 | 填写：年份或年份区间 |
| 许可证全文位置 | 填写：LICENSE 文件路径 |
| NOTICE 文件路径 | 填写：NOTICE 文件路径；无第三方依赖时写「不适用，原因：……」 |
| 免责声明 | 填写：责任边界或不担保条款的采用情况 |

## 8. 待确认事项汇总

| 编号 | 字段 | 缺失内容 | 补充责任人 | 计划补齐时间 | 影响范围 |
| --- | --- | --- | --- | --- | --- |
| T-001 | 填写：字段名 | 填写：具体缺什么 | 填写：姓名或角色 | 填写：YYYY-MM-DD | 填写：受影响的章节或门禁 |

## 9. 关联规范
````
