# 提交信息规范

> 本文件解决什么问题：定义 Conventional Commits 的字段、格式、填写说明与示例，保证历史可读、可自动生成变更日志与版本号。

## 1. 格式

```text
<类型>[可选作用域][可选 !]: <描述>

[可选正文]

[可选脚注]
```

## 2. 类型

完整的十类类型如下，覆盖常见开源项目的提交场景：

| 类型 | 含义 |
| --- | --- |
| `feat` | 新增功能 |
| `fix` | 修复缺陷 |
| `docs` | 文档变更 |
| `style` | 格式调整，不改变逻辑（空白、格式化、缺少分号等） |
| `refactor` | 重构，不新增功能也不修复缺陷 |
| `perf` | 性能优化的代码变更 |
| `test` | 添加缺失测试或更正现有测试 |
| `build` | 影响构建系统或外部依赖的变更（如 npm、gulp） |
| `ci` | 持续集成配置与脚本的变更（如 GitHub Actions、CircleCI） |
| `chore` | 构建、依赖、工具链等杂项 |

### 2.1 团队写法的对照与取舍

不同协作模式下存在三种常见写法，项目应在立项时选定一种并全队统一：

| 写法 | 格式 | 适用 | 局限 |
| --- | --- | --- | --- |
| 工作写法 | `[任务卡号] 作者: 修改内容` | 使用看板、结对编程的团队 | 依赖任务卡号体系，无卡号时不适用 |
| 常规写法 | `[分类] 组件（可选）: 修改内容` | 需要按业务模块筛选历史的团队 | 需团队约定分类表，有额外成本 |
| 开源写法 | `<type>(<scope>): <subject>` | 开源库与应用，需自动生成 CHANGELOG | 类型与作用域较多，学习成本较高 |

本项目统一采用开源写法（即 Conventional Commits），理由：机器可读，可自动生成变更日志与版本号。工作写法与常规写法仅在闭源团队中按约定使用，不得混入对外仓库。

## 3. 字段定义

| 字段 | 必填 | 类型 | 填写要点 | 示例 |
| --- | --- | --- | --- | --- |
| 类型 | 是 | 枚举 | 十类之一，不得自创 | `feat` |
| 作用域 | 否 | 文本 | 模块名，小写短词，不含空格 | `parser` |
| 破坏性标记 | 否 | `!` | 置于类型或作用域之后、冒号之前 | `feat!:` |
| 描述 | 是 | 文本 | 祈使句、小写开头、≤72 字符、结尾无句号 | `add TOML config support` |
| 正文 | 否 | 文本 | 说明动机与实现，与描述空一行 | `Allow the parser to read TOML...` |
| 脚注 | 否 | 文本 | `BREAKING CHANGE:` 或 `Refs: #N` | `BREAKING CHANGE: ...` |
| 关联需求 | 否 | `REQ-NNN` | 写入正文或脚注，便于追踪 | `Refs: REQ-001` |

## 4. 填写说明

1. **描述**：使用祈使句（add、fix、remove），写「做了什么」而非「做了修改」；中文项目可写中文描述，但须全仓库统一。
2. **作用域**：取模块名而非文件名；跨模块变更省略作用域，不写 `all` 或 `global`。
3. **正文**：仅在描述不足以说明动机时写；不复述描述，不写过程流水账。
4. **破坏性变更**：`feat!:` / `fix!:` 与 `BREAKING CHANGE:` 脚注二选一或并用；二者出现时，须同步写入 [变更日志规范](./变更日志规范.md) 与 [迁移指南规范](./迁移指南规范.md)。
5. **原子性**：一次提交只做一件事；格式化与逻辑变更分两次提交。
6. **安全**：不得包含密钥、令牌、个人信息、内部地址；提交前用密钥扫描核对（见 [安全与隐私规范](./安全与隐私规范.md)）。
7. **版本联动**：`feat` 触发次版本递增，`fix` 触发修订版本递增，`BREAKING CHANGE` 触发主版本递增，详见 [版本管理规范](./版本管理规范.md)。

常见错误：

| 错误写法 | 问题 | 修正方式 |
| --- | --- | --- |
| `wip`、`update`、`fix bug` | 无信息量，违反 H10 | 写明对象与行为 |
| `feat: Added new feature.` | 非祈使句、大写开头、有句号 | `feat: add config loader` |
| `feat(全部): 优化` | 作用域无效、描述模糊 | 用具体模块名并写明改动 |
| 一次提交含格式化与功能变更 | 破坏原子性 | 拆为 `style:` 与 `feat:` 两次提交 |
| 提交信息含内网地址 | 信息泄漏 | 移除并走密钥扫描 |

## 5. 完整示例

```text
feat(parser): add support for TOML config

Allow the parser to read TOML configuration files in addition to YAML.
Refs: REQ-001

BREAKING CHANGE: the `config` option now accepts a file path instead of an object.
```

各字段含义：`feat` 为类型，`parser` 为作用域，冒号后为简短描述；正文说明动机与实现，脚注关联需求；末尾脚注声明破坏性变更并给出迁移方向。

修复类示例：

```text
fix(spacing): avoid false positives before Chinese punctuation

The spacing rule previously flagged strings such as 「使用Node.js，」 because
the punctuation check ran after whitespace normalization.

Refs: REQ-004, #142
```
