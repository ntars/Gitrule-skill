# 代码审查规范

> 本文件解决什么问题：定义拉取请求的描述模板、审查意见模板、审查记录、字段与流程，保证合并质量与知识共享。

## 1. 规范条文

1. 作者须在 PR 描述中说明变更目的、影响范围与自测结果，模板见 [Git工作流与分支规范](./Git工作流与分支规范.md)。
2. 审查者须给出具体、可执行的意见，区分「必须修改」与「建议」。
3. 合并前须至少有 1 名审查者批准，CI 全绿（对应硬规则 H9）；禁止作者自行批准自己的 PR。
4. 审查意见有分歧时升级至维护者裁定（见 [行为准则规范](./行为准则规范.md)）。
5. 合并后删除源分支，保持分支列表整洁。

## 2. 审查清单

审查者须逐项确认：

| # | 维度 | 检查要点 | 判定 |
| --- | --- | --- | --- |
| 1 | 正确性 | 逻辑正确，边界与异常已处理 | 通过 / 需修改 |
| 2 | 测试 | 变更有对应测试，测试通过 | 通过 / 需修改 |
| 3 | 风格 | 符合 [代码风格规范](./代码风格规范.md) | 通过 / 需修改 |
| 4 | 安全 | 无敏感信息、无注入风险、权限校验正确 | 通过 / 需修改 |
| 5 | 文档 | 接口或行为变更已同步文档 | 通过 / 需修改 |
| 6 | 范围 | 变更聚焦，无无关改动 | 通过 / 需修改 |
| 7 | 提交信息 | 符合 [提交信息规范](./提交信息规范.md) | 通过 / 需修改 |
| 8 | 追踪 | 需求追踪矩阵已更新 | 通过 / 需修改 |

## 3. 审查意见模板

```markdown
### 意见 {{序号}}：{{一句话标题}}

- 级别：{{必须修改 / 建议 / 提问}}
- 位置：{{文件路径:行号}}
- 问题：{{描述可观察的问题，不评价人}}
- 依据：{{规范条款 / 需求编号 / 风险说明}}
- 建议：{{具体的修改方式或替代方案}}

示例：
### 意见 1：异常分支未覆盖
- 级别：必须修改
- 位置：`src/rules/spacing.ts:42`
- 问题：当输入含不完整 Markdown 时抛出异常，未返回规则命中结果。
- 依据：REQ-001 验收条件第 2 条（边界路径）。
- 建议：在此处捕获解析异常并按「解析失败」返回命中，补一条边界用例。
```

## 4. 审查记录模板

```markdown
## 审查记录：{{PR 编号}}

审查者：{{姓名}} ｜ 审查日期：{{YYYY-MM-DD}} ｜ 轮次：{{第 N 轮}}

| 意见编号 | 级别 | 处理结论 | 处理人 | 验证方式 |
| --- | --- | --- | --- | --- |
| 1 | 必须修改 | 已修改 | 作者 | 见提交 abc1234 |
| 2 | 建议 | 不采纳 | 作者 | 理由：{{说明}} |

结论：{{批准 / 需修改后再审 / 拒绝}}
- 批准条件：全部「必须修改」项已处理，CI 全绿。
- 未决项：{{无 / 列出}}
```

## 5. 字段定义

| 字段 | 必填 | 类型 | 填写要点 | 示例 |
| --- | --- | --- | --- | --- |
| 级别 | 是 | 枚举 | 必须修改 / 建议 / 提问 | `必须修改` |
| 位置 | 是 | `路径:行号` | 精确到行，禁止只写文件名 | `src/parser.ts:42` |
| 问题 | 是 | 文本 | 描述现象，不评价作者 | `解析异常未捕获` |
| 依据 | 是 | 文本 | 规范条款或 REQ 编号 | `REQ-001 验收条件 2` |
| 建议 | 是 | 文本 | 可执行，不只说「请优化」 | `捕获异常并返回命中` |
| 处理结论 | 是 | 枚举 | 已修改 / 不采纳 / 延后 | `已修改` |
| 验证方式 | 是 | 文本 | 提交哈希或复核方式 | `见提交 abc1234` |
| 结论 | 是 | 枚举 | 批准 / 需修改后再审 / 拒绝 | `批准` |

## 6. 填写说明

1. **级别区分**：「必须修改」指阻断合并的问题（正确性、安全、测试缺失）；「建议」不影响合并；「提问」须作者澄清但不要求改动。
2. **意见表述**：描述可观察问题，禁止「这里写得很差」等评价性语言。
3. **位置**：精确到行号；跨文件问题在每条意见中分别标注。
4. **依据**：能追溯则追溯；无规范依据时写明风险或影响，禁止「我觉得」。
5. **处理结论**：「不采纳」须写理由；「延后」须写明后续跟踪位置。
6. **批准**：确认全部「必须修改」项已闭环，且 CI 全绿；作者不得自批自己的 PR。
7. **分歧**：审查者与作者意见不一致时升级维护者，裁定结论写入审查记录。

常见错误：

| 错误写法 | 问题 | 修正方式 |
| --- | --- | --- |
| 「这里不行」 | 无问题、无依据、无建议 | 补三要素 |
| 「建议优化一下性能」 | 不可执行 | 给出具体做法与判定指标 |
| 只写文件名不写行号 | 定位困难 | 精确到行 |
| 作者自行批准 | 违反规定 | 由他人审查 |
| 「必须修改」用于个人偏好 | 级别滥用 | 降级为「建议」 |

## 7. 完整示例

```markdown
## 审查记录：#12

审查者：李四 ｜ 审查日期：2026-11-18 ｜ 轮次：第 1 轮

| 意见编号 | 级别 | 处理结论 | 处理人 | 验证方式 |
| --- | --- | --- | --- | --- |
| 1 | 必须修改 | 已修改 | 王五 | 见提交 a1b2c3d |
| 2 | 建议 | 不采纳 | 王五 | 理由：当前 QPS 未达瓶颈，避免过度设计 |
| 3 | 提问 | 已澄清 | 王五 | 已在 PR 正文补充说明 |

结论：批准
- 批准条件：全部「必须修改」项已处理，CI 全绿（run #128）。
- 未决项：无
```
