# 项目立项与需求规范

> 本文件解决什么问题：定义立项阶段的目标陈述、需求采集与范围界定的模板与字段，确保项目从一开始就有清晰、可验证、可追溯的依据。

## 1. 规范条文

1. 立项文档须回答六问：是什么、为什么做、做到什么程度、不给谁用、谁在用、受什么限制。
2. 需求须区分「必须 / 应当 / 可以」三级，用语约定见 [通用写作规范](./通用写作规范.md)。
3. 每条需求须可验证：以 Given/When/Then 给出验收条件，或给出可判定的度量阈值。
4. 每条需求须有稳定编号与来源，禁止无编号的需求条目。
5. 信息不足时标注「【待确认：字段名】」，不得猜测填充，规则见 [信息采集与模板](./信息采集与模板.md)。
6. 范围须同时写明纳入项与排除项；非目标为空视为范围未界定。
7. 范围变更须记录原因、影响与决策人，并进入 [需求追踪矩阵规范](./需求追踪矩阵规范.md) 的变更记录。

## 3. 需求条目模板

```markdown
### REQ-{{三位序号}}：{{需求标题}}

- 来源：{{工单号 / 访谈 / 竞品 / 推测}}
- 优先级：{{必须 / 应当 / 可以}}
- 关联目标：{{G1 / G2 / …}}
- 用户故事：作为{{角色}}，我希望{{行为}}，以便{{价值}}
- 验收条件：
  1. Given {{前置条件}}
     When {{操作}}
     Then {{预期结果}}
  2. Given {{边界或异常前置条件}}
     When {{操作}}
     Then {{预期结果}}
- 状态：{{待确认 / 已确认 / 已实现 / 已验证 / 已废弃}}
- 关联追踪：{{见需求追踪矩阵中的需求 ID}}
```

## 4. 字段定义

### 4.1 立项书字段

| 字段 | 必填 | 类型 | 填写要点 | 示例 |
| --- | --- | --- | --- | --- |
| 文档版本 | 是 | 文本 | 语义化版本或日期版本 | `v0.1` |
| 状态 | 是 | 枚举 | 草稿 / 评审中 / 已批准 | `评审中` |
| 决策人 | 是 | 文本 | 对范围与优先级有最终决定权的人 | `张三` |
| 一句话定位 | 是 | 文本 | 目标用户 + 核心能力 + 痛点，≤60 字 | 为的前端开发者提供… |
| 立项依据 | 是 | 文本 | 至少一条可溯源记录，禁止「团队决定」 | `ISSUE-142` |
| 目标 / 非目标 | 是 | 表格 | 每条目标配对可验证结果；非目标至少一条 | `G1：冷启动 <2s` |
| 成功标准 | 是 | 表格 | 指标须有基线、阈值、测量方式与时间 | `错误率 <0.1%` |
| 约束条件 | 是 | 列表 | 四类均须填写，无则写「无」 | `须兼容 Node 18+` |
| 待确认 | 否 | 列表 | 仅用【待确认：字段名】格式 | `【待确认：预算上限】` |

### 4.2 需求条目字段

| 字段 | 必填 | 类型 | 填写要点 | 示例 |
| --- | --- | --- | --- | --- |
| 编号 | 是 | `REQ-NNN` | 三位序号，连续、不复用、不重排 | `REQ-007` |
| 来源 | 是 | 文本 | 可追溯到具体记录 | `用户访谈 #3` |
| 优先级 | 是 | 枚举 | 必须 / 应当 / 可以 | `必须` |
| 关联目标 | 是 | 列表 | 对应立项书的 G 编号 | `G1` |
| 用户故事 | 是 | 文本 | 角色 + 行为 + 价值三要素齐全 | 作为…我希望…以便… |
| 验收条件 | 是 | 列表 | 至少 1 组 Given/When/Then，须含边界或异常 | 见模板 |
| 状态 | 是 | 枚举 | 五态之一，仅前进不回退 | `已确认` |

## 5. 填写说明

1. **一句话定位**：按「为谁 + 提供什么 + 解决什么」三段式写；若删掉修饰语后句子不成立，说明缺少实质信息。
2. **成功标准**：每条须同时具备基线与阈值。「提升性能」「体验更好」判定为不合格，须改为「P95 启动耗时由 3s 降至 <1.5s」。
3. **非目标**：写明明确排除的范围与判定边界，而非「以后再说」；无非空非目标时，视为范围未界定。
4. **需求编号**：一经分配永久固定；需求废弃时状态改为「已废弃」，编号不得回收或重用。
5. **验收条件**：须覆盖正常路径与至少一条边界或异常路径；无法客观判定的条件（如「界面美观」）须转换为可验证的度量或检查项。
6. **待确认项**：立项允许存在待确认项，但须列全并指定确认人；进入开发前须清零。

常见错误：

| 错误写法 | 问题 | 修正方式 |
| --- | --- | --- |
| 「做一个好用的工具」 | 无目标用户、无可验证结果 | 补用户角色与阈值指标 |
| 非目标写「无」 | 范围未界定，易蔓延 | 列出本期明确排除项 |
| 需求无编号，正文直接描述 | 无法追踪与引用 | 分配 `REQ-NNN` 并全域引用 |
| 验收条件写「功能正常」 | 不可判定 | 拆为 Given/When/Then |
| 推测内容当作既定需求 | 来源不可溯 | 标注来源为「推测」并转待确认 |

## 6. 完整示例

```markdown
# 项目立项书：markdown-lint-cli

文档版本：v0.1 ｜ 状态：评审中 ｜ 决策人：李四 ｜ 日期：2026-11-18

## 一句话定位
为中文技术写作者提供命令行 Markdown 规范检查工具，解决多仓库文档风格不一致且无自动校验的问题。

## 背景与动机
- 现状：12 个仓库的 README 由各维护者手写，风格不统一。
- 现有方案不足：通用英文 lint 工具不支持中英文空格规则；人工评审平均耗时 25 分钟/篇。
- 机会窗口：团队正统一开源首页，需一次性实施规范。
- 立项依据：ISSUE-142、2026-11-10 文档评审纪要。

## 目标与非目标
| 类型 | 条目 | 可验证结果 |
| --- | --- | --- |
| 目标 G1 | 自动检查 8 类格式问题 | 对 50 篇样本文档检出率 ≥95% |
| 目标 G2 | 单次检查耗时可控 | 1000 行文档检查 <2s |
| 非目标 N1 | 不提供文档内容润色 | 仅输出规则命中位置，不改写文本 |

## 成功标准
| 指标 | 基线 | 目标值 | 验证方式 | 验证时间 |
| --- | --- | --- | --- | --- |
| 人工评审耗时 | 25 分钟/篇 | <5 分钟/篇 | 5 名维护者对照实验 | v1.0 发布前 |

### REQ-001：检查中英文混排空格
- 来源：ISSUE-142
- 优先级：必须
- 关联目标：G1
- 用户故事：作为文档维护者，我希望自动标出中英文间缺失的空格，以便统一排版。
- 验收条件：
  1. Given 文档含「使用Node.js开发」
     When 执行检查
     Then 输出该行行号与「中英文间缺少空格」提示
  2. Given 文档该处已有空格
     When 执行检查
     Then 不输出该规则命中
- 状态：已确认
```
