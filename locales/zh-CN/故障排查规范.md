# 故障排查规范

> 本文件解决什么问题：定义故障排查文档（Troubleshooting / FAQ）的结构、条目写法与维护机制，使使用者能按现象定位原因并自行解决常见问题。

## 1. 适用场景

以下情况须提供故障排查文档：

1. 安装或构建失败存在多种常见原因。
2. 配置项之间存在冲突，错误提示不足以说明解决方法。
3. 特定平台或版本存在已知限制。
4. 用户反复提出同类问题，且答案可标准化。

## 2. 文件位置与命名

1. 内容较少时，作为 README 的一个章节，标题为「常见问题」或「故障排查」。
2. 内容较多时，单独建 `docs/troubleshooting.md` 或 `FAQ.md`，README 保留入口链接。
3. 问题按主题分组，如「安装」「配置」「运行」「性能」「网络」。

## 3. 文档结构

1. **开头说明**：本文档覆盖的常见问题范围与适用版本。
2. **问题索引**：按主题列出问题标题，支持快速跳转。
3. **问题条目**：按统一结构逐条展开。
4. **仍无法解决**：指向 issue、讨论区等求助渠道。

## 4. 条目结构

每个问题条目须包含以下部分：

| 部分 | 内容 | 要求 |
| --- | --- | --- |
| 现象 | 用户看到的具体表现 | 含完整错误信息，不得只写「报错」 |
| 触发条件 | 何时出现 | 明确版本、平台、操作 |
| 原因 | 根本原因 | 说明机制，不止给出结论 |
| 解决方案 | 可执行步骤 | 编号列出，含命令或配置 |
| 验证 | 如何确认已修复 | 给出预期输出 |
| 关联 | 相关文档或 issue 链接 | 可选 |

## 5. 条目写法示例

```markdown
### 安装时提示 `EACCES: permission denied`

**现象**：执行 `npm install -g <package>` 时提示权限不足。

**触发条件**：在 Linux 或 macOS 下以普通用户安装全局包。

**原因**：全局安装目录的写权限属于系统管理员，当前用户无权写入。

**解决方案**：

```bash
mkdir -p ~/.npm-global
npm config set prefix '~/.npm-global'
export PATH=~/.npm-global/bin:$PATH
npm install -g <package>
```

**验证**：执行 `<package> --version` 输出版本号即成功。

## 6. 写作要求

1. 问题标题使用用户会搜索的表述，而非内部术语。
2. 错误信息原样保留，便于用户比对；敏感信息须脱敏（见 [安全与隐私规范](./安全与隐私规范.md)）。
3. 解决方案给出完整命令，不假设用户已设置环境变量。
4. 一个条目只解决一个问题，不合并多种原因。
5. 涉及已知缺陷时，说明影响范围与规避方式，不承诺修复时间。
6. 与迁移相关的问题链接到迁移指南（见 [迁移指南规范](./迁移指南规范.md)）。

## 7. 维护机制

1. 同一问题被重复提问三次以上时，须新增或改写条目。
2. 版本升级后复核全部条目，删除已失效内容。
3. 每个条目可标注最后验证的版本，便于判断是否仍适用。
4. 问题索引随条目增减同步更新。

## 8. 禁止事项

1. 禁止把故障排查文档写成功能介绍。
2. 禁止只写「重启试试」等无诊断价值的答案。
3. 禁止省略错误信息与触发条件。
4. 禁止保留已修复或已失效的条目。
