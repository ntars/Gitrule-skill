# 程式碼所有權規範

> 本檔案解決什麼問題：定義 `.github/CODEOWNERS` 檔案的語法、所有權分配與審查路由規則，使每個變更自動分配給具備責任的審查者。

## 1. 設計原則

1. **路徑到人的明確對映**：每條規則指明某路徑由誰負責，避免無人審查或重複審查。
2. **最小必要 owners**：單個路徑的所有者控制在 1–3 人，過多導致責任分散。
3. **預設承接**：設定全域性預設所有者，覆蓋未被顯式規則匹配的路徑。
4. **與團隊結構同步**：成員變更時及時更新，避免失效賬號阻塞審查。

## 2. 檔案位置與語法

### 2.1 路徑

`CODEOWNERS` 檔案可置於以下任一位置，按優先順序取第一個命中：

1. 倉庫根目錄 `CODEOWNERS`；
2. `docs/CODEOWNERS`；
3. `.github/CODEOWNERS`（推薦）。

### 2.2 語法規則

```text
# 注释以 # 开头
<路径模式>  <所有者>  [<所有者>...]
```

- 每行一條規則，路徑模式後跟一個或多個所有者。
- 所有者格式為 `@用户名` 或 `@组织/团队`。
- 使用郵箱作為所有者須與 GitHub 賬號關聯。
- 路徑區分大小寫，支援萬用字元 `*`、`**`。

### 2.3 示例

```text
# 默认所有者
*                       @org/maintainers

# 按目录分配
/src/core/              @org/core-team
/src/api/               @org/api-team @alice
/docs/                  @org/docs-team

# 按文件类型分配
*.md                    @org/docs-team
/.github/workflows/      @org/devops-team
```

## 3. 匹配規則

1. 僅最後一條匹配規則生效，不累加；因此通用規則須寫在前面，特殊規則寫在後面。
2. 目錄規則匹配該目錄及其子目錄，除非以 `/` 開頭限定根路徑。
3. 規則順序決定優先順序，須從寬到窄排列。
4. 無匹配路徑由預設所有者承擔審查責任。

## 4. 所有權分配策略

| 維度 | 分配依據 |
| --- | --- |
| 目錄 | 按模組或子系統邊界分配 |
| 檔案型別 | 文件、配置、測試可按型別統一分配 |
| 關鍵路徑 | 安全、釋出、CI 配置由核心維護者獨佔 |
| 新成員 | 先以非必需審查者身份參與，熟悉後轉正式所有者 |

## 5. 與審查流程的聯動

1. PR 建立時，GitHub 自動請求匹配路徑的所有者審查。
2. 必需審查要求透過分支保護規則配置，見 [Git工作流與分支規範](./Git工作流與分支規範.md)。
3. 所有者應在約定時限內響應，超時由預設所有者承接。
4. 所有者變更須同步更新檔案，避免失效賬號阻塞流程（見 [程式碼審查規範](./程式碼審查規範.md)）。

## 6. 維護要求

1. 每次組織架構或團隊職責變更後複核一次。
2. 倉庫移交、成員離場須立即移除對應所有者。
3. 檔案變更須經至少一名現有所有者審查，防止許可權自行擴散。
4. 不得將所有者指向不活躍賬號或機器人賬號（自動化專用除外）。

## 7. 禁止事項

1. 禁止使用過寬的通配規則導致所有人都是所有者。
2. 禁止將敏感路徑（釋出、金鑰配置）分配給無審查能力的成員。
3. 禁止在檔案中寫入私人聯絡方式。
4. 禁止長期保留已離職成員的所有者身份。
