# 架構設計文件規範

> 本檔案解決什麼問題：定義架構文件與架構決策記錄（ADR）的模板、欄位與寫法，說明系統邊界、模組職責、質量屬性與關鍵取捨，並保證決策可追溯。

## 1. 規範條文

1. 架構文件（`docs/architecture.md`）只描述結構與邊界，不含使用示例，職責邊界見 [文件矩陣](./文件矩陣.md)。
2. 每條重大技術決策須有對應 ADR；無 ADR 的決策視為未記錄決策。
3. ADR 編號連續、永久固定；一旦採納不改寫歷史，狀態變更透過新增 ADR 記錄並標註「被替代」。
4. 架構描述須與程式碼實現保持一致；程式碼與文件不一致時以程式碼為準並立即修訂文件。
5. 每條架構決策須能回溯到一條或多條需求，追蹤關係見 [需求追蹤矩陣規範](./需求追蹤矩陣規範.md)。
6. 質量屬性須給出可驗證的度量目標，禁止僅寫「高效能」「高可用」。

## 2. 架構文件模板

```markdown
# 架構設計：{{项目名称}}

文件版本：{{v1.0}} ｜ 對應程式碼版本：{{tag}} ｜ 最後核對日期：{{YYYY-MM-DD}}

## 系統上下文
- 系統職責：{{一句话说明系统边界内的责任}}
- 外部參與者：{{用户、上游系统、下游系统}}
- 輸入輸出：{{进入系统的请求与系统产出的结果}}
- 邊界之外：{{明确不由本系统承担的职责}}

## 模組劃分
| 模組 | 唯一職責 | 對外介面 | 依賴模組 | 不負責 |
| --- | --- | --- | --- | --- |
| {{模块名}} | {{仅一件事}} | {{接口名}} | {{模块名}} | {{明确排除}} |

## 關鍵資料流
1. {{触发点}} → {{模块 A}}：{{传递的数据}}
2. {{模块 A}} → {{模块 B}}：{{转换与传递}}
3. {{模块 B}} → {{结果}}：{{最终产出}}

## 技術選型
| 領域 | 選型 | 備選 | 決策依據 | ADR |
| --- | --- | --- | --- | --- |
| {{语言 / 框架 / 存储}} | {{采用项}} | {{未采用项}} | {{取舍理由}} | {{ADR-000N}} |

## 質量屬性
| 屬性 | 目標值 | 驗證方式 | 關聯 ADR |
| --- | --- | --- | --- |
| 效能 | {{P95 延迟 < X ms}} | {{压测方式}} | {{ADR-000N}} |
| 可用性 | {{月度可用性 ≥ X%}} | {{监控统计}} | {{ADR-000N}} |
| 安全 | {{敏感数据零明文落盘}} | {{审计方式}} | {{ADR-000N}} |
| 可擴充套件性 | {{横向扩容至 N 节点无需改代码}} | {{扩容演练}} | {{ADR-000N}} |

## 約束與取捨
- 技術約束：{{语言版本、平台、兼容性}}
- 已放棄方案及原因：{{方案 A：原因}}
- 已知技術債：{{债务项与偿还条件}}
```

## 3. ADR 模板

```markdown
# ADR-{{四位序号}}：{{决策标题}}

- 狀態：{{提议 / 已采纳 / 已废弃 / 被 ADR-000N 替代}}
- 日期：{{YYYY-MM-DD}}
- 決策人：{{姓名}}
- 關聯需求：{{REQ-001 / …}}

## 背景
{{面临的客观问题与约束，须可验证，不写主观偏好}}

## 決策
{{采用的方案，一句话陈述，须明确到可执行的程度}}

## 備選方案
| 方案 | 優點 | 缺點 | 未採用原因 |
| --- | --- | --- | --- |
| {{方案 A}} | | | |
| {{方案 B（采用）}} | | | — |

## 後果
- 正面：{{获得的能力}}
- 負面：{{引入的成本或限制}}
- 後續任務：{{需要跟进的事项}}

## 相關檔案
- {{架构文档中受影响的章节}}
- {{替代或被引用的 ADR}}
```

## 4. 欄位定義

### 4.1 架構文件欄位

| 欄位 | 必填 | 型別 | 填寫要點 | 示例 |
| --- | --- | --- | --- | --- |
| 對應程式碼版本 | 是 | tag | 與 [版本管理規範](./版本管理規範.md) 的 tag 一致 | `v1.2.0` |
| 最後核對日期 | 是 | 日期 | 每次程式碼變更後須更新 | `2026-11-18` |
| 模組唯一職責 | 是 | 文字 | 一個模組只寫一件事 | `解析并校验 Markdown 规则` |
| 不負責 | 是 | 文字 | 明確邊界，防止職責漂移 | `不负责文本改写` |
| 技術選型.決策依據 | 是 | 文字 | 須引用 ADR 編號 | `见 ADR-0002` |
| 質量屬性.目標值 | 是 | 度量 | 含單位與閾值，可驗證 | `P95 < 150ms` |
| 已知技術債 | 否 | 列表 | 寫明償還觸發條件 | `待 v2 替换解析器` |

### 4.2 ADR 欄位

| 欄位 | 必填 | 型別 | 填寫要點 | 示例 |
| --- | --- | --- | --- | --- |
| 編號 | 是 | `ADR-NNNN` | 四位序號，連續、永久固定 | `ADR-0002` |
| 狀態 | 是 | 列舉 | 提議 / 已採納 / 已廢棄 / 被替代 | `已采纳` |
| 關聯需求 | 是 | 列表 | 對應立項書的 REQ 編號 | `REQ-001` |
| 背景 | 是 | 文字 | 陳述客觀約束，禁止「我覺得」 | `需兼容 Node 18` |
| 決策 | 是 | 文字 | 一句話、可執行 | `采用 remark 作为解析器` |
| 備選方案 | 是 | 表格 | 至少包含 1 個未採用方案 | 見模板 |
| 否定理由 | 是 | 文字 | 每個未採用方案均須給出 | 見模板 |
| 後果 | 是 | 列表 | 正面、負面、後續任務三項齊全 | 見模板 |

## 5. 填寫說明

1. **模組劃分**：每行的「唯一職責」若出現「和」「以及」連線的兩件事，應拆為兩個模組。
2. **資料流**：按時間順序編號，標明傳遞的資料內容，禁止只寫模組名箭頭。
3. **質量屬性**：每條須有目標值、驗證方式與 ADR 引用；缺任一者視為不完整。
4. **ADR 背景**：寫問題與約束，不寫決策本身；決策只在「決策」段出現一次。
5. **備選方案**：即使只有一種方案，也須寫明「考慮過自行實現，因維護成本過高未採用」；無備選視為未充分論證。
6. **狀態變更**：不修改原 ADR 正文，新建 ADR 並將原文狀態改為「被 ADR-000N 替代」。
7. **技術債**：須寫償還觸發條件，禁止只列現象。

常見錯誤：

| 錯誤寫法 | 問題 | 修正方式 |
| --- | --- | --- |
| 架構文件裡放 API 呼叫示例 | 與 [API文件規範](./API文件規範.md) 職責重疊 | 移到 API 文件，架構只留介面名 |
| 「系統需高效能」 | 無閾值、不可驗證 | 給出 P95 延遲目標與壓測方式 |
| ADR 只有決策沒有備選 | 未論證 | 補至少 1 個未採用方案及原因 |
| 修改已採納 ADR 的正文 | 歷史被改寫 | 新建 ADR 標註替代關係 |
| 決策無法關聯需求 | 追溯鏈斷裂 | 補關聯 REQ 編號 |

## 6. 完整示例

```markdown
# ADR-0002：採用 remark 作為 Markdown 解析層

- 狀態：已採納
- 日期：2026-11-18
- 決策人：李四
- 關聯需求：REQ-001、REQ-004

## 背景
需支援 GFM 與中文文字節點定位，且執行時依賴須相容 Node 18；團隊維護解析器的人力上限為 0.5 人月/季度。

## 決策
採用 remark 生態作為唯一 Markdown 解析層，規則以外掛形式實現。

## 備選方案
| 方案 | 優點 | 缺點 | 未採用原因 |
| --- | --- | --- | --- |
| 自研解析器 | 完全可控 | 需長期維護邊界用例 | 超出人力上限 |
| marked | 輕量 | 中文節點定位能力弱 | 不滿足 REQ-004 |

## 後果
- 正面：GFM 相容性由上游維護，節點定位滿足驗收條件。
- 負面：外掛 API 變更需跟進上游版本。
- 後續任務：在 CI 中鎖定 remark 主版本並訂閱 its release 通知。
```
