# 遷移指南規範

> 本檔案解決什麼問題：定義破壞性變更時遷移指南的結構、內容要素與釋出時機，使使用者能夠按步驟從舊版本平滑升級到新版本。

## 1. 觸發條件

出現以下任一情況須提供遷移指南：

1. 提交資訊含 `BREAKING CHANGE:` 或 `feat!:` / `fix!:`（見 [提交資訊規範](./提交資訊規範.md)）。
2. 配置鍵名、預設值或優先順序發生變化。
3. API 簽名、返回結構或錯誤碼發生變化。
4. 最低執行時版本提升，或不再支援某平臺。
5. 目錄結構或檔案命名發生變更，影響使用者引用路徑。

## 2. 檔案位置與命名

1. 改動較小的遷移說明寫入 `CHANGELOG.md` 對應版本的條目中。
2. 改動較大、涉及多步驟操作時，單獨建 `docs/migration/` 目錄下的檔案，按版本命名，如 `docs/migration/v2.md`。
3. 跨大版本的完整遷移路徑在 `docs/migration/README.md` 中建立索引。
4. README 只放遷移提示與連結，不展開步驟（見 [文件矩陣](./文件矩陣.md)）。

## 3. 文件結構

遷移指南須按以下順序組織：

1. **標題與版本**：標明源版本與目標版本，如「從 v1.x 遷移到 v2.0」。
2. **影響概覽**：列出變更類別與影響範圍，說明哪些使用者必須遷移。
3. **前置條件**：遷移前須完成的準備，如備份、環境版本升級。
4. **變更清單**：逐項列出破壞性變更，每項包含「舊行為」「新行為」「變更原因」。
5. **遷移步驟**：編號列出可執行的操作，給出命令或程式碼示例。
6. **驗證方式**：遷移後如何確認成功，給出檢查命令或預期輸出。
7. **回滾方式**：遷移失敗時如何恢復到舊版本。
8. **常見問題**：列出高頻問題與解答。
9. **獲取幫助**：指向 issue、討論區或文件站。

### 3.1 可複製空白模板

下列模板逐項對應第 3 節的九項結構，複製後替換佔位符即可使用：

````markdown
# 從 {{源版本}} 遷移到 {{目标版本}}

> 本指南說明從 {{源版本}} 升級至 {{目标版本}} 所需的全部操作，適用於 {{适用使用者范围}}。

## 1. 影響概覽

| 變更類別 | 具體內容 | 影響範圍 | 是否必須遷移 |
| --- | --- | --- | --- |
| {{变更类别}} | {{变更内容}} | {{受影响的使用者场景}} | {{是否必须迁移}} |

## 2. 前置條件

- {{前置准备}}
- {{检查项与确认命令}}

## 3. 變更清單

### {{变更项名称}}

- 舊行為：{{旧版本行为}}
- 新行為：{{新版本行为}}
- 變更原因：{{变更原因}}

遷移前：

```{{代码语言}}
{{旧配置或旧代码}}
```

遷移後：

```{{代码语言}}
{{新配置或新代码}}
```

## 4. 遷移步驟

1. {{迁移步骤}}
2. {{迁移步骤}}
3. {{人工处理步骤}}

## 5. 驗證方式

```bash
{{可独立运行的检查命令}}
```

預期輸出：{{预期结果}}

## 6. 回滾方式

1. {{恢复旧版本的操作}}
2. {{恢复旧配置的操作}}

## 7. 常見問題

### {{问题}}

答：{{解答}}

## 8. 獲取幫助

- 問題反饋：{{issue 地址}}
- 討論區：{{讨论区地址}}
- 相關文件：{{文档链接}}
````

佔位符對照：

| 佔位符 | 必填 | 填寫要點 |
| --- | --- | --- |
| `{{源版本}}` / `{{目标版本}}` | 是 | 與目標 tag 一致，格式 `vX.Y.Z` |
| `{{适用使用者范围}}` | 是 | 寫明哪些使用者必須遷移，避免含糊表述 |
| `{{变更类别}}` | 是 | 配置、API、執行時、目錄四類中至少一類 |
| `{{是否必须迁移}}` | 是 | 寫明該變更是否要求使用者執行遷移 |
| `{{旧行为}}` / `{{新行为}}` | 是 | 逐項對照，不得只寫一側 |
| `{{代码语言}}` | 是 | 程式碼塊語言標識，如 `yaml`、`json`、`js` |
| `{{前置准备}}` | 是 | 遷移前須完成的備份與環境檢查 |
| `{{迁移步骤}}` | 是 | 每步可直接執行，含命令或程式碼 |
| `{{人工处理步骤}}` | 是 | 不可自動遷移的步驟須在此顯式標註 |
| `{{检查命令}}` / `{{预期结果}}` | 是 | 命令可獨立執行，結果可判定 |
| `{{回滚方式}}` | 是 | 不得省略，見第 7 節禁止事項 |

## 4. 內容要求

### 4.1 變更對照示例

```markdown
### 配置項 `timeout` 更名為 `timeoutMs`

- 舊行為：在配置檔案中使用 `timeout: 5000`，單位為秒。
- 新行為：改用 `timeoutMs: 5000`，單位為毫秒。
- 變更原因：統一時間單位，避免與 API 引數不一致。

遷移前：

```yaml
timeout: 5
```

遷移後：

```yaml
timeoutMs: 5000
```

### 4.2 寫作要求

1. 每步給出可直接執行的命令或程式碼，不得只描述「修改配置」。
2. 給出遷移前與遷移後的對照，便於逐項核對。
3. 明確標註不可自動遷移、須人工處理的步驟。
4. 影響範圍須具體，避免「可能影響部分使用者」等含糊表述。
5. 驗證命令須可獨立執行，含預期輸出。

## 5. 釋出時機與聯動

1. 遷移指南須與包含破壞性變更的版本同步釋出，不得滯後。
2. `CHANGELOG.md` 對應條目須連結到遷移指南（見 [變更日誌規範](./變更日誌規範.md)）。
3. PR 模板的破壞性變更區塊須提示填寫遷移方式（見 [Issue與PR模板規範](./Issue與PR模板規範.md)）。
4. 版本號遵循語義化版本，破壞性變更須遞增主版本（見 [版本管理規範](./版本管理規範.md)）。
5. README 在顯著位置提示舊版本使用者閱讀遷移指南。

## 6. 廢棄與保留策略

1. 遷移指南須長期保留，不得在新版本釋出後刪除。
2. 舊版本文件可標記為「不再維護」，但須保留入口。
3. 跨多個大版本的升級須提供分步路徑，不得要求一次性跨越全部變更。

## 7. 禁止事項

1. 禁止只寫「有破壞性變更，請自行調整」。
2. 禁止省略回滾方式。
3. 禁止在遷移步驟中使用無法執行的虛擬碼。
4. 禁止刪除歷史版本的遷移指南。
