# README視覺排版規範

> 本檔案解決什麼問題：定義 README 的排版層次、段落組織、表格、截圖與 GIF 的使用場景及放置位置，使文件在資訊密度與視覺吸引力之間取得平衡。

本文「實測」資料來自本專案對頭部開源專案 README 的抽樣統計（樣本 N=120）；標杆做法取自多個高星專案的首屏結構取證。

## 1. 排版層次

### 1.1 標題層級

README 須建立清晰的標題層級，遵循以下約束：

1. 全文僅保留一個一級標題（`#`），即專案名稱，位於檔案首行。
2. 二級標題（`##`）為主要章節，數量以 6–12 個為宜；實測中位數為 7 個。
3. 三級標題（`###`）用於章節內細分，僅在二級標題內容較長時使用。
4. 不得出現標題層級跳躍（如從 `#` 直接到 `###`）。
5. 標題文字簡潔，使用名詞或名詞短語，末尾不加句號。

### 1.2 首屏結構順序

首屏指讀者無需滾動即可看到的內容，按以下順序組織：

1. 居中 Logo 或專案橫幅（可選）；
2. 一級標題（專案名稱）；
3. 徽章行（詳見 [徽章規範](./徽章規範.md)）；
4. 一句話定位（說明專案是什麼、給誰用、解決什麼問題）；
5. 章節導航連結行（可選，適用於長 README）；
6. 核心功能或特性摘要。

標杆取證：`fd`、`ripgrep` 在定位後緊跟章節導航；`next.js`、`rust-lang/rust` 使用居中 Logo 與橫幅開場；`vscode` 在定位後即插入產品截圖。

### 1.3 段落與留白

- 每段控制在 1–4 行，避免大段密集文字。
- 段落之間空一行，保證渲染後的呼吸感。
- 關鍵結論前置，解釋後置。
- 中文與英文、數字之間保留一個空格；中英文標點按各自語境使用。

## 2. 表格使用規範

### 2.1 使用場景

表格適用於多維度、可對比的資訊。實測 36.7% 的樣本使用表格，是配置說明、相容性矩陣、命令對照的推薦形式。適用場景包括：

- 配置項說明（鍵名、型別、預設值、作用）；
- 平臺 / 版本相容性矩陣；
- 命令或引數對照；
- 功能對比（本專案與其他方案）；
- 路線圖與狀態。

### 2.2 放置位置

表格緊跟所屬二級標題，前置一句引導語說明表格用途；表格後若有例外情況，另起段落補充。

### 2.3 書寫要求

| 要求 | 說明 |
| --- | --- |
| 列數控制 | 3–6 列，超過 6 列考慮拆分 |
| 表頭明確 | 每列給出簡短 noun 表頭，避免空表頭 |
| 對齊一致 | 全文表格對齊方式統一 |
| 內容簡短 | 單元格內不寫長段落，必要時用腳註或連結展開 |
| 無空單元格 | 無內容處寫明「無」或「不適用」 |

## 3. 程式碼塊使用規範

### 3.1 使用場景

程式碼塊用於命令、配置、API 呼叫與示例輸出。實測 66.7% 的樣本包含程式碼塊，是「快速開始」章節的必備元素，中位數為 2 個。

### 3.2 書寫要求

1. 每個程式碼塊必須標註語言，例如 `bash`、`json`、`python`、`javascript`，便於語法高亮。
2. 命令示例給出完整可執行命令，不得省略前置步驟。
3. 需要展示結果時，另起程式碼塊標註 `text`，並在文字中說明預期輸出。
4. 程式碼塊前後各留一行空行。
5. 單塊內容控制在 20 行以內，過長示例拆分為多塊或移入 `examples/` 目錄並給出連結。
6. 互動式命令使用 `$` 提示符時須全篇統一。

格式示例：

```bash
npm install <package-name>
```

```text
✓ Installation complete
```

## 4. 截圖與 GIF 使用規範

### 4.1 使用場景與取捨

| 元素 | 適用場景 | 注意事項 |
| --- | --- | --- |
| 靜態截圖 | 應用介面、執行結果、圖表 | 實測使用率 63.3%，最常用 |
| GIF / 動圖 | 命令列演示、互動流程、前後對比 | 檔案體積大，須壓縮，控制時長 |
| Logo / 橫幅 | 品牌識別、首屏首頁 | 提供深淺色雙版本 |
| 示意圖 | 架構、流程、資料流 | 須隨文件版本同步更新 |

實測 63.3% 的樣本包含圖片。標杆取證：`fd` 使用 `doc/screencast.svg` 作為 Demo，`ripgrep` 使用搜尋結果截圖，`vscode` 使用產品執行截圖，`rust`、`next.js` 使用深淺色自適應的 Logo 橫幅。

### 4.2 放置位置

1. Logo / 橫幅：檔案最頂部，居中。
2. 產品截圖：一句話定位之後、「快速開始」之前，用於建立直觀認知。
3. GIF 演示：獨立「Demo / 演示」章節，緊跟「核心功能」之後。
4. 架構示意圖：放入「架構」或「設計」章節，或移入 `docs/architecture.md` 並在 README 中連結。

### 4.3 書寫要求

- 每張圖片必須提供 `alt` 文字，描述畫面內容，不得使用 `image`、`截图` 等無意義文字。
- 圖片使用相對路徑引用倉庫內資源，或使用穩定的絕對 URL；避免使用帶時效性的臨時連結。
- 需要自適應主題的圖片，使用 HTML `<picture>` 配合 `prefers-color-scheme` 提供深淺雙版本。
- 控制圖片體積：截圖優先使用 WebP 或最佳化後的 PNG，GIF 優先轉為短影片或壓縮動圖。
- 圖片寬度適配：使用 `width` 屬性或外層容器限制，避免撐破頁面。

## 5. 連結與導航

### 5.1 章節導航

README 超過 200 行時，在首屏加入導航連結行，指向主要章節：

```markdown
[安裝](#安裝) · [快速開始](#快速開始) · [文件](#文件) · [貢獻](#參與貢獻)
```

### 5.2 相對連結優先

倉庫內文件、圖片、許可證一律使用相對路徑，保證 Fork 與離線閱讀時仍可用。外部連結須為權威來源（官方文件、包管理頁、CI 頁面）。

## 6. 美觀度與吸引力的實施清單

1. 首屏具備 Logo 或清晰標題，3 秒內傳達專案定位。
2. 徽章統一樣式、語義配色、數量適中。
3. 一級標題唯一，二級標題 6–12 個，層級無跳躍。
4. 至少一個可複製執行的程式碼示例。
5. 至少一張能體現產品價值的截圖或 Demo。
6. 表格用於對比類資訊，列數受控、表頭清晰。
7. 所有圖片有 `alt`，所有程式碼塊有語言標註。
8. 長文件具備章節導航。
9. 深淺主題下的圖片與徽章均可讀。
