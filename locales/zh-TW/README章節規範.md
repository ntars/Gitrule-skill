# README章節規範

> 本檔案解決什麼問題：定義各語言目錄的 README 必須包含的 20 個章節、各章必須包含與不得出現的內容，以及版權行標準格式。

## 1. 章節總要求

以下 20 章必須全部存在，順序固定，各語言版本一一對應。

| 序號 | 章節 | 必須包含 | 不得出現 |
| --- | --- | --- | --- |
| 1 | 專案名稱與定位 | 專案名、倉庫描述（`国家语言 \| 英语` 雙語合併格式）、話題標籤（拉滿 20 個，僅英文）、一句話定位、語言切換連結、當前版本、維護狀態 | 空泛形容詞；倉庫描述超過 120 字元；話題標籤大小寫混用或含非英文詞 |
| 2 | 專案簡介 | 背景、待解決問題、核心思路、適用場景、不適用場景，以及分列的優勢與侷限（侷限須含影響範圍與規避方式） | 一句話帶過；只列優勢不列侷限 |
| 3 | 核心功能 | 按模組分組的功能條目，每條含觸發條件與結果 | 僅列功能名 |
| 4 | 核心特性 | 按 [特性與工程取捨寫法](./特性與工程取捨寫法.md) 結構展開 | 無證據的誇讚 |
| 5 | 設計細節與工程取捨 | 按 [特性與工程取捨寫法](./特性與工程取捨寫法.md) 結構展開 | 與功能重複的描述 |
| 6 | 技術棧與依賴清單 | 執行時、構建、測試工具鏈及版本約束；依賴明細指向 NOTICE | 缺版本號 |
| 7 | 安裝與部署 | 環境要求、安裝步驟、驗證命令、升級與解除安裝方式、容器化說明 | 跳步或省略驗證 |
| 8 | 快速開始 | 最小可執行示例，含完整命令與預期輸出 | 無法執行的虛擬碼 |
| 9 | 配置說明 | 配置項表格（鍵名、型別、預設值、必填、取值範圍、作用、示例）、配置優先順序、熱更新支援 | 缺預設值 |
| 10 | API 或模組說明 | 介面簽名、引數、返回值、錯誤碼、呼叫示例、限流與配額 | 缺錯誤碼 |
| 11 | 目錄結構 | 樹形結構與每層職責說明 | 逐檔案羅列無說明 |
| 12 | 效能表現 | 測試環境、測試方法、指標資料、瓶頸分析、調優建議 | 無測試條件的數字 |
| 13 | 安全與隱私 | 資料收集與儲存、傳輸加密、許可權模型、漏洞上報渠道、已知風險 | 承諾絕對安全 |
| 14 | 相容性說明 | 作業系統、執行時、瀏覽器、資料庫版本矩陣，明確不支援項 | 含糊表述 |
| 15 | 已知問題與限制 | 已知問題（描述、影響範圍、臨時規避方案、跟蹤連結）、當前限制、未實現功能清單（功能、未實現原因、計劃狀態） | 隱瞞嚴重缺陷；把未實現功能寫成已實現 |
| 16 | 更新日誌 | 遵循 Keep a Changelog 結構，版本號遵循語義化版本 | 無日期的條目 |
| 17 | 後續路線圖 | 計劃項、狀態、目標版本，標註「非承諾」 | 承諾交付時間 |
| 18 | 參與貢獻 | 開發環境搭建、分支模型、提交規範、PR 要求、行為準則、Issue 模板 | 僅寫「歡迎 PR」 |
| 19 | 版權與許可 | 版權行、許可證名稱、SPDX 識別符號、許可證全文位置 | 缺著作權人 |
| 20 | NOTICE 合規宣告 | 第三方依賴摘要、指向 NOTICE 檔案的相對連結 | 用本章替代 NOTICE |

## 1.1 首頁四問與一句話文案

README 首屏須回答四個問題，順序固定：

1. 專案做什麼；
2. 專案解決什麼問題；
3. 專案有什麼特性；
4. 最小的 hello world 示例。

其中第 1 問對應「一句話定位」，須同時滿足三點：說明專案型別、限定詞精確、可被直接複述。成熟專案的公開文案可作參照：

| 專案 | 一句話文案 | 結構分析 |
| --- | --- | --- |
| Angular | One framework. Mobile & desktop. | 品類 + 覆蓋範圍 |
| React | A declarative, efficient, and flexible JavaScript library for building user interfaces. | 三個限定詞 + 品類 + 用途 |
| Vue | A progressive, incrementally-adoptable JavaScript framework for building UI on the web. | 兩個特性 + 品類 + 用途 |

寫法約束：

- 不得使用「強大」「優秀」「革命性」等無資訊形容詞；
- 須給出品類詞（庫、框架、工具、應用），使讀者一眼歸類；
- 特性限定詞不超過三個，避免堆砌；
- 中文版本須控制在 60 字以內，英文版本控制在 25 詞以內。

第 3 問「有什麼特性」須同時披露不適用場景。有效寫法示例：說明某訊息中介軟體「僅支援 QoS 級別 0，需要級別 1 的場景不適用」；無效寫法為只羅列優點。特性對比須基於可驗證事實，不得貶損同類專案。

第 4 問的 hello world 示例須在兩步內完成安裝與執行；安裝步驟繁瑣的專案應提供容器映象或線上演示環境，避免讀者在看完 README 後放棄。
