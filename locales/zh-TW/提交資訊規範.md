# 提交資訊規範

> 本檔案解決什麼問題：定義 Conventional Commits 的欄位、格式、填寫說明與示例，保證歷史可讀、可自動生成變更日誌與版本號。

## 1. 格式

```text
<类型>[可选作用域][可选 !]: <描述>

[可选正文]

[可选脚注]
```

## 2. 型別

完整的十類型別如下，覆蓋常見開源專案的提交場景：

| 型別 | 含義 |
| --- | --- |
| `feat` | 新增功能 |
| `fix` | 修復缺陷 |
| `docs` | 文件變更 |
| `style` | 格式調整，不改變邏輯（空白、格式化、缺少分號等） |
| `refactor` | 重構，不新增功能也不修復缺陷 |
| `perf` | 效能最佳化的程式碼變更 |
| `test` | 新增缺失測試或更正現有測試 |
| `build` | 影響構建系統或外部依賴的變更（如 npm、gulp） |
| `ci` | 持續整合配置與指令碼的變更（如 GitHub Actions、CircleCI） |
| `chore` | 構建、依賴、工具鏈等雜項 |

### 2.1 團隊寫法的對照與取捨

不同協作模式下存在三種常見寫法，專案應在立項時選定一種並全隊統一：

| 寫法 | 格式 | 適用 | 侷限 |
| --- | --- | --- | --- |
| 工作寫法 | `[任务卡号] 作者: 修改内容` | 使用看板、結對程式設計的團隊 | 依賴任務卡號體系，無卡號時不適用 |
| 常規寫法 | `[分类] 组件（可选）: 修改内容` | 需要按業務模組篩選歷史的團隊 | 需團隊約定分類表，有額外成本 |
| 開源寫法 | `<type>(<scope>): <subject>` | 開源庫與應用，需自動生成 CHANGELOG | 型別與作用域較多，學習成本較高 |

本專案統一採用開源寫法（即 Conventional Commits），理由：機器可讀，可自動生成變更日誌與版本號。工作寫法與常規寫法僅在閉源團隊中按約定使用，不得混入對外倉庫。

## 3. 欄位定義

| 欄位 | 必填 | 型別 | 填寫要點 | 示例 |
| --- | --- | --- | --- | --- |
| 型別 | 是 | 列舉 | 十類之一，不得自創 | `feat` |
| 作用域 | 否 | 文字 | 模組名，小寫短詞，不含空格 | `parser` |
| 破壞性標記 | 否 | `!` | 置於型別或作用域之後、冒號之前 | `feat!:` |
| 描述 | 是 | 文字 | 祈使句、小寫開頭、≤72 字元、結尾無句號 | `add TOML config support` |
| 正文 | 否 | 文字 | 說明動機與實現，與描述空一行 | `Allow the parser to read TOML...` |
| 腳註 | 否 | 文字 | `BREAKING CHANGE:` 或 `Refs: #N` | `BREAKING CHANGE: ...` |
| 關聯需求 | 否 | `REQ-NNN` | 寫入正文或腳註，便於追蹤 | `Refs: REQ-001` |

## 4. 填寫說明

1. **描述**：使用祈使句（add、fix、remove），寫「做了什麼」而非「做了修改」；中文專案可寫中文描述，但須全倉庫統一。
2. **作用域**：取模組名而非檔名；跨模組變更省略作用域，不寫 `all` 或 `global`。
3. **正文**：僅在描述不足以說明動機時寫；不復述描述，不寫過程流水賬。
4. **破壞性變更**：`feat!:` / `fix!:` 與 `BREAKING CHANGE:` 腳註二選一或並用；二者出現時，須同步寫入 [變更日誌規範](./變更日誌規範.md) 與 [遷移指南規範](./遷移指南規範.md)。
5. **原子性**：一次提交只做一件事；格式化與邏輯變更分兩次提交。
6. **安全**：不得包含金鑰、令牌、個人資訊、內部地址；提交前用金鑰掃描核對（見 [安全與隱私規範](./安全與隱私規範.md)）。
7. **版本聯動**：`feat` 觸發次版本遞增，`fix` 觸發修訂版本遞增，`BREAKING CHANGE` 觸發主版本遞增，詳見 [版本管理規範](./版本管理規範.md)。

常見錯誤：

| 錯誤寫法 | 問題 | 修正方式 |
| --- | --- | --- |
| `wip`、`update`、`fix bug` | 無資訊量，違反 H10 | 寫明物件與行為 |
| `feat: Added new feature.` | 非祈使句、大寫開頭、有句號 | `feat: add config loader` |
| `feat(全部): 优化` | 作用域無效、描述模糊 | 用具體模組名並寫明改動 |
| 一次提交含格式化與功能變更 | 破壞原子性 | 拆為 `style:` 與 `feat:` 兩次提交 |
| 提交資訊含內網地址 | 資訊洩漏 | 移除並走金鑰掃描 |

## 5. 完整示例

```text
feat(parser): add support for TOML config

Allow the parser to read TOML configuration files in addition to YAML.
Refs: REQ-001

BREAKING CHANGE: the `config` option now accepts a file path instead of an object.
```

各欄位含義：`feat` 為型別，`parser` 為作用域，冒號後為簡短描述；正文說明動機與實現，腳註關聯需求；末尾腳註宣告破壞性變更並給出遷移方向。

修復類示例：

```text
fix(spacing): avoid false positives before Chinese punctuation

The spacing rule previously flagged strings such as 「使用Node.js，」 because
the punctuation check ran after whitespace normalization.

Refs: REQ-004, #142
```
