# 資訊採集與模板

> 本檔案解決什麼問題：定義撰寫文件前須採集的專案資訊欄位、未確認資訊的標記規則，並提供佔位符索引、術語對照模板、依賴清單模板與可直接複製的專案資訊採集正文。

## 1. 必填欄位（缺失即阻斷）

| 欄位 | 說明 | 影響章節 |
| --- | --- | --- |
| 專案名稱 | 倉庫名與展示名，兩者不一致時須說明 | 全篇 |
| 一句話定位 | 不超過 60 字，說明專案是什麼、為誰解決什麼問題 | 第 1 章 |
| 倉庫描述（國家語言與英語） | 兩種語言各不超過 120 字元，分別說明專案型別與核心用途 | 第 1 章 |
| 話題標籤 | 拉滿 20 個小寫英文詞，用 `-` 連線，大小寫混用或非英文視為缺項 | 第 1 章 |
| 專案背景 | 立項原因、現有方案的不足 | 第 2 章 |
| 核心功能清單 | 按模組分組，含使用者可感知的行為 | 第 3 章 |
| 技術棧 | 語言、框架、執行時版本約束 | 第 6 章 |
| 依賴清單 | 名稱、版本、許可證、版權方、來源地址 | 第 6 章、NOTICE |
| 許可證型別 | 專案自身許可證，須為 SPDX 識別符號 | 第 19 章 |
| 著作權人 | 個人姓名或組織全稱，與年份 | 第 19 章、NOTICE |
| 安裝與執行方式 | 環境要求、命令、預期結果 | 第 7、8 章 |

## 2. 選填欄位

配置項清單、API 定義、目錄結構、效能測試資料、相容性矩陣、已知問題、更新日誌、路線圖、貢獻流程、安全策略、截圖與演示地址、外部素材來源。

## 3. 欄位填寫說明與示例

| 欄位 | 填寫說明 | 示例 |
| --- | --- | --- |
| 專案名稱 | 倉庫名使用小寫字母、數字與 `-`；展示名可使用品牌寫法，兩者不一致時註明原因 | 倉庫名 `markdown-lint-cli`，展示名 `Markdown Lint CLI` |
| 一句話定位 | 包含品類詞與限定詞，不堆砌形容詞，不超過 60 字 | `面向技术文档团队的 Markdown 规范检查命令行工具` |
| 倉庫描述（國家語言與英語） | 國家語言與英語各自獨立成句，均不超過 120 字元，不以口號替代描述 | `中文：检查 Markdown 文档结构的命令行工具` / `English: A CLI tool for checking Markdown document structure` |
| 話題標籤 | 全部小寫英文，詞間用 `-` 連線，拉滿 20 個，完整覆蓋語言、形態、用途、生態、場景 | `go cli markdown linter developer-tools` |
| 技術棧 | 寫明主語言、框架與執行時版本約束，不寫「最新版本」 | `Go >= 1.22；Cobra v1.8.x` |
| 依賴清單 | 每項含版本、許可證、版權方與官方地址；來源不明時按未確認項標註 | 見附錄 C 的依賴清單表格模板 |
| 許可證型別 | 使用 SPDX 識別符號，不使用「開源」「可自由使用」等模糊說法 | `MIT` |
| 安裝與執行方式 | 給出當前工作目錄、完整命令與可核對的預期輸出 | 在倉庫根目錄執行 `go install ./cmd/mdlint`，輸出版本號 |
| 未確認項 | 使用固定標記，寫明缺失內容與補充責任人，不用「暫定」替代 | `【待确认：依赖 foo 的许可证类型，责任人：张三】` |

## 4. 未確認資訊的標記規則

1. 統一格式：`【待确认：具体缺什么】`，不得使用「暫定」「大概」「可能」等模糊表述替代。
2. 標註位置：正文對應位置一處，文末「待確認事項彙總」再列一次。
3. 涉及許可證、版權、依賴來源的未確認項，必須在 NOTICE 中顯式標註，不得省略整個條目。
4. 待確認事項彙總須包含編號、欄位、缺失內容、補充責任人與計劃補齊時間；無責任人或時間的條目不得進入階段 0（見 [執行流程](./執行流程.md)）。

## 5. 附錄 A · 佔位符索引

`{{项目名称}}`、`{{一句话定位}}`、`{{当前版本}}`、`{{维护状态}}`、`{{许可证 SPDX}}`、`{{著作权人}}`、`{{年份}}`、`{{分支名}}`、`{{仓库地址}}`、`{{最低运行时版本}}`

使用規則：

1. 本索引僅列採集階段的基礎欄位；README 全量佔位符及其說明以 [README標準模板](./README標準模板.md) 的佔位符對照表為準。
2. 正式佔位符統一寫成 `{{纯名}}`，不得在花括號內巢狀說明文字、反引號或第二個佔位符；規範示例中的自然語言花括號內容不視為正式佔位符。
3. 採集表中的自然語言欄位不直接使用佔位符；生成 README 時再按對照表對映到對應占位符，最終文件中不得留下任何說明性花括號內容。

## 9. 附錄 D · 可複製專案資訊採集正文

將以下內容複製到目標專案的 `项目信息采集表.md`，逐項替換「填寫：」後的內容。無法確認的欄位按第 4 節規則標註，並在第 8 節彙總。

````markdown
# 專案資訊採集表

> 本檔案用於一次性採集文件生成所需資訊。填寫完成後，依據採集結果生成 README、NOTICE 與其他交付文件。

## 1. 基本資訊

| 欄位 | 填寫內容 |
| --- | --- |
| 倉庫名 | 填寫：小寫字母、數字與連字元組成的倉庫名 |
| 展示名 | 填寫：對外展示的專案名稱；與倉庫名一致時寫「同倉庫名」 |
| 倉庫地址 | 填寫：完整 HTTPS 地址 |
| 目標分支 | 填寫：預設分支名稱 |
| 語言碼 | 填寫：優先語言碼，如 zh-CN |
| 當前版本 | 填寫：語義化版本號或「未釋出」 |
| 維護狀態 | 填寫：活躍維護 / 低頻維護 / 已歸檔 |

## 2. 定位與適用範圍

| 欄位 | 填寫內容 |
| --- | --- |
| 一句話定位 | 填寫：不超過 60 字，含品類詞與限定詞 |
| 倉庫描述（國家語言） | 填寫：不超過 120 字元 |
| 倉庫描述（English） | 填寫：不超過 120 字元 |
| 話題標籤 | 填寫：拉滿 20 個小寫英文詞，用連字元連線 |
| 專案背景 | 填寫：立項原因與現有方案的不足 |
| 適用場景 | 填寫：逐條列出，每條含觸發條件 |
| 不適用場景 | 填寫：逐條列出，每條說明原因 |
| 優勢 | 填寫：每條附可核對依據 |
| 侷限 | 填寫：每條含影響範圍與規避方式 |

## 3. 功能與特性

| 模組 | 使用者可感知行為 | 觸發條件 | 結果 | 證據或連結 |
````
