# 開發手冊模板規範

> 本檔案解決什麼問題：定義「雲端編寫、本地執行」兩階段開發手冊的骨架、任務卡格式、交接協議與校驗門禁，讓同一個想法可由雲端模型轉寫為無歧義任務卡，並由本地編碼模型按部分接力執行。

## 1. 定位與使用流程

1. 本規範面向「一個雲端推理模型 + 一個本地編碼模型」的分工場景：雲端負責把模糊想法轉寫為明確方案，本地負責按方案確定性執行。
2. 使用流程固定為四步，順序不得跳過：
   - 前置核查：檢查想法是否存在錯誤前提、邏輯跳躍或資訊缺失；資訊不足先向使用者提問，禁止腦補。
   - 雲端編寫：按第 9 節規範掃描開源方案並填寫手冊。
   - 使用者審核：重點審核驗收命令、採納記錄與禁區。
   - 本地執行：按機器可讀索引注入對應章節與交接記錄，逐部分執行。
3. 手冊正文中禁止出現「等」「相關」「適當」「盡量」「必要時」等含糊詞；每處不是給出精確值，就是給出決策規則。

## 2. 手冊骨架

每份開發手冊固定包含以下部分，順序不變：

| 部分 | 職責 |
| --- | --- |
| 機器可讀索引 | 章節路徑、對應程式碼目錄、驗收命令、階段標記的導航表 |
| 採納記錄 | 開源供應鏈記錄表，全專案單一真源（見第 11 節） |
| 專案憲法 | 全專案不變量，每個部分必注入 |
| 術語表 | 術語與通俗解釋、對應程式碼的對照 |
| 模組章節 | 每模組一章，按第 4 節結構編寫 |
| 發行章節 | 建置與發布規範，發布動作須使用者確認 |
| 官網文案章節 | 面向普通使用者的文案規範，不注入本地模型 |
| 變更記錄 | 日期、章節、變更與決策人 |

## 3. 專案憲法

專案憲法為每個本地執行部分必注入的不變量，固定含五項：

1. 技術棧與版本：精確到版本號。
2. 目錄結構約定：樹狀圖加每個目錄一句話職責。
3. 程式碼規範：按專案類型裁剪，基線為模組化按需載入、最小最直接程式碼、不添加非要求的功能、註解完整且專業概念用通俗語言註解；介面類專案遵循 Apple HIG，字體單位一律使用 px 或 rem，禁止使用 rpx。
4. 全域禁區：絕不許做的事，例如不引入未進採納記錄的依賴、不改契約檔案。
5. 輸出語言規範：說明、日誌、進度與錯誤訊息使用簡體中文；程式碼、命令、檔案路徑與專有名詞可保留原文。

## 4. 模組章節結構

每個模組章節固定含九節，順序不變：

| 節 | 職責 |
| --- | --- |
| 模組職責 | 1-3 句，寫清做什麼、不做什麼 |
| 依賴的開源方案 | 名稱、用途、採納記錄編號 |
| 檔案清單 | 路徑、動作（新建/修改/唯讀）、職責；總數不超過 10 個，超出拆章 |
| 介面契約 | 簽名、路由、協定欄位精確到類型，附完整輸入輸出樣例 |
| 資料與狀態 | 存什麼、存哪裡、格式；專業概念用通俗語言註解 |
| 依賴關係 | 需要先讀、會呼叫、絕不改三組檔案清單 |
| 任務卡 | 本模組拆成的部分，每卡獨立執行 |
| 本章禁區 | 本模組特別不許做的事 |
| 設計備註 | 選型理由、放棄的方案、事實與推測的區分；不注入本地模型 |

## 5. 任務卡格式

一張任務卡等於一次本地會話等於一條驗收命令，固定欄位如下：

| 欄位 | 要求 |
| --- | --- |
| 目標 | 一句話，可機器驗證 |
| 前置條件 | 依賴的上一部分與檔案均已存在 |
| 步驟 | 編號列出，每步一個確定性動作，一次做完不打斷不追問 |
| 驗收命令 | 可直接複製執行；還沒有驗收體系時，第一張卡必須先搭建驗收命令 |
| 期望結果 | 精確輸出、退出碼或斷言數 |
| 失敗處理 | 按典型錯誤逐條給出處置；連續失敗 3 次必須停止並寫入交接記錄 |
| 交接要求 | 聲明必須寫入交接記錄的欄位 |

硬性約束：

1. 一張卡觸達檔案超過 10 個就拆卡；一章超過 6 張卡就拆章。
2. 凡涉及交付自檢的卡，須顯式列出冗餘程式碼清理與 README、NOTICE、LICENSE 同步點。
3. 涉及刪除或覆蓋檔案的動作一律停下，寫入交接記錄的 block 欄位，等使用者確認。
4. 含糊到寫不出驗收命令的任務不得填卡，單獨標註「需使用者決策」。

## 6. PROGRESS 交接協議

交接記錄檔案 PROGRESS.md 是部分與部分之間的唯一真源，格式固定：

| 欄位 | 要求 |
| --- | --- |
| done | 本卡目標是否達成 |
| files | 實際改動的檔案清單 |
| decisions | 過程決策，格式為「選擇了 A，因為 B」 |
| next | 下一張卡編號與入口，必須寫到檔案路徑與入口函式，不許寫「繼續完善」 |
| block | 未解決問題，無則留空 |

1. 每張卡收尾必須追加一條，格式不許改。
2. 本地執行時只注入最新一條，歷史條目不注入。
3. 斷點恢復：收到「繼續」指令時，先讀最新一條確認斷點，從 next 指向的入口繼續，禁止憑記憶或猜測重做已完成步驟。

## 7. 本地注入預算

harness 按下表拼裝每個部分的上下文，總預算不超過 24K（32K 工作窗的 75%）：

| 注入項 | 預算 |
| --- | --- |
| 專案憲法 | 2-3K |
| 當前任務卡所屬章節 | 2-5K |
| 交接記錄最新一條 | 約 0.5K |
| 交接提示詞骨架 | 約 0.3K |
| 程式碼與工具輸出 | 剩餘額度 |

不注入：採納記錄全表（只注入本卡涉及條目）、設計備註、官網文案章節。

## 8. 交接提示詞鐵律

每個部分開工時注入固定開場，鐵律固定六條：

1. 全程使用簡體中文輸出；程式碼、命令、路徑與專有名詞可保留原文。
2. 只做任務卡內的事，不添加非要求的功能、配置或擴充能力。
3. 不臆造、不虛構；不確定的 API 簽名直接說明不確定；事實與推測顯式區分。
4. 驗收命令失敗時按任務卡的失敗處理執行，不許自行更改驗收標準。
5. 涉及刪除、覆蓋檔案的動作一律停下，等使用者確認。
6. 完成後嚴格按交接要求寫交接記錄，然後結束。

## 9. 雲端填寫規範

雲端模型填寫手冊前先完成兩項前置，再逐章填寫：

1. 前提核查：檢查錯誤前提、邏輯跳躍與資訊缺失，不足先問使用者。
2. 開源方案掃描：檢索開源生態中可用的現成方案，先掃後填，能用成熟方案不造輪子，結果登記進採納記錄。

填寫時遵守：

1. 消滅一切含糊詞，每處給精確值或決策規則。
2. 設計決策寫進設計備註，含選型理由與放棄的方案，供使用者審核，不注入本地模型。
3. 給本地模型的指令按「它不知道專案背景」來寫，所有前提顯式寫出。
4. 合規底線：許可證不明標「待確認」；強 copyleft 方案標註衍生義務提示；修改過的開源程式碼保留原始版權與修改說明；採納項必須同步 README、README_EN、NOTICE、LICENSE，同步動作作為對應任務卡的顯式步驟與驗收內容。
5. 文件格式規範引用本倉庫對應規範，不在手冊中複製規範正文。

## 10. 階段狀態與工作窗

機器可讀索引中每章帶階段標記，據此調整本地工作窗：

| 階段 | 特徵 | 工作窗 |
| --- | --- | --- |
| 綠地 | 按凍結契約填實現 | 16-24K |
| 成長 | 跨模組功能，預設檔 | 32K |
| 維護 | 重構與跨模組排查 | 48-64K，並行相應減少 |

維護期章節須額外附排查指引：症狀、可能位置、驗證命令三列表。

## 11. 採納記錄、發行與官網文案

1. 採納記錄表欄位固定為：名稱、類別、版本、用途、許可證、版權方、官方地址、是否修改、修改說明、聲明方式、採納狀態；採納狀態分「可立即採用、需評估、暫不可用」三檔。
2. 發行章節覆蓋建置腳本、CI 矩陣、checksum、簽名環境變數模板；發行卡的驗收命令是建置產物檢查；對外發布動作不進本地模型，由使用者確認後執行。
3. 官網文案章節面向普通使用者：禁止出現程式碼、命令列、技術名詞與空詞；結構為首屏定位、痛點、亮點、信任、下載、場景故事、常見問題；語氣平靜克制。

## 12. 跨專案引用與校驗

1. 目標專案引用本規範時，透過 `gitrule spec` 讀取全文，把手冊骨架複製為專案內手冊的初始骨架；本規範不隨專案修訂，專案內手冊的演進在專案倉庫閉環。
2. 涉及文件產出的任務卡，驗收命令追加 `gitrule check`；多語言專案追加 `gitrule xcheck`；術語表變更後執行 `gitrule termcheck`。
3. `gitrule check` 的文件違規屬可自動修復類，可先執行 `gitrule optimize` 後複檢，仍不通過再寫入交接記錄的 block 欄位。
4. Gitrule 規範只管文件與倉庫規範，程式碼質量歸各專案測試與驗證腳本，兩者不互相替代。
