# 專案命名規範

> 本檔案解決什麼問題：定義倉庫名的字元、大小寫、分詞、長度、語義等硬性規則，以及命名公式、約定字尾、檢索流程與配套後設資料要求。

## 1. 硬性規則

| 規則 | 要求 | 反例 |
|---|---|---|
| 字符集 | 僅 `a-z`、`0-9`、`-` | `My_Proj`、`我的项目` |
| 大小寫 | 全小寫 | `MyProject` |
| 分詞 | kebab-case，用 `-` 連線 | `myproject`、`my_project` |
| 長度 | 2–25 字元 | 超長的拼接名 |
| 結尾 | 名詞或以形態字尾收尾 | 以 `-project`、`-test` 結尾 |
| 版本 | 不含版本號、年份、日期 | `tool-v2`、`app2024` |
| 無資訊詞 | 禁止 `my`/`demo`/`test`/`new`/`tmp` | `my-new-demo` |
| 唯一性 | GitHub / npm / PyPI 各檢索一次 | 與知名庫重名 |
| 語義 | 名字本身能讀出「做什麼」 | `xyz`、`abc123` |

## 2. 命名公式（四選一）

```text
<技术>-<对象>          vue-virtual-table      go-ratelimit
<对象>-<形态>          note-cli   image-api   config-loader
<动词>-<对象>          parse-markdown   sync-dotfiles
<领域>-<子领域>        web-ui-kit   data-pipeline
```

## 3. 約定式字尾

`-cli` 命令列 / `-sdk` 客戶端庫 / `-api` `-server` 服務端 / `-template` `-boilerplate` 腳手架 / `-loader` `-parser` 中介軟體 / `-kit` 元件集 / `-notes` `-guide` 文件 / `dotfiles` 配置倉 / `awesome-xxx` 資源合集。

## 4. 命名流程

1. 用一句話寫出「專案給誰解決什麼問題」。
2. 從這句話裡取核心名詞 + 形態，套用第 2 節任一公式。
3. 生成 3 個候選，逐一做重名檢索。
4. 選最能在不看 README 時被理解的那個。
5. 中文名不寫進倉庫名，寫在 README 首行標題後。

## 5. 配套後設資料

### 5.1 倉庫簡介（description）

- 與倉庫名同源，句式：`<做什么> for <谁>`。
- 雙語合併格式：`國家語言 | 英語`，先寫國家語言版本，接半形豎線（兩側各留一個空格），再接英文版本。中文專案示例：

```text
轻量级 Go 命令行 JSON 处理工具 | A lightweight Go CLI for JSON processing
```

- 長度：國家語言與英語各不超過 120 字元，雙語合計不超過 350 字元（GitHub 上限）。
- 雙語合計超限時的取捨：優先壓縮英文版而非國家語言版——中文資訊密度更高，壓縮中文損失的資訊更多；壓縮時先刪修飾詞與重複限定，再合併同義表述，最後保留兩個語言版本各自完整的主謂結構。
- 不含換行、Markdown 語法與 Emoji；兩種語言的結尾標點風格保持一致（統一加句號或統一不加）。

### 5.2 話題（topics）

- 拉滿 20 個（GitHub 上限），完整覆蓋，不留空位。
- 全部使用英文，不得使用中文或其他語言；全小寫，用 `-` 連線，不含空格與特殊字元。
- 完整覆蓋語言、領域、形態、生態、場景五類，另可附加 documentation、open-source 等通用詞。
- 建立倉庫時即設定，不得留空；倉庫改名或重新定位後複核一次。
