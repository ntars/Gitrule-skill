# 程式碼審查規範

> 本檔案解決什麼問題：定義拉取請求的描述模板、審查意見模板、審查記錄、欄位與流程，保證合併質量與知識共享。

## 1. 規範條文

1. 作者須在 PR 描述中說明變更目的、影響範圍與自測結果，模板見 [Git工作流與分支規範](./Git工作流與分支規範.md)。
2. 審查者須給出具體、可執行的意見，區分「必須修改」與「建議」。
3. 合併前須至少有 1 名審查者批准，CI 全綠（對應硬規則 H9）；禁止作者自行批准自己的 PR。
4. 審查意見有分歧時升級至維護者裁定（見 [行為準則規範](./行為準則規範.md)）。
5. 合併後刪除源分支，保持分支列表整潔。

## 2. 審查清單

審查者須逐項確認：

| # | 維度 | 檢查要點 | 判定 |
| --- | --- | --- | --- |
| 1 | 正確性 | 邏輯正確，邊界與異常已處理 | 透過 / 需修改 |
| 2 | 測試 | 變更有對應測試，測試透過 | 透過 / 需修改 |
| 3 | 風格 | 符合 [程式碼風格規範](./程式碼風格規範.md) | 透過 / 需修改 |
| 4 | 安全 | 無敏感資訊、無注入風險、許可權校驗正確 | 透過 / 需修改 |
| 5 | 文件 | 介面或行為變更已同步文件 | 透過 / 需修改 |
| 6 | 範圍 | 變更聚焦，無無關改動 | 透過 / 需修改 |
| 7 | 提交資訊 | 符合 [提交資訊規範](./提交資訊規範.md) | 透過 / 需修改 |
| 8 | 追蹤 | 需求追蹤矩陣已更新 | 透過 / 需修改 |

## 3. 審查意見模板

```markdown
### 意見 {{序号}}：{{一句话标题}}

- 級別：{{必须修改 / 建议 / 提问}}
- 位置：{{文件路径:行号}}
- 問題：{{描述可观察的问题，不评价人}}
- 依據：{{规范条款 / 需求编号 / 风险说明}}
- 建議：{{具体的修改方式或替代方案}}

示例：
### 意見 1：異常分支未覆蓋
- 級別：必須修改
- 位置：`src/rules/spacing.ts:42`
- 問題：當輸入含不完整 Markdown 時丟擲異常，未返回規則命中結果。
- 依據：REQ-001 驗收條件第 2 條（邊界路徑）。
- 建議：在此處捕獲解析異常並按「解析失敗」返回命中，補一條邊界用例。
```

## 4. 審查記錄模板

```markdown
## 審查記錄：{{PR 编号}}

審查者：{{姓名}} ｜ 審查日期：{{YYYY-MM-DD}} ｜ 輪次：{{第 N 轮}}

| 意見編號 | 級別 | 處理結論 | 處理人 | 驗證方式 |
| --- | --- | --- | --- | --- |
| 1 | 必須修改 | 已修改 | 作者 | 見提交 abc1234 |
| 2 | 建議 | 不採納 | 作者 | 理由：{{说明}} |

結論：{{批准 / 需修改后再审 / 拒绝}}
- 批准條件：全部「必須修改」項已處理，CI 全綠。
- 未決項：{{无 / 列出}}
```

## 5. 欄位定義

| 欄位 | 必填 | 型別 | 填寫要點 | 示例 |
| --- | --- | --- | --- | --- |
| 級別 | 是 | 列舉 | 必須修改 / 建議 / 提問 | `必须修改` |
| 位置 | 是 | `路径:行号` | 精確到行，禁止只寫檔名 | `src/parser.ts:42` |
| 問題 | 是 | 文字 | 描述現象，不評價作者 | `解析异常未捕获` |
| 依據 | 是 | 文字 | 規範條款或 REQ 編號 | `REQ-001 验收条件 2` |
| 建議 | 是 | 文字 | 可執行，不只說「請最佳化」 | `捕获异常并返回命中` |
| 處理結論 | 是 | 列舉 | 已修改 / 不採納 / 延後 | `已修改` |
| 驗證方式 | 是 | 文字 | 提交雜湊或複核方式 | `见提交 abc1234` |
| 結論 | 是 | 列舉 | 批准 / 需修改後再審 / 拒絕 | `批准` |

## 6. 填寫說明

1. **級別區分**：「必須修改」指阻斷合併的問題（正確性、安全、測試缺失）；「建議」不影響合併；「提問」須作者澄清但不要求改動。
2. **意見表述**：描述可觀察問題，禁止「這裡寫得很差」等評價性語言。
3. **位置**：精確到行號；跨檔案問題在每條意見中分別標註。
4. **依據**：能追溯則追溯；無規範依據時寫明風險或影響，禁止「我覺得」。
5. **處理結論**：「不採納」須寫理由；「延後」須寫明後續跟蹤位置。
6. **批准**：確認全部「必須修改」項已閉環，且 CI 全綠；作者不得自批自己的 PR。
7. **分歧**：審查者與作者意見不一致時升級維護者，裁定結論寫入審查記錄。

常見錯誤：

| 錯誤寫法 | 問題 | 修正方式 |
| --- | --- | --- |
| 「這裡不行」 | 無問題、無依據、無建議 | 補三要素 |
| 「建議最佳化一下效能」 | 不可執行 | 給出具體做法與判定指標 |
| 只寫檔名不寫行號 | 定位困難 | 精確到行 |
| 作者自行批准 | 違反規定 | 由他人審查 |
| 「必須修改」用於個人偏好 | 級別濫用 | 降級為「建議」 |

## 7. 完整示例

```markdown
## 審查記錄：#12

審查者：李四 ｜ 審查日期：2026-11-18 ｜ 輪次：第 1 輪

| 意見編號 | 級別 | 處理結論 | 處理人 | 驗證方式 |
| --- | --- | --- | --- | --- |
| 1 | 必須修改 | 已修改 | 王五 | 見提交 a1b2c3d |
| 2 | 建議 | 不採納 | 王五 | 理由：當前 QPS 未達瓶頸，避免過度設計 |
| 3 | 提問 | 已澄清 | 王五 | 已在 PR 正文補充說明 |

結論：批准
- 批准條件：全部「必須修改」項已處理，CI 全綠（run #128）。
- 未決項：無
```
