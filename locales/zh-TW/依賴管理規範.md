# 依賴管理規範

> 本檔案解決什麼問題：定義依賴引入申請、依賴清單、鎖定與更新的模板與欄位，保證構建可復現、依賴可追溯、許可證合規。

## 1. 規範條文

1. 引入新依賴須說明用途、許可證與維護狀態（見 [開源合規規範](./開源合規規範.md)）。
2. 優先選擇許可證相容、社群活躍的依賴；禁止引入來源不明或許可證不明的依賴。
3. 依賴版本須寫入 lockfile 並提交倉庫，保證乾淨環境可復現構建（對應硬規則 H9 與維度 D5）。
4. 版本號須鎖定實際解析版本，不使用範圍表示式作為最終交付。
5. 依賴更新須自動化工具輔助，更新後須透過 CI；漏洞須及時處理或記錄緩解措施。
6. 依賴清單與 NOTICE 保持一致（見 [NOTICE規範](./NOTICE規範.md)）。

## 2. 依賴引入申請模板

```markdown

- 申請人：{{姓名}}
- 用途：{{一句话说明解决什么问题}}
- 是否可自建：{{是 / 否；是则说明为何仍引入}}
- 替代方案評估：{{已评估的替代包及未选原因}}

| 欄位 | 值 |
| --- | --- |
| 包名 | {{包名}} |
| 引入版本 | {{精确版本号}} |
| 許可證 | {{SPDX ID}} |
| 許可證相容性 | {{兼容 / 不兼容 / 需法务确认}} |
| 最近釋出時間 | {{YYYY-MM-DD}} |
| 維護狀態 | {{活跃 / 低频 / 停滞}} |
| 周下載量 | {{数值}} |
| 傳遞依賴數量 | {{数值}} |
| 已知漏洞 | {{无 / CVE 编号与处置}} |
| 打包體積影響 | {{增量 KB}} |

- 結論：{{批准 / 拒绝 / 有条件批准}}
- 審批人：{{姓名}}
```

## 3. 依賴清單模板

```markdown
# 依賴清單：{{项目名称}}

更新時間：{{YYYY-MM-DD}} ｜ lockfile：{{路径}} ｜ 生成工具：{{工具与版本}}

| 依賴 | 引入版本 | 鎖定版本 | 型別 | 許可證 | 用途 | 最後審查 |
| --- | --- | --- | --- | --- | --- | --- |
| {{包名}} | {{^1.2.0}} | {{1.2.3}} | 直接 / 間接 | {{MIT}} | {{用途}} | {{YYYY-MM-DD}} |

## 更新記錄
| 日期 | 依賴 | 版本變化 | 原因 | 驗證結果 |
| --- | --- | --- | --- | --- |
| {{YYYY-MM-DD}} | {{包名}} | {{1.2.2 → 1.2.3}} | {{安全修复}} | {{CI 全绿}} |

## 例外與緩解
| 依賴 | 問題 | 緩解措施 | 複核日期 |
| --- | --- | --- | --- |
| {{包名}} | {{漏洞 / 停滞}} | {{限制使用范围}} | {{YYYY-MM-DD}} |
```

## 4. 欄位定義

| 欄位 | 必填 | 型別 | 填寫要點 | 示例 |
| --- | --- | --- | --- | --- |
| 申請編號 | 是 | `DEP-NNN` | 連續、不復用 | `DEP-007` |
| 用途 | 是 | 文字 | 說明解決的問題，禁止「方便開發」 | `解析 TOML 配置` |
| 替代方案評估 | 是 | 文字 | 至少評估 1 個替代項 | `评估过 toml-js，因维护停滞未选` |
| 引入版本 | 是 | 精確版本 | 不得使用 `^` 或 `~` | `1.2.3` |
| 鎖定版本 | 是 | 精確版本 | 與 lockfile 一致 | `1.2.3` |
| 許可證 | 是 | SPDX ID | 與 [LICENSE規範](./LICENSE規範.md) 寫法一致 | `MIT` |
| 維護狀態 | 是 | 列舉 | 活躍 / 低頻 / 停滯，附判定依據 | `活跃（近 30 天有提交）` |
| 傳遞依賴數量 | 是 | 數值 | 過多時須說明體積與風險影響 | `12` |
| 已知漏洞 | 是 | 文字 | 無則寫「無」，不得留空 | `无` |
| 複核日期 | 是 | 日期 | 例外項須設複核日期 | `2026-12-31` |

## 5. 填寫說明

1. **自建評估**：先回答「能否用標準庫或現有能力實現」；能自建仍引入的須說明理由。
2. **許可證**：須為 SPDX ID；`UNLICENSED`、自定義許可須轉為「需法務確認」，不得直接引入。
3. **維護狀態**：以最近釋出時間與 issue 響應為據，禁止「看起來有人維護」。
4. **版本鎖定**：交付時 lockfile 中須為精確解析版本；`package.json` 可保留範圍表示式，但 lockfile 必須精確。
5. **更新節奏**：自動化更新每開啟，人工確認合併；每次更新須透過 CI 並核對許可證變化。
6. **漏洞處理**：優先升級到安全版本；無法升級時寫明緩解措施與複核日期，並進入 [事故響應規範](./事故響應規範.md) 的風險登記。
7. **清單同步**：引入或移除依賴後，同步更新依賴清單與 NOTICE，三者（lockfile、清單、NOTICE）須一致。

常見錯誤：

| 錯誤寫法 | 問題 | 修正方式 |
| --- | --- | --- |
| 「用一個庫處理配置」 | 無具體包名與用途 | 寫包名、版本、解決問題 |
| 許可證寫「開源」 | 不可判定相容性 | 寫 SPDX ID |
| lockfile 未提交 | 構建不可復現 | 提交 lockfile（對應 H9） |
| 傳遞依賴數量留空 | 風險不可見 | 填具體數值 |
| 漏洞不寫緩解措施 | 風險無跟蹤 | 補措施與複核日期 |

## 6. 完整示例

```markdown
## 依賴引入申請：remark

- 申請編號：DEP-001
- 申請人：王五
- 用途：作為 Markdown 解析層，支撐規則引擎的節點定位需求（REQ-001、REQ-004）。
- 是否可自建：否；自建無法在人力上限內覆蓋 GFM 邊界用例。
- 替代方案評估：評估過 marked，因中文節點定位能力不足未選。

| 欄位 | 值 |
| --- | --- |
| 包名 | remark |
| 引入版本 | 15.0.1 |
| 許可證 | MIT |
| 許可證相容性 | 相容 |
| 最近釋出時間 | 2026-11-02 |
| 維護狀態 | 活躍（近 30 天有提交） |
| 周下載量 | 4,200,000 |
| 傳遞依賴數量 | 18 |
| 已知漏洞 | 無 |
| 打包體積影響 | +42 KB |

- 結論：批准，隨 ADR-0002 一併實施
- 審批人：李四
```
