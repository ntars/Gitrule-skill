# 專案立項與需求規範

> 本檔案解決什麼問題：定義立項階段的目標陳述、需求採集與範圍界定的模板與欄位，確保專案從一開始就有清晰、可驗證、可追溯的依據。

## 1. 規範條文

1. 立項文件須回答六問：是什麼、為什麼做、做到什麼程度、不給誰用、誰在用、受什麼限制。
2. 需求須區分「必須 / 應當 / 可以」三級，用語約定見 [通用寫作規範](./通用寫作規範.md)。
3. 每條需求須可驗證：以 Given/When/Then 給出驗收條件，或給出可判定的度量閾值。
4. 每條需求須有穩定編號與來源，禁止無編號的需求條目。
5. 資訊不足時標註「【待確認：欄位名】」，不得猜測填充，規則見 [資訊採集與模板](./資訊採集與模板.md)。
6. 範圍須同時寫明納入項與排除項；非目標為空視為範圍未界定。
7. 範圍變更須記錄原因、影響與決策人，並進入 [需求追蹤矩陣規範](./需求追蹤矩陣規範.md) 的變更記錄。


## 3. 需求條目模板

```markdown
### REQ-{{三位序号}}：{{需求标题}}

- 來源：{{工单号 / 访谈 / 竞品 / 推测}}
- 優先順序：{{必须 / 应当 / 可以}}
- 關聯目標：{{G1 / G2 / …}}
- 使用者故事：作為{{角色}}，我希望{{行为}}，以便{{价值}}
- 驗收條件：
  1. Given {{前置条件}}
     When {{操作}}
     Then {{预期结果}}
  2. Given {{边界或异常前置条件}}
     When {{操作}}
     Then {{预期结果}}
- 狀態：{{待确认 / 已确认 / 已实现 / 已验证 / 已废弃}}
- 關聯追蹤：{{见需求追踪矩阵中的需求 ID}}
```

## 4. 欄位定義

### 4.1 立項書欄位

| 欄位 | 必填 | 型別 | 填寫要點 | 示例 |
| --- | --- | --- | --- | --- |
| 文件版本 | 是 | 文字 | 語義化版本或日期版本 | `v0.1` |
| 狀態 | 是 | 列舉 | 草稿 / 評審中 / 已批准 | `评审中` |
| 決策人 | 是 | 文字 | 對範圍與優先順序有最終決定權的人 | `张三` |
| 一句話定位 | 是 | 文字 | 目標使用者 + 核心能力 + 痛點，≤60 字 | 為的前端開發者提供… |
| 立項依據 | 是 | 文字 | 至少一條可溯源記錄，禁止「團隊決定」 | `ISSUE-142` |
| 目標 / 非目標 | 是 | 表格 | 每條目標配對可驗證結果；非目標至少一條 | `G1：冷启动 <2s` |
| 成功標準 | 是 | 表格 | 指標須有基線、閾值、測量方式與時間 | `错误率 <0.1%` |
| 約束條件 | 是 | 列表 | 四類均須填寫，無則寫「無」 | `须兼容 Node 18+` |
| 待確認 | 否 | 列表 | 僅用【待確認：欄位名】格式 | `【待确认：预算上限】` |

### 4.2 需求條目欄位

| 欄位 | 必填 | 型別 | 填寫要點 | 示例 |
| --- | --- | --- | --- | --- |
| 編號 | 是 | `REQ-NNN` | 三位序號，連續、不復用、不重排 | `REQ-007` |
| 來源 | 是 | 文字 | 可追溯到具體記錄 | `用户访谈 #3` |
| 優先順序 | 是 | 列舉 | 必須 / 應當 / 可以 | `必须` |
| 關聯目標 | 是 | 列表 | 對應立項書的 G 編號 | `G1` |
| 使用者故事 | 是 | 文字 | 角色 + 行為 + 價值三要素齊全 | 作為…我希望…以便… |
| 驗收條件 | 是 | 列表 | 至少 1 組 Given/When/Then，須含邊界或異常 | 見模板 |
| 狀態 | 是 | 列舉 | 五態之一，僅前進不回退 | `已确认` |

## 5. 填寫說明

1. **一句話定位**：按「為誰 + 提供什麼 + 解決什麼」三段式寫；若刪掉修飾語後句子不成立，說明缺少實質資訊。
2. **成功標準**：每條須同時具備基線與閾值。「提升效能」「體驗更好」判定為不合格，須改為「P95 啟動耗時由 3s 降至 <1.5s」。
3. **非目標**：寫明明確排除的範圍與判定邊界，而非「以後再說」；無非空非目標時，視為範圍未界定。
4. **需求編號**：一經分配永久固定；需求廢棄時狀態改為「已廢棄」，編號不得回收或重用。
5. **驗收條件**：須覆蓋正常路徑與至少一條邊界或異常路徑；無法客觀判定的條件（如「介面美觀」）須轉換為可驗證的度量或檢查項。
6. **待確認項**：立項允許存在待確認項，但須列全並指定確認人；進入開發前須清零。

常見錯誤：

| 錯誤寫法 | 問題 | 修正方式 |
| --- | --- | --- |
| 「做一個好用的工具」 | 無目標使用者、無可驗證結果 | 補使用者角色與閾值指標 |
| 非目標寫「無」 | 範圍未界定，易蔓延 | 列出本期明確排除項 |
| 需求無編號，正文直接描述 | 無法追蹤與引用 | 分配 `REQ-NNN` 並全域引用 |
| 驗收條件寫「功能正常」 | 不可判定 | 拆為 Given/When/Then |
| 推測內容當作既定需求 | 來源不可溯 | 標註來源為「推測」並轉待確認 |

## 6. 完整示例

```markdown
# 專案立項書：markdown-lint-cli

文件版本：v0.1 ｜ 狀態：評審中 ｜ 決策人：李四 ｜ 日期：2026-11-18

## 一句話定位
為中文技術寫作者提供命令列 Markdown 規範檢查工具，解決多倉庫文件風格不一致且無自動校驗的問題。

## 背景與動機
- 現狀：12 個倉庫的 README 由各維護者手寫，風格不統一。
- 現有方案不足：通用英文 lint 工具不支援中英文空格規則；人工評審平均耗時 25 分鐘/篇。
- 機會視窗：團隊正統一開源首頁，需一次性實施規範。
- 立項依據：ISSUE-142、2026-11-10 文件評審紀要。

## 目標與非目標
| 型別 | 條目 | 可驗證結果 |
| --- | --- | --- |
| 目標 G1 | 自動檢查 8 類格式問題 | 對 50 篇樣本文件檢出率 ≥95% |
| 目標 G2 | 單次檢查耗時可控 | 1000 行文件檢查 <2s |
| 非目標 N1 | 不提供文件內容潤色 | 僅輸出規則命中位置，不改寫文字 |

## 成功標準
| 指標 | 基線 | 目標值 | 驗證方式 | 驗證時間 |
| --- | --- | --- | --- | --- |
| 人工評審耗時 | 25 分鐘/篇 | <5 分鐘/篇 | 5 名維護者對照實驗 | v1.0 釋出前 |

### REQ-001：檢查中英文混排空格
- 來源：ISSUE-142
- 優先順序：必須
- 關聯目標：G1
- 使用者故事：作為文件維護者，我希望自動標出中英文間缺失的空格，以便統一排版。
- 驗收條件：
  1. Given 文件含「使用Node.js開發」
     When 執行檢查
     Then 輸出該行行號與「中英文間缺少空格」提示
  2. Given 文件該處已有空格
     When 執行檢查
     Then 不輸出該規則命中
- 狀態：已確認
```
