# コードオーナーシップ規範

> このファイルが解決する問題：`.github/CODEOWNERS` ファイルの構文、オーナーシップの割り当て、レビューのルーティングルールを定義し、各変更が責任を持つレビュアーへ自動的に割り当てられるようにします。

## 1. 設計原則

1. **パスから人への明確なマッピング**：各ルールはあるパスを誰が担当するかを明示し、レビューされない状態や重複レビューを避けます。
2. **最小限の必要な owners**：単一パスのオーナーは 1〜3 人に抑え、多すぎると責任が分散します。
3. **既定の引き継ぎ**：グローバルな既定オーナーを設定し、明示的なルールに一致しないパスをカバーします。
4. **チーム構造との同期**：メンバーの変更時に速やかに更新し、無効なアカウントがレビューを阻害することを避けます。

## 2. ファイルの位置と構文

### 2.1 パス

`CODEOWNERS` ファイルは以下のいずれかの位置に配置でき、優先度に従って最初に一致したものを使用します：

1. リポジトリのルートディレクトリ `CODEOWNERS`；
2. `docs/CODEOWNERS`；
3. `.github/CODEOWNERS`（推奨）。

### 2.2 構文規則

```text
# 注释以 # 开头
<路径模式>  <所有者>  [<所有者>...]
```

- 1 行に 1 つのルールを記述し、パスパターンの後に 1 つ以上の所有者を続けます。
- 所有者の形式は `@ユーザー名` または `@組織/チーム` です。
- メールアドレスを所有者として使用する場合は GitHub アカウントと関連付ける必要があります。
- パスは大文字小文字を区別し、ワイルドカード `*`、`**` をサポートします。

### 2.3 例

```text
# 默认所有者
*                       @org/maintainers

# 按目录分配
/src/core/              @org/core-team
/src/api/               @org/api-team @alice
/docs/                  @org/docs-team

# 按文件类型分配
*.md                    @org/docs-team
/.github/workflows/      @org/devops-team
```

## 3. マッチング規則

1. 最後に一致したルールのみが有効であり、累積されません；そのため汎用的なルールを前に、特殊なルールを後ろに記述しなければなりません。
2. ディレクトリのルールはそのディレクトリとそのサブディレクトリに一致します。ただし `/` で始めてルートパスに限定した場合を除きます。
3. ルールの順序が優先度を決めるため、広いものから狭いものへと並べなければなりません。
4. 一致しないパスは既定のオーナーがレビュー責任を負います。

## 4. オーナーシップ割り当ての戦略

| 次元 | 割り当ての根拠 |
| --- | --- |
| ディレクトリ | モジュールまたはサブシステムの境界で割り当てる |
| ファイル種別 | ドキュメント、設定、テストは種別ごとに統一的に割り当て可能 |
| 重要パス | セキュリティ、リリース、CI の設定は中核メンテナーが独占する |
| 新メンバー | まずは必須でないレビュアーとして参加し、習熟後に正式なオーナーへ移行する |

## 5. レビューフローとの連動

1. PR の作成時に、GitHub が一致するパスのオーナーへ自動的にレビューを依頼します。
2. 必須レビューの要件はブランチ保護ルールで設定し、[Gitワークフローとブランチ規範](./Gitワークフローとブランチ規範.md) を参照します。
3. オーナーは取り決めた期限内に応答すべきであり、超過した場合は既定のオーナーが引き継ぎます。
4. オーナーの変更はファイルに同期して反映しなければならず、無効なアカウントがフローを阻害することを避けます（[コードレビュー規範](./コードレビュー規範.md) を参照）。

## 6. 保守の要件

1. 組織構造またはチームの責務が変更されるたびに 1 回見直します。
2. リポジトリの移管やメンバーの離脱時には、対応するオーナーを直ちに削除しなければなりません。
3. ファイルの変更は少なくとも 1 名の現任オーナーのレビューを受けなければならず、権限の自己拡散を防ぎます。
4. オーナーを非アクティブなアカウントやボットアカウントに向けてはなりません（自動化専用の場合を除く）。

## 7. 禁止事項

1. 広すぎるワイルドカードルールを使用し、全員がオーナーになることは禁止です。
2. 機密性の高いパス（リリース、鍵の設定）をレビュー能力のないメンバーに割り当てることは禁止です。
3. ファイルに私的な連絡先を書き込むことは禁止です。
4. 退職したメンバーのオーナー権限を長期間保持することは禁止です。
