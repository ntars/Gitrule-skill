# アーキテクチャ設計書規範

> このファイルが解決する問題：アーキテクチャ文書とアーキテクチャ決定記録（ADR）のテンプレート、フィールド、書き方を定義し、システム境界、モジュールの責務、品質属性、重要なトレードオフを説明するとともに、意思決定の追跡可能性を保証する。

## 1. 規範条文

1. アーキテクチャ文書（`docs/architecture.md`）は構造と境界のみを記述し、使用例を含めない。責務の境界は [ドキュメントマトリクス](./ドキュメントマトリクス.md) を参照。
2. 重大な技術的意思決定にはそれぞれ対応する ADR がなければならない。ADR のない決定は記録されていない決定とみなす。
3. ADR の番号は連続し、永久に固定される。一度採用したら履歴を書き換えず、状態の変更は新しい ADR を追加して記録し、「置き換えられた」と表示する。
4. アーキテクチャの記述はコードの実装と一致していなければならない。コードとドキュメントが一致しない場合はコードを正とし、直ちにドキュメントを修正する。
5. 各アーキテクチャ決定は一つまたは複数の要求まで遡れなければならない。追跡の関係は [要求トレーサビリティマトリクス規範](./要求トレーサビリティマトリクス規範.md) を参照。
6. 品質属性には検証可能な測定目標を示さなければならず、「高性能」「高可用性」とだけ書くことは禁止する。

## 2. アーキテクチャ文書テンプレート

```markdown
# アーキテクチャ設計：{{项目名称}}

文書バージョン：{{v1.0}} ｜ 対応コードバージョン：{{tag}} ｜ 最終確認日：{{YYYY-MM-DD}}

## システムコンテキスト
- システムの責務：{{一句话说明系统边界内的责任}}
- 外部の関与者：{{用户、上游系统、下游系统}}
- 入出力：{{进入系统的请求与系统产出的结果}}
- 境界の外側：{{明确不由本系统承担的职责}}

## モジュール分割
| モジュール | 唯一の責務 | 外部インターフェース | 依存モジュール | 担わないこと |
| --- | --- | --- | --- | --- |
| {{模块名}} | {{仅一件事}} | {{接口名}} | {{模块名}} | {{明确排除}} |

## 主要なデータフロー
1. {{触发点}} → {{模块 A}}：{{传递的数据}}
2. {{模块 A}} → {{模块 B}}：{{转换与传递}}
3. {{模块 B}} → {{结果}}：{{最终产出}}

## 技術選定
| 領域 | 選定 | 代替案 | 決定の根拠 | ADR |
| --- | --- | --- | --- | --- |
| {{语言 / 框架 / 存储}} | {{采用项}} | {{未采用项}} | {{取舍理由}} | {{ADR-000N}} |

## 品質属性
| 属性 | 目標値 | 検証方法 | 関連 ADR |
| --- | --- | --- | --- |
| 性能 | {{P95 延迟 < X ms}} | {{压测方式}} | {{ADR-000N}} |
| 可用性 | {{月度可用性 ≥ X%}} | {{监控统计}} | {{ADR-000N}} |
| セキュリティ | {{敏感数据零明文落盘}} | {{审计方式}} | {{ADR-000N}} |

## 制約とトレードオフ

- 断念した案とその理由：{{方案 A：原因}}
- 既知の技術的負債：{{债务项与偿还条件}}
```

## 3. ADR テンプレート

```markdown
# ADR-{{四位序号}}：{{决策标题}}

- 状態：{{提议 / 已采纳 / 已废弃 / 被 ADR-000N 替代}}
- 日付：{{YYYY-MM-DD}}
- 決定者：{{姓名}}
- 関連要求：{{REQ-001 / …}}

## 背景
{{面临的客观问题与约束，须可验证，不写主观偏好}}

## 決定
{{采用的方案，一句话陈述，须明确到可执行的程度}}

## 代替案
| 案 | 長所 | 短所 | 採用しなかった理由 |
| --- | --- | --- | --- |
| {{方案 A}} | | | |
| {{方案 B（采用）}} | | | — |

## 帰結
- プラス面：{{获得的能力}}
- マイナス面：{{引入的成本或限制}}
- 後続タスク：{{需要跟进的事项}}

## 関連ファイル
- {{架构文档中受影响的章节}}
- {{替代或被引用的 ADR}}
```

## 4. フィールド定義

### 4.1 アーキテクチャ文書のフィールド

| フィールド | 必須 | 種別 | 記入の要点 | 例 |
| --- | --- | --- | --- | --- |
| 対応コードバージョン | はい | tag | [バージョン管理規範](./バージョン管理規範.md) の tag と一致させる | `v1.2.0` |
| 最終確認日 | はい | 日付 | コード変更のたびに更新しなければならない | `2026-11-18` |
| モジュールの唯一の責務 | はい | テキスト | 一つのモジュールには一つのことだけを書く | `Markdown ルールの解析と検証` |
| 担わないこと | はい | テキスト | 境界を明確にし、責務の逸脱を防ぐ | `テキストの書き換えは担わない` |
| 技術選定.決定の根拠 | はい | テキスト | ADR の番号を引用しなければならない | `ADR-0002 を参照` |
| 品質属性.目標値 | はい | 測定値 | 単位としきい値を含み、検証可能であること | `P95 < 150ms` |
| 既知の技術的負債 | いいえ | リスト | 返済のトリガー条件を明記する | `v2 でパーサーを置き換える予定` |

### 4.2 ADR のフィールド

| フィールド | 必須 | 種別 | 記入の要点 | 例 |
| --- | --- | --- | --- | --- |
| 番号 | はい | `ADR-NNNN` | 四桁の連番。連続し、永久に固定 | `ADR-0002` |
| 状態 | はい | 列挙 | 提案中 / 採用済み / 廃止済み / 置き換え済み | `採用済み` |
| 関連要求 | はい | リスト | 立ち上げ書の REQ 番号に対応 | `REQ-001` |
| 背景 | はい | テキスト | 客観的な制約を述べる。「私はこう思う」は禁止 | `Node 18 との互換性が必要` |
| 決定 | はい | テキスト | 一文で、実行可能であること | `パーサーとして remark を採用する` |
| 代替案 | はい | 表 | 採用しなかった案を少なくとも 1 つ含む | テンプレートを参照 |
| 否定理由 | はい | テキスト | 採用しなかった案それぞれについて示す | テンプレートを参照 |
| 帰結 | はい | リスト | プラス面、マイナス面、後続タスクの三項目を揃える | テンプレートを参照 |

## 5. 記入説明

1. **モジュール分割**：各行の「唯一の責務」に「および」「ならびに」で結ばれた二つのことが現れたら、二つのモジュールに分割すべきである。
2. **データフロー**：時系列順に番号を付け、受け渡すデータの内容を示す。モジュール名と矢印だけを書くことは禁止する。
3. **品質属性**：各項目には目標値、検証方法、ADR の引用がなければならない。いずれかが欠けていれば不完全とみなす。
4. **ADR の背景**：問題と制約を書き、決定そのものは書かない。決定は「決定」の段落に一度だけ現れる。
5. **代替案**：案が一つしかない場合でも、「自前実装も検討したが、保守コストが高すぎるため採用しなかった」と明記しなければならない。代替案がない場合は十分な論証がなされていないとみなす。
6. **状態の変更**：元の ADR の本文は修正せず、新しい ADR を作成して元の状態を「ADR-000N により置き換え」に変更する。
7. **技術的負債**：返済のトリガー条件を書かなければならず、現象だけを列挙することは禁止する。

よくある誤り：

| 誤った書き方 | 問題 | 修正方法 |
| --- | --- | --- |
| アーキテクチャ文書に API 呼び出しの例を置く | [APIドキュメント規範](./APIドキュメント規範.md) と責務が重複する | API ドキュメントへ移し、アーキテクチャにはインターフェース名のみを残す |
| 「システムは高性能である必要がある」 | しきい値がなく検証できない | P95 レイテンシの目標と負荷試験の方法を示す |
| ADR に決定だけがあり代替案がない | 論証されていない | 採用しなかった案を少なくとも 1 つとその理由を補う |
| 採用済み ADR の本文を修正する | 履歴が書き換えられる | 新しい ADR を作成し置き換えの関係を示す |
| 決定を要求に関連付けられない | 追跡の連鎖が途切れる | 関連する REQ 番号を補う |

## 6. 完全な例

```markdown
# ADR-0002：Markdown 解析層として remark を採用

- 状態：採用済み
- 日付：2026-11-18
- 決定者：李四
- 関連要求：REQ-001、REQ-004

## 背景
GFM と中国語テキストノードの位置特定をサポートする必要があり、ランタイムの依存関係は Node 18 と互換でなければならない。チームがパーサーの保守に割ける人的資源の上限は 0.5 人月/四半期である。

## 決定
remark のエコシステムを唯一の Markdown 解析層として採用し、ルールはプラグインとして実装する。

## 代替案
| 案 | 長所 | 短所 | 採用しなかった理由 |
| --- | --- | --- | --- |
| 自前のパーサー | 完全に制御できる | 境界事例を長期にわたり保守する必要がある | 人的資源の上限を超える |
| marked | 軽量 | 中国語ノードの位置特定能力が弱い | REQ-004 を満たさない |

## 帰結
- プラス面：GFM の互換性は上流で保守され、ノードの位置特定は受け入れ条件を満たす。
- マイナス面：プラグイン API の変更に上流バージョンで追従する必要がある。
- 後続タスク：CI で remark のメジャーバージョンを固定し、そのリリース通知を購読する。
```
