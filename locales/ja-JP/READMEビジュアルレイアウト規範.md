# READMEビジュアルレイアウト規範

> このファイルが解決する問題：README のレイアウト階層、段落構成、表、スクリーンショット、GIF の用途と配置位置を定義し、ドキュメントが情報密度と視覚的訴求の間でバランスを取れるようにする。

本文の「実測」データは、本プロジェクトがトップオープンソースプロジェクトの README を抽出統計したもの（サンプル N=120）である。ベンチマークの手法は、複数の高 star プロジェクトのファーストビュー構造の検証から得た。

## 1. レイアウト階層

### 1.1 見出し階層

README は明確な見出し階層を確立し、以下の制約に従うこと：

1. 全文で一級見出し（`#`）を一つだけ保持する。すなわちプロジェクト名で、ファイルの先頭行に置く。
2. 二級見出し（`##`）を主要セクションとし、数は 6〜12 個が適切である。実測の中央値は 7 個。
3. 三級見出し（`###`）はセクション内の細分化に用い、二級見出しの内容が長い場合にのみ使用する。
4. 見出し階層の飛躍（`#` から直接 `###` など）を生じてはならない。
5. 見出しの文字は簡潔にし、名詞または名詞句を用い、末尾に句点を付けない。

### 1.2 ファーストビューの構成順序

ファーストビューとは、読者がスクロールせずに見える内容を指し、以下の順序で構成する：

1. 中央寄せのロゴまたはプロジェクトバナー（任意）。
2. 一級見出し（プロジェクト名）。
3. バッジ行（詳細は [バッジ規範](./バッジ規範.md)）。
4. 一言の位置づけ（プロジェクトが何か、誰が使うか、何を解決するかを説明）。
5. セクションナビのリンク行（任意。長い README に適する）。
6. 中核機能または特性の要約。

ベンチマーク検証：`fd`、`ripgrep` は位置づけの直後にセクションナビを置く。`next.js`、`rust-lang/rust` は中央寄せロゴとバナーで始める。`vscode` は位置づけの直後に製品スクリーンショットを挿入する。

### 1.3 段落と余白

- 各段落は 1〜4 行に抑え、長い密集した文字を避ける。
- 段落の間は一行空け、レンダリング後の余白を確保する。
- 重要な結論を前に置き、説明を後に置く。
- 中国語と英語、数字の間には空白を一つ入れる。中国語・日本語・英語の句読点はそれぞれの文脈に従って用いる。

## 2. 表の使用規範

### 2.1 使用場面

表は多次元で比較可能な情報に適する。実測では 36.7% のサンプルが表を使用しており、設定の説明、互換性マトリクス、コマンド対照の推奨形式である。適用場面は以下を含む：

- 設定項目の説明（キー名、型、既定値、役割）。
- プラットフォーム／バージョンの互換性マトリクス。
- コマンドまたはパラメータの対照。
- 機能の比較（本プロジェクトと他の方式）。
- ロードマップと状態。

### 2.2 配置位置

表は所属する二級見出しの直後に置き、前に表の用途を説明する導入文を一句添える。表の後に例外がある場合は、別の段落で補足する。

### 2.3 記述要件

| 要件 | 説明 |
| --- | --- |
| 列数の制御 | 3〜6 列。6 列を超える場合は分割を検討する |
| 見出しの明確化 | 各列に短い名詞の見出しを与え、空の見出しを避ける |
| 配置の一貫性 | 全文の表で配置方法を統一する |
| 内容の簡潔化 | セル内に長い段落を書かず、必要なら脚注やリンクで展開する |
| 空セルの禁止 | 内容のない箇所には「なし」または「該当なし」と書く |

## 3. コードブロックの使用規範

### 3.1 使用場面

コードブロックはコマンド、設定、API 呼び出し、実行例の出力に用いる。実測では 66.7% のサンプルがコードブロックを含み、「クイックスタート」セクションの必須要素で、中央値は 2 個。

### 3.2 記述要件

1. 各コードブロックには言語を必ず注記する。例えば `bash`、`json`、`python`、`javascript` で、シンタックスハイライトを可能にする。
2. コマンド例は完全に実行可能なコマンドを示し、前段の手順を省略してはならない。
3. 結果を示す必要がある場合は、別のコードブロックに `text` を注記し、文章で期待される出力を説明する。
4. コードブロックの前後にはそれぞれ空行を一行入れる。
5. 単一ブロックの内容は 20 行以内に抑え、長い例は複数のブロックに分割するか `examples/` ディレクトリへ移してリンクを示す。
6. 対話式コマンドで `$` プロンプトを用いる場合は全編で統一する。

書式の例：

```bash
npm install <package-name>
```

```text
✓ Installation complete
```

## 4. スクリーンショットと GIF の使用規範

### 4.1 使用場面と取捨

| 要素 | 適用場面 | 注意事項 |
| --- | --- | --- |
| 静止スクリーンショット | アプリ画面、実行結果、図表 | 実測の使用率 63.3%、最も多用される |
| GIF / 動画 | コマンドラインのデモ、対話フロー、前後の比較 | ファイルサイズが大きいため圧縮し、再生時間を抑える |
| ロゴ / バナー | ブランドの識別、ファーストビューのトップページ | 明暗二バージョンを提供する |
| 模式図 | アーキテクチャ、フロー、データフロー | ドキュメントのバージョンに合わせて同期更新する |

実測では 63.3% のサンプルが画像を含む。ベンチマーク検証：`fd` は `doc/screencast.svg` を Demo として用い、`ripgrep` は検索結果のスクリーンショットを用い、`vscode` は製品の実行画面を用い、`rust`、`next.js` は明暗に自動適応するロゴバナーを用いている。

### 4.2 配置位置

1. ロゴ／バナー：ファイルの最上部、中央寄せ。
2. 製品スクリーンショット：一言の位置づけの後、「クイックスタート」の前。直感的な認知を確立するために用いる。
3. GIF デモ：独立した「Demo / デモ」セクションで、「中核機能」の直後に置く。
4. アーキテクチャ模式図：「アーキテクチャ」または「設計」セクションに置くか、`docs/architecture.md` へ移して README からリンクする。

### 4.3 記述要件

- 各画像には `alt` テキストを必ず提供し、画面の内容を説明すること。`image`、`スクリーンショット` などの無意味なテキストを用いてはならない。
- 画像は相対パスでリポジトリ内のリソースを参照するか、安定した絶対 URL を用いる。有効期限のある一時リンクを避ける。
- テーマに自動適応する必要がある画像は、HTML の `<picture>` と `prefers-color-scheme` を組み合わせて明暗二バージョンを提供する。
- 画像のサイズを制御する：スクリーンショットは WebP または最適化した PNG を優先し、GIF は短い動画または圧縮した動画への変換を優先する。
- 画像幅の適応：`width` 属性または外側コンテナの制限を用い、ページの崩れを避ける。

## 5. リンクとナビゲーション

### 5.1 セクションナビ

README が 200 行を超える場合、ファーストビューにナビのリンク行を加え、主要セクションを指し示す：

```markdown
[インストール](#インストール) · [クイックスタート](#クイックスタート) · [ドキュメント](#ドキュメント) · [コントリビューション](#コントリビューション)
```

### 5.2 相対リンクの優先

リポジトリ内のドキュメント、画像、ライセンスは一律に相対パスを用い、Fork やオフライン閲覧でも利用できるようにする。外部リンクは権威ある出所（公式ドキュメント、パッケージ管理ページ、CI ページ）でなければならない。

## 6. 美観と訴求力の実施チェックリスト

1. ファーストビューにロゴまたは明確な見出しがあり、3 秒以内にプロジェクトの位置づけを伝える。
2. バッジはスタイルを統一し、意味に応じた配色で、数は適切とする。
3. 一級見出しは唯一、二級見出しは 6〜12 個、階層に飛躍がない。
4. コピーして実行できるコード例が少なくとも一つある。
5. 製品の価値を示すスクリーンショットまたは Demo が少なくとも一つある。
6. 表は比較系の情報に用い、列数を制御し、列見出しを明確にする。
7. すべての画像に `alt` があり、すべてのコードブロックに言語注記がある。
8. 長いドキュメントにはセクションナビがある。
9. 明暗テーマのいずれでも画像とバッジが判読できる。
