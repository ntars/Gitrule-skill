# オープンソース普及規範

> このファイルが解決する問題：オープンソースプロジェクトのリリース前後における普及チャネル、リリースのリズム、トップページの素材とコミュニティ運営の規範を定義し、利用可能なドキュメントを備えたプロジェクトが目標ユーザーに適合した露出を得られるようにする。

本ファイルのチャネル一覧と原則は、phodal『GitHub 漫游指南』の普及に関する章を参考にしている。同プロジェクトは 11,362 star の規模で、これらの手法が中国語オープンソースコミュニティにおいて適用可能であることを実証している。

## 1. 基本原則

1. **品質を普及より優先する**：普及は既存の品質を増幅するだけで、欠落を修復しない。README、例、ドキュメント、テストが整う前に普及を開始してはならない。
2. **プロジェクトそのものが普及のすべてではない**：コードと README に加えて、詳細なドキュメント、サンプルプログラム、問題対応の仕組みを用意しなければならない。
3. **動機を明確にする**：普及は具体的な目標（初期ユーザーの獲得、コントリビューターの募集、フィードバックの収集）に資するものであり、star 数を追うために普及してはならない。
4. **チャネルを適合させる**：プロジェクトの技術スタックと目標ユーザーに応じてチャネルを選択し、無差別な投放を避ける。
5. **誠実に示す**：star 数、ダウンロード数、利用事例を捏造してはならない。機能の比較は検証可能な事実に基づかなければならない。

## 2. リリース前準備チェックリスト

| 種別 | 要件 | 判定根拠 |
| --- | --- | --- |
| トップページ | README が四つの問いのチェック（何をするか / 何を解決するか / 機能 / 例）を通過する | [READMEセクション規範](./READMEセクション規範.md) |
| 一言コピー | カテゴリと限定詞が明確で、単独で復唱できる | 同上 1.1 節 |
| 例 | 2 ステップ以内で実行できる hello world を提供する | [README標準テンプレート](./README標準テンプレート.md) |
| ドキュメント | インストール、設定、API ドキュメントが揃っている | [ドキュメントマトリクス](./ドキュメントマトリクス.md) |
| ライセンス | LICENSE が存在し、README の表示と一致する | [LICENSE規範](./LICENSE規範.md) |
| コンプライアンス | NOTICE が第三者の依存関係を網羅する | [NOTICE規範](./NOTICE規範.md) |
| コミュニティ窓口 | Issue テンプレート、コントリビューションガイド、行動規範が整っている | [コントリビューションガイド規範](./コントリビューションガイド規範.md) |
| 対応の仕組み | 問題対応の担当者と対応期限を明確にする | [インシデント対応規範](./インシデント対応規範.md) |

上記のチェックリストを完了せずに普及することは、本規範が禁止する行為である。

## 3. チャネルの分類

### 3.1 国際技術コミュニティ

| チャネル | 適用する内容 | 注意事項 |
| --- | --- | --- |
| Hacker News | 技術実装、深みのあるエンジニアリング設計 | タイトルは平実にし、マーケティング的な表現を避ける |
| Reddit の該当板 | ライブラリ、ツール、フレームワーク | 各板の自己宣伝ルールを遵守する |
| Lobsters | システムプログラミング、エンジニアリング実践 | コミュニティはマーケティングに敏感である |
| 技術週報（JavaScript Weekly など） | ライブラリとツール | 簡潔なプロジェクト概要を提供する |
| 公式ブログとドキュメントサイト | 深掘りした紹介とバージョン説明 | 他チャネルの着地点とする |

### 3.2 中国語技術コミュニティ

| チャネル | 適用する内容 |
| --- | --- |
| 掘金 | フロントエンド、モバイル、エンジニアリング実践 |
| 開発者頭条 | 総合的な技術プロジェクト |
| V2EX | ツール、効率化ソフトウェア、スタートアッププロジェクト |
| 知乎 | 技術的な解説と設計のトレードオフ |
| WeChat 公式アカウント | 深掘りの長文、シリーズのチュートリアル |
| 極客頭条 | 総合的な技術ニュース |

### 3.3 プロジェクト独自のチャネル

1. プロジェクトの README にあるコミュニティ窓口（Discussions、Discord）；
2. プロジェクト専用のソーシャルアカウント。バージョンとイベントの発信に用いる；
3. ドキュメントサイトとサンプルサイト。外部からの流入を受け止めるページとする。

## 4. リリースのリズム

1. **予熱期**：第 2 節のチェックリストを完了し、一言コピー、スクリーンショット、Demo のアニメーションなどの素材を準備する。
2. **初回公開期**：最も適合する 1〜2 のチャネルで公開し、同じ内容を複数プラットフォームで連投することを避ける。
3. **対応期**：初回公開後の 72 時間は高頻度で対応し、Issue とフィードバックを処理する。
4. **イテレーション期**：バージョンのリリースリズムに沿って継続的に更新し、各リリースに変更説明を添える。
5. **定着期**：頻出する問題を FAQ として整理し、ドキュメントに還元する。

## 5. トップページ素材の要件

| 素材 | 仕様 | 用途 |
| --- | --- | --- |
| 一言コピー | 中国語 60 字以内 / 英語 25 語以内。リポジトリの Description は「国家言語 \| 英語」の二言語併記形式を採用し、[プロジェクト命名規範](./プロジェクト命名規範.md) 第 5 節を参照 | リポジトリの Description、ソーシャルの概要 |
| スクリーンショット | ライト・ダークの 2 バージョン、幅を抑制する | README のファーストビュー |
| Demo アニメーション | 圧縮後のサイズを抑制し、中核フローを示す | README のデモセクション |
| ロゴ | SVG 形式、ライト・ダークの 2 バージョンを含む | ファーストビューとソーシャルカード |
| 機能比較表 | 検証可能な事実に基づき、適用しない場面を含む | README またはドキュメントサイト |

素材はバージョンに合わせて同期更新し、旧版の画面を表示することを避けなければならない。

## 6. コミュニティ運営

1. 初めてのコントリビューターに明確な窓口を提供する。たとえば `good first issue` ラベルなど。
2. 問題対応には記録を残し、同じ問題が繰り返し発生することを避ける。
3. 行動規範はすべてのコミュニティチャネルに適用される。[行動規範](./行動規範.md) を参照。
4. コントリビューターへの謝辞はまとめて掲載し、本文の各所に散在させることを避ける。
5. star の誘導や相互いいねなどによって虚偽の注目を集めてはならない。

## 7. 禁止事項

1. 品質チェックリストが未完了の状態で普及することを禁止する。
2. プロジェクトのデータや利用事例を捏造または誇張することを禁止する。
3. 同一の内容を複数チャネルで連投することを禁止する。
4. 自らの印象を高めるために同種のプロジェクトを貶めることを禁止する。
5. 誘導的な手段で star 数を獲得することを禁止する。
