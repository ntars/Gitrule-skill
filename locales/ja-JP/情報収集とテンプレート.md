# 情報収集とテンプレート

> このファイルが解決する問題：ドキュメントを書く前に収集すべきプロジェクト情報の項目、未確認情報のマーキング規則を定義し、プレースホルダー索引、用語対照テンプレート、依存関係一覧テンプレート、そのままコピーできるプロジェクト情報収集の本文を提供する。

## 1. 必須項目（欠落は即ブロック）

| 項目 | 説明 | 影響するセクション |
| --- | --- | --- |
| プロジェクト名 | リポジトリ名と表示名。両者が一致しない場合は説明を要する | 全体 |
| 一言での位置づけ | 60 字以内。プロジェクトが何であり、誰のどの課題を解決するかを示す | 第 1 章 |
| リポジトリ説明（現地語と英語） | 2 言語それぞれ 120 文字以内。プロジェクトの種別と中核用途をそれぞれ示す | 第 1 章 |
| トピックタグ | 小文字英語 20 個を上限まで埋め、`-` で連結する。大文字小文字の混在や英語以外は欠落とみなす | 第 1 章 |
| プロジェクト背景 | 立ち上げの理由、既存手法の不足 | 第 2 章 |
| 中核機能一覧 | モジュール別に分類し、ユーザーが認識できる振る舞いを含める | 第 3 章 |
| 技術スタック | 言語、フレームワーク、ランタイムのバージョン制約 | 第 6 章 |
| 依存関係一覧 | 名称、バージョン、ライセンス、著作権者、入手元アドレス | 第 6 章、NOTICE |
| ライセンス種別 | プロジェクト自身のライセンス。SPDX 識別子でなければならない | 第 19 章 |
| 著作権者 | 個人名または組織の正式名称、および年 | 第 19 章、NOTICE |
| インストールと実行の方法 | 環境要件、コマンド、期待される結果 | 第 7、8 章 |

## 2. 任意項目

設定項目一覧、API 定義、ディレクトリ構成、性能テストデータ、互換性マトリクス、既知の問題、更新履歴、ロードマップ、コントリビューション手順、セキュリティポリシー、スクリーンショットとデモアドレス、外部素材の出所。

## 3. 項目の記入説明と例

| 項目 | 記入説明 | 例 |
| --- | --- | --- |
| プロジェクト名 | リポジトリ名は小文字、数字と `-` を使用する。表示名はブランド表記を使ってよい。両者が一致しない場合は理由を明記する | リポジトリ名 `markdown-lint-cli`、表示名 `Markdown Lint CLI` |
| 一言での位置づけ | カテゴリ語と限定語を含め、形容詞を積み上げず、60 字以内とする | `技術ドキュメントチーム向けの Markdown 規範チェックコマンドラインツール` |
| リポジトリ説明（現地語と英語） | 現地語と英語をそれぞれ独立した文とし、いずれも 120 文字以内とする。スローガンで説明を代替してはならない | `中文：检查 Markdown 文档结构的命令行工具` / `English: A CLI tool for checking Markdown document structure` |
| トピックタグ | すべて小文字英語とし、語間は `-` で連結する。20 個を上限まで埋め、言語、形態、用途、エコシステム、シナリオを網羅する | `go cli markdown linter developer-tools` |
| 技術スタック | 主要言語、フレームワーク、ランタイムのバージョン制約を明記する。「最新バージョン」とは書かない | `Go >= 1.22；Cobra v1.8.x` |
| 依存関係一覧 | 各項目にバージョン、ライセンス、著作権者、公式アドレスを含める。出所が不明な場合は未確認項目として注記する | 付録 C の依存関係一覧表テンプレートを参照 |
| ライセンス種別 | SPDX 識別子を使用し、「オープンソース」「自由に使用可能」などの曖昧な表現を使わない | `MIT` |
| インストールと実行の方法 | 現在の作業ディレクトリ、完全なコマンド、検証可能な期待出力を示す | リポジトリのルートで `go install ./cmd/mdlint` を実行し、バージョン番号を出力する |
| 未確認項目 | 固定のマーキングを用い、欠落内容と補完の責任者を明記する。「暫定」で代替しない | `【要確認：依存関係 foo のライセンス種別、責任者：張三】` |

## 4. 未確認情報のマーキング規則

1. 統一形式：`【要確認：具体的に何が欠けているか】`。これに代えて「暫定」「おそらく」「可能性がある」などの曖昧な表現を使用してはならない。
2. 注記位置：本文の該当箇所に 1 か所、文末の「要確認事項一覧」にもう一度列挙する。
3. ライセンス、著作権、依存関係の出所に関わる未確認項目は、NOTICE に明示的に注記しなければならず、項目全体を省略してはならない。
4. 要確認事項一覧には、番号、項目、欠落内容、補完の責任者、補完予定時期を含めなければならない。責任者または時期のない項目はフェーズ 0 に進んではならない（[実行プロセス](./実行プロセス.md) を参照）。

## 5. 付録 A · プレースホルダー索引

`{{项目名称}}`、`{{一句话定位}}`、`{{当前版本}}`、`{{维护状态}}`、`{{许可证 SPDX}}`、`{{著作权人}}`、`{{年份}}`、`{{分支名}}`、`{{仓库地址}}`、`{{最低运行时版本}}`

使用規則：

1. 本索引は収集フェーズの基本項目のみを列挙する。README の全プレースホルダーとその説明は [README標準テンプレート](./README標準テンプレート.md) のプレースホルダー対照表を基準とする。
2. 正式なプレースホルダーは統一して `{{纯名}}` と書き、波括弧内に説明文、バッククォート、2 つ目のプレースホルダーを入れ子にしてはならない。規範の例にある自然言語の波括弧内容は正式なプレースホルダーとはみなさない。
3. 収集表の自然言語項目はプレースホルダーを直接使用しない。README を生成する際に対照表に従って対応するプレースホルダーへマッピングし、最終ドキュメントに説明的な波括弧内容を一切残してはならない。

## 9. 付録 D · コピー可能なプロジェクト情報収集本文

以下の内容を対象プロジェクトの `项目信息采集表.md` にコピーし、「記入：」以降の内容を項目ごとに置き換える。確認できない項目は第 4 節の規則に従って注記し、第 8 節で一覧化する。

````markdown
# プロジェクト情報収集表

> 本ファイルは、ドキュメント生成に必要な情報を一度に収集するために用いる。記入完了後、収集結果に基づいて README、NOTICE その他の成果ドキュメントを生成する。

## 1. 基本情報

| 項目 | 記入内容 |
| --- | --- |
| リポジトリ名 | 記入：小文字、数字、ハイフンで構成されるリポジトリ名 |
| 表示名 | 記入：対外的に表示するプロジェクト名。リポジトリ名と一致する場合は「リポジトリ名に同じ」と書く |
| リポジトリのアドレス | 記入：完全な HTTPS アドレス |
| 対象ブランチ | 記入：デフォルトブランチ名 |
| 言語コード | 記入：優先言語コード。例：zh-CN |
| 現在のバージョン | 記入：セマンティックバージョニングのバージョン番号、または「未リリース」 |
| 保守状態 | 記入：活発に保守 / 低頻度で保守 / アーカイブ済み |

## 2. 位置づけと適用範囲

| 項目 | 記入内容 |
| --- | --- |
| 一言での位置づけ | 記入：60 字以内。カテゴリ語と限定語を含める |
| リポジトリ説明（現地語） | 記入：120 文字以内 |
| リポジトリ説明（English） | 記入：120 文字以内 |
| トピックタグ | 記入：小文字英語 20 個を上限まで埋め、ハイフンで連結する |
| プロジェクト背景 | 記入：立ち上げの理由と既存手法の不足 |
| 適用シナリオ | 記入：項目ごとに列挙し、各項目にトリガー条件を含める |
| 非適用シナリオ | 記入：項目ごとに列挙し、各項目に理由を示す |
| 強み | 記入：各項目に検証可能な根拠を付す |
| 制約 | 記入：各項目に影響範囲と回避方法を含める |

## 3. 機能と特性

| モジュール | ユーザーが認識できる振る舞い | トリガー条件 | 結果 | 根拠またはリンク |
| --- | --- | --- | --- | --- |
| 記入：モジュール名 | 記入：振る舞いの説明 | 記入：トリガー方法 | 記入：出力または状態変化 | 記入：テスト、スクリーンショット、ドキュメントのリンク |

| 依存関係一覧 | 記入：依存関係一覧ファイルのパス、または本節に付録 C の表を挿入する |

## 5. 提供と利用
````
