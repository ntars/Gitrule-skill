# 依存関係管理規範

> このファイルが解決する問題：依存関係の導入申請、依存関係一覧、固定と更新のテンプレートおよび項目を定義し、ビルドが再現可能で、依存関係が追跡可能で、ライセンスがコンプライアンスに適合することを保証する。

## 1. 規範条文

1. 新しい依存関係を導入する場合は、用途、ライセンス、保守状態を説明しなければならない（[オープンソースコンプライアンス規範](./オープンソースコンプライアンス規範.md) を参照）。
2. ライセンスが互換でコミュニティが活発な依存関係を優先して選ぶ。出所不明またはライセンス不明の依存関係の導入は禁止する。
3. 依存関係のバージョンは lockfile に書き込み、リポジトリにコミットし、クリーンな環境でビルドが再現できることを保証しなければならない（ハードルール H9 と観点 D5 に対応）。
4. バージョン番号は実際に解決されたバージョンで固定し、範囲式を最終成果物として使用してはならない。
5. 依存関係の更新は自動化ツールの支援を受け、更新後は CI を通過しなければならない。脆弱性は速やかに処理するか、緩和措置を記録する。
6. 依存関係一覧と NOTICE は一致していなければならない（[NOTICE規範](./NOTICE規範.md) を参照）。

```markdown
| 項目 | 値 |
| --- | --- |

| 導入バージョン | {{精确版本号}} |
```


## 4. 項目定義

| 項目 | 必須 | 型 | 記入要点 | 例 |
| --- | --- | --- | --- | --- |
| 申請番号 | はい | `DEP-NNN` | 連番で、再利用しない | `DEP-007` |
| 用途 | はい | テキスト | 解決する問題を説明する。「開発が楽になる」は禁止 | `TOML 設定の解析` |
| 代替案の評価 | はい | テキスト | 少なくとも 1 つの代替案を評価する | `toml-js を評価したが、保守停滞のため選ばず` |
| 導入バージョン | はい | 正確なバージョン | `^` や `~` を使用してはならない | `1.2.3` |
| 固定バージョン | はい | 正確なバージョン | lockfile と一致させる | `1.2.3` |
| ライセンス | はい | SPDX ID | [LICENSE規範](./LICENSE規範.md) の書き方と一致させる | `MIT` |
| 保守状態 | はい | 列挙 | 活発 / 低頻度 / 停滞。判定根拠を付す | `活発（直近 30 日にコミットあり）` |
| 推移的依存関係の数 | はい | 数値 | 多い場合はサイズとリスクへの影響を説明する | `12` |
| 既知の脆弱性 | はい | テキスト | ない場合は「なし」と書き、空欄にしてはならない | `なし` |
| 再確認日 | はい | 日付 | 例外項目には再確認日を設ける | `2026-12-31` |

## 5. 記入説明

1. **自作の評価**：まず「標準ライブラリや既存の機能で実現できないか」に答える。自作できるのに導入する場合は理由を説明しなければならない。
2. **ライセンス**：SPDX ID でなければならない。`UNLICENSED` や独自ライセンスは「法務確認が必要」に切り替え、直接導入してはならない。
3. **保守状態**：最終公開日と issue への応答を根拠とする。「誰かが保守しているように見える」は禁止。
4. **バージョン固定**：納品時は lockfile 内が正確に解決されたバージョンでなければならない。`package.json` は範囲式を残してよいが、lockfile は正確でなければならない。
5. **更新のリズム**：自動更新を毎週有効にし、人が確認してマージする。各更新は CI を通過し、ライセンスの変化を確認しなければならない。
6. **脆弱性の処理**：安全なバージョンへのアップグレードを優先する。アップグレードできない場合は緩和措置と再確認日を明記し、[インシデント対応規範](./インシデント対応規範.md) のリスク登録に加える。
7. **一覧の同期**：依存関係を導入または削除した後、依存関係一覧と NOTICE を同期して更新し、三者（lockfile、一覧、NOTICE）が一致していなければならない。

よくある誤り：

| 誤った書き方 | 問題 | 修正方法 |
| --- | --- | --- |
| 「ライブラリを 1 つ使って設定を処理する」 | 具体的なパッケージ名と用途がない | パッケージ名、バージョン、解決する問題を書く |
| ライセンスを「オープンソース」と書く | 互換性を判定できない | SPDX ID を書く |
| lockfile が未コミット | ビルドが再現できない | lockfile をコミットする（H9 に対応） |
| 推移的依存関係の数が空欄 | リスクが見えない | 具体的な数値を記入する |
| 脆弱性に緩和措置を書かない | リスクが追跡されない | 措置と再確認日を補う |

## 6. 完全な例

```markdown
## 依存関係導入申請：remark

- 申請番号：DEP-001
- 申請者：王五
- 用途：Markdown 解析層として、ルールエンジンのノード位置特定の要求（REQ-001、REQ-004）を支える。
- 自作可能か：いいえ。自作では人的上限の範囲内で GFM の境界ケースを網羅できない。
- 代替案の評価：marked を評価したが、中国語のノード位置特定能力が不足するため選ばなかった。

| 項目 | 値 |
| --- | --- |
| パッケージ名 | remark |
| 導入バージョン | 15.0.1 |
| ライセンス | MIT |
| ライセンスの互換性 | 互換 |
| 最終公開日 | 2026-11-02 |
| 保守状態 | 活発（直近 30 日にコミットあり） |
| 週間ダウンロード数 | 4,200,000 |
| 推移的依存関係の数 | 18 |
| 既知の脆弱性 | なし |
| バンドルサイズへの影響 | +42 KB |

- 結論：承認。ADR-0002 と併せて実施する
- 承認者：李四
```
