# 監査レポート形式

> このファイルが解決する問題：監査レポートの唯一の納品形式、フィールド要件、記入例を定義し、レポートが別のエージェントによってそのまま実行できることを保証する。

レポートは監査工程の唯一の成果物である。各問題は証拠・責任主体・アクションを同時に備えなければならず、実行できない結論をレポートに記載してはならない。

## 1. レポートの骨格

````markdown
# プッシュ監査レポート · {{仓库名}}

結論：{{结论}}
モード：{{模式}}
リポジトリ：{{仓库名}} · {{可见性}} · {{许可证}} · 既定ブランチ {{默认分支}}

## 一、ゲート状態
| ゲート | 状態 | 未決項目 |
| --- | --- | --- |
| A セキュリティ | {{门禁状态}} | {{未决项}} |
| B 品質 | {{门禁状态}} | {{未决项}} |
| C トップページ | {{门禁状态}} | {{未决项}} |

## 二、問題一覧
| レベル | 次元 | 問題 | 証拠（パス:行 / コマンド出力） | 責任エージェント | アクション |
| --- | --- | --- | --- | --- | --- |
| {{等级}} | {{维度}} | {{问题}} | {{证据}} | {{责任agent}} | {{动作}} |

## 三、ドキュメントマトリクスの状態
| ファイル | 状態 | 欠落/修正待ち項目 |
| --- | --- | --- |
| {{文件路径}} | {{状态}} | {{待改项}} |

## 四、プッシュ実行チェックリスト
- [ ] {{推送规则}}

## 五、通過の説明
{{放行说明}}
````

## 2. フィールド定義

| フィールド | 必須 | 型 | 記入の要点 | 例 |
| --- | --- | --- | --- | --- |
| リポジトリ名 | はい | テキスト | GitHub のリポジトリ名と一字一句一致させる | `markdown-lint-cli` |
| 結論 | はい | 列挙 | `ALLOW PUSH` または `BLOCK PUSH` のみ。P0 がゼロでない場合は必ず後者 | `BLOCK PUSH` |
| モード | はい | 列挙 | 非公開の一時スクリプト用リポジトリは「降格監査」と記し、それ以外は「完全監査」 | `完全監査` |
| 可視性 | はい | 列挙 | `private` / `public`。公開前にライセンスを再確認する | `private` |
| ライセンス | はい | SPDX 識別子 | ライセンスがなければ `NONE` と記し、この場合の結論は必ず `BLOCK PUSH` | `MIT` |
| 既定ブランチ | はい | テキスト | 実際のブランチ名を記し、想定の `main` を記さない | `main` |
| ゲート状態 | はい | 列挙 ×3 | A/B/C を各 1 行。「未決項目」欄に `SKIP` の理由を注記する | `FAIL` |
| 未決項目 | 条件付き必須 | テキスト | 状態が `FAIL` または `SKIP` の場合は必須。阻害または省略の理由を列挙する | `D1 で .env を検出` |
| レベル | はい | 列挙 | `P0` 阻害 / `P1` プッシュ前に修正または登録 / `P2` 提案 | `P0` |
| 次元 | はい | `D1`–`D14` | 番号は [監査次元マトリクス](./監査次元マトリクス.md) を参照 | `D1` |
| 問題 | はい | テキスト | 事実を一文で述べ、推測や情緒的な表現を記さない | `ルートに .env が存在する` |
| 証拠 | はい | パス:行 またはコマンド出力 | 再確認可能でなければならない。証拠が取れない場合は `SKIP + 原因` と記す | `.env:3` |
| 責任エージェント | はい | エージェント名 | 具体的な実行役割を記し、「関係者」と記さない | `security-auditor` |
| アクション | はい | テキスト | そのまま実行できる操作とし、対象ファイルを含める | `.env を削除し、鍵をローテーションして履歴をクリーンアップする` |
| ファイルパス | はい | テキスト | [ドキュメントマトリクス](./ドキュメントマトリクス.md) の一覧に従って項目ごとに列挙する | `SECURITY.md` |
| ドキュメントマトリクスの状態 | はい | 表の各行 | ファイルごとに存在・欠落・修正待ちを明記する | `SECURITY.md 欠落` |
| プッシュ実行チェックリスト | はい | チェックボックスリスト | [プッシュとリリース規範](./プッシュとリリース規範.md) のルールに従って 1 項目ずつ展開する | `- [ ] .gitignore が有効であることを確認する` |
| 通過の説明 | はい | テキスト | 阻害時は原因と解除条件を記し、通過時は満たしたハードルールを記す | `P0 ゼロ化後に再確認可能` |

## 3. 記入説明

1. **結論を優先する**：まず P0 の件数を判定し、その後で結論を記す。いずれかの P0 がゼロでない場合、`ALLOW PUSH` を出力してはならない。
2. **証拠を必須とする**：各問題には `パス:行番号` または複製可能なコマンド出力がなければならない。証拠のない結論は `SKIP` と記して原因を明記し、`PASS` と記してはならない。
3. **責任を役割に割り当てる**：責任エージェントには [監査次元マトリクス](./監査次元マトリクス.md) の役割名を用い、1 つの問題に 1 つの責任主体を対応させる。
4. **アクションを実行可能にする**：アクションは対象ファイルと操作種別を明示しなければならない。「後続で対応」「各自調整」は無効とみなす。
5. **ゲートを一致させる**：A/B/C の 3 行の状態は問題一覧と対応させる。いずれかのゲートが `FAIL` の場合、結論は必ず `BLOCK PUSH` とする。
6. **ドキュメントマトリクスを項目ごとに扱う**：一覧に従ってファイルごとに列挙し、「ドキュメントはほぼ揃っている」とだけ記してはならない。
7. **チェックリストを展開する**：プッシュ実行チェックリストはルールを 1 項目ずつ展開しなければならず、「規範に従って実行」で代替してはならない。

よくある誤り：

| 誤った記述 | 問題 | 修正方法 |
| --- | --- | --- |
| 証拠欄に「問題がありそう」と記す | パスも出力もなく、再確認できない | `ファイルパス:行番号` またはコマンド出力を補う |
| P0 がゼロでないのに `ALLOW PUSH` と記す | ハードルール違反 | `BLOCK PUSH` に変更し、解除条件を明記する |
| チェックできない項目に `PASS` と記す | 結果の捏造 | `SKIP` と記し、未決項目に原因を注記する |
| 責任主体に「関係者」と記す | 責任主体が存在しない | 具体的なエージェント名を記す |
| アクションに「後続で対応」と記す | 実行できない | 対象ファイルと具体的な操作を明記する |
| 既定ブランチを確認せず `main` と記す | 実際と一致しない | `git branch` の出力を基準とする |

## 4. 完全な例

以下は `BLOCK PUSH` の完全な記入例である：

````markdown
# プッシュ監査レポート · markdown-lint-cli

結論：BLOCK PUSH
モード：完全監査
リポジトリ：markdown-lint-cli · private · NONE · 既定ブランチ main

## 一、ゲート状態
| ゲート | 状態 | 未決項目 |
| --- | --- | --- |
| A セキュリティ | FAIL | D1 で .env を検出、D2 に LICENSE なし |
| B 品質 | SKIP | リポジトリに依存関係が未インストールで、ビルドとテストを実行できない |
| C トップページ | FAIL | README にインストールのセクションと最小例がない |

## 二、問題一覧
| レベル | 次元 | 問題 | 証拠（パス:行 / コマンド出力） | 責任エージェント | アクション |
| --- | --- | --- | --- | --- | --- |
| P0 | D1 | ルートに .env が存在する | `.env:3` に DATABASE_URL | security-auditor | .env を削除し、データベース資格情報をローテーションして履歴をクリーンアップする |
| P0 | D2 | ライセンスファイルがない | `ls LICENSE` の出力が `No such file or directory` | license-checker | リポジトリ所有者がライセンスを確定したうえで LICENSE を生成する |
| P1 | D13 | README にインストールのセクションがない | `README.md:1-28` に「インストール」の見出しがない | readme-writer | README標準テンプレートに従ってインストールと最小例を追記する |

## 三、ドキュメントマトリクスの状態
| ファイル | 状態 | 欠落/修正待ち項目 |
| --- | --- | --- |
| README.md | 修正待ち | インストールのセクションと最小例がない |
| LICENSE | 欠落 | 所有者によるライセンス種別の確定待ち |
| SECURITY.md | 欠落 | 未作成 |

## 四、プッシュ実行チェックリスト
- [ ] git status がクリーンであることを確認する
- [ ] すべてのシークレットスキャンを実行する（履歴のコミットを含む）
- [ ] ローカルで build、test、lint を通過する
- [ ] ドキュメントマトリクスが揃っている

## 五、通過の説明
阻害原因：P0 が 2 件（資格情報の漏えい、ライセンスなし）あり、さらに依存関係が未インストールのため品質ゲートを判定できない。解除条件：鍵のローテーションと履歴のクリーンアップを完了し、ライセンスを確定し、ビルド可能な環境でテストを再実行して P0 をゼロにした後に再確認する。
````

`ALLOW PUSH` の場合、第 5 節には「すべてのハードルールを満たし、三層ゲートがすべて PASS であり、プッシュを実行できる。」と記してよい。その他の各節は実情に応じて記入し、証拠とチェックリストを省略してはならない。

## 5. 納品順序

1. ルート README の言語ナビゲーションの全内容。
2. 各完了済み言語ディレクトリの README の全内容。言語コードとファイルパスを 1 つずつ列挙する。
3. NOTICE ファイルの内容。
4. LICENSE 方針の説明（利用者がライセンスを指定していない場合は、候補と差異のみを示し、直接生成しない）。
5. 確認待ち事項の集約。
6. 監査レポート（本レポート）。
7. GitHub プッシュの手順。
