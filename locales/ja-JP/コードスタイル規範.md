# コードスタイル規範

> このファイルが解決する問題：コードスタイル設定テンプレート、命名規約表、コメント規則、記入説明を定義し、スタイルの相違を減らし、可読性とレビュー効率を高める。

## 1. 規範条文

1. スタイル規則は自動化ツールを基準とし、人間はツールで網羅できない部分のみを扱う。
2. フォーマット設定はリポジトリにコミットし（例：フォーマッタ設定ファイル）、異なる環境間の一貫性を保証しなければならない。
3. CI にフォーマットチェックを組み込み、通過しない場合はマージしてはならない（[テスト規範](./テスト規範.md) を参照）。
4. マジックナンバーとハードコードされた定数を使用してはならず、名前付き定数として抽出しなければならない。
5. 行末は LF に統一し、ファイルは改行で終わらせる（観点 D3 リポジトリ衛生に対応）。

## 2. スタイル設定テンプレート

```markdown
# コードスタイル規約：{{项目名称}}

設定バージョン：{{v1.0}} ｜ 対象言語とバージョン：{{如 TypeScript 5.x}} ｜ フォーマッタ：{{如 Prettier 3.x}}

## フォーマット規則（ツールによる強制）
| 規則 | 値 | ツール設定項目 | 協議可能か |
| --- | --- | --- | --- |
| インデント | {{2 空格 / 4 空格 / Tab}} | {{配置项名}} | いいえ |
| 行幅 | {{100 字符}} | {{配置项名}} | いいえ |
| 引用符 | {{单引号 / 双引号}} | {{配置项名}} | いいえ |
| 行末 | LF | `endOfLine: lf` | いいえ |
| ファイル末尾の改行 | 必須 | ツールの既定 | いいえ |
| セミコロン | {{有 / 无}} | {{配置项名}} | いいえ |

## 命名規約（ツールで強制できず、人によるレビュー）
| 対象 | 規則 | 正例 | 反例 |
| --- | --- | --- | --- |
| 変数 | {{camelCase}} | `userName` | `UserName` |
| 定数 | {{UPPER_SNAKE_CASE}} | `MAX_RETRY` | `maxRetry` |
| 関数 | {{动词开头 camelCase}} | `parseConfig` | `configParse` |
| クラス / 型 | {{PascalCase}} | `ConfigLoader` | `config_loader` |
| ファイル名 | {{kebab-case}} | `config-loader.ts` | `ConfigLoader.ts` |
| 真偽値 | {{is/has/can 前缀}} | `isValid` | `valid` |
| コレクション | {{复数名词}} | `items` | `itemList` |

## コメント規則
- コメントを必ず書く場面：{{公开 API 的契约、非直观算法、绕开限制的临时方案}}
- 禁止するコメント：{{复述代码、无信息量、失效的旧注释、情绪化表述}}
- コメントの言語：{{与项目主语言一致}}
- TODO の形式：`// TODO({{负责人}}): {{事项}} — {{计划版本}}`

## ファイル構成
1. import の順序：{{标准库 → 第三方 → 本地模块，组内字典序}}
2. 宣言の順序：{{常量 → 类型 → 函数 → 导出}}
3. 1 ファイルの行数上限：{{300 行，超出须拆分}}

## 例外一覧
| 場面 | 例外規則 | 承認者 | 有効期限 |
| --- | --- | --- | --- |
| {{如生成代码}} | {{不参与格式化}} | {{姓名}} | {{至 v2.0}} |
```

## 3. 設定項目定義

| 項目 | 必須 | 型 | 記入要点 | 例 |
| --- | --- | --- | --- | --- |
| 設定バージョン | はい | テキスト | スタイル規則の変更時に増分する | `v1.0` |
| 対象言語とバージョン | はい | テキスト | メジャーバージョンを明示し、規則の漂流を避ける | `TypeScript 5.x` |
| フォーマッタ | はい | テキスト | lockfile のバージョンと一致させる | `Prettier 3.2` |
| 規則.値 | はい | 列挙 / 数値 | 一意でなければならず、「場合による」は禁止 | `2 スペース` |
| 協議可能か | はい | 列挙 | いいえ / はい。「はい」とする場合は協議条件を示す | `いいえ` |
| 命名の正例 | はい | コード | プロジェクトの既存コードから選ぶ | `parseConfig` |
| 命名の反例 | はい | コード | 実際に犯しやすい書き方でなければならない | `configParse` |
| TODO の責任者 | はい | テキスト | 「チーム」と書くことは禁止 | `张三` |
| 例外の有効期限 | はい | バージョン / 日付 | 期限到来時は再確認する | `至 v2.0` |

## 4. 記入説明

1. **ツール優先**：ツールで強制できる規則はすべてフォーマッタ設定に書き、人の記憶に頼らない。人による管理は命名、コメント、ファイル構成のみとする。
2. **行幅の値**：レビュー画面の幅を踏まえて設定する。一般的には 100 または 120 とし、一度決めたら個別ファイルで上書きしてはならない。
3. **命名の正例**：プロジェクトの既存コードから実在する名称を選び、教科書的なプレースホルダーの使用は禁止する。
4. **真偽値の命名**：`is`/`has`/`can` の接頭辞は意味と一致しなければならない。`isReady` が動作を表してはならない。
5. **TODO**：責任者、事項、計画バージョンを必ず含める。計画のない TODO はメインブランチに入れてはならない。
6. **例外一覧**：各例外には承認者と有効期限を要する。期限到来後に再確認されなければ自動的に失効する。

よくある誤り：

| 誤った書き方 | 問題 | 修正方法 |
| --- | --- | --- |
| 「コードはできるだけ簡潔に」 | 判定不能 | 関数長の上限など検査可能な規則に変える |
| 命名表に規則だけで反例がない | レビュー時に照合できない | 実際に犯しやすい反例を補う |
| コメントに「ここには以前バグがあった」 | 情報がなく失効しやすい | 現在の振る舞いと理由を説明する形に変える |
| TODO に責任者がない | 誰も追跡しない | 責任者と計画バージョンを補う |
| 例外に有効期限がない | 永久の免除になる | 有効期限と再確認者を補う |

## 5. 完全な例

```markdown
# コードスタイル規約：markdown-lint-cli

設定バージョン：v1.0 ｜ 対象言語とバージョン：TypeScript 5.x ｜ フォーマッタ：Prettier 3.2

## フォーマット規則（ツールによる強制）
| 規則 | 値 | ツール設定項目 | 協議可能か |
| --- | --- | --- | --- |
| インデント | 2 スペース | `tabWidth: 2` | いいえ |
| 行幅 | 100 文字 | `printWidth: 100` | いいえ |
| 引用符 | シングルクォート | `singleQuote: true` | いいえ |
| 行末 | LF | `endOfLine: lf` | いいえ |
| セミコロン | あり | `semi: true` | いいえ |

## 命名規約（人によるレビュー）
| 対象 | 規則 | 正例 | 反例 |
| --- | --- | --- | --- |
| 関数 | 動詞で始まる camelCase | `parseRules` | `rulesParser` |
| 定数 | UPPER_SNAKE_CASE | `DEFAULT_RULES` | `defaultRules` |
| ファイル名 | kebab-case | `rule-loader.ts` | `RuleLoader.ts` |

## コメント規則
- コメントを必ず書く場面：規則のマッチング意味論、上流 API の振る舞いを回避する処理。
- 禁止するコメント：コードの復述、「バグを 1 つ修正した」、責任者のない TODO。
- TODO の形式：`// TODO(王五): 一時パーサーの置き換え — v2.0`

## 例外一覧
| 場面 | 例外規則 | 承認者 | 有効期限 |
| --- | --- | --- | --- |
| fixtures ディレクトリ | フォーマット対象外 | 李四 | v2.0 まで |
```
