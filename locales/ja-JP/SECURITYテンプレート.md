# SECURITYテンプレート

> このファイルが解決する問題：そのまま複製できるセキュリティポリシーのテンプレートを提供し、プロジェクトが SECURITY.md を生成できるようにする。対応バージョン、脆弱性の報告経路、対応フロー、開示原則を明確にし、付随する記入説明では報告経路の選定と機密情報の取り扱いを扱う。

## 1. 使用説明

1. 第 3 節「テンプレート本文」の全内容を複製し、プロジェクトルートの `SECURITY.md` として新規作成する。
2. 第 4 節に従ってプレースホルダーを置き換える。報告経路は実際に到達可能で、攻撃面を公開しないアドレスでなければならない。
3. 第 5 節のシナリオ別変種に従って調整する。複数バージョンを保守しないプロジェクトでは、対応バージョン表から旧バージョンの行を削除する。
4. セキュリティルールと機密情報の要件は [セキュリティとプライバシー規範](./セキュリティとプライバシー規範.md) を参照。コミュニティガバナンスの次元は [監査次元マトリクス](./監査次元マトリクス.md) を参照。

## 2. カスタマイズ原則

- **非公開経路を優先する**：脆弱性の報告は非公開経路で行い、報告者に公開イシューで詳細を開示するよう求めてはならない。
- **期限を明確にする**：初回応答と修正の時間範囲を示し、無期限の約束を避ける。
- **情報を最小化する**：報告者には再現に必要な最小限の情報提供を求め、実際の本番データの提出を禁止する。
- **法務と整合させる**：開示原則は適用法令およびプラットフォームポリシーと整合させ、規制業種では法務の審査を受けなければならない。

## 3. テンプレート本文

```markdown
# セキュリティポリシー

> このファイルは {{项目名称}} のセキュリティサポート範囲と脆弱性の報告方法を説明するものであり、セキュリティ研究者、コントリビューター、利用者に適用されます。

## 対応バージョン

| バージョン | セキュリティ報告を受け付けるか |
| --- | --- |
| {{当前版本}} | はい |
| {{上一版本}} | {{是否接受}} |
| それ以前のバージョン | いいえ |

## 報告経路

公開イシュー、ディスカッション、ソーシャルチャネルを通じてセキュリティ脆弱性を報告しないでください。以下の非公開経路から提出してください：

- セキュリティメール：{{真实可达的安全邮箱}}
- 非公開報告窓口：{{私有漏洞报告地址}}

上記の経路がない場合は、{{备用私有联系方式}} からメンテナーに連絡してください。

## 報告内容

対応効率を高めるため、可能な限り以下を提供してください：

- 影響を受けるバージョンとコンポーネント；
- 脆弱性の種類と潜在的な影響；
- 最小限の再現手順または概念実証；
- 推奨する修正方針（任意）。

実際の本番データ、鍵、個人を特定できる情報を提出しないでください。

## 対応フロー

| 段階 | 時間範囲 | 説明 |
| --- | --- | --- |
| 受領確認 | {{首次响应时限}} | メンテナーが報告の受領を確認する |
| 初期評価 | {{评估时限}} | セキュリティ問題に該当するか、影響範囲を判断する |
| 修正と検証 | {{修复时限}} | 修正を完了して検証する。複雑な問題は別途協議する |
| 公開リリース | 修正完了後 {{发布延迟}} | セキュリティアドバイザリと修正版をリリースする |

## 開示原則

- メンテナーは修正のリリースまで、報告者の身元と報告内容を秘密に保つ。
- メンテナーの同意なく、報告者は修正リリース前に脆弱性の詳細を公開してはならない。
- 修正リリース後、メンテナーはセキュリティアドバイザリで報告者に謝辞を述べる（報告者の同意を得た場合）。
- 善意であり本ポリシーに適合するセキュリティ研究は責任を問われない。

## 例外と免責

本ポリシーはセキュリティ保証を約束するものではなく、プロジェクトの内容は「現状のまま」提供されます。詳細は [免責事項](./DISCLAIMER.md) と [LICENSE](./LICENSE) を参照してください。
```

## 4. プレースホルダー対照表とフィールド定義

| プレースホルダー | 必須 | フィールド定義 | 記入例 |
| --- | --- | --- | --- |
| `{{项目名称}}` | はい | プロジェクトの対外名称 | `FooBar` |
| `{{当前版本}}` | はい | 保守中の最新バージョンまたは `main` | `v2.3.0` |
| `{{上一版本}}` | いいえ | なお保守中の直前バージョン | `v2.2.x` |
| `{{是否接受}}` | はい | 当該バージョンでセキュリティ報告を受け付けるか | `はい` |
| `{{真实可达的安全邮箱}}` | はい | セキュリティ報告専用のメールアドレス | `security@example.com` |
| `{{私有漏洞报告地址}}` | はい | 非公開報告の窓口 | `https://github.com/owner/repo/security/advisories/new` |
| `{{备用私有联系方式}}` | いいえ | 主経路が使用できない場合の代替手段 | `メンテナーアカウントへのダイレクトメッセージ` |
| `{{首次响应时限}}` | はい | 報告の受領を確認するまでの時間範囲 | `3 営業日` |
| `{{评估时限}}` | はい | 初期評価を完了するまでの時間範囲 | `7 営業日` |
| `{{修复时限}}` | はい | 修正を完了するまでの時間範囲 | `30 日` |
| `{{发布延迟}}` | はい | 修正後、公開リリースまでの間隔 | `7 日` |

## 5. 記入説明とシナリオ別変種

| シナリオ | 必ず残すセクション | 削除可能なセクション | 調整の要点 |
| --- | --- | --- | --- |
| 単一バージョンのプロジェクト | 報告経路、報告内容、対応フロー、開示原則 | 対応バージョン表から旧バージョンの行を削除 | 現行バージョンは `main` または最新タグと記す |
| 複数バージョンの保守 | すべて | なし | 報告を受け付けるバージョンを 1 行ずつ列挙する |
| 個人プロジェクト | すべて | 対応バージョンは簡略化してよい | 非公開経路には長期保有のメールアドレスを使う |
| 企業プロジェクト | すべて | なし | 期限は内部のセキュリティ制度と一致させ、法務の審査を受ける |
| 規制業種 | すべて | なし | コンプライアンス通報義務とデータ保持要件を追加する |

よくある誤りの対照：

| 誤った記述 | 結果 | 正しい記述 |
| --- | --- | --- |
| 「Issue で脆弱性を報告してください」 | 詳細が公開され、リスクが拡大する | 非公開経路を使用する |
| 「できるだけ早く対応します」 | 明確な見通しがなく、報告者が判断できない | 段階ごとに時間範囲を示す |
| 期限を「24 時間以内に修正」と記す | 過度な約束となり、履行できない | 妥当な範囲を記し、複雑な問題は別途協議すると注記する |
| マスキングを求めていない | 報告者が実際の本番データを提出するおそれがある | 実データと鍵の提出を明確に禁止する |

## 6. 完全な例

以下は報告経路の段落を記入済みにした例であり、形式の参考にのみ供する。

```markdown
## 報告経路

公開イシュー、ディスカッション、ソーシャルチャネルを通じてセキュリティ脆弱性を報告しないでください。以下の非公開経路から提出してください：

- セキュリティメール：security@example.com
- 非公開報告窓口：https://github.com/example/democli/security/advisories/new

実際の本番データ、鍵、個人を特定できる情報を提出しないでください。
```
