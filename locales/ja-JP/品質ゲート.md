# 品質ゲート

> このファイルが解決する問題：三層ゲートの通過条件、判定チェックリストのテンプレートとフィールドを定義し、プッシュの通過判定を統一・実行可能・再検証可能にする。

## 1. 三層ゲート

| 層 | 意味 | 通過条件 |
| --- | --- | --- |
| Gate A · セキュリティゲート | 秘密鍵、プライバシー、ライセンス、大容量ファイル | P0 ゼロ |
| Gate B · 品質ゲート | ビルド、テスト、lint、コミット規範、ブランチ保護 | P0 ゼロ、P1 は記録済みで未対応 |
| Gate C · トップページゲート | README、メタデータ、ドキュメントマトリクス、バッジ、リンク | P0 ゼロ、P1 ≤ 3 かつ日程設定済み |

A、B、C のすべてがグリーンである場合にのみ `✅ ALLOW PUSH` を出力します。未通過の項目は修正するか理由を明記し、結果を [監査レポート形式](./監査レポート形式.md) に記録します。

## 2. 納品前の 14 項目判定

ドキュメントの納品前に項目ごとに判定し、未通過の項目は修正するか理由を明記します。

| 番号 | チェック項目 | 判定基準 |
| --- | --- | --- |
| G1 | 口語表現と曖昧さ | 全文を検索して口語表現と曖昧な指示語を洗い出し、ヒット数が 0 であること |
| G2 | セクションの完全性 | 中国語版と英語版がともに 20 章で、順序が一致していること |
| G3 | 機能とディレクトリの整合性 | README が説明する機能のすべてに対応するモジュールがディレクトリ構造内に存在すること |
| G4 | 機能の根拠 | 各機能に根拠があるか、未定として明記されていること |
| G5 | 設計詳細の網羅 | 第 8 節の 10 分類すべてに項目があるか、該当しない旨が明記されていること |
| G6 | 依存関係の完全性 | 直接依存と間接依存の数が依存関係ツリーと一致すること |
| G7 | ライセンスの正確性 | 各依存関係の SPDX 識別子が公式の宣言と一致すること |
| G8 | ライセンス原文 | 全文の添付を要するライセンスすべてに英語原文が添付されていること |
| G9 | 著作権表示 | プロジェクト自身と他者の著作権表示がともに完全であること |
| G10 | 二言語の同期 | セクション、表、用語、コードブロックが両側で一致していること |
| G11 | コマンドの実行可能性 | インストール、クイックスタート、プッシュのコマンドがそのまま実行できること |
| G12 | 未確認事項の集約 | すべての未確認事項が集約され、位置を特定できること |
| G13 | 素材の出典 | すべての素材に出典とライセンスの記録があること |
| G14 | 機密情報 | 秘密鍵、トークン、内部ネットワークアドレス、個人のプライバシー情報がないこと |

## 4. フィールド定義

| フィールド | 必須 | 型 | 記入の要点 | 例 |
| --- | --- | --- | --- | --- |
| 判定者 | はい | テキスト | 一意であること、「チーム」は禁止 | `王五` |
| 結論 | はい | 列挙 | PASS / FAIL / SKIP | `PASS` |
| 根拠 | はい | テキスト | パス + 行番号またはコマンド出力、根拠のない判定は禁止 | `gitleaks: 0 findings` |
| レベル | 条件付き必須 | 列挙 | FAIL の場合は P0 / P1 / P2 が必須 | `P0` |
| 対応 | 条件付き必須 | テキスト | FAIL の場合は具体的なアクションと責任者が必須 | `鍵をローテーションし履歴をクリーンアップ` |
| SKIP の理由 | 条件付き必須 | テキスト | SKIP の場合は必須、理由なきスキップは禁止 | `ビルドスクリプトなし` |
| 通過結論 | はい | 列挙 | ALLOW PUSH / BLOCK PUSH | `BLOCK PUSH` |
| ブロック原因 | 条件付き必須 | テキスト | BLOCK の場合は必須、P0 を列挙 | `A2 履歴内の秘密鍵がヒット` |

## 5. 記入説明

1. **根拠の必須化**：各判定には根拠が必要です。根拠のない PASS は無効とみなし、SKIP に変更して理由を説明します。
2. **レベルの対応**：FAIL にはレベルを付けます。P0 は通過を直接ブロックし、P1 は未対応事項として登録し、P2 は提案として記録します。
3. **Gate C の基準**：P1 ≤ 3 かつ日程設定済みの場合にのみ PASS とします。超過する場合はレベルを下げて対応するか、ブロックします。
4. **SKIP の使用**：チェックできない場合は SKIP + 理由を付けます。PASS と書いてはなりません。条件が整った後に再チェックします。
5. **一貫性**：ゲート判定は [監査次元マトリクス](./監査次元マトリクス.md) の P0/P1/P2 レベル、[ハードルール](./ハードルール.md) のブロック規則と一致していなければなりません。
6. **通過**：3 項目すべてがグリーンの場合にのみ `✅ ALLOW PUSH` を出力します。いずれかが FAIL なら `⛔ BLOCK PUSH` を出力し、ブロック原因を列挙します。
7. **納品形式**：判定結果は [監査レポート形式](./監査レポート形式.md) に従って出力します。通過後は [プッシュとリリース規範](./プッシュとリリース規範.md) を実行します。

よくある誤り：

| 誤った記述 | 問題 | 修正方法 |
| --- | --- | --- |
| 結論が PASS だが根拠が空 | 判定が無効 | 根拠を補うか SKIP に変更 |
| P0 が未解消のまま ALLOW PUSH と記述 | ハードルール違反 | BLOCK PUSH に変更 |
| SKIP に理由がない | チェック漏れの疑い | 理由を補う |
| Gate C で P1 が 5 項目あるのに PASS | 基準超過 | レベルを下げるかブロック |
| 判定結果が文章のみでチェックリストがない | 再検証できない | テンプレートに項目ごとに記入 |

## 6. 完全な例

```markdown
# ゲート判定：markdown-lint-cli v1.0.0

判定日：2026-11-20 ｜ 判定者：王五 ｜ リポジトリ：example/markdown-lint-cli

## Gate A · セキュリティゲート
| 番号 | チェック項目 | 結論 | 根拠 | レベル | 対応 |
| --- | --- | --- | --- | --- | --- |
| A1 | 作業ツリーの秘密鍵 | PASS | gitleaks detect: 0 findings | — | — |
| A2 | 履歴内の秘密鍵 | PASS | gitleaks --log-opts=--all: 0 findings | — | — |
| A4 | LICENSE の有無と種類 | PASS | LICENSE 第 1 行 MIT | — | — |
| A5 | 大容量ファイルと LFS | PASS | find -size +50M: なし | — | — |

結論：PASS、未決項目：なし

## Gate B · 品質ゲート
| 番号 | チェック項目 | 結論 | 根拠 | レベル | 対応 |
| --- | --- | --- | --- | --- | --- |
| B1 | ビルドの成功 | PASS | run #128 | — | — |
| B2 | テストの成功 | PASS | 132/132 passed | — | — |
| B4 | コミットメッセージ規範 | PASS | git log --oneline すべて適合 | — | — |

## 総合判定
- A：PASS ｜ B：PASS ｜ C：PASS

- ブロック原因：なし
```
