# 移行ガイド規範

> このファイルが解決する問題：破壊的変更時の移行ガイドの構造、内容要素、公開時期を定義し、利用者が手順に沿って旧バージョンから新バージョンへ円滑にアップグレードできるようにする。

## 1. トリガー条件

以下のいずれかに該当する場合は移行ガイドを提供しなければならない：

1. コミットメッセージに `BREAKING CHANGE:` または `feat!:` / `fix!:` を含む（[コミットメッセージ規範](./コミットメッセージ規範.md) を参照）。
2. 設定キー名、デフォルト値、または優先順位が変化する。
3. API のシグネチャ、戻り値の構造、またはエラーコードが変化する。
4. 最低ランタイムバージョンが引き上げられる、またはあるプラットフォームをサポートしなくなる。
5. ディレクトリ構造またはファイル命名が変更され、利用者の参照パスに影響する。

## 2. ファイルの位置と命名

1. 変更が小さい移行の説明は `CHANGELOG.md` の該当バージョンの項目に書く。
2. 変更が大きく、複数手順の操作を伴う場合は、`docs/migration/` ディレクトリ配下にファイルを別途作成し、バージョンごとに命名する（例：`docs/migration/v2.md`）。
3. メジャーバージョンをまたぐ完全な移行経路は `docs/migration/README.md` に索引を作成する。
4. README には移行の注意喚起とリンクのみを置き、手順を展開しない（[ドキュメントマトリクス](./ドキュメントマトリクス.md) を参照）。

## 3. ドキュメントの構造

移行ガイドは以下の順序で構成しなければならない：

1. **タイトルとバージョン**：移行元バージョンと移行先バージョンを明示する（例：「v1.x から v2.0 への移行」）。
2. **影響の概観**：変更のカテゴリと影響範囲を列挙し、どの利用者が必ず移行すべきかを説明する。
3. **前提条件**：移行前に完了しておくべき準備（バックアップ、環境バージョンのアップグレードなど）。
4. **変更一覧**：破壊的変更を項目ごとに列挙し、各項目に「旧動作」「新動作」「変更理由」を含める。
5. **移行手順**：実行可能な操作を番号付きで列挙し、コマンドまたはコード例を示す。
6. **検証方法**：移行後に成功を確認する方法を示し、確認コマンドまたは期待される出力を提示する。
7. **ロールバック方法**：移行に失敗した場合に旧バージョンへ戻す方法。
8. **よくある質問**：頻出する質問と回答を列挙する。
9. **サポートの入手**：issue、ディスカッション、ドキュメントサイトを案内する。

### 3.1 複製可能な空テンプレート

以下のテンプレートは第 3 節の九項目の構造に項目ごとに対応しており、複製してプレースホルダーを置き換えればそのまま使用できる：

````markdown
# {{源版本}} から {{目标版本}} への移行

> 本ガイドは {{源版本}} から {{目标版本}} へアップグレードするために必要なすべての操作を説明するものであり、{{适用使用者范围}} に適用されます。

## 1. 影響の概観

| 変更カテゴリ | 具体的内容 | 影響範囲 | 移行必須か |
| --- | --- | --- | --- |
| {{变更类别}} | {{变更内容}} | {{受影响的使用者场景}} | {{是否必须迁移}} |

## 2. 前提条件

- {{前置准备}}
- {{检查项与确认命令}}

## 3. 変更一覧

### {{变更项名称}}

- 旧動作：{{旧版本行为}}
- 新動作：{{新版本行为}}
- 変更理由：{{变更原因}}

移行前：

```{{代码语言}}
{{旧配置或旧代码}}
```

移行後：

```{{代码语言}}
{{新配置或新代码}}
```

## 4. 移行手順

1. {{迁移步骤}}
2. {{迁移步骤}}
3. {{人工处理步骤}}

## 5. 検証方法

```bash
{{可独立运行的检查命令}}
```

期待される出力：{{预期结果}}

## 6. ロールバック方法

1. {{恢复旧版本的操作}}
2. {{恢复旧配置的操作}}

## 7. よくある質問

### {{问题}}

回答：{{解答}}

## 8. サポートの入手

- 問題報告：{{issue 地址}}
- ディスカッション：{{讨论区地址}}
- 関連ドキュメント：{{文档链接}}
````

プレースホルダー対照：

| プレースホルダー | 必須 | 記入の要点 |
| --- | --- | --- |
| `{{源版本}}` / `{{目标版本}}` | はい | 対象のタグと一致させる。書式は `vX.Y.Z` |
| `{{适用使用者范围}}` | はい | どの利用者が必ず移行すべきかを明記し、曖昧な表現を避ける |
| `{{变更类别}}` | はい | 設定、API、ランタイム、ディレクトリの四類のうち少なくとも一類 |
| `{{是否必须迁移}}` | はい | その変更が利用者に移行の実行を求めるかどうかを明記する |
| `{{旧行为}}` / `{{新行为}}` | はい | 項目ごとに対照させ、片側だけを書いてはならない |
| `{{代码语言}}` | はい | コードブロックの言語識別子（例：`yaml`、`json`、`js`） |
| `{{前置准备}}` | はい | 移行前に完了すべきバックアップと環境確認 |
| `{{迁移步骤}}` | はい | 各手順は直接実行でき、コマンドまたはコードを含む |
| `{{人工处理步骤}}` | はい | 自動移行できない手順はここで明示的に示さなければならない |
| `{{检查命令}}` / `{{预期结果}}` | はい | コマンドは単独で実行でき、結果は判定可能であること |
| `{{回滚方式}}` | はい | 省略してはならない。第 7 節の禁止事項を参照 |

## 4. 内容要件

### 4.1 変更対照の例

```markdown
### 設定項目 `timeout` を `timeoutMs` に改名

- 旧動作：設定ファイルで `timeout: 5000` を使用する。単位は秒。
- 新動作：`timeoutMs: 5000` に変更する。単位はミリ秒。
- 変更理由：時間の単位を統一し、API パラメータとの不一致を避ける。

移行前：

```yaml
timeout: 5
```

移行後：

```yaml
timeoutMs: 5000
```

### 4.2 執筆要件

1. 各手順には直接実行できるコマンドまたはコードを示し、「設定を変更する」とだけ記述してはならない。
2. 移行前と移行後の対照を示し、項目ごとに照合できるようにする。
3. 自動移行できず手作業が必要な手順を明確に示す。
4. 影響範囲は具体的でなければならず、「一部のユーザーに影響する可能性がある」といった曖昧な表現を避ける。
5. 検証コマンドは単独で実行でき、期待される出力を含まなければならない。

## 5. 公開時期と連動

1. 移行ガイドは破壊的変更を含むバージョンと同時に公開しなければならず、遅れてはならない。
2. `CHANGELOG.md` の該当項目は移行ガイドへリンクしなければならない（[変更履歴規範](./変更履歴規範.md) を参照）。
3. PR テンプレートの破壊的変更のブロックは、移行方法の記入を促さなければならない（[IssueとPRテンプレート規範](./IssueとPRテンプレート規範.md) を参照）。
4. バージョン番号はセマンティックバージョニングに従い、破壊的変更ではメジャーバージョンを繰り上げなければならない（[バージョン管理規範](./バージョン管理規範.md) を参照）。
5. README の目立つ位置で、旧バージョンの利用者に移行ガイドを読むよう促す。

## 6. 廃止と保持の方針

1. 移行ガイドは長期にわたって保持しなければならず、新バージョンの公開後に削除してはならない。
2. 旧バージョンのドキュメントは「メンテナンス終了」と表示してよいが、入口は保持しなければならない。
3. 複数のメジャーバージョンをまたぐアップグレードでは段階的な経路を提供しなければならず、すべての変更を一度に跨越することを求めてはならない。

## 7. 禁止事項

1. 「破壊的変更があるため、各自で調整してください」とだけ書くことは禁止する。
2. ロールバック方法の省略は禁止する。
3. 移行手順で実行不能な擬似コードを使用することは禁止する。
4. 過去バージョンの移行ガイドを削除することは禁止する。
