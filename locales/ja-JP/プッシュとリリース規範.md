# プッシュとリリース規範

> このファイルが解決する問題：プッシュの前・中・後のアクションリスト、tag とリリースの規則、インシデント処理の流れ、および完全な GitHub プッシュ手順と失敗時の対応マトリクスを定義する。

## 1. プッシュ前

1. `git status` がクリーンで、未追跡の機密ファイルがないこと。
2. `git log` に WIP がなく、`fix bug` がなく、個人情報の漏えいがないこと。
3. `.gitignore` が有効で、成果物と依存関係が追跡されていないことを確認する。
4. ローカルで build、test、lint を通過させる。
5. 全体の秘密鍵スキャンを実行する（過去のコミットを含む）。
6. ドキュメントマトリクスが揃っていること（[ドキュメントマトリクス](./ドキュメントマトリクス.md) を参照）。

## 2. プッシュの操作

7. 個人ブランチをプッシュする：`git push -u origin feat/xxx`。
8. メインブランチは PR 経由のみで、直接 push しない。
9. `push --force` は禁止。自分のブランチを書き換える場合は `--force-with-lease` を用いる。
10. プッシュ済みの公共ブランチに対して rebase/amend してはならない。
11. 単一ファイルが 50MB を超える場合は先に LFS を通してからプッシュする。
12. 初回プッシュ前にリポジトリの公開範囲を確認する：既定は private とし、公開が本当に必要な場合に public へ切り替える。

## 3. tag とリリース

13. tag の形式は `vMAJOR.MINOR.PATCH` で、必ず annotated とする：`git tag -a v1.0.0 -m "release: 1.0.0"`。
14. tag は CI がグリーンで Release Notes が準備できた後にのみ打つ。
15. 破壊的変更は必ず `feat!:` または `BREAKING CHANGE:` とし、CHANGELOG に移行方法を示す。

## 4. Phase 6 · プッシュ後（Post-Push）

- annotated tag を打つ；
- Release Notes を書く；
- バッジとリンクが利用可能であることを検証する；
- CI がグリーンであることを確認する；
- About 欄の情報が正しいことを確認する（description / topics / リンク / social preview）。

## 5. インシデント処理

16. **秘密鍵をプッシュしてしまった**：直ちにローテーションする → `git filter-repo` でクリーンアップする → 保護ブランチへの強制プッシュは管理者手順を経る → 告知する。
17. **大容量ファイルを誤ってプッシュした**：LFS へ移行するか履歴を書き換える。ファイルを削除するだけではならない。

## 6. GitHub プッシュ手順の規範

手順には以下の 7 つの部分を含め、コマンドは完全に実行可能な形で示します。

### 6.1 事前の安全確保

1. プッシュ前にローカルリポジトリとリモートリポジトリを完全にバックアップし、`git clone --mirror` によるミラーバックアップを推奨します。
2. リモートリポジトリにコラボレーターがいないこと、またはコラボレーターにプッシュの一時停止を通知済みであることを確認します。
3. 対象ブランチで強制プッシュの保護が有効になっていないことを確認します。

### 6.2 ローカルの整理

```bash
git status
git diff --name-status HEAD
git ls-files
```

3 つの出力を照合し、コミット予定の変更がローカルディレクトリと一致していること、一時ファイル、ビルド成果物、旧版ドキュメントの残骸がないことを確認します。`.gitignore` はビルド成果物とローカル設定ファイルを対象にしなければなりません。

### 6.3 一貫性の確認

```bash
git fetch origin
git diff --name-status HEAD origin/{{分支名}}
```

このコマンドはリモートとローカルのファイル差分を一覧します。リモートに存在しローカルで削除済みのファイルは、ローカルで `git rm` を実行してからコミットし、削除操作をバージョン履歴に入れなければなりません。

### 6.4 コミットとプッシュ

```bash
git add -A
git commit -m "docs: 重建项目文档（README、README_EN、NOTICE）"
git push --force-with-lease origin {{分支名}}
```

`--force` ではなく `--force-with-lease` を採用し、リモートに他者の新しいコミットがある場合はプッシュを拒否して、他者の作業を上書きすることを避けます。リモートリポジトリを削除して再作成するのは高リスクな操作であり、個人のリポジトリでミラーバックアップを完了している場合にのみ使用し、手順にはデータ損失のリスクを明示しなければなりません。

### 6.5 プッシュ後の検証

```bash
git ls-remote --heads origin
gh repo view --web
```

Web 画面でファイル一覧、README の表示、言語切り替えリンク、NOTICE リンクが有効であることを項目ごとに確認します。

### 6.6 失敗時の対応マトリクス

| エラーの種類 | 典型的な症状 | 対応策 | リスクの注意 |
| --- | --- | --- | --- |
| 認証失敗 | `Authentication failed`、`Permission denied (publickey)` | HTTPS から SSH に切り替えて鍵を設定する、または `gh auth login` の後にプッシュする | なし |
| ネットワーク切断 | `Failed to connect`、`RPC failed` | ネットワークを変更する、プロキシを設定する、`git config --global http.postBuffer 524288000` を実行する | なし |
| ファイルサイズ超過 | `remote: error: File exceeds 100 MB` | コミット履歴から大容量ファイルを除去する、または Git LFS を有効化する | 履歴を書き換えた後はコラボレーターに再クローンを通知すること |
| 大文字小文字の衝突 | ファイル名の大文字小文字の不一致により重複した項目が生じる | `git mv` で修正してコミットする | なし |
| 履歴の競合 | `non-fast-forward`、`fetch first` | 優先的に `git pull --rebase` を実行する；上書きが本当に必要な場合は `--force-with-lease` を用いる | 他者のコミットを上書きすると復旧できない |
| ブランチ保護 | `protected branch hook declined` | PR の流れでマージする、または管理者が一時的に規則を調整する | 規則の調整は記録すること |
| リポジトリの破損 | `fatal: not a git repository`、オブジェクトの欠落 | 再クローンしてから作業ツリーの変更をコピーする | 先に作業ツリーをバックアップすること |

### 6.7 ロールバック

プッシュ完了後に問題を発見した場合は、`git revert` で逆方向のコミットを生成します。公開済みの履歴を上書きする強制プッシュを再度行ってはなりません。
