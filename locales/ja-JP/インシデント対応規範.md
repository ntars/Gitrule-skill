# インシデント対応規範

> このファイルが解決する問題：インシデント報告テンプレート、タイムライン記録、コミュニケーションテンプレート、振り返りのフィールドを定義し、障害の制御可能性、情報の同期、経験の蓄積を保証する。

## 1. 規範条文

1. インシデントの重大度：P0 は中核機能が利用不可またはデータ破損。P1 は重大な機能損傷が多数のユーザーに影響。P2 は局所的な問題で影響は限定的。
2. 対応フロー：検知 → 重大度判定 → 止血 → 特定 → 修復 → 告知。止血は特定より優先する。
3. P0/P1 のインシデントは毎回振り返りを行い、タイムライン、根本原因、影響、対応、改善項目を記録しなければならない。
4. 改善項目は [ロードマップ規範](./ロードマップ規範.md) に組み込み、クローズまで追跡しなければならない。
5. 振り返りはシステムの改善に焦点を当て、個人の責任を追及しない。
6. 鍵の漏洩：直ちにローテーション → 履歴のクリーンアップ → 告知。削除コミットのみで済ませてはならない（[セキュリティとプライバシー規範](./セキュリティとプライバシー規範.md) を参照）。
7. 大きなファイルの誤プッシュ：LFS への移行または履歴の書き換えを行う（[プッシュとリリース規範](./プッシュとリリース規範.md) を参照）。

- 継続時間：{{N 分钟}}
- 指揮者：{{姓名}}

## 3. コミュニケーションテンプレート

```markdown
## インシデント通知（初報）

- 時刻：{{YYYY-MM-DD HH:MM}}
- 重大度：{{P0 / P1 / P2}}
- 現象：{{用户可感知的现象，不写内部细节}}
- 影響：{{受影响范围}}
- 現在の措置：{{正在做什么}}
- 次回更新時刻：{{HH:MM}}

## インシデント通知（復旧）

- 復旧時刻：{{HH:MM}}
- 復旧確認：{{验证方式与结果}}
- 残存する影響：{{无 / 描述}}
- 今後：{{复盘安排}}
```

## 4. フィールド定義

| フィールド | 必須 | 種別 | 記入の要点 | 例 |
| --- | --- | --- | --- | --- |
| インシデント番号 | はい | `INC-YYYYMMDD-NN` | 当日の連番。連続させ、再利用しない | `INC-20261118-01` |
| インシデント重大度 | はい | 列挙 | P0 / P1 / P2 | `P1` |
| 継続時間 | はい | 時間 | 検知から復旧までの分数 | `42 分` |
| 指揮者 | はい | テキスト | 唯一。意思決定と同期を担う | `李四` |
| 影響を受けたユーザー比率 | はい | テキスト | 推定根拠を示すこと | `約 8%、エラーログの件数を根拠とする` |
| タイムライン | はい | 表 | 各時点に時刻と情報源を含む | テンプレートを参照 |
| 根本原因 | はい | テキスト | 直接原因と根本原因を区別する | `ロールバック演習の欠如` |
| 改善項目.検証方法 | はい | テキスト | 判定可能で、しきい値を含む | `次回の演習でロールバック <5 分` |
| 次回更新時刻 | はい | 時刻 | 対応中は必須。「随時更新」は禁止 | `18:30` |

## 5. 記入説明

1. **重大度判定**：影響範囲と深刻度に基づいて判定する。不確実な場合は高い側に判定し、後から調整して理由を記録する。
2. **止血優先**：まずサービスを復旧させ（ロールバック、縮退、レート制限）、その後に根本原因を特定する。特定が止血を遅らせてはならない。
3. **タイムライン**：発生時刻の順に記録し、情報源は追跡可能でなければならない（アラート ID、コマンド、ログ断片）。事後に記憶で補記してはならない。
4. **根本原因**：直接原因は引き金となった事象、根本原因は体系的な欠陥である。両方とも記入しなければならない。
5. **コミュニケーション**：初報では次回更新時刻を示さなければならない。復旧通知では検証方法と残存する影響を説明しなければならない。
6. **改善項目**：最大三件とし、ロードマップに組み込んで追跡する。担当者のいない改善項目は報告に含めてはならない。
7. **振り返り**：システムとプロセスの改善に焦点を当て、個人を評価しない。責任の追及や「某氏が不注意で」といった表現は書かない。
8. **特殊なインシデント**：鍵の漏洩は H12 に従って処理する。大きなファイルの誤プッシュは LFS 移行として処理する。いずれも個別に記録を残さなければならない。

よくある誤り：

| 誤った書き方 | 問題 | 修正方法 |
| --- | --- | --- |
| 根本原因の特定を先に行い止血が後になる | 障害の継続時間が延びる | まずロールバックで復旧する |
| タイムラインを事後に補記する | 事実の信頼性がない | 対応中に即時記録する |
| 根本原因に「某氏が不注意で」と書く | 個人への帰責となり改善価値がない | プロセスまたはツールの層まで掘り下げる |
| 通知に「できるだけ早く修復」と書く | 次回更新時刻がない | 具体的な時刻を示す |
| 改善項目に検証方法がない | クローズの判定ができない | しきい値と確認時期を補う |

## 6. 完全な例

```markdown
# インシデント報告：INC-20261118-01

- インシデント重大度：P1
- 検知時刻：2026-11-18 10:12
- 復旧時刻：2026-11-18 10:54
- 継続時間：42 分
- 指揮者：李四
- 現在の状態：振り返り済み

## 影響範囲
| 次元 | 説明 |
| --- | --- |
| 影響を受けた機能 | ルール検査 API が 5xx を返す |
| 影響を受けたユーザー比率 | 約 8%、5xx ログの件数を根拠とする |
| データへの影響 | なし |
| ビジネスへの影響 | 42 分間、検査タスクを送信できない |

## 根本原因
- 直接原因：ルールプラグインの読み込みパスが新しい設定で上書きされ、起動に失敗した。
- 根本原因：設定変更がプレリリース検証に組み込まれていなかった。

## 改善項目
| 番号 | アクション | 担当者 | 期限 | 検証方法 | 状態 |
| --- | --- | --- | --- | --- | --- |
| A-01 | 設定変更をプレリリースのチェックリストに組み込む | 王五 | 2026-11-25 | 次回 5 回の変更すべてにチェック記録があること | 未着手 |
```
