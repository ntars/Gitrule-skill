# コミットメッセージ規範

> このファイルが解決する問題：Conventional Commits のフィールド、書式、記入説明、例を定義し、履歴の可読性、変更履歴とバージョン番号の自動生成を保証する。

## 1. 書式

```text
<类型>[可选作用域][可选 !]: <描述>

[可选正文]

[可选脚注]
```

## 2. タイプ

十種類のタイプは以下のとおりで、一般的なオープンソースプロジェクトのコミット場面を網羅する：

| タイプ | 意味 |
| --- | --- |
| `feat` | 新機能の追加 |
| `fix` | 不具合の修正 |
| `docs` | ドキュメントの変更 |
| `style` | ロジックを変えない書式調整（空白、フォーマット、セミコロンの欠落など） |
| `refactor` | リファクタリング。新機能の追加も不具合の修正もしない |
| `perf` | 性能最適化のコード変更 |
| `test` | 不足しているテストの追加、または既存テストの修正 |
| `build` | ビルドシステムや外部依存関係に影響する変更（npm、gulp など） |
| `ci` | 継続的インテグレーションの設定とスクリプトの変更（GitHub Actions、CircleCI など） |
| `chore` | ビルド、依存関係、ツールチェーンなどの雑多な作業 |

### 2.1 チーム固有の書き方の比較と取捨選択

協働の形態によって三つの一般的な書き方があり、プロジェクトは立ち上げ時に一つを選定し、チーム全体で統一すべきである：

| 書き方 | 書式 | 適用 | 限界 |
| --- | --- | --- | --- |
| 業務での書き方 | `[タスクカード番号] 作成者: 変更内容` | カンバン、ペアプログラミングを用いるチーム | タスクカード番号の体系に依存し、番号がない場合は適用できない |
| 慣例的な書き方 | `[分類] コンポーネント（任意）: 変更内容` | 業務モジュール単位で履歴を絞り込みたいチーム | チームで分類表を取り決める必要があり、追加コストがかかる |
| オープンソースでの書き方 | `<type>(<scope>): <subject>` | オープンソースのライブラリとアプリケーション。CHANGELOG の自動生成が必要 | タイプとスコープが多く、学習コストが比較的高い |

本プロジェクトはオープンソースでの書き方（すなわち Conventional Commits）に統一する。理由は、機械可読であり、変更履歴とバージョン番号を自動生成できることである。業務での書き方と慣例的な書き方は、クローズドソースのチーム内でのみ取り決めに従って使用し、外部向けリポジトリに混入させてはならない。

## 3. フィールド定義

| フィールド | 必須 | 種別 | 記入の要点 | 例 |
| --- | --- | --- | --- | --- |
| タイプ | はい | 列挙 | 十種類のいずれか。独自に作ってはならない | `feat` |
| スコープ | いいえ | テキスト | モジュール名。小文字の短い語で、空白を含まない | `parser` |
| 破壊的変更のマーク | いいえ | `!` | タイプまたはスコープの後、コロンの前に置く | `feat!:` |
| 説明 | はい | テキスト | 命令形、小文字で始める、72 文字以下、末尾に句点を付けない | `add TOML config support` |
| 本文 | いいえ | テキスト | 動機と実装を説明する。説明とは空行で区切る | `Allow the parser to read TOML...` |
| フッター | いいえ | テキスト | `BREAKING CHANGE:` または `Refs: #N` | `BREAKING CHANGE: ...` |
| 関連要求 | いいえ | `REQ-NNN` | 本文またはフッターに書き、追跡しやすくする | `Refs: REQ-001` |

## 4. 記入説明

1. **説明**：命令形（add、fix、remove）を用い、「何をしたか」を書き、「変更を加えた」とは書かない。中国語プロジェクトでは中国語の説明を書いてもよいが、リポジトリ全体で統一しなければならない。
2. **スコープ**：ファイル名ではなくモジュール名を取る。モジュールをまたぐ変更ではスコープを省略し、`all` や `global` とは書かない。
3. **本文**：説明だけでは動機を伝えきれない場合にのみ書く。説明を繰り返さず、作業の経過を綴らない。
4. **破壊的変更**：`feat!:` / `fix!:` と `BREAKING CHANGE:` フッターのいずれか一方、または併用とする。これらが現れた場合は、[変更履歴規範](./変更履歴規範.md) と [移行ガイド規範](./移行ガイド規範.md) にも同時に書き込まなければならない。
5. **原子性**：一回のコミットでは一つのことだけを行う。フォーマットとロジックの変更は二回に分けてコミットする。
6. **セキュリティ**：鍵、トークン、個人情報、内部アドレスを含めてはならない。コミット前にシークレットスキャンで確認する（[セキュリティとプライバシー規範](./セキュリティとプライバシー規範.md) を参照）。
7. **バージョンとの連動**：`feat` はマイナーバージョンの繰り上げを、`fix` はパッチバージョンの繰り上げを、`BREAKING CHANGE` はメジャーバージョンの繰り上げを引き起こす。詳細は [バージョン管理規範](./バージョン管理規範.md) を参照。

よくある誤り：

| 誤った書き方 | 問題 | 修正方法 |
| --- | --- | --- |
| `wip`、`update`、`fix bug` | 情報量がなく、H10 に違反する | 対象と行為を明記する |
| `feat: Added new feature.` | 命令形でなく、大文字で始まり、句点がある | `feat: add config loader` |
| `feat(全部): 最適化` | スコープが無効で、説明が曖昧 | 具体的なモジュール名を用い、変更内容を明記する |
| 一回のコミットにフォーマットと機能変更が混在 | 原子性を損なう | `style:` と `feat:` の二回のコミットに分ける |
| コミットメッセージに社内アドレスを含む | 情報漏洩 | 除去し、シークレットスキャンを通す |

## 5. 完全な例

```text
feat(parser): add support for TOML config

Allow the parser to read TOML configuration files in addition to YAML.
Refs: REQ-001

BREAKING CHANGE: the `config` option now accepts a file path instead of an object.
```

各フィールドの意味：`feat` がタイプ、`parser` がスコープ、コロンの後が簡潔な説明である。本文は動機と実装を説明し、フッターは要求を関連付ける。末尾のフッターは破壊的変更を宣言し、移行の方向性を示す。

修正系の例：

```text
fix(spacing): avoid false positives before Chinese punctuation

The spacing rule previously flagged strings such as 「使用Node.js，」 because
the punctuation check ran after whitespace normalization.

Refs: REQ-004, #142
```
