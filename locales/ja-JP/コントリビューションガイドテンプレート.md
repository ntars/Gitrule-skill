# コントリビューションガイドテンプレート

> このファイルが解決する問題：そのまま複製できるコントリビューションガイドのテンプレートを提供し、プロジェクトが CONTRIBUTING.md を生成できるようにする。参加方法、環境構築、ブランチモデル、コミット規範、PR 要件、テスト要件、行動規範、ライセンスの声明を網羅し、付随する記入説明では各類型のプロジェクトにおける調整方法を扱う。

## 1. 使用説明

1. 第 3 節「テンプレート本文」の全内容を複製し、プロジェクトルートの `CONTRIBUTING.md` として新規作成する。
2. 第 4 節に従ってプレースホルダーを置き換える。すべてのコマンドはそのまま実行できる実際のコマンドでなければならない。
3. 第 5 節のシナリオ別変種に従って調整する。ドキュメント型のプロジェクトではテストコマンドの段落を削除し、Issue と PR のフローを残す。
4. ルールの根拠は [コントリビューションガイド規範](./コントリビューションガイド規範.md) を参照。ブランチとコミットの詳細はそれぞれ [Gitワークフローとブランチ規範](./Gitワークフローとブランチ規範.md)、[コミットメッセージ規範](./コミットメッセージ規範.md) を参照。

## 2. カスタマイズ原則

- **実行可能にする**：コマンドには作業ディレクトリと依存関係の前提を書き切る。「依存関係をインストールする」とだけ記し、具体的なコマンドを欠くことを禁止する。
- **トリガー条件を持たせる**：各手順には、いつ実行するか、期待される結果は何かを明記する。
- **空疎にしない**：「PR を歓迎します」とだけ記し、実質的なフローを欠くことを禁止する。[品質ゲート](./品質ゲート.md) のコミュニティガバナンスのチェックに対応する。
- **複製せず引用する**：コミットとテストのルールは対応する規範を引用し、本ファイルで全文を繰り返さない。

## 3. テンプレート本文

````markdown
# コントリビューションガイド

> このファイルは {{项目名称}} へのコントリビューションの方法を説明するものであり、外部のコントリビューターと初めて参加する方に適用されます。

## 参加方法

| 方法 | 適用場面 | 窓口 |
| --- | --- | --- |
| イシューでの議論 | 機能の提案、問題のフィードバック | {{议题入口}} |
| ドキュメントの改善 | 誤字、例の追加、構成の最適化 | 直接 PR を送る |
| コードのコントリビューション | 不具合の修正、機能の実装 | 下記のフローを参照 |
| 問題のフィードバック | 利用の妨げ、異常の再現 | {{问题反馈入口}} |

## 開発環境の構築

前提：{{环境前提}}

```bash
# リポジトリをクローンする
git clone {{仓库地址}}
cd {{项目目录名}}

# 依存関係をインストールする
{{依赖安装命令}}

# ローカルで実行する
{{本地运行命令}}
```

期待される結果：{{验证本地环境可用的方式}}

## ブランチモデル

- {{基准分支}} から個人のブランチを作成し、命名形式は `{{分支命名格式}}` とする（例：`feat/简短描述`）。
- 1 つの PR では 1 つのことだけを扱い、変更範囲が大きすぎる場合は分割する。
- {{受保护分支}} への直接コミットを禁止し、PR を通じてマージしなければならない。

## コミット規範

コミットメッセージは Conventional Commits に従い、形式は `type(scope): subject` とする。よく使う種別：`feat`、`fix`、`docs`、`refactor`、`test`、`chore`。例：

```text
feat(cli): add config file support
```

完全なルールは [コミットメッセージ規範]({{提交规范链接}}) を参照してください。

## PR の要件

PR を送る前に、以下のセルフチェックを完了してください：

- [ ] 変更範囲が単一であり、対応するイシューまたは説明がある。
- [ ] コミットメッセージが上記の形式に適合している。
- [ ] ローカルで `{{测试命令}}` を実行し、すべて成功した。
- [ ] ドキュメントをコードと同期して更新した。
- [ ] 鍵、秘密鍵、機密情報を持ち込んでいない。
- [ ] 説明に変更内容、理由、検証方法を記した。

## テスト要件

| チェック項目 | コマンド | 合格基準 |
| --- | --- | --- |
| 単体テスト | `{{单元测试命令}}` | すべて成功 |
| 静的解析 | `{{lint 命令}}` | エラーなし |
| ビルド検証 | `{{构建命令}}` | ビルド成功 |

カバレッジのしきい値：{{覆盖率要求}}。

## 行動規範

本プロジェクトに参加することは、[行動規範](./CODE_OF_CONDUCT.md) を遵守することに同意したものとみなされます。

## Issue 規範

- 質問する前に既存のイシューを検索し、重複を避ける。
- 不具合報告には、環境情報、再現手順、期待する結果、実際の結果、エラーログを含めなければならない。
- 機能の提案では、利用シナリオと、採用しない場合の代替案を説明しなければならない。

## ライセンスの声明

コントリビューションの内容は既定で本プロジェクトのライセンス {{许可证名称及 SPDX 标识符}} に従い、全文は [LICENSE](./LICENSE) を参照してください。提出することは、当該ライセンスで自らのコントリビューションを許諾する権利があることを意味します。
````

## 5. 記入説明とシナリオ別変種

| シナリオ | 必ず残すセクション | 削除可能なセクション | 調整の要点 |
| --- | --- | --- | --- |
| コードプロジェクト | すべて | なし | コマンドは実際に実行し、検証を通過しなければならない |
| ドキュメントプロジェクト | 参加方法、PR の要件、行動規範、ライセンス | テスト要件、開発環境の構築 | テストの表を削除し、PR のセルフチェックを残す |
| 個人プロジェクト | 参加方法、PR の要件、行動規範、ライセンス | 環境構築は簡略化してよい | 外部からのコントリビューションを受け入れるかを明確にする |
| 企業プロジェクト | すべて | なし | コントリビューターライセンス契約（CLA）のリンクと法務要件を追加する |

よくある誤りの対照：

| 誤った記述 | 結果 | 正しい記述 |
| --- | --- | --- |
| 「あらゆる形のコントリビューションを歓迎します」 | 具体的な道筋がなく、コントリビューターが着手できない | 参加方法の表と窓口を列挙する |
| 「テストを実行すればよい」 | コマンドと合格基準が分からない | コマンド、合格基準、カバレッジしきい値を明記する |
| コマンドを `npm install` と記すが、プロジェクトは pnpm を使用 | コマンドが実行できない | 実際の lockfile と一致させる |

## 6. 完全な例

以下はコマンドの段落を記入済みにした例であり、形式の参考にのみ供する。

```bash
# リポジトリをクローンする
git clone https://github.com/owner/repo.git
cd repo

# 依存関係をインストールする
pnpm install

# ローカルで実行する
pnpm dev
```

期待される結果：localhost:3000 にアクセスするとトップページが表示される。
