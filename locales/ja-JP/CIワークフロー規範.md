# CIワークフロー規範

> このファイルが解決する問題：`.github/workflows/*.yml` 継続的インテグレーションワークフローのトリガー条件、ジョブ分割、キャッシュ戦略、セキュリティ設定を定義し、ビルド・テスト・チェックを再現可能かつ監査可能にする。

## 1. 設計原則

1. **単一責任**：各ワークフローは 1 種類の目的（ビルド、テスト、リリース、ドキュメントデプロイ）のみを担い、リリースとテストを 1 つのワークフローに混在させてはなりません。
2. **迅速なフィードバック**：軽量なチェック（lint、フォーマット）を前に、時間のかかるタスク（完全なテストマトリクス）を後に置きます。
3. **再現可能**：依存関係のバージョンを固定し、固定バージョンの Actions を使用し、キャッシュは高速化のみに用いて結果を変えません。
4. **最小権限**：ワークフローはタスクごとに権限を付与し、既定は読み取り専用とし、リリースタスクのみ個別に権限を昇格します（[セキュリティとプライバシー規範](./セキュリティとプライバシー規範.md) を参照）。

## 2. ファイル構造

### 2.1 命名とパス

- パスは `.github/workflows/*.yml` に固定します。
- ファイル名は小文字とハイフンを用い、責務に応じて命名します。例：`ci.yml`、`release.yml`、`docs.yml`。
- ワークフローの `name` フィールドはファイル名の意味と一致しなければなりません。

### 2.2 必須ブロック

| ブロック | 役割 | 要件 |
| --- | --- | --- |
| `name` | ワークフローの表示名 | 簡潔で責務が読み取れること |
| `on` | トリガー条件 | ブランチ、パス、イベントを明確にすること |
| `permissions` | 権限の宣言 | 明示的に宣言し、既定は最小とすること |
| `jobs` | ジョブの集合 | 責務ごとに分割すること |

### 2.3 トリガー条件の設計

| トリガーイベント | 適用 | 注意 |
| --- | --- | --- |
| `push` | メインブランチとリリースブランチ | ブランチ範囲を限定し、全ブランチでの発動を避ける |
| `pull_request` | すべての PR | マージ前のチェックを保証する |
| `workflow_dispatch` | 手動トリガー | リリース、ロールバックなど統制された操作に用いる |
| `schedule` | 定時タスク | 依存関係更新のチェック、夜間ビルドに用いる |
| `release` | リリース後の処理 | 成果物のアップロードと告知に用いる |

## 3. ジョブの分割

推奨する段階の順序：

1. **静的解析**：フォーマット、lint、型チェック。
2. **ビルド**：ビルド成果物を生成し、後続のジョブで再利用する。
3. **テスト**：単体テスト、統合テスト。マトリクスで並列化してよい。
4. **成果物の検証**：ビルド成果物のサイズ、署名、完全性をチェックする。
5. **リリース**：CI がすべてグリーンで条件を満たす場合にのみ実行します（[プッシュとリリース規範](./プッシュとリリース規範.md) を参照）。

ジョブ間は `needs` で依存関係を宣言し、失敗時に中断されることを保証します。後続のジョブを失敗状態のまま継続させてはなりません。

## 4. マトリクスビルド

`strategy.matrix` を用いて複数バージョン、複数プラットフォームを網羅します：

```yaml
strategy:
  fail-fast: false
  matrix:
    os: [ubuntu-latest, macos-latest, windows-latest]
    node-version: [18, 20, 22]
```

要件：

- バージョンはプロジェクトがサポートを宣言する最低バージョンと最新バージョンを網羅すること（[互換性の説明](./READMEセクション規範.md) 第 14 章を参照）。
- `fail-fast` は `false` に設定し、各組み合わせを最後まで実行して互換性の問題を特定しやすくすること。
- マトリクスの次元は 3 つを超えないこと。組み合わせの爆発を避ける。

## 5. キャッシュ戦略

| キャッシュ対象 | キーの推奨 | 注意 |
| --- | --- | --- |
| 依存関係ディレクトリ | パッケージマネージャーのロックファイルのハッシュ | ロックファイルの変更で失効 |
| ビルド成果物 | ソースコードと設定のハッシュ | ビルドの入力と一致させること |
| ツールチェーン | バージョン番号 | バージョン更新で失効 |

キャッシュは高速化のみで、ビルド結果を変えません。キャッシュがヒットした場合でも完全なテストを実行しなければなりません。

## 6. セキュリティ設定

1. 秘密鍵はリポジトリの Secrets を通じて注入し、ワークフローファイルやログへの記述は禁止します。
2. 各ワークフローは `permissions` を明示的に宣言し、既定は `contents: read` とします。
3. サードパーティの Action は固定バージョンまたはコミットハッシュで参照し、浮動タグを避けます。
4. PR が Fork から来た場合、Secrets の注入を禁止し、権限昇格攻撃を防ぎます。
5. リリースタスクはメインのチェックと分離し、保護ブランチまたは tag でのみ発動させます。

## 7. ステータスバッジ

ワークフローは README にステータスバッジを提供すべきであり、形式は次のとおりです：

```markdown
[![CI](https://github.com/{owner}/{repo}/actions/workflows/ci.yml/badge.svg)](https://github.com/{owner}/{repo}/actions/workflows/ci.yml)
```

バッジのパラメータと配置は [バッジ規範](./バッジ規範.md) を参照してください。

## 8. 禁止事項

1. ワークフローに秘密鍵や内部アドレスをハードコードしてはならない。
2. `continue-on-error` を使ってテストの失敗を覆い隠してはならない。
3. 同一の条件に対して相互に矛盾する複数のトリガー規則を設定してはならない。
4. メインブランチのチェックが未通過の状態でリリースを実行してはならない。
