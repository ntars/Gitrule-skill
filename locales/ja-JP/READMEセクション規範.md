# READMEセクション規範

> このファイルが解決する問題：各言語ディレクトリの README が必ず含むべき 20 のセクション、各章に必ず含める内容と含めてはならない内容、および著作権行の標準形式を定義します。

## 1. セクション全体の要件

以下の 20 章はすべて存在しなければならず、順序は固定で、各言語版が一対一で対応します。

| 番号 | セクション | 必ず含めるもの | 含めてはならないもの |
| --- | --- | --- | --- |
| 1 | プロジェクト名と位置づけ | プロジェクト名、リポジトリの説明（`国家语言 \| 英语` の二言語併記形式）、トピックタグ（最大 20 個まで埋め、英語のみ）、一言の位置づけ、言語切り替えリンク、現在のバージョン、メンテナンス状態 | 空虚な形容詞；リポジトリの説明が 120 文字を超えるもの；トピックタグの大文字小文字の混用や英語以外の語を含むもの |
| 2 | プロジェクト概要 | 背景、解決すべき問題、中核となる考え方、適用場面、適用しない場面、および利点と限界を分けて記載（限界には影響範囲と回避方法を含める） | 一文で済ませる；利点のみを挙げて限界を挙げない |
| 3 | 中核機能 | モジュールごとにグループ化した機能項目。各項目にトリガー条件と結果を含める | 機能名のみを列挙する |
| 4 | 中核特性 | [機能とエンジニアリングトレードオフの書き方](./機能とエンジニアリングトレードオフの書き方.md) の構造で展開する | 根拠のない称賛 |
| 5 | 設計の詳細とエンジニアリングトレードオフ | [機能とエンジニアリングトレードオフの書き方](./機能とエンジニアリングトレードオフの書き方.md) の構造で展開する | 機能と重複する記述 |
| 6 | 技術スタックと依存関係一覧 | ランタイム、ビルド、テストのツールチェーンとバージョン制約。依存関係の明細は NOTICE を指す | バージョン番号の欠落 |
| 7 | インストールとデプロイ | 環境要件、インストール手順、検証コマンド、アップグレードとアンインストールの方法、コンテナ化の説明 | 手順の省略や検証の省略 |
| 8 | クイックスタート | 最小限の実行可能な例。完全なコマンドと期待される出力を含む | 実行できない疑似コード |
| 9 | 設定の説明 | 設定項目の表（キー名、型、既定値、必須、値の範囲、役割、例）、設定の優先順位、ホットリロードの対応 | 既定値の欠落 |
| 10 | API またはモジュールの説明 | インターフェースシグネチャ、パラメータ、戻り値、エラーコード、呼び出し例、レート制限とクォータ | エラーコードの欠落 |
| 11 | ディレクトリ構造 | ツリー構造と各階層の役割の説明 | 説明のないファイル単位の列挙 |
| 12 | 性能 | テスト環境、テスト方法、指標データ、ボトルネック分析、チューニングの提案 | テスト条件のない数値 |
| 13 | セキュリティとプライバシー | データの収集と保存、通信の暗号化、権限モデル、脆弱性の報告窓口、既知のリスク | 絶対的な安全の約束 |
| 14 | 互換性の説明 | OS、ランタイム、ブラウザ、データベースのバージョンマトリクス。非対応項目を明示 | 曖昧な表現 |
| 15 | 既知の問題と制限 | 既知の問題（説明、影響範囲、一時的な回避策、追跡リンク）、現在の制限、未実装機能の一覧（機能、未実装の理由、計画の状態） | 重大な欠陥の隠蔽；未実装機能を実装済みと書く |
| 16 | 変更履歴 | Keep a Changelog の構造に従い、バージョン番号はセマンティックバージョニングに従う | 日付のない項目 |
| 17 | 今後のロードマップ | 計画項目、状態、目標バージョン。「約束ではない」と明記 | 提供時期の約束 |
| 18 | コントリビューションへの参加 | 開発環境の構築、ブランチモデル、コミット規範、PR の要件、行動規範、Issue テンプレート | 「PR 歓迎」とだけ書く |
| 19 | 著作権とライセンス | 著作権行、ライセンス名、SPDX 識別子、ライセンス全文の場所 | 著作権者の欠落 |
| 20 | NOTICE コンプライアンス声明 | 第三者依存関係の摘要、NOTICE ファイルへの相対リンク | 本章で NOTICE を代替する |

## 1.1 ファーストビューの四つの問いと一言コピー

README のファーストビューは四つの問いに答えなければならず、順序は固定です。

1. プロジェクトは何をするのか；
2. プロジェクトは何を解決するのか；
3. プロジェクトにはどんな特性があるのか；
4. 最小限の hello world の例。

うち第 1 の問いは「一言の位置づけ」に対応し、同時に三つの点を満たさなければなりません。プロジェクトの種類を示すこと、限定詞が正確であること、そのまま復唱できること。成熟したプロジェクトの公開コピーは参照になります。

| プロジェクト | 一言コピー | 構造の分析 |
| --- | --- | --- |
| Angular | One framework. Mobile & desktop. | カテゴリ + 対応範囲 |
| React | A declarative, efficient, and flexible JavaScript library for building user interfaces. | 三つの限定詞 + カテゴリ + 用途 |
| Vue | A progressive, incrementally-adoptable JavaScript framework for building UI on the web. | 二つの特性 + カテゴリ + 用途 |

記述の制約：

- 「強力」「優秀」「革命的」など情報のない形容詞を使用してはならない；
- カテゴリを表す語（ライブラリ、フレームワーク、ツール、アプリケーション）を示し、読み手が一目で分類できるようにすること；
- 特性の限定詞は三つ以内とし、積み上げを避ける；
- 中国語版は 60 字以内、英語版は 25 語以内に収めること。

第 3 の問い「どんな特性があるか」は、適用しない場面も同時に開示しなければなりません。有効な記述の例：あるメッセージミドルウェアについて「QoS レベル 0 のみをサポートし、レベル 1 が必要な場面には適さない」と説明する。無効な記述は長所を並べるだけのものです。特性の比較は検証可能な事実に基づかなければならず、同類のプロジェクトを貶めてはなりません。

第 4 の問いの hello world の例は、2 ステップ以内でインストールと実行を完了できなければなりません。インストール手順が煩雑なプロジェクトはコンテナイメージやオンラインデモ環境を提供し、読み手が README を読み終えた後に断念する事態を避けるべきです。
