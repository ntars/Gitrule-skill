# 開発マニュアルテンプレート規範

> 本ファイルが解決する課題：「クラウドで記述し、ローカルで実行する」二段階の開発マニュアルの骨格、タスクカード形式、引き継ぎプロトコルと検証ゲートを定義し、同一のアイデアをクラウドモデルが曖昧さのないタスクカードへ書き換え、ローカルのコーディングモデルが部分ごとにリレー方式で実行できるようにする。

## 1. 位置づけと使用フロー

1. 本規範は「クラウド推論モデル 1 個 + ローカルコーディングモデル 1 個」の分業シナリオを対象とする。クラウド側は曖昧なアイデアを明確な実装方針へ書き換える責務を担い、ローカル側は方案に従って決定論的に実行する責務を担う。
2. 使用フローは四段階に固定され、順序の省略は禁止する：
   - 事前チェック：アイデアに誤った前提、論理の飛躍、情報の欠落がないかを確認する。情報が不足していれば先にユーザーへ質問し、憶測での補完は禁止する。
   - クラウド記述：第 9 節の規範に従ってオープンソースソリューションをスキャンし、マニュアルを記入する。
   - ユーザーレビュー：検収コマンド、採用記録、禁則を重点的にレビューする。
   - ローカル実行：機械可読索引に従って対応する章と引き継ぎ記録を注入し、部分ごとに実行する。
3. マニュアル本文では「など」「関連」「適宜」「可能な限り」「必要に応じて」などの曖昧な語の使用を禁止する。いずれの箇所も、正確な値を示すか、意思決定ルールを示すかのどちらかとする。

## 2. マニュアルの骨格

すべての開発マニュアルは以下の部分を固定で含み、順序は変更しない：

| 部分 | 責務 |
| --- | --- |
| 機械可読索引 | 章のパス、対応するコードディレクトリ、検収コマンド、フェーズマークのナビゲーション表 |
| 採用記録 | オープンソースサプライチェーンの記録表であり、プロジェクト全体の単一の真の情報源（第 11 節参照） |
| プロジェクト憲法 | プロジェクト全体の不変項目であり、すべての部分に必ず注入する |
| 用語集 | 用語と平易な説明、対応するコードの対照 |
| モジュール章 | モジュールごとに 1 章とし、第 4 節の構造に従って記述する |
| リリース章 | ビルドと配布の規範であり、リリース操作はユーザーの確認を要する |
| 公式サイト文案章 | 一般ユーザー向けの文案規範であり、ローカルモデルには注入しない |
| 変更記録 | 日付、章、変更内容と意思決定者 |

## 3. プロジェクト憲法

プロジェクト憲法はローカル実行の各部分に必ず注入する不変項目であり、五つの項目で固定される：

1. 技術スタックとバージョン：バージョン番号まで正確に記す。
2. ディレクトリ構造の約束：ツリー図に各ディレクトリの一文での責務を添える。
3. コーディング規範：プロジェクト種別に応じて調整し、基準はモジュール化された必要時ロード、最小かつ最も直接的なコード、要求されていない機能を追加しないこと、コメントの完全性と専門概念を平易な言葉でコメントすること。UI 系プロジェクトは Apple HIG に従い、フォントの単位は px または rem のみを使用し、rpx の使用は禁止する。
4. グローバル禁則：絶対に許されない行為。例えば採用記録に登録されていない依存関係の導入をしない、契約ファイルを改変しない。
5. 出力言語規範：説明、ログ、進捗、エラーメッセージは簡体字中国語を使用する。コード、コマンド、ファイルパス、固有名詞は原文のままとできる。

## 4. モジュール章の構造

各モジュール章は九つの節で固定され、順序は変更しない：

| 節 | 責務 |
| --- | --- |
| モジュールの責務 | 1〜3 文で、何をするか、何をしないかを明記する |
| 依存するオープンソースソリューション | 名称、用途、採用記録番号 |
| ファイル一覧 | パス、操作（新規作成／変更／読み取り専用）、責務。総数は 10 個以内とし、超えた場合は章を分割する |
| インターフェース契約 | シグネチャ、ルーティング、プロトコルフィールドを型まで正確に記し、入出力の完全なサンプルを添える |
| データと状態 | 何を、どこに、どの形式で保存するか。専門概念は平易な言葉でコメントする |
| 依存関係 | 先に読むべきファイル、呼び出すファイル、絶対に改変しないファイルの三組のリスト |
| タスクカード | 本モジュールを分割した部分であり、各カードは独立して実行する |
| 本章の禁則 | 本モジュールが特に許されない行為 |
| 設計備考 | 選定理由、断念した実装方針、事実と推測の区別。ローカルモデルには注入しない |

## 5. タスクカードの形式

1 枚のタスクカードは 1 回のローカルセッションと 1 条の検収コマンドに等しく、フィールドは以下のとおり固定する：

| フィールド | 要求 |
| --- | --- |
| 目的 | 一文で、機械が検証できる内容とする |
| 事前条件 | 依存する前の部分とファイルがすべて存在していること |
| 手順 | 番号付きで列挙し、各手順は一つの決定論的な操作とし、一度に完結させ、中断も追加質問もしない |
| 検収コマンド | そのままコピーして実行できること。検収体系がまだない場合、最初のカードは必ず先に検収コマンドを構築する |
| 期待結果 | 正確な出力、終了コードまたはアサーション数 |
| 失敗時処理 | 典型的なエラーごとに処置を逐条示す。連続 3 回失敗したら必ず停止し、引き継ぎ記録へ書き込む |
| 引き継ぎ要求 | 引き継ぎ記録に書き込むべきフィールドを宣言する |

ハード制約：

1. 1 枚のカードが触れるファイルが 10 個を超えたらカードを分割する。1 章のカードが 6 枚を超えたら章を分割する。
2. 納品セルフチェックに関わるカードは、冗長コードの整理と README、NOTICE、LICENSE の同期ポイントを明示的に列挙しなければならない。
3. ファイルの削除または上書きに関わる操作はすべて停止し、引き継ぎ記録の block フィールドに書き込み、ユーザーの確認を待つ。
4. 曖昧すぎて検収コマンドを書けないタスクはカードに記入せず、単独で「ユーザーの判断が必要」と注記する。

## 6. PROGRESS 引き継ぎプロトコル

引き継ぎ記録ファイル PROGRESS.md は部分と部分の間の唯一の真の情報源であり、形式は固定する：

| フィールド | 要求 |
| --- | --- |
| done | 本カードの目的が達成されたかどうか |
| files | 実際に変更したファイルの一覧 |
| decisions | 過程での意思決定。形式は「A を選択した。理由は B」 |
| next | 次のカードの番号とエントリ。ファイルパスとエントリ関数まで書くこと。「引き続き改善する」のような書き方は禁止 |
| block | 未解決の問題。なければ空欄とする |

1. 各カードの締めくくりに必ず 1 条追加し、形式の変更は禁止する。
2. ローカル実行時は最新の 1 条のみ注入し、履歴の条目は注入しない。
3. 中断からの復帰：「継続」の指示を受け取ったら、先に最新の 1 条を読んで中断地点を確認し、next が指すエントリから続行する。記憶や憶測で完了済みの手順をやり直すことは禁止する。

## 7. ローカル注入予算

harness は以下の表に従って各部分のコンテキストを組み立て、総予算は 24K 以内（32K 作業ウィンドウの 75%）とする：

| 注入項目 | 予算 |
| --- | --- |
| プロジェクト憲法 | 2-3K |
| 現在のタスクカードが属する章 | 2-5K |
| 引き継ぎ記録の最新 1 条 | 約 0.5K |
| 引き継ぎプロンプトの骨格 | 約 0.3K |
| コードとツール出力 | 残り枠 |

注入しないもの：採用記録の全表（本カードに関わる条目のみ注入）、設計備考、公式サイト文案章。

## 8. 引き継ぎプロンプトの鉄則

各部分の開始時には固定のオープニングを注入し、鉄則は六条で固定する：

1. 全程で簡体字中国語で出力する。コード、コマンド、パス、固有名詞は原文のままとできる。
2. タスクカード内の作業のみを行い、要求されていない機能、設定、拡張能力を追加しない。
3. 創作せず、捏造しない。確信できない API シグネチャは直接に不確かであると説明する。事実と推測を明示的に区別する。
4. 検収コマンドが失敗した場合はタスクカードの失敗時処理に従って実行し、検収基準を独自に変更してはならない。
5. ファイルの削除、上書きに関わる操作はすべて停止し、ユーザーの確認を待つ。
6. 完了後は引き継ぎ要求に厳密に従って引き継ぎ記録を書き、その後終了する。

## 9. クラウド記入規範

クラウドモデルはマニュアルを記入する前に二つの事前作業を完了し、その後章ごとに記入する：

1. 前提の核查：誤った前提、論理の飛躍、情報の欠落を確認し、不足していれば先にユーザーに質問する。
2. オープンソースソリューションのスキャン：オープンソースエコシステムで利用可能な既存の方案を検索し、先にスキャンしてから記入する。成熟したソリューションを使える場合は車輪の再発明をしない。結果は採用記録へ登録する。

記入時に遵守する：

1. すべての曖昧な語を排除し、いずれの箇所も正確な値または意思決定ルールを示す。
2. 設計上の意思決定は設計備考へ書き込み、選定理由と断念した実装方針を含め、ユーザーのレビューに供する。ローカルモデルには注入しない。
3. ローカルモデルへの指示は「このモデルはプロジェクトの背景を知らない」前提で書き、すべての前提を明示的に記す。
4. コンプライアンスのボトムライン：ライセンスが不明な場合は「確認待ち」と注記する。強 copyleft のソリューションには派生物の義務に関する注意を注記する。改変したオープンソースコードは原本の著作権と変更説明を保持する。採用項目は README、README_EN、NOTICE、LICENSE を必ず同期し、同期操作を対応するタスクカードの明示的な手順と検収内容とする。
5. ドキュメント形式規範は本リポジトリの対応する規範を引用し、マニュアル内に規範本文を複製しない。

## 10. フェーズ状態と作業ウィンドウ

機械可読索引では各章にフェーズマークを付け、それに応じてローカルの作業ウィンドウを調整する：

| フェーズ | 特徴 | 作業ウィンドウ |
| --- | --- | --- |
| グリーンフィールド | 凍結された契約に従って実装を記入する | 16-24K |
| 成長 | モジュール横断の機能、デフォルト設定 | 32K |
| 保守 | リファクタリングとモジュール横断の調査 | 48-64K、並列度は相応に減らす |

保守期の章には追加で調査ガイドを添える必要がある：症状、考えられる位置、検証コマンドの三列の表。

## 11. 採用記録、リリースと公式サイト文案

1. 採用記録表のフィールドは次のとおり固定する：名称、カテゴリ、バージョン、用途、ライセンス、著作権者、公式アドレス、改変の有無、変更説明、表明方法、採用状態。採用状態は「即時採用可、要評価、現時点で利用不可」の三段階に分ける。
2. リリース章はビルドスクリプト、CI マトリクス、checksum、署名環境変数テンプレートを網羅する。リリースカードの検収コマンドはビルド成果物のチェックであり、対外的な公開操作はローカルモデルに入れず、ユーザーの確認の後に実行する。
3. 公式サイト文案章は一般ユーザーを対象とする：コード、コマンドライン、技術用語、空語の使用を禁止する。構成はファーストビューの位置づけ、ペインポイント、ハイライト、信頼、ダウンロード、シナリオストーリー、よくある質問とし、語調は落ち着いて抑制的とする。

## 12. プロジェクト間参照と検証

1. 対象プロジェクトが本規範を参照する場合は `gitrule spec` で全文を読み込み、マニュアルの骨格をプロジェクト内マニュアルの初期骨格として複製する。本規範はプロジェクトに合わせて改訂せず、プロジェクト内マニュアルの進化はプロジェクトリポジトリ内で完結させる。
2. ドキュメント成果物に関わるタスクカードは、検収コマンドに `gitrule check` を追加する。多言語プロジェクトは `gitrule xcheck` を追加する。用語集の変更後は `gitrule termcheck` を実行する。
3. `gitrule check` のドキュメント違反が自動修復可能な種類である場合は、先に `gitrule optimize` を実行してから再検査し、それでも通らなければ引き継ぎ記録の block フィールドに書き込む。
4. Gitrule 規範はドキュメントとリポジトリ規範のみを管轄し、コード品質は各プロジェクトのテストと検証スクリプトが担い、両者は互いに代替しない。
