# Gitワークフローとブランチ規範

> このファイルが解決する問題：ブランチモデル、命名規則、プルリクエストの説明テンプレート、マージ戦略を定義し、メインラインの安定、協業の秩序、変更の追跡可能性を保証します。

## 1. 規範条文

1. 既定ブランチ（`main` または `master`）は保護しなければならず、直接の push は禁止する（ハードルール H7 に対応）。
2. すべての変更は個人ブランチ + プルリクエストを経てメインラインへマージする。
3. 長期ブランチと短期ブランチは明確に区分し、ブランチが長期間マージされない状態を避ける。
4. 公開ブランチへの `git push --force` は禁止する。個人ブランチの書き換えには `--force-with-lease` を用いる（H8 に対応）。
5. すでにプッシュされた公開ブランチへの rebase/amend は禁止する。マージ前に CI とコードレビューを通過しなければならない。

## 2. ブランチモデル

| ブランチ種別 | ライフサイクル | 作成元 | マージ先 | 命名形式 | 例 |
| --- | --- | --- | --- | --- | --- |
| 既定ブランチ | 長期 | — | — | `main` | `main` |
| 機能ブランチ | 短期、≤2 週間 | `main` | `main` | `feat/<概要>` | `feat/user-login` |
| 修正ブランチ | 短期、≤1 週間 | `main` | `main` | `fix/<概要>` | `fix/token-expiry` |
| ドキュメントブランチ | 短期 | `main` | `main` | `docs/<概要>` | `docs/api-guide` |
| リリースブランチ | 中期 | `main` | `main` + tag | `release/<バージョン>` | `release/1.2.0` |
| 緊急修正 | 短期、≤24 時間 | リリース tag | `main` + tag | `hotfix/<概要>` | `hotfix/payment-error` |

命名規則：小文字の kebab-case とし、概要は意図を表現できるものにすること。`test`、`temp`、`wip`、`my-xxx` は禁止。要求を関連付ける場合は要求番号を付加し、たとえば `feat/spacing-rule-req001` とします。

## 3. プルリクエストの説明テンプレート

```markdown
## 変更の目的
{{一句话说明为什么需要此变更，关联需求编号}}

## 変更内容
- {{具体改动 1}}
- {{具体改动 2}}

## 影響範囲
- 影響を受けるモジュール：{{模块名}}
- 互換性を破壊するか：{{是 / 否；是则给出迁移说明}}
- 設定やデータの移行を伴うか：{{是 / 否；是则说明}}

## 検証方法
- 自己テストのコマンド：{{命令}}
- 追加または変更したテスト：{{TC 编号}}
- CI の実行 URL：{{URL}}

## 関連
- 要求：{{REQ-NNN}}
- トレーサビリティマトリクス：{{已更新 / 待更新}}
- ドキュメント：{{docs/api.md#章节 / 无}}
- Issue：{{#编号 / 无}}

## セルフチェック
- [ ] コミットメッセージが規範に適合している
- [ ] 機密情報を含んでいない
- [ ] 要求トレーサビリティマトリクスを更新した
- [ ] 破壊的変更を変更履歴に記載した
```

## 4. フィールド定義

| フィールド | 必須 | 型 | 記載の要点 | 例 |
| --- | --- | --- | --- | --- |
| ブランチ概要 | はい | kebab-case | 単独で意図を表現でき、情報のない語は禁止 | `spacing-rule` |
| 関連要求 | はい | `REQ-NNN` | 立ち上げの番号と一致する | `REQ-001` |
| 変更の目的 | はい | テキスト | 「何を変えたか」ではなく「なぜか」を説明する | `中国語句読点の誤検出を修正` |
| 影響範囲 | はい | テキスト | 互換性を破壊するかを明確にすること | `いいえ` |
| 自己テストのコマンド | はい | コマンド | コピーして実行できること | `npm test -- -t spacing` |
| テスト番号 | はい | `TC-NNN` | テスト規範の番号と一致する | `TC-001` |
| CI の URL | はい | URL | レビュー担当者が照合しやすいこと | `https://github.com/.../runs/123` |
| セルフチェックリスト | はい | チェック | 項目ごとにチェックし、まとめて一度にチェックしてはならない | — |

## 5. 記入説明

1. **ブランチのライフサイクル**：2 週間を超えてマージされていない機能ブランチは、イテレーション振り返りで理由を説明し、分割またはクローズすること。
2. **概要の命名**：変更の目的から中核となる名詞 + 動作を取り、`fix2`、`new-feature` などの曖昧な名前は禁止。
3. **変更の目的**：問題と価値を書く。「コードを更新」「ロジックを最適化」は不合格。
4. **影響範囲**：互換性の破壊にチェックを入れた場合は、同時に変更履歴へ `BREAKING CHANGE:` を記載すること。
5. **自己テストのコマンド**：レビュー担当者がそのままコピーして実行し、同じ結論を得られること。手順が複雑な場合はスクリプトのパスを書く。
6. **トレーサビリティマトリクス**：PR のマージ前に [要求トレーサビリティマトリクス規範](./要求トレーサビリティマトリクス規範.md) の実装 PR と状態のフィールドを更新すること。
7. **force push**：他者がレビューしていない自分のブランチにのみ `--force-with-lease` を用い、PR で理由を説明しなければならない。

よくある誤り：

| 誤った記述 | 問題 | 修正方法 |
| --- | --- | --- |
| ブランチ名が `test`、`temp` | 意図の情報がない | `feat/<具体的な能力>` に変更する |
| PR の説明に「bug を修正」とだけ書く | 影響をレビューできない | 目的、影響、検証方法を補う |
| `main` へ直接 push する | H7 に反する | PR によるマージに切り替える |
| レビュー済みブランチを書き換えて強制 push する | レビューの結論が無効になる | 新たなコミットで指摘に応答する |
| マージ後にソースブランチを削除しない | ブランチ一覧が膨張する | マージ後すぐに削除する |

## 6. 完全な例

```markdown
## 変更の目的
中国語の句読点が英単語に隣接する際に空白ルールが誤検出される問題を修正する（REQ-004）。

## 変更内容
- ルールエンジンに句読点の境界判定を追加
- 対応するリグレッションケースを追加

## 影響範囲
- 影響を受けるモジュール：spacing ルール
- 互換性を破壊するか：いいえ
- 設定やデータの移行を伴うか：いいえ

## 検証方法
- 自己テストのコマンド：`npm test -- -t "中文标点"`
- 追加または変更したテスト：TC-007-regression-142
- CI の実行 URL：https://github.com/example/markdown-lint-cli/actions/runs/128

## 関連
- 要求：REQ-004
- トレーサビリティマトリクス：更新済み
- ドキュメント：なし
- Issue：#142

## セルフチェック
- [x] コミットメッセージが規範に適合している
- [x] 機密情報を含んでいない
- [x] 要求トレーサビリティマトリクスを更新した
- [x] 破壊的変更を変更履歴に記載した（本変更に破壊的変更はなし）
```
