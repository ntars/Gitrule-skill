# LICENSE規範

> このファイルが解決する問題：プロジェクトライセンスの SPDX 表記、LICENSE 全文の要件、著作権表示行の位置、GitHub の検出機構、階層ライセンスのファイル配置と確認フロー、および確認なしに記載してはならないルールを定義します。

## 1. 基本ルール

1. プロジェクトのライセンスは SPDX 識別子で README に明記しなければならず、対応する LICENSE ファイルを提供します。
2. LICENSE ファイルは当該ライセンスの公式な英語全文でなければならず、条項を削除・改変してはなりません。文言の書き換え、段落の並べ替え、Markdown での再整形はすべて自動検出を失敗させます。
3. 著作権表示行はファイルの先頭または README の第 19 章に配置し、形式は [READMEセクション規範](./READMEセクション規範.md) を参照します。

## 2. GitHub の検出機構

GitHub はオープンソースの licensee を用いてリポジトリのライセンスを判定します。結果はリポジトリページのバッジ、API の license フィールド、および license キーワード検索でヒットするかどうかを左右します。ルールは次のとおりです：

1. 走査するのは 2 か所のみ：プロジェクトのルートディレクトリと、最上位の `LICENSES/` ディレクトリです。`locales/`、`docs/` などのサブディレクトリ内の同名ファイルは判定対象外です。
2. ルートディレクトリではファイル名で採点し、高得点が優先されます：`LICENSE` は 1.00、`LICENSE.md` は 0.95、`COPYING` は 0.90、`LICENSE-MIT` のような接尾辞付きは 0.70。
3. 最上位 `LICENSES/` ディレクトリ内のファイルは、ファイル名が SPDX 識別子の形式で拡張子が `.txt`、`.md`、`.markdown`、`.html` のとき 1.00、それ以外は 0.00。
4. ファイル内容は当該ライセンスの公式全文と高度に一致しなければなりません。「本プロジェクトは某某ライセンスを採用する」といった宣言だけのファイルは検出されず、検出されたとしても非標準の値になります。
5. 互いに異なる複数のライセンスが検出された場合、プロジェクトレベルの結果は特定のライセンスを返さないことがあり、リポジトリページには `View license` または `Other` と表示されます。
6. README の自然言語による宣言は判定対象外です。「本プロジェクトは MIT ライセンスである」と書いても MIT として検出されるわけではありません。

したがって：**README の宣言と LICENSE ファイルは 2 つの独立した機構であり、両方を備えなければなりません。** またルートディレクトリに複数のライセンスファイルがある場合、最終的にどれが報告されるかはファイル名の採点と内容の一致度の双方に左右され、予測できません。実測ではデュアルライセンスのリポジトリはいずれもその一方のみが報告されました。

## 3. 階層ライセンスのファイル配置

階層ライセンスとは、リポジトリ内の部分ごとに異なるライセンスを適用することです。たとえばコードは MIT、ドキュメントは CC BY 4.0 とします。この場合は次の順序で配置を決めます：

| 方案 | ルートに置くもの | 自動検出の結果 | 適用条件 |
| --- | --- | --- | --- |
| 単層（既定） | `LICENSE` 1 部 | 当該ライセンスとして安定して検出 | 各層のライセンスが同一、または差異が利用者の義務に影響しない |
| 階層＋説明 | `LICENSE` に主ライセンス、別に `LICENSING.md` | ルート `LICENSE` のライセンスとして安定して検出 | 階層化が必要で、バッジの明確さも保ちたい |
| 階層＋REUSE | 最上位 `LICENSES/` に各ライセンスの全文 | 非標準の値に退化する可能性 | 下流が REUSE 準拠を明確に要求する場合のみ |

トレードオフ：

1. ルート直下に複数のライセンスファイルを置かないでください。実測ではデュアルライセンスのリポジトリはいずれも一方のみが報告され、もう一方はリポジトリページでも API でも不可視となり、対外的に 1 種類のライセンスしか宣言していないのと同じになります。
2. REUSE の配置はバッジの明確さと衝突します：`LICENSES/` に複数のライセンスを置くと複数ライセンスと判定され、`reuse lint` の全緑と引き換えに自動検出の結果が不明確になります。両方を完全に満たすことはできず、プロジェクト側が权衡する必要があります。
3. 「階層＋説明」を採用する場合、`LICENSING.md` というファイル名は `LICENSE` や `COPYING` のパターンを含まないため、ライセンスファイルと誤認されず、ルート `LICENSE` の検出に影響しません。
4. どの配置を選んでも、README の第 19 章に SPDX 式（例：`MIT AND CC-BY-4.0`）と各層の適用範囲を明記しなければなりません。人間が読むレベルで情報が失われない唯一の場所です。

## 4. 階層の判断と確認フロー

階層ライセンスは法的な意味を伴います。作成または最適化の前に必ず往復して確認し、臆測で埋めてはなりません。

1. 勝手に階層化してはなりません。ユーザーが明確に要求していない場合は単層として扱い、レポートに「階層化が必要な場合、選択可能な方案と差異は次のとおり」と記載します。
2. 階層化を提案するときは根拠を報告しなければなりません：各層が実際に覆う内容の範囲、候補ライセンスとその義務の差異、下流の利用者への影響、および自動検出の結果がどう変わるか。
3. 書き込む前に少なくとも 2 回確認します：1 回目は階層の組み合わせ（どの層にどのライセンスか）、2 回目はファイル配置（ルートファイルにどれを置くか、`LICENSES/` を作るか）。
4. プッシュ前に再度確認します。生成後は「ファイルを生成しました。確認のうえご自身でコミットしてください」と明確に伝え、ユーザーの代わりにコミットやプッシュをしてはなりません。
5. 確認を得ていない候補方案はレポートまたは一時ファイルにのみ書き、`LICENSE`、`LICENSES/`、`LICENSING.md` として書き出してはなりません。
6. ある部分がどの層に属するか判断できない場合は「【要確認：階層の帰属】」と注記し、疑義のあるファイルを列挙します。既定で分類してはなりません。

## 5. 免責事項の要件

ライセンスの文言は法的効力を持ちます。テンプレートとツールは判定ルールとファイル配置のみを提供し、法的助言を構成しません。

1. README の第 19 章または `LICENSING.md` に免責事項を含め、ライセンスの選択はプロジェクト側が自ら確認することを説明しなければなりません。
2. 免責事項は NOTICE の免責事項と一致しなければならず、一方にあり他方にないという状態にしてはなりません。
3. 「準拠判定が完了した」と主張してはならず、「ルールに沿ってファイル配置と SPDX 表記の過不足を確認した」とだけ説明できます。
4. 階層ライセンスの法的効力は各ライセンスの原文に従います。リポジトリ内の説明文は索引にすぎず、条項を変更しません。
