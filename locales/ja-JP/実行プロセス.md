# 実行プロセス

> このファイルが解決する問題：立ち上げから納品までの完全なフェーズ順序、各フェーズの開始条件と成果物、および情報が不足している場合のブロッキング質問ルールを定義する。

## 1. 総括プッシュフロー（Phase 0–6）

### Phase 0 · 立ち上げ（Project Init）

出力：プロジェクト名の候補 3 件 + 選定理由 + 名称重複検索の結論 + リポジトリのメタデータ表（description / topics / デフォルトブランチ / 可視性 / license）。命名規則は [プロジェクト命名規範](./プロジェクト命名規範.md) を参照してください。

### Phase 1 · 棚卸し（Inventory）

リポジトリをスキャンし、構造化された一覧を出力します：
- 技術スタック、エントリーファイル、パッケージマネージャー、lockfile
- 既存のドキュメント、不足しているドキュメント
- リポジトリ容量の上位 10 件の大きなファイル
- 既存の CI / テンプレート / 保護ルール
- 現在の git 状態：未追跡ファイル、未コミットの変更、履歴内の疑わしいコミット

### Phase 2 · 並列レビュー（Audit）

[監査次元マトリクス](./監査次元マトリクス.md) に従って次元をサブエージェントに分派し並列実行します。分派方法は [サブエージェント委譲契約](./サブエージェント委譲契約.md) を参照してください。各サブエージェントは構造化された結論のみを返し、長文の散文は返しません。

### Phase 3 · 修正（Fix）

P0 → P1 → P2 の順に TODO を列挙し、担当エージェントと想定アクションを明記します。P0 が未クローズの場合は Phase 5 に進んではなりません。

### Phase 4 · ドキュメント生成（Docs）

[ドキュメントマトリクス](./ドキュメントマトリクス.md) に従って 1 ファイルずつドキュメントエージェントに分派します。**一度に 1 ファイルだけ書き、書き終えて検証してから次に進みます。**

### Phase 5 · プッシュ（Push）

[プッシュとリリース規範](./プッシュとリリース規範.md) に従って実行し、結果を 1 件ずつエコーバックします。

### Phase 6 · プッシュ後（Post-Push）

tag を作成し、Release Notes を書き、バッジとリンクの可用性を検証し、CI がグリーンであることを確認し、About 欄の情報が正しいことを確認します。

## 2. ドキュメント生成フロー（フェーズ 0–5）

フェーズ順に進め、前のフェーズが完了していない場合は次のフェーズに進んではなりません。

| フェーズ | 名称 | 開始条件 | 成果物 |
| --- | --- | --- | --- |
| 0 | 情報検証 | 本規範とプロジェクト資料を受領 | 確認済み情報リスト、不足情報リスト |
| 1 | ブロッキング質問 | 必須フィールドの欠落がある（[情報収集とテンプレート](./情報収集とテンプレート.md) を参照） | 構造化された質問リスト。フィールド別にグループ化 |
| 2 | フレームワーク確認 | 必須フィールドが揃っている | README のセクション目次と各章の要点アウトライン。ユーザーの確認に供する |
| 3 | ドキュメント生成 | ユーザーがフレームワークを確認、または確認不要と明示 | すべての成果物 |
| 4 | 品質ゲート | ドキュメント生成が完了 | [品質ゲート](./品質ゲート.md) の項目別判定結果 |
| 5 | 納品 | ゲートがすべて通過、または未通過項目が明記済み | [監査レポート形式](./監査レポート形式.md) の順に出力し、プッシュ手順を添付 |

## 3. フェーズ 1 の質問ルール

1. フィールド別にグループ化して質問し、1 ラウンドで 15 項目を超えてはならない。
2. 各質問には用途と影響するセクションを説明し、ユーザーが優先度を判断できるようにする。
3. ユーザーが特定の項目を提供できないと明示した場合は、ドキュメントの該当箇所に「【未確認：フィールド名】」と記載し、文末に集約する。
4. ユーザーが「あなたの判断で」と回答した場合は、推奨値を提示してよいが、「【推奨値、ユーザー確認待ち】」と明記しなければならない。
