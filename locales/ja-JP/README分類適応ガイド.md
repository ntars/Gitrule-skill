# README分類適応ガイド

> このファイルが解決する問題：ライブラリ、アプリケーション、コマンドラインツール、フレームワーク、リソース集などのプロジェクト類型ごとに、README のセクション取捨、視覚的重点、バッジ設定の差異化された提案を示し、各類型の要素が美観と訴求力をどう高めるかを説明する。

汎用テンプレートはすべてのプロジェクトに適用できるが、類型の異なるプロジェクトでは読者の関心が異なる。本ファイルは汎用規範の上に、類型に向けた調整の提案を示す。読者は [README標準テンプレート](./README標準テンプレート.md) を基礎とし、本ファイルの該当類型に従って取捨すること。

## 1. 類型の概観

| 類型 | 読者の第一の問い | トップページの重心 | 必須セクション | 省略可能なセクション |
| --- | --- | --- | --- | --- |
| ライブラリ / SDK | インストール方法と API の使い方 | バージョンとライセンス | インストール、クイックスタート、API、互換性 | デプロイ、スクリーンショット |
| アプリケーション | アプリの外観と中核機能 | スクリーンショットと機能 | 機能、スクリーンショット、インストール、クイックスタート | API リファレンス |
| コマンドラインツール | コマンドの使い方と性能 | コマンド例と Demo | インストール、使い方、コマンド対照、Demo | アーキテクチャ、設定（少ない場合） |
| フレームワーク | エコシステムと学習コスト | ドキュメントの入り口と例 | 位置づけ、クイックスタート、ドキュメント、コミュニティ | 性能の詳細（外部リンク可） |
| リソース集 | 何を収録し、どう検索するか | 目次の分類とナビゲーション | 目次、分類、コントリビューションガイド | インストール、API |

## 2. ライブラリ / SDK

典型的な代表：axios などの HTTP クライアント、ユーティリティ関数ライブラリ、クライアント SDK。

### 2.1 セクションの取捨

- 「一言の位置づけ + バージョン + ライセンス」を前に置き、読者が互換性を判断できるようにする。
- 「インストール」を最前とし、パッケージマネージャのコマンド（npm、pip、cargo など）を示す。
- 「クイックスタート」は独立して実行できる完全な例でなければならない。
- 「API リファレンス」は主 README に詳しく載せるか、`docs/api.md` へリンクする。API 項目が多すぎる場合は、README には要約 + リンクのみを置く。
- 「互換性」で対応する言語バージョン、ランタイム、プラットフォームを説明する。

### 2.2 視覚的重点

- バッジの重点：バージョン、ビルド状態、ライセンス、ダウンロード数、パッケージサイズ。
- 画像の使用は控えめにし、通常はスクリーンショットを要しない。小型のロゴで識別性を確立してよい。
- API パラメータは表で示し、可読性を高める。

### 2.3 美観を高める要点

1. バージョンとライセンスのバッジを最上部に置き、即座に信頼性を確立する。
2. クイックスタートのコードブロックをファーストビュー付近に置き、試すハードルを下げる。
3. API の表は列幅と既定値の列を統一し、認知の負担を減らす。

## 3. アプリケーション

典型的な代表：エディタ、デスクトップツール、エンドユーザー向けの製品。

### 3.1 セクションの取捨

- ファーストビューには製品のスクリーンショットまたは実行画面を必ず含め、まず価値を示してから実装を語る。
- 「中核機能」は技術モジュールではなく、ユーザーのシナリオで構成する。
- 「インストール」は各プラットフォームのインストーラまたはダウンロードの入り口を網羅する。
- 「クイックスタート」は最短の導入経路を示す。
- ソースからのビルド手順は `CONTRIBUTING.md` へ外部リンクしてよい。

### 3.2 視覚的重点

- バッジの重点：バージョン、ビルド状態、ライセンス、ダウンロード数。
- スクリーンショットは位置づけの後に置き、トップページの中核要素とする。
- 機能一覧にはアイコンや短いスクリーンショットを添え、走査の効率を高める。

### 3.3 美観を高める要点

1. 高品質な製品スクリーンショットを中央に示し、明暗テーマに自動適応させる。
2. 機能の項目は短文 + アイコンで示し、長い説明を避ける。
3. ダウンロードの入り口を目立たせ、ボタン形式のリンクを用いる。

## 4. コマンドラインツール

典型的な代表：fd、ripgrep などのターミナルツール。

### 4.1 セクションの取捨

- 「一言の位置づけ」の直後にセクションナビを置き、移動しやすくする。
- 「インストール」は主要なパッケージマネージャとプラットフォーム別バイナリを列挙する。
- 「使い方」はタスク志向とし、よく使うコマンドの例を示す。
- 「コマンド対照」または「同類ツールとの比較」は需要の高い項目である。
- 「Demo」は GIF またはターミナル録画で実際の効果を示す。
- 性能データにはテスト環境と方法を注記すること。

### 4.2 視覚的重点

- バッジの重点：バージョン、ビルド状態、プラットフォーム対応、ライセンス。
- Demo 動画は中核の視覚資産で、速度と使用体験を示す。
- コマンドは言語注記付きのコードブロック、出力は `text` ブロックを用いる。

### 4.3 美観を高める要点

1. コマンド例を最上部に置き、スクロールせずにコピーして使えるようにする。
2. Demo 動画で実際のターミナルの効果を示し、「速い」という印象を強める。
3. 多言語のリンク（中国語、韓国語の翻訳など）はバッジ行の近くに置く。

## 5. フレームワーク

典型的な代表：next.js などのフルスタックフレームワーク。

### 5.1 セクションの取捨

- ファーストビューで位置づけ、エコシステムの規模、学習の入り口を強調する。
- 「ドキュメント」の入り口を必ず目立たせ、通常は独立したドキュメントサイトを指す。
- 「コミュニティ」でディスカッション領域、インスタントメッセージのチャネル、行動規範を説明する。
- 「クイックスタート」は最小のプロジェクト作成コマンドを示す。
- 深い内容（アーキテクチャ、API）は外部リンクとし、README で展開しない。

### 5.2 視覚的重点

- バッジの重点：バージョン、ビルド状態、ライセンス、コミュニティチャネル。
- ブランドロゴと `for-the-badge` スタイルのバッジを組み合わせ、トップページを強化する。
- Showcase のスクリーンショットでエコシステムの事例を示してよい。

### 5.3 美観を高める要点

1. 中央寄せロゴ + 大型で統一スタイルのバッジで、ブランド化されたファーストビューを形成する。
2. ドキュメントとコミュニティの入り口を目立つナビブロックで示す。
3. Good First Issues などの初心者向けの入り口でコントリビューションのハードルを下げる。

## 6. リソース集

典型的な代表：awesome 系のリスト。

### 6.1 セクションの取捨

- ファーストビューをロゴとスポンサー情報で始めるのはよくある手法である。
- 本文はテーマ別の分類で目次を構成し、明確なナビゲーションを提供する。
- 「コントリビューションガイド」で収録基準と投稿形式を説明する。
- インストール、API、デプロイなどのセクションは不要である。

### 6.2 視覚的重点

- バッジの数は緩和してよいが、スタイルは統一すること。
- 目次の分類は二級見出し + リストとし、項目に短い説明を添える。
- スポンサーのロゴは表またはグリッドで並べ、整列を保つ。

### 6.3 美観を高める要点

1. 目次の構造を明確にし、分類見出しの階層を一致させる。
2. 各項目に一言の説明を添え、リンクだけにしない。
3. スポンサーと謝辞の領域を整然と整列させ、本文の読解を妨げないようにする。

## 7. 類型をまたぐ汎用原則

1. **読者優先**：ファーストビューで読者が最も気にする問いに答える。類型の差異は順序に影響するだけで、情報の完全性には影響しない。
2. **スタイルの統一**：同一プロジェクトのバッジ、見出し、コードブロックのスタイルは必ず一致させる。
3. **コピー可能な例**：いずれの類型でも、そのまま実行できる例を少なくとも一つ提供する。
4. **外部リンク**：トップページの責務を超える深い内容は独立したドキュメントへ外部リンクする。
5. **継続的な同期**：スクリーンショット、バージョンバッジ、機能一覧はバージョンに合わせて更新し、古い情報で信頼性を損なわないようにする。
