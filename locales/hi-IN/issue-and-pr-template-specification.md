# Issue और PR टेम्पलेट विनिर्देश

> यह दस्तावेज़ किन समस्याओं का समाधान करता है: `.github/ISSUE_TEMPLATE/*.yml` संरचित फ़ॉर्म तथा `.github/PULL_REQUEST_TEMPLATE.md` स्व-जाँच सूची के फ़ील्ड डिज़ाइन, प्रारूप और लेखन आवश्यकताओं को परिभाषित करना, ताकि समस्या-प्रतिक्रिया और परिवर्तन-कमिट के लिए क्रियान्वयन-योग्य इनपुट बाधाएँ उपलब्ध हों।

## 1. डिज़ाइन सिद्धांत

1. **मुक्त पाठ की तुलना में संरचना को प्राथमिकता**: इश्यू फ़ॉर्म YAML में परिभाषित होते हैं, ड्रॉपडाउन, चेकबॉक्स और अनिवार्य फ़ील्ड के माध्यम से भरने का मार्गदर्शन करते हैं, जिससे अप्रभावी प्रतिक्रियाएँ घटती हैं।
2. **अनिवार्य फ़ील्ड न्यूनतम रखें**: केवल समस्या को स्थित करने के लिए आवश्यक फ़ील्ड रखें, वैकल्पिक फ़ील्ड को अनिवार्य के रूप में चिह्नित न करें।
3. **स्व-जाँच को स्पष्ट करें**: PR टेम्पलेट में जाँच सूची के रूप में चयन-योग्य स्व-जाँच मदें सूचीबद्ध करें, ताकि योगदानकर्ता महत्वपूर्ण चरण न छोड़ें।
4. **एकल उत्तरदायित्व**: इश्यू फ़ॉर्म जानकारी एकत्र करने के लिए उत्तरदायी है, परियोजना-परिचय नहीं देता; PR टेम्पलेट स्व-जाँच के लिए उत्तरदायी है, सुविधा-विवरण को दोहराता नहीं (देखें [दस्तावेज़ मैट्रिक्स](./document-matrix.md))।

## 2. Issue फ़ॉर्म संरचना

### 2.1 फ़ाइलें और नामकरण

- पथ `.github/ISSUE_TEMPLATE/*.yml` पर निश्चित है, प्रत्येक टेम्पलेट के लिए एक फ़ाइल।
- फ़ाइल नाम में लोअरकेस और हाइफ़न का उपयोग करें, जैसे `bug-report.yml`, `feature-request.yml`, `question.yml`।
- कम से कम “त्रुटि रिपोर्ट” और “फ़ीचर अनुरोध” दो प्रकार के टेम्पलेट प्रदान करें।

### 2.2 मानक फ़ील्ड

| फ़ील्ड | प्रकार | अनिवार्य | उद्देश्य |
| --- | --- | --- | --- |
| `name` | स्ट्रिंग | हाँ | टेम्पलेट प्रदर्शित नाम |
| `description` | स्ट्रिंग | हाँ | टेम्पलेट उद्देश्य विवरण |
| `title` | स्ट्रिंग उपसर्ग | हाँ | स्वतः उत्पन्न इश्यू शीर्षक उपसर्ग |
| `labels` | सरणी | नहीं | स्वतः जोड़े जाने वाले लेबल |
| `body` | सरणी | हाँ | फ़ॉर्म फ़ील्ड सूची |

`body` में सामान्य फ़ील्ड प्रकार:

| प्रकार | उपयुक्त परिदृश्य | उदाहरण |
| --- | --- | --- |
| `markdown` | विवरण पाठ, कोई इनपुट नहीं | भरने के निर्देश |
| `textarea` | लंबा पाठ विवरण | समस्या पुनरुत्पादन के चरण |
| `input` | एकल-पंक्ति लघु पाठ | संस्करण संख्या |
| `dropdown` | सीमित विकल्प | ऑपरेटिंग सिस्टम, गंभीरता |
| `checkboxes` | बहु-पुष्टि | क्या दोहराए इश्यू पहले से खोजे गए |

### 2.3 त्रुटि रिपोर्ट फ़ील्ड सूची

1. समस्या विवरण (`textarea`, अनिवार्य): क्या हुआ।
2. अपेक्षित व्यवहार (`textarea`, अनिवार्य): क्या होना चाहिए था।
3. पुनरुत्पादन के चरण (`textarea`, अनिवार्य): क्रमांकित सूची, स्वतंत्र रूप से पुनरुत्पादन-योग्य।
4. पर्यावरण जानकारी (`input` या `dropdown`): ऑपरेटिंग सिस्टम, रनटाइम, परियोजना संस्करण।
5. लॉग या स्क्रीनशॉट (`textarea`): त्रुटि जानकारी दें, संवेदनशील जानकारी का मास्किंग अनिवार्य है।
6. दोहराव जाँच पुष्टि (`checkboxes`, अनिवार्य): मौजूदा issue पहले ही खोजे जा चुके हैं।

### 2.4 फ़ीचर अनुरोध फ़ील्ड सूची

1. समस्या कथन (`textarea`, अनिवार्य): वर्तमान में कौन-सी क्षमता का अभाव है।
2. उपयोग परिदृश्य (`textarea`, अनिवार्य): किसे किन परिस्थितियों में आवश्यकता है।
3. अपेक्षित समाधान (`textarea`): कैसे क्रियान्वित होना चाहिए।
4. वैकल्पिक समाधान (`textarea`): अन्य विचारित तरीके।
5. संगतता प्रभाव (`dropdown`): क्या इसमें ब्रेकिंग परिवर्तन सम्मिलित हैं।

## 3. PR टेम्पलेट संरचना

### 3.1 अनिवार्य खंड

`PULL_REQUEST_TEMPLATE.md` में निम्नलिखित खंड होने चाहिए, क्रम निश्चित है:

1. परिवर्तन विवरण: इस बार क्या बदला गया, तथा संबंधित issue संख्या।
2. परिवर्तन प्रकार: चेकबॉक्स से चयन करें (फ़ीचर, फ़िक्स, दस्तावेज़, रिफ़ैक्टर, परीक्षण आदि, प्रकार देखें [कमिट संदेश विनिर्देश](./commit-message-specification.md))।
3. स्व-परीक्षण सूची: चयन-योग्य स्व-जाँच मदें।
4. ब्रेकिंग परिवर्तन: यदि नहीं है तो “कोई नहीं” लिखें; यदि है तो माइग्रेशन विधि लिखें (देखें [माइग्रेशन गाइड विनिर्देश](./migration-guide-specification.md))।
5. संबंधित दस्तावेज़: क्या README, CHANGELOG, API दस्तावेज़ समकालिक रूप से अद्यतन किए गए।

### 3.2 स्व-परीक्षण सूची का उदाहरण

```markdown
## स्व-परीक्षण सूची

- [ ] स्थानीय बिल्ड सफल
- [ ] संबंधित परीक्षण सफल, नई सुविधा के लिए परीक्षण जोड़े गए
- [ ] [कमिट संदेश विनिर्देश](./commit-message-specification.md) के अनुसार कमिट संदेश लिखा गया
- [ ] दस्तावेज़ समकालिक रूप से अद्यतन किए गए या पुष्टि की गई कि अद्यतन आवश्यक नहीं
- [ ] कोई गोपनीय कुंजी, निजी डेटा या बड़ी फ़ाइल शामिल नहीं की गई
```

## 4. प्रतिलिपि-योग्य टेम्पलेट

### 4.1 त्रुटि रिपोर्ट फ़ॉर्म

`.github/ISSUE_TEMPLATE/bug-report.yml` के रूप में सहेजें:

```yaml
name: त्रुटि रिपोर्ट
description: पुनरुत्पादन-योग्य कार्यशीलता विसंगति की रिपोर्ट करें
title: "[Bug]: "
labels: ["bug"]
body:
  - type: markdown
    attributes:
      value: |
        सबमिट करने से पहले मौजूदा issue खोजें, दोहराव से बचें।
        गोपनीय कुंजी, टोकन या व्यक्तिगत निजी जानकारी चिपकाएँ नहीं।
  - type: checkboxes
    id: duplicate-check
    attributes:
      label: दोहराव जाँच
      options:
        - label: मैंने मौजूदा issue खोज लिए हैं, यह दोहराई गई रिपोर्ट नहीं है
          required: true
  - type: textarea
    id: description
    attributes:
      label: समस्या विवरण
      description: वास्तव में क्या हुआ
      placeholder: install कमांड चलाने के बाद प्रोग्राम का एग्ज़िट कोड 1 है
    validations:
      required: true
  - type: textarea
    id: expected
    attributes:
      label: अपेक्षित व्यवहार
      description: क्या होना चाहिए था
    validations:
      required: true
  - type: textarea
    id: steps
    attributes:
      label: पुनरुत्पादन के चरण
      description: क्रमांकित करें, ताकि अन्य स्वतंत्र रूप से पुनरुत्पादन कर सकें
      placeholder: |
        1. कमांड चलाएँ
        2. आउटपुट देखें
        3. विसंगति दिखाई देती है
    validations:
      required: true
  - type: input
    id: version
    attributes:
      label: परियोजना संस्करण
      placeholder: v1.0.0
    validations:
      required: true
  - type: dropdown
    id: os
    attributes:
      label: ऑपरेटिंग सिस्टम
      options:
        - macOS
        - Linux
        - Windows
        - अन्य
    validations:
      required: true
  - type: textarea
    id: logs
    attributes:
      label: लॉग या स्क्रीनशॉट
      description: त्रुटि जानकारी दें, संवेदनशील जानकारी का मास्किंग अनिवार्य है
      render: shell
  - type: checkboxes
    id: security
    attributes:
      label: सूचना सुरक्षा पुष्टि
      options:
        - label: पुष्टि की गई कि गोपनीय कुंजी, टोकन या व्यक्तिगत निजता शामिल नहीं है
          required: true
```

```yaml
      required: true
  - type: textarea

    attributes:
      label: अपेक्षित समाधान

    id: alternatives
```

### 4.3 PR टेम्पलेट

`.github/PULL_REQUEST_TEMPLATE.md` के रूप में सहेजें:

````markdown
## परिवर्तन विवरण

{{变更说明}}

## परिवर्तन प्रकार

- [ ] फ़ीचर (feat)
- [ ] फ़िक्स (fix)
- [ ] दस्तावेज़ (docs)
- [ ] प्रारूप (style)
- [ ] रिफ़ैक्टर (refactor)
- [ ] परीक्षण (test)
- [ ] बिल्ड या टूलचेन (build / ci)

## स्व-परीक्षण सूची

- [ ] स्थानीय बिल्ड सफल
- [ ] संबंधित परीक्षण सफल, नई सुविधा के लिए परीक्षण जोड़े गए
- [ ] कमिट संदेश विनिर्देश के अनुसार कमिट संदेश लिखा गया
- [ ] दस्तावेज़ समकालिक रूप से अद्यतन किए गए या पुष्टि की गई कि अद्यतन आवश्यक नहीं
- [ ] कोई गोपनीय कुंजी, निजी डेटा या बड़ी फ़ाइल शामिल नहीं की गई

## ब्रेकिंग परिवर्तन

{{破坏性变更说明}}

## संबंधित दस्तावेज़

- [ ] README समकालिक है या अद्यतन आवश्यक नहीं
- [ ] CHANGELOG दर्ज किया गया
- [ ] API दस्तावेज़ समकालिक है या अद्यतन आवश्यक नहीं
````

### 4.4 प्लेसहोल्डर तुलना तालिका

| प्लेसहोल्डर | अनिवार्य | भरने के मुख्य बिंदु |
| --- | --- | --- |
| `{{变更说明}}` | हाँ | एक वाक्य में परिवर्तन बताएँ, `#संख्या` रूप में issue संख्या संलग्न करें |
| `{{破坏性变更说明}}` | हाँ | ब्रेकिंग परिवर्तन न हो तो “कोई नहीं” लिखें; हो तो माइग्रेशन चरण लिखें और माइग्रेशन गाइड लिंक करें |

YAML फ़ॉर्म के `name`, `description`, `title`, `labels` टेम्पलेट मेटाडेटा हैं, परियोजना की वास्तविक स्थिति के अनुसार बदलें; `body` में फ़ील्ड प्रकार और `required` मान अनुभाग 2, 3 की फ़ील्ड सूची के अनुसार समायोजित करें, अनिवार्य मदें हटाई नहीं जा सकतीं।

त्रुटि रिपोर्ट भरने का उदाहरण:

````markdown
3. `npm run build` चलाएँ, एग्ज़िट कोड 1 देखा गया

## परियोजना संस्करण

v1.0.0

## ऑपरेटिंग सिस्टम

macOS

## लॉग या स्क्रीनशॉट

````

## 5. लेखन आवश्यकताएँ

1. फ़ील्ड विवरण में आदेशात्मक या कथनात्मक वाक्य का उपयोग करें, बोलचाल की भाषा नहीं।
2. प्रत्येक अनिवार्य फ़ील्ड के लिए भरने का उदाहरण या प्रारूप आवश्यकता दें।
3. संकेत पाठ में स्पष्ट करें “यह जानकारी क्यों आवश्यक है”, अस्पष्ट आवश्यकताओं से बचें।
4. निजता से संबंधित फ़ील्ड में मास्किंग का संकेत दें (देखें [सुरक्षा और निजता विनिर्देश](./security-and-privacy-specification.md))।
5. टेम्पलेट परियोजना के विकास के साथ अद्यतन होते हैं, अप्रचलित फ़ील्ड हटाई जानी चाहिए, लंबे समय तक संचित न रहें।

## 6. निषिद्ध बातें

1. सभी समस्या प्रकारों को एक मुक्त-पाठ टेम्पलेट में मिलाना निषिद्ध है।
2. समस्या को स्थित करने से असंबंधित अनिवार्य फ़ील्ड निर्धारित करना निषिद्ध है।
3. टेम्पलेट में परियोजना-परिचय या मार्केटिंग सामग्री रखना निषिद्ध है।
4. PR टेम्पलेट में स्व-परीक्षण सूची और ब्रेकिंग परिवर्तन घोषणा छोड़ना निषिद्ध है।
