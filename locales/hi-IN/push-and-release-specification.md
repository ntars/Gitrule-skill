# पुश और रिलीज़ विनिर्देश

> यह फ़ाइल कौन-सी समस्या हल करती है: पुश से पहले/दौरान/बाद की कार्रवाई-सूची, tag और रिलीज़ के नियम, घटना प्रबंधन प्रक्रिया, तथा संपूर्ण GitHub पुश मार्गदर्शिका और विफलता प्रबंधन मैट्रिक्स को परिभाषित करना।

## 1. पुश से पहले

1. `git status` साफ़ हो, कोई असूचीबद्ध संवेदनशील फ़ाइल न हो।
2. `git log` में कोई WIP न हो, कोई `fix bug` न हो, व्यक्तिगत जानकारी का रिसाव न हो।
3. पुष्टि करें कि `.gitignore` प्रभावी है, निर्माण आर्टिफ़ैक्ट और निर्भरताएँ ट्रैक नहीं हो रही हैं।
4. स्थानीय स्तर पर build, test और lint पास हों।
5. पूर्ण कुंजी स्कैन चलाएँ (ऐतिहासिक कमिट सहित)।
6. दस्तावेज़ मैट्रिक्स पूर्ण हो (देखें [दस्तावेज़ मैट्रिक्स](./document-matrix.md))।

## 2. पुश कार्रवाइयाँ

7. व्यक्तिगत शाखा पुश करें: `git push -u origin feat/xxx`।
8. मुख्य शाखा में केवल PR से जाएँ, सीधे push न करें।
9. `push --force` निषिद्ध है; अपनी शाखा का पुनर्लेखन `--force-with-lease` से करें।
10. पहले से पुश की गई सार्वजनिक शाखा पर rebase/amend निषिद्ध है।
11. एकल फ़ाइल >50MB हो तो पहले LFS से जाएँ, फिर पुश करें।
12. पहली बार पुश करने से पहले भंडार की दृश्यता की पुष्टि करें: डिफ़ॉल्ट private, सार्वजनिक करना वास्तव में आवश्यक हो तभी public पर स्विच करें।

## 3. tag और रिलीज़

13. tag प्रारूप `vMAJOR.MINOR.PATCH`, annotated अवश्य हो: `git tag -a v1.0.0 -m "release: 1.0.0"`।
14. tag केवल CI हरा होने और Release Notes तैयार होने के बाद लगाएँ।
15. परिवर्तन तोड़ने वाले बदलावों के लिए `feat!:` या `BREAKING CHANGE:` अवश्य हो, और CHANGELOG में माइग्रेशन विधि दी जाए।

## 4. Phase 6 · पुश के बाद (Post-Push)

- annotated tag लगाएँ;
- Release Notes लिखें;
- बैज और लिंक की उपलब्धता सत्यापित करें;
- CI हरा होने की पुष्टि करें;
- About क्षेत्र की जानकारी सही होने की पुष्टि करें (description / topics / लिंक / social preview)।

## 5. घटना प्रबंधन

16. **कुंजी पुश हो चुकी है**: तुरंत रोटेट करें → `git filter-repo` से सफ़ाई करें → संरक्षित शाखा पर बलपूर्वक पुश के लिए व्यवस्थापक प्रक्रिया अपनाएँ → घोषणा करें।
17. **गलती से बड़ी फ़ाइल पुश हो गई**: LFS माइग्रेशन या इतिहास पुनर्लेखन करें, केवल फ़ाइल हटाकर न छोड़ें।

## 6. GitHub पुश मार्गदर्शिका विनिर्देश

मार्गदर्शिका में निम्नलिखित सात भाग अवश्य शामिल हों, और आदेश पूर्ण रूप से निष्पादन-योग्य संस्करण में दिए जाएँ।

### 6.1 पूर्व-सुरक्षा

1. पुश से पहले स्थानीय भंडार और रिमोट भंडार का पूर्ण बैकअप लें; `git clone --mirror` से मिरर बैकअप बनाना अनुशंसित है।
2. पुष्टि करें कि रिमोट भंडार में कोई सहयोगी नहीं है, या सहयोगियों को पुश रोकने की सूचना दे दी गई है।
3. पुष्टि करें कि लक्ष्य शाखा पर बलपूर्वक पुश सुरक्षा सक्षम नहीं है।

### 6.2 स्थानीय व्यवस्थापन

```bash
git status
git diff --name-status HEAD
git ls-files
```

तीनों आउटपुट की जाँच करें और पुष्टि करें कि कमिट होने वाले परिवर्तन स्थानीय निर्देशिका से मेल खाते हैं, तथा कोई अस्थायी फ़ाइल, निर्माण आर्टिफ़ैक्ट या पुराने संस्करण के दस्तावेज़ का अवशेष नहीं है। `.gitignore` में निर्माण आर्टिफ़ैक्ट और स्थानीय कॉन्फ़िगरेशन फ़ाइलें अवश्य शामिल हों।

### 6.3 संगतता जाँच

```bash
git fetch origin
git diff --name-status HEAD origin/{{分支名}}
```

यह आदेश रिमोट और स्थानीय फ़ाइलों का अंतर सूचीबद्ध करता है। जो फ़ाइलें रिमोट पर मौजूद हैं किंतु स्थानीय स्तर पर हटा दी गई हैं, उनके लिए स्थानीय स्तर पर `git rm` चलाकर कमिट करें, ताकि विलोपन की कार्रवाई संस्करण इतिहास में दर्ज हो जाए।

### 6.4 कमिट और पुश

```bash
git add -A
git commit -m "docs: 重建项目文档（README、README_EN、NOTICE）"
git push --force-with-lease origin {{分支名}}
```

`--force` के बजाय `--force-with-lease` अपनाएँ, जो रिमोट पर किसी अन्य के नए कमिट होने की स्थिति में पुश अस्वीकार करता है और दूसरों के कार्य को अधिलेखित होने से बचाता है। रिमोट भंडार को हटाकर पुनः बनाना उच्च-जोखिम कार्रवाई है, इसका प्रयोग केवल व्यक्तिगत भंडार में और मिरर बैकअप पूर्ण हो जाने पर ही करें; मार्गदर्शिका में डेटा हानि के जोखिम को स्पष्ट रूप से अंकित करना चाहिए।

### 6.5 पुश के बाद सत्यापन

```bash
git ls-remote --heads origin
gh repo view --web
```

वेब इंटरफ़ेस पर एक-एक करके फ़ाइल सूची, README रेंडरिंग, भाषा-परिवर्तन लिंक और NOTICE लिंक की वैधता की पुष्टि करें।

### 6.6 विफलता प्रबंधन मैट्रिक्स

| त्रुटि प्रकार | विशिष्ट अभिव्यक्ति | समाधान | जोखिम चेतावनी |
| --- | --- | --- | --- |
| प्रमाणीकरण विफलता | `Authentication failed` या `Permission denied (publickey)` | HTTPS से SSH पर स्विच करके कुंजी कॉन्फ़िगर करें, या `gh auth login` के बाद पुश करें | कोई नहीं |
| नेटवर्क व्यवधान | `Failed to connect` या `RPC failed` | नेटवर्क बदलें, प्रॉक्सी कॉन्फ़िगर करें, `git config --global http.postBuffer 524288000` चलाएँ | कोई नहीं |
| फ़ाइल आकार सीमा पार | `remote: error: File exceeds 100 MB` | कमिट इतिहास से बड़ी फ़ाइल हटाएँ या Git LFS सक्षम करें | इतिहास पुनर्लेखन के बाद सहयोगियों को पुनः क्लोन करने की सूचना दें |
| केस विरोधाभास | फ़ाइल नाम के केस में असंगति से डुप्लिकेट प्रविष्टियाँ | `git mv` से सुधारें और कमिट करें | कोई नहीं |
| इतिहास विरोधाभास | `non-fast-forward` या `fetch first` | पहले `git pull --rebase`; अधिलेखन वास्तव में आवश्यक हो तो `--force-with-lease` का प्रयोग करें | दूसरों के कमिट अधिलेखित होने पर पुनर्प्राप्ति संभव नहीं |
| शाखा सुरक्षा | `protected branch hook declined` | PR प्रक्रिया से विलय करें, या व्यवस्थापक अस्थायी रूप से नियम समायोजित करे | नियम समायोजन अंकित होना चाहिए |
| भंडार क्षति | `fatal: not a git repository` या ऑब्जेक्ट अनुपलब्ध | पुनः क्लोन करके कार्यक्षेत्र के परिवर्तन कॉपी करें | कार्यक्षेत्र का बैकअप पहले लें |

### 6.7 वापसी

पुश पूरा होने के बाद यदि कोई समस्या मिले, तो `git revert` से उलटा कमिट बनाएँ; पहले से सार्वजनिक हो चुके इतिहास को बलपूर्वक पुश करके अधिलेखित करना निषिद्ध है।

## संबंधित फ़ाइलें

- पुश से पहले [गुणवत्ता द्वार](./quality-gate.md) के तीन-स्तरीय द्वार पार करने होंगे
- कुंजी और बड़ी फ़ाइलों की लाल रेखाएँ देखें [पूर्ण नियम](./hard-rules.md) के H3/H5/H12
- कमिट संदेश विनिर्देश आयाम D7 में आता है, देखें [समीक्षा आयाम मैट्रिक्स](./review-dimension-matrix.md)
- रिलीज़ दस्तावेज़ `docs/release.md` की जिम्मेदारियाँ देखें [दस्तावेज़ मैट्रिक्स](./document-matrix.md)
