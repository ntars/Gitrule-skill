# समीक्षा रिपोर्ट प्रारूप

> यह फ़ाइल कौन-सी समस्या हल करती है: समीक्षा रिपोर्ट के अनन्य परिदान प्रारूप, फ़ील्ड आवश्यकताओं और भरने के उदाहरणों को परिभाषित करना, ताकि रिपोर्ट किसी अन्य agent द्वारा सीधे निष्पादित की जा सके।

रिपोर्ट समीक्षा चरण की अनन्य परिदान-वस्तु है। प्रत्येक समस्या में साक्ष्य, उत्तरदायी पक्ष और कार्रवाई तीनों एक साथ होने चाहिए; जिन निष्कर्षों को निष्पादित नहीं किया जा सकता, उन्हें रिपोर्ट में नहीं लिखा जाना चाहिए।

## 2. फ़ील्ड परिभाषाएँ

| फ़ील्ड | अनिवार्य | प्रकार | भरने के मुख्य बिंदु | उदाहरण |
| --- | --- | --- | --- | --- |
| भंडार नाम | हाँ | पाठ | GitHub भंडार नाम से शब्दशः मेल खाए | `markdown-lint-cli` |
| निष्कर्ष | हाँ | प्रगणन | केवल `ALLOW PUSH` या `BLOCK PUSH`; P0 शून्य न होने पर अनिवार्यतः उत्तरार्ध | `BLOCK PUSH` |
| मोड | हाँ | प्रगणन | निजी अस्थायी स्क्रिप्ट भंडार के लिए “अवनत समीक्षा” लिखा जा सकता है, शेष के लिए “पूर्ण समीक्षा” | `पूर्ण समीक्षा` |
| दृश्यता | हाँ | प्रगणन | `private` / `public`; सार्वजनिक करने से पहले लाइसेंस पुनः जाँचें | `private` |
| लाइसेंस | हाँ | SPDX पहचानकर्ता | लाइसेंस न होने पर `NONE` लिखें, तब निष्कर्ष अनिवार्यतः `BLOCK PUSH` होगा | `MIT` |
| डिफ़ॉल्ट शाखा | हाँ | पाठ | वास्तविक शाखा नाम लिखें, अनुमानित `main` न लिखें | `main` |
| द्वार स्थिति | हाँ | प्रगणन ×3 | A/B/C में से प्रत्येक के लिए एक पंक्ति; `SKIP` होने पर “लंबित मद” में कारण अंकित करें | `FAIL` |
| लंबित मद | सशर्त अनिवार्य | पाठ | स्थिति `FAIL` या `SKIP` होने पर अनिवार्य, अवरोध या छूट का कारण सूचीबद्ध करें | `D1 में .env मिला` |
| स्तर | हाँ | प्रगणन | `P0` अवरोध / `P1` पुश से पहले सुधार या पंजीकरण / `P2` सुझाव | `P0` |
| आयाम | हाँ | `D1`–`D14` | संख्या देखें [समीक्षा आयाम मैट्रिक्स](./review-dimension-matrix.md) | `D1` |
| समस्या | हाँ | पाठ | एक वाक्य में तथ्य लिखें, अनुमान या भावुक शब्दावली न लिखें | `मूल निर्देशिका में .env मौजूद है` |
| साक्ष्य | हाँ | पथ:पंक्ति या कमांड आउटपुट | पुनः जाँच योग्य होना अनिवार्य; साक्ष्य न मिलने पर `SKIP + कारण` लिखें | `.env:3` |
| उत्तरदायी agent | हाँ | agent नाम | ठोस निष्पादन भूमिका लिखें, “संबंधित व्यक्ति” न लिखें | `security-auditor` |
| कार्रवाई | हाँ | पाठ | सीधे निष्पादन योग्य कार्य, लक्ष्य फ़ाइल सहित | `.env हटाएँ, कुंजियाँ घुमाएँ और इतिहास साफ़ करें` |
| फ़ाइल पथ | हाँ | पाठ | [दस्तावेज़ मैट्रिक्स](./document-matrix.md) की सूची के अनुसार मद-वार सूचीबद्ध करें | `SECURITY.md` |
| दस्तावेज़ मैट्रिक्स स्थिति | हाँ | तालिका पंक्ति-वार | प्रत्येक फ़ाइल के लिए मौजूद, अनुपलब्ध या सुधार-लंबित अंकित करें | `SECURITY.md अनुपलब्ध` |
| पुश निष्पादन सूची | हाँ | चेकबॉक्स सूची | [पुश और रिलीज़ विनिर्देश](./push-and-release-specification.md) के नियमों के अनुसार मद-वार विस्तार करें | `- [ ] .gitignore प्रभावी होने की पुष्टि करें` |
| पारण विवरण | हाँ | पाठ | अवरोध होने पर कारण और हटाने की शर्तें लिखें; पारित होने पर संतुष्ट पूर्ण नियम लिखें | `P0 शून्य होने पर पुनः समीक्षा संभव` |

## 3. भरने के निर्देश

1. **निष्कर्ष पहले**: पहले P0 की संख्या तय करें, फिर निष्कर्ष लिखें। कोई भी P0 शून्य न होने पर `ALLOW PUSH` नहीं लिखा जा सकता।
2. **साक्ष्य अनिवार्य**: प्रत्येक समस्या के साथ `पथ:पंक्ति संख्या` या प्रतिलिपि-योग्य कमांड आउटपुट होना चाहिए। साक्ष्य-रहित निष्कर्ष पर `SKIP` अंकित करें और कारण लिखें, `PASS` नहीं लिखा जा सकता।
3. **उत्तरदायित्व भूमिका तक**: उत्तरदायी agent के लिए [समीक्षा आयाम मैट्रिक्स](./review-dimension-matrix.md) में दी गई भूमिका-नाम प्रयोग करें, एक समस्या के लिए एक उत्तरदायी पक्ष।
4. **कार्रवाई निष्पादन योग्य**: कार्रवाई में लक्ष्य फ़ाइल और संक्रिया-प्रकार स्पष्ट होना चाहिए; “बाद में संभालेंगे” और “स्वयं समायोजित कर लेंगे” अमान्य माने जाते हैं।
5. **द्वार-स्थिति सुसंगत**: A/B/C तीनों पंक्तियों की स्थिति समस्या सूची से मेल खानी चाहिए; कोई भी द्वार `FAIL` होने पर निष्कर्ष अनिवार्यतः `BLOCK PUSH` होगा।
6. **दस्तावेज़ मैट्रिक्स मद-वार**: सूची के अनुसार प्रत्येक फ़ाइल अलग-अलग सूचीबद्ध करें, केवल “दस्तावेज़ लगभग पूर्ण हैं” नहीं लिखा जा सकता।
7. **सूची का विस्तार**: पुश निष्पादन सूची में नियम मद-वार विस्तृत करें, “विनिर्देश के अनुसार निष्पादन करें” से स्थान न भरें।

सामान्य त्रुटियाँ:

| ग़लत लेखन | समस्या | सुधार का तरीका |
| --- | --- | --- |
| साक्ष्य कॉलम में “संदिग्ध समस्या है” लिखना | पथ नहीं, आउटपुट नहीं, पुनः जाँच असंभव | `फ़ाइल पथ:पंक्ति संख्या` या कमांड आउटपुट जोड़ें |
| P0 शून्य न होते हुए `ALLOW PUSH` लिखना | पूर्ण नियम का उल्लंघन | `BLOCK PUSH` में बदलें, हटाने की शर्तें स्पष्ट लिखें |
| जाँच न हो सकने वाली मद पर `PASS` लिखना | परिणाम गढ़ना | `SKIP` लिखें और लंबित मद में कारण अंकित करें |
| उत्तरदायी पक्ष में “संबंधित व्यक्ति” लिखना | कोई उत्तरदायी इकाई नहीं | ठोस agent नाम लिखें |
| कार्रवाई में “बाद में संभालेंगे” लिखना | निष्पादन योग्य नहीं | लक्ष्य फ़ाइल और ठोस संक्रिया स्पष्ट लिखें |
| डिफ़ॉल्ट शाखा को बिना पुष्टि `main` लिखना | वास्तविकता से मेल नहीं | `git branch` के आउटपुट को मान्य मानें |

## 4. पूर्ण उदाहरण

नीचे `BLOCK PUSH` का पूर्ण भरा हुआ उदाहरण दिया गया है:

````markdown
# पुश समीक्षा रिपोर्ट · markdown-lint-cli

निष्कर्ष: BLOCK PUSH
मोड: पूर्ण समीक्षा
भंडार: markdown-lint-cli · private · NONE · डिफ़ॉल्ट शाखा main

## 1. द्वार स्थिति
| द्वार | स्थिति | लंबित मद |
| --- | --- | --- |
| A सुरक्षा | FAIL | D1 में .env मिला, D2 में LICENSE नहीं |
| B गुणवत्ता | SKIP | भंडार में निर्भरताएँ स्थापित नहीं हैं, बिल्ड और परीक्षण निष्पादित नहीं हो सकते |
| C मुख्य पृष्ठ | FAIL | README में इंस्टॉल अनुभाग और न्यूनतम उदाहरण अनुपलब्ध |

## 2. समस्या सूची
| स्तर | आयाम | समस्या | साक्ष्य (पथ:पंक्ति / कमांड आउटपुट) | उत्तरदायी agent | कार्रवाई |
| --- | --- | --- | --- | --- | --- |
| P0 | D1 | मूल निर्देशिका में .env मौजूद है | `.env:3` में DATABASE_URL है | security-auditor | .env हटाएँ, डेटाबेस क्रेडेंशियल घुमाएँ और इतिहास साफ़ करें |
| P0 | D2 | लाइसेंस फ़ाइल अनुपलब्ध | `ls LICENSE` का आउटपुट `No such file or directory` | license-checker | भंडार स्वामी द्वारा लाइसेंस की पुष्टि के बाद LICENSE बनाएँ |
| P1 | D13 | README में इंस्टॉल अनुभाग अनुपलब्ध | `README.md:1-28` में “इंस्टॉल” शीर्षक नहीं | readme-writer | README मानक टेम्पलेट के अनुसार इंस्टॉल और न्यूनतम उदाहरण जोड़ें |

## 3. दस्तावेज़ मैट्रिक्स स्थिति
| फ़ाइल | स्थिति | अनुपलब्ध/सुधार-लंबित मद |
| --- | --- | --- |
| README.md | सुधार-लंबित | इंस्टॉल अनुभाग और न्यूनतम उदाहरण अनुपलब्ध |
| LICENSE | अनुपलब्ध | स्वामी द्वारा लाइसेंस प्रकार की पुष्टि शेष |
| SECURITY.md | अनुपलब्ध | अभी तक नहीं बनाई गई |

## 4. पुश निष्पादन सूची
- [ ] git status के स्वच्छ होने की पुष्टि करें
- [ ] पूर्ण कुंजी स्कैन चलाएँ (इतिहास के कमिट सहित)
- [ ] स्थानीय रूप से build, test और lint पास करें
- [ ] दस्तावेज़ मैट्रिक्स पूर्ण है

## 5. पारण विवरण
अवरोध का कारण: 2 मदें P0 हैं (क्रेडेंशियल लीक, लाइसेंस अनुपलब्ध), और निर्भरताएँ स्थापित न होने के कारण गुणवत्ता द्वार का निर्धारण संभव नहीं। हटाने की शर्तें: कुंजी रोटेशन और इतिहास की सफ़ाई पूरी करें, लाइसेंस निश्चित करें, बिल्ड-योग्य वातावरण में परीक्षण दोबारा चलाएँ और P0 शून्य करने के बाद पुनः समीक्षा करें।
````

`ALLOW PUSH` होने पर पाँचवें अनुभाग में लिखा जा सकता है: “सभी पूर्ण नियम संतुष्ट हैं, तीनों स्तरों के द्वार PASS हैं, पुश निष्पादित किया जा सकता है।” शेष अनुभाग वास्तविक स्थिति के अनुसार भरें, साक्ष्य और सूची को छोड़ा नहीं जा सकता।

## 5. परिदान क्रम

1. मूल README की भाषा-नाविगेशन की पूर्ण सामग्री।
2. प्रत्येक पूर्ण हो चुकी भाषा निर्देशिका की README का पूर्ण पाठ, भाषा-कोड और फ़ाइल पथ मद-वार सूचीबद्ध करें।
3. NOTICE फ़ाइल की सामग्री।
4. LICENSE योजना का विवरण (यदि उपयोगकर्ता ने लाइसेंस निर्दिष्ट नहीं किया है, तो केवल उम्मीदवार और अंतर दें, सीधे न बनाएँ)।
5. पुष्टि-लंबित मदों का सारांश।
6. समीक्षा रिपोर्ट (यह रिपोर्ट)।
7. GitHub पुश मार्गदर्शन।
