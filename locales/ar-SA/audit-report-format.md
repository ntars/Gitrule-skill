# صيغة تقرير المراجعة

> المشكلة التي يحلها هذا الملف: يحدد صيغة التسليم الوحيدة لتقرير المراجعة ومتطلبات حقوله وأمثلة تعبئته، بما يضمن أن يكون التقرير قابلاً للتنفيذ مباشرةً من وكيل آخر.

التقرير هو المُخرَج الوحيد لمرحلة المراجعة. ويجب أن يجمع كل بند مشكلة الدليل والجهة المسؤولة والإجراء في الوقت نفسه؛ ولا يجوز إدراج نتيجة غير قابلة للتنفيذ في التقرير.

## 1. هيكل التقرير

````markdown
# تقرير مراجعة الدفع · {{仓库名}}

النتيجة: {{结论}}
النمط: {{模式}}
المستودع: {{仓库名}} · {{可见性}} · {{许可证}} · الفرع الافتراضي {{默认分支}}

## I. حالة البوابات
| البوابة | الحالة | البنود المعلقة |
| --- | --- | --- |
| A الأمان | {{门禁状态}} | {{未决项}} |
| B الجودة | {{门禁状态}} | {{未决项}} |
| C الصفحة الرئيسية | {{门禁状态}} | {{未决项}} |

## II. قائمة المشكلات
| المستوى | البُعد | المشكلة | الدليل (مسار:سطر / خرج الأمر) | الوكيل المسؤول | الإجراء |
| --- | --- | --- | --- | --- | --- |
| {{等级}} | {{维度}} | {{问题}} | {{证据}} | {{责任agent}} | {{动作}} |

## III. حالة مصفوفة الوثائق
| الملف | الحالة | النواقص/البنود المطلوب تعديلها |
| --- | --- | --- |
| {{文件路径}} | {{状态}} | {{待改项}} |

## IV. قائمة تنفيذ الدفع
- [ ] {{推送规则}}

## V. توضيح التجاوز
{{放行说明}}
````

## 2. تعريف الحقول

| الحقل | إلزامي | النوع | نقاط التعبئة | مثال |
| --- | --- | --- | --- | --- |
| اسم المستودع | نعم | نص | مطابق حرفياً لاسم المستودع في GitHub | `markdown-lint-cli` |
| النتيجة | نعم | تعداد | `ALLOW PUSH` أو `BLOCK PUSH` فقط؛ وعند عدم تصفير P0 يجب أن تكون الثانية | `BLOCK PUSH` |
| النمط | نعم | تعداد | يجوز كتابة «مراجعة مخفّضة» للمستودعات الخاصة للسكربتات المؤقتة، وما عداها «مراجعة كاملة» | `مراجعة كاملة` |
| الظهور | نعم | تعداد | `private` / `public`؛ ويجب مراجعة الرخصة قبل الإتاحة العامة | `private` |
| الرخصة | نعم | معرّف SPDX | يُكتب `NONE` عند غياب الرخصة، وعندها يجب أن تكون النتيجة `BLOCK PUSH` | `MIT` |
| الفرع الافتراضي | نعم | نص | يُكتب اسم الفرع الفعلي، لا `main` المفترض | `main` |
| حالة البوابة | نعم | تعداد ×3 | سطر لكل من A/B/C؛ وعند `SKIP` يُذكر السبب في «البنود المعلقة» | `FAIL` |
| البنود المعلقة | إلزامي شرطياً | نص | إلزامي عندما تكون الحالة `FAIL` أو `SKIP`، بسرد سبب الإيقاف أو التخطي | `D1 كشف .env` |
| المستوى | نعم | تعداد | `P0` يوقف / `P1` يُصلَح أو يُسجَّل قبل الدفع / `P2` مقترح | `P0` |
| البُعد | نعم | `D1`–`D14` | الترقيم في [مصفوفة أبعاد المراجعة](./review-dimension-matrix.md) | `D1` |
| المشكلة | نعم | نص | جملة تقرر واقعة، دون تخمين أو انفعال | `ملف .env موجود في الجذر` |
| الدليل | نعم | مسار:سطر أو خرج أمر | يجب أن يكون قابلاً للتحقق؛ وعند التعذر يُكتب `SKIP + السبب` | `.env:3` |
| الوكيل المسؤول | نعم | اسم الوكيل | يُكتب الدور المنفّذ المحدد، لا «المعنيون» | `security-auditor` |
| الإجراء | نعم | نص | عملية قابلة للتنفيذ مباشرةً، مع الملف الهدف | `حذف .env وتدوير المفاتيح وتنظيف السجل` |
| مسار الملف | نعم | نص | يُسرد بنداً بنداً وفق قائمة [مصفوفة الوثائق](./document-matrix.md) | `SECURITY.md` |
| حالة مصفوفة الوثائق | نعم | جدول سطراً سطراً | وسم كل ملف بالوجود أو الغياب أو الحاجة إلى تعديل | `SECURITY.md مفقود` |
| قائمة تنفيذ الدفع | نعم | قائمة مربعات اختيار | تُفصَّل بنداً بنداً وفق قواعد [مواصفة الدفع والإصدار](./push-and-release-specification.md) | `- [ ] التأكد من فعالية .gitignore` |
| توضيح التجاوز | نعم | نص | عند الإيقاف يُكتب السبب وشرط الرفع؛ وعند التجاوز تُكتب القواعد المطلقة المستوفاة | `يمكن المراجعة بعد تصفير P0` |

## 3. إرشادات التعبئة

1. **النتيجة أولاً**: يُحدَّد عدد P0 أولاً، ثم تُكتب النتيجة. ولا يجوز إخراج `ALLOW PUSH` مع بقاء أي P0 دون تصفير.
2. **الدليل إلزامي**: يجب أن يحمل كل بند مشكلة `مسار:رقم السطر` أو خرج أمر قابلاً للنسخ. والنتيجة بلا دليل تُوسم `SKIP` مع بيان السبب، ولا يجوز كتابة `PASS`.
3. **المسؤولية بالأدوار**: يستخدم الوكيل المسؤول أسماء الأدوار في [مصفوفة أبعاد المراجعة](./review-dimension-matrix.md)، ويقابل كل مشكلة جهة مسؤولة واحدة.
4. **الإجراء قابل للتنفيذ**: يجب أن يحدد الإجراء الملف الهدف ونوع العملية؛ وتُعدّ عبارات «معالجة لاحقة» و«تعديل ذاتي» غير صالحة.
5. **اتساق البوابات**: تتقابل حالات الأسطر الثلاثة A/B/C مع قائمة المشكلات؛ وعند `FAIL` في أي بوابة يجب أن تكون النتيجة `BLOCK PUSH`.
6. **مصفوفة الوثائق بنداً بنداً**: تُسرد ملفاً ملفاً وفق القائمة، ولا يجوز الاكتفاء بعبارة «الوثائق مكتملة تقريباً».
7. **تفصيل القائمة**: يجب تفصيل قواعد قائمة تنفيذ الدفع بنداً بنداً، ولا يجوز استبدالها بعبارة «التنفيذ وفق المواصفة».

أخطاء شائعة:

| الكتابة الخاطئة | المشكلة | طريقة التصحيح |
| --- | --- | --- |
| كتابة «يبدو أن هناك مشكلة» في حقل الدليل | لا مسار ولا خرج، فيتعذر التحقق | إضافة `مسار الملف:رقم السطر` أو خرج الأمر |
| كتابة `ALLOW PUSH` مع بقاء P0 | مخالفة القواعد المطلقة | التغيير إلى `BLOCK PUSH` مع بيان شرط الرفع |
| كتابة `PASS` لبند يتعذر فحصه | اختلاق نتيجة | كتابة `SKIP` مع بيان السبب في البنود المعلقة |
| كتابة «المعنيون» كجهة مسؤولة | لا جهة مسؤولة محددة | كتابة اسم الوكيل المحدد |
| كتابة «معالجة لاحقة» كإجراء | غير قابل للتنفيذ | بيان الملف الهدف والعملية المحددة |
| كتابة `main` كفرع افتراضي دون تحقق | مخالف للواقع | الاعتماد على خرج `git branch` |

## 4. مثال كامل

التالي مثال تعبئة كامل لحالة `BLOCK PUSH`:

````markdown
# تقرير مراجعة الدفع · markdown-lint-cli

النتيجة: BLOCK PUSH
النمط: مراجعة كاملة
المستودع: markdown-lint-cli · private · NONE · الفرع الافتراضي main

## I. حالة البوابات
| البوابة | الحالة | البنود المعلقة |
| --- | --- | --- |
| A الأمان | FAIL | D1 كشف .env، D2 لا يوجد LICENSE |
| B الجودة | SKIP | التبعيات غير مثبتة في المستودع، فيتعذر تنفيذ البناء والاختبارات |
| C الصفحة الرئيسية | FAIL | README يفتقد قسم التثبيت والمثال الأدنى |

## II. قائمة المشكلات
| المستوى | البُعد | المشكلة | الدليل (مسار:سطر / خرج الأمر) | الوكيل المسؤول | الإجراء |
| --- | --- | --- | --- | --- | --- |
| P0 | D1 | ملف .env موجود في الجذر | `.env:3` يحتوي DATABASE_URL | security-auditor | حذف .env وتدوير بيانات اعتماد قاعدة البيانات وتنظيف السجل |
| P0 | D2 | لا يوجد ملف رخصة | خرج `ls LICENSE` هو `No such file or directory` | license-checker | توليد LICENSE بعد تأكيد نوع الرخصة من مالك المستودع |
| P1 | D13 | README يفتقد قسم التثبيت | `README.md:1-28` لا يحتوي عنوان «التثبيت» | readme-writer | إضافة التثبيت والمثال الأدنى وفق القالب القياسي لـ README |

## III. حالة مصفوفة الوثائق
| الملف | الحالة | النواقص/البنود المطلوب تعديلها |
| --- | --- | --- |
| README.md | يحتاج تعديلاً | يفتقد قسم التثبيت والمثال الأدنى |
| LICENSE | مفقود | بانتظار تأكيد نوع الرخصة من المالك |
| SECURITY.md | مفقود | لم يُنشأ بعد |

## IV. قائمة تنفيذ الدفع
- [ ] التأكد من نظافة git status
- [ ] تنفيذ فحص شامل للمفاتيح (بما في ذلك الإيداعات السابقة)
- [ ] نجاح build وtest وlint محلياً
- [ ] اكتمال مصفوفة الوثائق

## V. توضيح التجاوز
سبب الإيقاف: وجود 2 بند من P0 (تسريب بيانات اعتماد، وغياب رخصة)، وتعذر الحكم على بوابة الجودة لعدم تثبيت التبعيات. شرط الرفع: إتمام تدوير المفاتيح وتنظيف السجل، وتحديد الرخصة، وإعادة تشغيل الاختبارات في بيئة قابلة للبناء، ثم المراجعة بعد تصفير P0.
````

في حالة `ALLOW PUSH` يجوز كتابة القسم الخامس: «استُوفيت جميع القواعد المطلقة، والبوابات الثلاث كلها PASS، ويمكن تنفيذ الدفع.» وتُعبَّأ بقية الأقسام وفق الواقع، دون إغفال الأدلة والقائمة.

## 5. ترتيب التسليم

1. المحتوى الكامل لتنقل اللغات في README الجذر.
2. المحتوى الكامل لملف README في كل مجلد لغة مكتمل، مع سرد رمز اللغة ومسار الملف بنداً بنداً.
3. محتوى ملف NOTICE.
4. شرح خطة LICENSE (وإذا لم يحدد المستخدم الرخصة، تُقدَّم الخيارات المرشحة وفروقها فقط، دون توليد مباشر).
5. ملخص البنود قيد التأكيد.
6. تقرير المراجعة (هذا التقرير).
7. إرشادات الدفع إلى GitHub.
