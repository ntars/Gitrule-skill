# مواصفة رسالة الإيداع

> المشكلة التي يحلها هذا الملف: يحدد حقول Conventional Commits وصيغتها وتعليمات تعبئتها وأمثلتها، بما يضمن سجلًا مقروءًا وإمكانية توليد سجل التغييرات ورقم الإصدار تلقائيًا.

## 1. الصيغة

```text
<النوع>[النطاق الاختياري][اختياري !]: <الوصف>

[النص الأساسي الاختياري]

[الحاشية الاختيارية]
```

## 2. الأنواع

الفئات العشر الكاملة كما يلي، وتغطي حالات الإيداع الشائعة في مشاريع المصادر المفتوحة:

| النوع | المعنى |
| --- | --- |
| `feat` | ميزة جديدة |
| `fix` | إصلاح خلل |
| `docs` | تغيير في الوثائق |
| `style` | تعديل تنسيقي لا يغيّر المنطق (مسافات بيضاء، تنسيق، فاصلة منقوطة ناقصة، إلخ) |
| `refactor` | إعادة هيكلة، لا تضيف ميزة ولا تصلح خللًا |
| `perf` | تغيير في الشيفرة لتحسين الأداء |
| `test` | إضافة اختبارات ناقصة أو تصحيح اختبارات قائمة |
| `build` | تغيير يؤثر في نظام البناء أو التبعيات الخارجية (مثل npm وgulp) |
| `ci` | تغيير في إعدادات التكامل المستمر وسكربتاته (مثل GitHub Actions وCircleCI) |
| `chore` | مهام متنوعة مثل البناء والتبعيات وسلسلة الأدوات |

### 2.1 مقارنة صيغ الفريق والاختيار بينها

توجد ثلاث صيغ شائعة باختلاف أنماط التعاون، ويجب على المشروع أن يختار واحدة عند انطلاقه ويوحّدها على مستوى الفريق كله:

| الصيغة | الشكل | الملاءمة | القيود |
| --- | --- | --- | --- |
| صيغة العمل | `[رقم بطاقة المهمة] المؤلف: المحتوى المعدَّل` | الفرق التي تستخدم لوحات المهام والبرمجة الثنائية | تعتمد على منظومة أرقام بطاقات المهام، ولا تصلح عند غياب البطاقة |
| الصيغة التقليدية | `[التصنيف] المكوّن (اختياري): المحتوى المعدَّل` | الفرق التي تحتاج إلى تصفية السجل حسب وحدات العمل | تحتاج إلى جدول تصنيفات يتفق عليه الفريق، وله كلفة إضافية |
| صيغة المصادر المفتوحة | `<type>(<scope>): <subject>` | مكتبات المصادر المفتوحة وتطبيقاتها التي تحتاج إلى توليد CHANGELOG تلقائيًا | الأنواع والنطاقات كثيرة، وكلفة التعلّم أعلى |

يعتمد هذا المشروع صيغة المصادر المفتوحة (أي Conventional Commits) لتوحيد الممارسة، والسبب: أنها مقروءة آليًا، وتتيح توليد سجل التغييرات ورقم الإصدار تلقائيًا. أما صيغة العمل والصيغة التقليدية فتُستخدمان في الفرق المغلقة المصدر وفق ما يتفق عليه، ولا يجوز خلطهما في المستودعات العامة.

## 3. تعريف الحقول

| الحقل | إلزامي | النوع | نقاط التعبئة | مثال |
| --- | --- | --- | --- | --- |
| النوع | نعم | تعداد | واحد من الفئات العشر، ولا يجوز ابتداع نوع جديد | `feat` |
| النطاق | لا | نص | اسم المكوّن، كلمة قصيرة بأحرف صغيرة، بلا مسافات | `parser` |
| علامة التغيير الجذري | لا | `!` | توضع بعد النوع أو النطاق وقبل النقطتين | `feat!:` |
| الوصف | نعم | نص | جملة أمرية، تبدأ بحرف صغير، ≤72 حرفًا، بلا نقطة في النهاية | `add TOML config support` |
| النص الأساسي | لا | نص | يوضح الدافع والتنفيذ، ويفصل عنه سطر فارغ | `Allow the parser to read TOML...` |
| الحاشية | لا | نص | `BREAKING CHANGE:` أو `Refs: #N` | `BREAKING CHANGE: ...` |
| المتطلب المرتبط | لا | `REQ-NNN` | يُكتب في النص الأساسي أو الحاشية لتسهيل التتبع | `Refs: REQ-001` |

## 4. تعليمات التعبئة

1. **الوصف**: يُستخدم فعل أمر (add، fix، remove)، ويُكتب «ما تم فعله» لا «تم إجراء تعديل»؛ ويجوز في المشاريع الصينية كتابة وصف صيني، لكن يجب توحيده على مستوى المستودع كله.
2. **النطاق**: يُؤخذ اسم المكوّن لا اسم الملف؛ وتُحذف النطاقات في التغييرات العابرة للمكونات، ولا يُكتب `all` أو `global`.
3. **النص الأساسي**: يُكتب فقط عندما لا يكفي الوصف لبيان الدافع؛ ولا يعيد صياغة الوصف، ولا يسرد سجلًا تفصيليًا للخطوات.
4. **التغيير الجذري**: يُختار بين `feat!:` / `fix!:` وحاشية `BREAKING CHANGE:` أو يُجمع بينهما؛ وعند ظهورهما يجب الكتابة المتزامنة في [مواصفة سجل التغييرات](./changelog-specification.md) و[مواصفة دليل الترحيل](./migration-guide-specification.md).
5. **الذرّية**: الإيداع الواحد يفعل شيئًا واحدًا؛ ويُفصل التنسيق عن تغييرات المنطق في إيداعين.
6. **الأمان**: لا يجوز تضمين مفاتيح سرية أو رموز وصول أو بيانات شخصية أو عناوين داخلية؛ ويُتحقق قبل الإيداع بفحص الأسرار (انظر [مواصفة الأمان والخصوصية](./security-and-privacy-specification.md)).
7. **الترابط مع الإصدار**: يُطلق `feat` زيادة الإصدار الفرعي، ويُطلق `fix` زيادة إصدار المراجعة، ويُطلق `BREAKING CHANGE` زيادة الإصدار الرئيسي، والتفاصيل في [مواصفة إدارة الإصدارات](./version-management-specification.md).

أخطاء شائعة:

| الصيغة الخاطئة | المشكلة | طريقة التصحيح |
| --- | --- | --- |
| `wip`、`update`、`fix bug` | لا تحمل معلومة، وتخالف H10 | كتابة الهدف والسلوك بوضوح |
| `feat: Added new feature.` | ليست جملة أمرية، وتبدأ بحرف كبير، وتنتهي بنقطة | `feat: add config loader` |
| `feat(全部): 优化` | النطاق غير صالح، والوصف غامض | استخدام اسم مكوّن محدد وبيان التغيير |
| إيداع واحد يجمع تنسيقًا وتغييرًا وظيفيًا | يخرق الذرّية | فصله إلى إيداعين `style:` و`feat:` |
| رسالة الإيداع تحتوي عنوانًا داخليًا | تسريب معلومات | إزالته والمرور بفحص الأسرار |

## 5. مثال كامل

```text
feat(parser): إضافة دعم لإعداد TOML

اسمح للمحلّل بقراءة ملفات إعداد TOML إلى جانب YAML.
Refs: REQ-001

BREAKING CHANGE: أصبح خيار `config` يقبل مسار ملف بدلًا من كائن.
```

معاني الحقول: `feat` هو النوع، و`parser` هو النطاق، وما بعد النقطتين وصف موجز؛ والنص الأساسي يوضح الدافع والتنفيذ، والحاشية تربط المتطلب؛ والحاشية الأخيرة تعلن التغيير الجذري وتبيّن اتجاه الترحيل.

مثال من نوع الإصلاح:

```text
fix(spacing): تجنّب النتائج الإيجابية الكاذبة قبل علامات الترقيم الصينية

كانت قاعدة التباعد تعلّم سابقًا سلاسل مثل 「使用Node.js，」 لأن
فحص علامات الترقيم كان يجري بعد تطبيع المسافات البيضاء.

Refs: REQ-004, #142
```
