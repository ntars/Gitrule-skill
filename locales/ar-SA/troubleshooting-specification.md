# مواصفة استكشاف الأعطال

> المشكلة التي يحلها هذا الملف: تحديد بنية وثيقة استكشاف الأعطال (Troubleshooting / FAQ) وطريقة كتابة بنودها وآلية صيانتها، ليتمكن المستخدم من تحديد السبب انطلاقاً من العَرَض وحل المشكلات الشائعة بنفسه.

## 1. حالات الاستخدام

يجب توفير وثيقة استكشاف الأعطال في الحالات التالية:

1. تعدد الأسباب الشائعة لفشل التثبيت أو البناء.
2. تعارض بين بنود الإعداد، وعدم كفاية رسائل الخطأ لبيان طريقة الحل.
3. وجود قيود معروفة على منصة أو إصدار رقمي محدّد.
4. تكرار المستخدمين لأسئلة من النوع نفسه، مع وجود إجابة قابلة للتوحيد.

## 2. موقع الملف وتسميته

1. عند قلة المحتوى، يُدرَج قسماً في README بعنوان «الأسئلة الشائعة» أو «استكشاف الأعطال».
2. عند كثرة المحتوى، يُنشأ ملف مستقل `docs/troubleshooting.md` أو `FAQ.md`، ويُبقي README رابط الدخول.
3. تُجمَّع المشكلات حسب الموضوع، مثل «التثبيت» و«الإعداد» و«التشغيل» و«الأداء» و«الشبكة».

## 3. بنية الوثيقة

1. **المقدمة**: نطاق المشكلات الشائعة التي تغطيها الوثيقة والإصدارات الرقمية المعنية.
2. **فهرس المشكلات**: عرض عناوين المشكلات حسب الموضوع، مع دعم الانتقال السريع.
3. **بنود المشكلات**: تفصيل كل بند وفق بنية موحدة.
4. **تعذّر الحل**: الإشارة إلى قنوات طلب المساعدة مثل issue ومنتدى النقاش.

## 4. بنية البند

يجب أن يتضمن كل بند مشكلة الأجزاء التالية:

| الجزء | المحتوى | المتطلب |
| --- | --- | --- |
| العَرَض | المظهر المحدد الذي يراه المستخدم | يتضمن رسالة الخطأ كاملة، ولا يجوز الاكتفاء بعبارة «حدث خطأ» |
| شرط التفعيل | متى يظهر | تحديد الإصدار الرقمي والمنصة والعملية |
| السبب | السبب الجذري | شرح الآلية، لا الاكتفاء بالنتيجة |
| الحل | خطوات قابلة للتنفيذ | مُرقّمة، تتضمن الأوامر أو الإعدادات |
| التحقق | كيف يُتأكد من الإصلاح | إعطاء المخرجات المتوقعة |
| الارتباط | روابط الوثائق أو الـ issue ذات الصلة | اختياري |

## 5. مثال على كتابة البند

```markdown
### يظهر عند التثبيت `EACCES: permission denied`

**العَرَض**: تظهر رسالة بعدم كفاية الصلاحيات عند تنفيذ `npm install -g <package>`.

**شرط التفعيل**: تثبيت حزمة عامة بمستخدم عادي على Linux أو macOS.

**السبب**: صلاحية الكتابة في مجلد التثبيت العام تعود لمدير النظام، ولا يملك المستخدم الحالي حق الكتابة فيه.

**الحل**:

```bash
mkdir -p ~/.npm-global
npm config set prefix '~/.npm-global'
export PATH=~/.npm-global/bin:$PATH
npm install -g <package>
```

**التحقق**: نجاح التنفيذ إذا أخرج `<package> --version` رقم الإصدار.

## 6. متطلبات الكتابة

1. تُصاغ عناوين المشكلات بعبارة يبحث عنها المستخدم، لا بمصطلح داخلي.
2. تُحفظ رسائل الخطأ كما هي، تسهيلاً للمقارنة؛ وتُخفى المعلومات الحساسة (انظر [مواصفة الأمن والخصوصية](./security-and-privacy-specification.md)).
3. يُعطى الحل بأمر كامل، دون افتراض أن المستخدم أعدّ متغيرات البيئة.
4. يعالج البند الواحد مشكلة واحدة، ولا تُدمج فيه أسباب متعددة.
5. عند وجود عيب معروف، يُوضَّح نطاق التأثير وطريقة التحايل، دون التزام بموعد إصلاح.
6. تُربط المشكلات المتعلقة بالترحيل بدليل الترحيل (انظر [مواصفة دليل الترحيل](./migration-guide-specification.md)).

## 7. آلية الصيانة

1. عند تكرار السؤال عن المشكلة نفسها أكثر من ثلاث مرات، يجب إضافة بند جديد أو إعادة كتابة بند قائم.
2. تُراجَع جميع البنود بعد ترقية الإصدار الرقمي، ويُحذف المحتوى الذي لم يعد صالحاً.
3. يجوز لكل بند أن يذكر الإصدار الرقمي الأخير الذي جرى التحقق عليه، للحكم على صلاحيته.
4. يُحدَّث فهرس المشكلات بالتوازي مع زيادة البنود أو نقصانها.

## 8. الممارسات المحظورة

1. يُحظر تحويل وثيقة استكشاف الأعطال إلى عرض للميزات.
2. يُحظر الاكتفاء بإجابات لا قيمة تشخيصية لها مثل «أعد التشغيل وجرّب».
3. يُحظر حذف رسالة الخطأ وشرط التفعيل.
4. يُحظر الإبقاء على بنود أُصلحت أو لم تعد صالحة.
