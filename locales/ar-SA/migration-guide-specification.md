# مواصفة دليل الترحيل

> ما تحله هذه الوثيقة: تحدد بنية دليل الترحيل وعناصره المحتوائية وتوقيت نشره عند التغييرات الكاسرة، ليتمكن المستخدمون من الترقية بسلاسة من الإصدار القديم إلى الإصدار الجديد خطوة بخطوة.

## 1. شروط الإطلاق

يجب توفير دليل ترحيل عند تحقق أي مما يلي:

1. تحتوي رسالة الـ commit على `BREAKING CHANGE:` أو `feat!:` / `fix!:` (انظر [مواصفة رسائل الـ commit](./commit-message-specification.md)).
2. تغيّر اسم مفتاح إعداد أو قيمته الافتراضية أو أولويته.
3. تغيّرت بصمة API أو بنية الإرجاع أو رموز الأخطاء.
4. ارتفع الحد الأدنى لإصدار بيئة التشغيل، أو توقف دعم منصة ما.
5. تغيّرت بنية المجلدات أو تسمية الملفات بما يؤثر في مسارات الاستدعاء لدى المستخدمين.

## 2. موقع الملف وتسميته

1. تُكتب ملاحظات الترحيل الصغيرة ضمن مدخل الإصدار المقابل في `CHANGELOG.md`.
2. عند التغييرات الكبيرة التي تتطلب خطوات متعددة، أنشئ ملفاً مستقلاً في مجلد `docs/migration/` مسمّى بحسب الإصدار، مثل `docs/migration/v2.md`.
3. يُبنى فهرس لمسار الترحيل الكامل عبر الإصدارات الرئيسية في `docs/migration/README.md`.
4. يقتصر README على تنبيه الترحيل والرابط، دون تفصيل الخطوات (انظر [مصفوفة الوثائق](./document-matrix.md)).

## 3. بنية الوثيقة

يُرتّب دليل الترحيل على النحو التالي:

1. **العنوان والإصدار**: بيان الإصدار المصدر والإصدار الهدف، مثل «الترحيل من v1.x إلى v2.0».
2. **نظرة عامة على الأثر**: سرد فئات التغيير ونطاق تأثيره، وبيان من يجب عليه الترحيل.
3. **المتطلبات المسبقة**: التحضيرات اللازمة قبل الترحيل، مثل النسخ الاحتياطي وترقية إصدار البيئة.
4. **قائمة التغييرات**: سرد التغييرات الكاسرة بنداً بنداً، ويتضمن كل بند «السلوك القديم» و«السلوك الجديد» و«سبب التغيير».
5. **خطوات الترحيل**: سرد العمليات القابلة للتنفيذ بأرقام، مع الأوامر أو أمثلة الكود.
6. **طريقة التحقق**: كيف يُتأكد من النجاح بعد الترحيل، مع أمر فحص أو مخرجات متوقعة.
7. **طريقة التراجع**: كيف يُستعاد الإصدار القديم عند فشل الترحيل.
8. **الأسئلة الشائعة**: سرد الأسئلة المتكررة وأجوبتها.
9. **الحصول على المساعدة**: الإشارة إلى Issue أو منتدى النقاش أو موقع الوثائق.

### 3.1 قالب فارغ قابل للنسخ

يطابق القالب التالي البنود التسعة في القسم 3 بنداً ببند؛ انسخه واستبدل العناصر النائبة لتستخدمه:

````markdown

- {{检查项与确认命令}}

مقابلة العناصر النائبة:

| العنصر النائب | إلزامي | نقاط التعبئة |
| --- | --- | --- |
| `{{源版本}}` / `{{目标版本}}` | نعم | مطابق للوسم tag الهدف، بصيغة `vX.Y.Z` |
| `{{适用使用者范围}}` | نعم | بيان من يجب عليه الترحيل صراحةً، وتجنّب العبارات الغامضة |
| `{{变更类别}}` | نعم | فئة واحدة على الأقل من الإعداد أو API أو بيئة التشغيل أو المجلدات |
| `{{是否必须迁移}}` | نعم | بيان ما إذا كان التغيير يفرض على المستخدم تنفيذ الترحيل |
| `{{旧行为}}` / `{{新行为}}` | نعم | مقابلة بنداً ببند، ولا يُكتب جانب واحد فقط |
| `{{代码语言}}` | نعم | معرّف لغة كتلة الكود، مثل `yaml` و`json` و`js` |
| `{{前置准备}}` | نعم | النسخ الاحتياطي وفحص البيئة اللازمان قبل الترحيل |
| `{{迁移步骤}}` | نعم | كل خطوة قابلة للتنفيذ مباشرة، مع الأمر أو الكود |
| `{{人工处理步骤}}` | نعم | الخطوات غير القابلة للترحيل الآلي تُعلَّم صراحةً هنا |
| `{{检查命令}}` / `{{预期结果}}` | نعم | الأمر قابل للتشغيل باستقلال، والنتيجة قابلة للحكم |
| `{{回滚方式}}` | نعم | لا يجوز حذفه، انظر المحظورات في القسم 7 |

## 4. متطلبات المحتوى

### 4.1 مثال على مقابلة التغييرات

```markdown
### إعادة تسمية عنصر الإعداد `timeout` إلى `timeoutMs`

- السلوك القديم: استخدام `timeout: 5000` في ملف الإعداد، بوحدة الثانية.
- السلوك الجديد: استخدام `timeoutMs: 5000`، بوحدة المللي ثانية.
- سبب التغيير: توحيد وحدة الزمن، وتجنّب عدم الاتساق مع معاملات API.

قبل الترحيل:

```yaml
timeout: 5
```

بعد الترحيل:

```yaml
timeoutMs: 5000
```

### 4.2 متطلبات الكتابة

1. أعطِ لكل خطوة أمراً أو كوداً قابلاً للتنفيذ مباشرة، ولا تكتفِ بوصف «عدّل الإعداد».
2. اعرض مقابلة بين ما قبل الترحيل وما بعده لتسهيل المراجعة بنداً ببند.
3. علّم صراحةً الخطوات التي لا تقبل الترحيل الآلي وتتطلب معالجة يدوية.
4. يجب أن يكون نطاق التأثير محدداً، وتجنّب عبارات غامضة مثل «قد يؤثر في بعض المستخدمين».
5. يجب أن يكون أمر التحقق قابلاً للتشغيل باستقلال، مع المخرجات المتوقعة.

## 5. توقيت النشر والترابط

1. يُنشر دليل الترحيل بالتزامن مع الإصدار الذي يحوي التغييرات الكاسرة، ولا يجوز تأخيره.
2. يجب أن يرتبط مدخل `CHANGELOG.md` المقابل بدليل الترحيل (انظر [مواصفة سجل التغييرات](./changelog-specification.md)).
3. يجب أن تنبّه كتلة التغييرات الكاسرة في قالب طلب السحب إلى تعبئة طريقة الترحيل (انظر [مواصفة قوالب Issue وطلب السحب](./issue-and-pr-template-specification.md)).
4. تتبع أرقام الإصدارات الإصدارَ الدلالي، والتغييرات الكاسرة ترفع الإصدار الرئيسي (انظر [مواصفة إدارة الإصدارات](./version-management-specification.md)).
5. ينبّه README في موضع بارز مستخدمي الإصدارات القديمة إلى قراءة دليل الترحيل.

## 6. سياسة الإهمال والاحتفاظ

1. يبقى دليل الترحيل محفوظاً على المدى الطويل، ولا يجوز حذفه بعد نشر إصدار جديد.
2. يمكن وسم وثائق الإصدارات القديمة بأنها «غير مُصانة»، مع الاحتفاظ بمدخلها.
3. الترقية عبر عدة إصدارات رئيسية تتطلب مساراً متدرجاً، ولا يجوز اشتراط تجاوز كل التغييرات دفعة واحدة.

## 7. المحظورات

1. يُحظر الاكتفاء بكتابة «توجد تغييرات كاسرة، عدّل بنفسك».
2. يُحظر حذف طريقة التراجع.
3. يُحظر استخدام كود زائف غير قابل للتنفيذ في خطوات الترحيل.
4. يُحظر حذف أدلة الترحيل الخاصة بالإصدارات السابقة.
