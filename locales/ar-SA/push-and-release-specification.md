# مواصفة الدفع والإصدار

> المشكلة التي يحلها هذا الملف: تحدد قائمة الإجراءات قبل الدفع وأثناءه وبعده، وقواعد tag والإصدار، ومسار معالجة الحوادث، ودليل الدفع الكامل إلى GitHub ومصفوفة معالجة الإخفاقات.

## 1. قبل الدفع

1. `git status` نظيف، ولا توجد ملفات حساسة غير متتبَّعة.
2. `git log` خالٍ من WIP، ومن `fix bug`، ومن تسريب معلومات شخصية.
3. التأكد من فعالية `.gitignore`، وأن المخرجات والتبعيات غير متتبَّعة.
4. النجاح المحلي في build وtest وlint.
5. تنفيذ فحص شامل للمفاتيح السرية (بما يشمل الإيداعات التاريخية).
6. اكتمال مصفوفة الوثائق (انظر [مصفوفة الوثائق](./document-matrix.md)).

## 2. إجراءات الدفع

7. دفع الفرع الشخصي: `git push -u origin feat/xxx`.
8. الفرع الرئيسي يُعدَّل عبر طلب سحب فقط، ولا يُدفع إليه مباشرة.
9. يُحظر `push --force`؛ ولإعادة كتابة فرعك الخاص استخدم `--force-with-lease`.
10. يُحظر rebase/amend على فرع عام سبق دفعه.
11. الملف الواحد >50MB يُدفع عبر LFS أولاً.
12. قبل الدفع الأول تأكد من ظهور المستودع: الافتراضي private، ولا يُحوَّل إلى public إلا عند الحاجة الفعلية إلى الإتاحة العامة.

## 3. tag والإصدار

13. صيغة tag هي `vMAJOR.MINOR.PATCH`، ويجب أن يكون annotated: `git tag -a v1.0.0 -m "release: 1.0.0"`.
14. لا يُنشأ tag إلا بعد نجاح CI واكتمال Release Notes.
15. التغييرات الكاسرة يجب أن تحمل `feat!:` أو `BREAKING CHANGE:`، مع بيان طريقة الترحيل في CHANGELOG.

## 4. المرحلة 6 · ما بعد الدفع (Post-Push)

- إنشاء annotated tag؛
- كتابة Release Notes؛
- التحقق من صلاحية الشارات والروابط؛
- التأكد من نجاح CI؛
- التأكد من صحة معلومات منطقة About (description / topics / الروابط / social preview).

## 5. معالجة الحوادث

16. **مفتاح سري سبق دفعه**: تدوير فوري ← تنظيف بـ `git filter-repo` ← الدفع القسري إلى فرع محمي يتطلب مسار المسؤول ← إعلان.
17. **دفع ملف كبير بالخطأ**: الترحيل إلى LFS أو إعادة كتابة التاريخ، ولا يجوز الاكتفاء بحذف الملف.

## 6. مواصفة دليل الدفع إلى GitHub

يجب أن يتضمن الدليل الأجزاء السبعة التالية، مع تقديم الأوامر بصيغة كاملة قابلة للتنفيذ.

### 6.1 الأمان المسبق

1. يجب قبل الدفع أخذ نسخة احتياطية كاملة للمستودع المحلي والمستودع البعيد، ويُنصح باستخدام `git clone --mirror` لإنتاج نسخة معكوسة احتياطية.
2. التأكد من عدم وجود متعاونين في المستودع البعيد، أو من إبلاغهم بإيقاف الدفع.
3. التأكد من عدم تفعيل حماية الدفع القسري على الفرع الهدف.

### 6.2 الترتيب المحلي

```bash
git status
git diff --name-status HEAD
git ls-files
```

تُراجع المخرجات الثلاث للتحقق من تطابق التغييرات المراد إيداعها مع المجلد المحلي، وخلوّه من الملفات المؤقتة ومخرجات البناء وبقايا الوثائق القديمة. ويجب أن يغطي `.gitignore` مخرجات البناء وملفات الإعداد المحلية.

### 6.3 التحقق من التطابق

```bash
git fetch origin
git diff --name-status HEAD origin/{{分支名}}
```

يسرد هذا الأمر فروق الملفات بين البعيد والمحلي. والملفات الموجودة على البعيد والمحذوفة محلياً يجب تنفيذ `git rm` لها محلياً ثم إيداعها، ليدخل الحذف إلى تاريخ الإصدارات.

### 6.4 الإيداع والدفع

```bash
git add -A
git commit -m "docs: إعادة بناء وثائق المشروع (README، README_EN، NOTICE)"
git push --force-with-lease origin {{分支名}}
```

يُستخدم `--force-with-lease` بدلاً من `--force`، فيُرفض الدفع عند وجود إيداعات جديدة لغيره على البعيد، ما يمنع الكتابة فوق عمل الآخرين. حذف المستودع البعيد ثم إعادة إنشائه عملية عالية الخطورة، ولا تُستخدم إلا في مستودع شخصي وبعد إتمام النسخة المعكوسة الاحتياطية، ويجب في الدليل وسم خطر فقدان البيانات صراحةً.

### 6.5 التحقق بعد الدفع

```bash
git ls-remote --heads origin
gh repo view --web
```

يُتحقق في الواجهة الويب بندًا بندًا من قائمة الملفات، وعرض README، وروابط تبديل اللغة، وصلاحية رابط NOTICE.

### 6.6 مصفوفة معالجة الإخفاقات

| نوع الخطأ | العَرَض النموذجي | المعالجة | تحذير المخاطر |
| --- | --- | --- | --- |
| فشل المصادقة | `Authentication failed`، `Permission denied (publickey)` | التحويل من HTTPS إلى SSH وإعداد المفتاح، أو استخدام `gh auth login` ثم الدفع | لا يوجد |
| انقطاع الشبكة | `Failed to connect`، `RPC failed` | تغيير الشبكة، وإعداد وكيل، وتنفيذ `git config --global http.postBuffer 524288000` | لا يوجد |
| تجاوز حجم الملف | `remote: error: File exceeds 100 MB` | إزالة الملف الكبير من تاريخ الإيداع أو تفعيل Git LFS | بعد إعادة كتابة التاريخ يجب إبلاغ المتعاونين بإعادة النسخ |
| تعارض حالة الأحرف | مدخلات مكررة بسبب عدم تطابق حالة أحرف أسماء الملفات | التصحيح بـ `git mv` ثم الإيداع | لا يوجد |
| تعارض التاريخ | `non-fast-forward`، `fetch first` | يُفضَّل `git pull --rebase`؛ وعند الحاجة الفعلية إلى الكتابة فوق استخدم `--force-with-lease` | الكتابة فوق إيداعات الآخرين لا يمكن التراجع عنها |
| حماية الفرع | `protected branch hook declined` | الدمج عبر مسار طلب السحب، أو تعديل القواعد مؤقتاً من المسؤول | تعديل القواعد يجب تسجيله |
| تلف المستودع | `fatal: not a git repository`، فقدان الكائنات | إعادة النسخ ثم نقل تغييرات مساحة العمل | يجب نسخ مساحة العمل احتياطياً أولاً |

### 6.7 التراجع

إذا ظهرت مشكلة بعد اكتمال الدفع، يُستخدم `git revert` لإنتاج إيداع معاكس؛ ولا يجوز الدفع القسري مرة أخرى للكتابة فوق تاريخ سبق إتاحته.

- مواصفة رسائل الإيداع تندرج تحت البُعد D7، انظر [مصفوفة أبعاد المراجعة](./review-dimension-matrix.md)
- مسؤولية وثيقة الإصدار `docs/release.md` في [مصفوفة الوثائق](./document-matrix.md)
