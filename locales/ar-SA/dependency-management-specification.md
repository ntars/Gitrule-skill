# مواصفة إدارة التبعيات

> المشكلة التي يحلها هذا الملف: تحديد قوالب وحقول طلب إدخال التبعيات وقائمة التبعيات والتثبيت والتحديث، بما يضمن إمكانية إعادة إنتاج البناء وقابلية تتبع التبعيات والتوافق مع الرخص.

## 1. نصوص المواصفة

1. يجب عند إدخال تبعية جديدة بيان الغرض والرخصة وحالة الصيانة (انظر [مواصفة الامتثال مفتوح المصدر](./open-source-compliance-specification.md)).
2. تُفضَّل التبعيات المتوافقة في الرخصة والنشطة مجتمعيًا؛ ويُحظر إدخال تبعيات مجهولة المصدر أو مجهولة الرخصة.
3. يجب كتابة إصدار التبعية في lockfile وإيداعه في المستودع، بما يضمن إعادة إنتاج البناء في بيئة نظيفة (يقابل القاعدة المطلقة H9 والبُعد D5).
4. يجب تثبيت رقم الإصدار على الإصدار المُحلَّل الفعلي، ولا يُستخدم تعبير نطاق كتسليم نهائي.
5. يجب أن تُساعد أدوات آلية في تحديث التبعيات، ويجب اجتياز CI بعد التحديث؛ وتُعالَج الثغرات في حينها أو تُسجَّل لها إجراءات تخفيف.
6. يجب أن تكون قائمة التبعيات متوافقة مع NOTICE (انظر [مواصفة NOTICE](./notice-specification.md)).

```markdown

- مقدم الطلب: {{姓名}}

- هل يمكن بناؤها داخليًا: {{是 / 否；是则说明为何仍引入}}
- تقييم البدائل: {{已评估的替代包及未选原因}}

| الحقل | القيمة |
| --- | --- |
| اسم الحزمة | {{包名}} |
| إصدار الإدخال | {{精确版本号}} |
| الرخصة | {{SPDX ID}} |
| توافق الرخصة | {{兼容 / 不兼容 / 需法务确认}} |
| تاريخ آخر إصدار | {{YYYY-MM-DD}} |
| حالة الصيانة | {{活跃 / 低频 / 停滞}} |
| التنزيلات الأسبوعية | {{数值}} |
| عدد التبعيات المتعدية | {{数值}} |
| الثغرات المعروفة | {{无 / CVE 编号与处置}} |
| أثر حجم الحزمة | {{增量 KB}} |

- القرار: {{批准 / 拒绝 / 有条件批准}}
- المعتمِد: {{姓名}}
```


## 4. تعريف الحقول

| الحقل | إلزامي | النوع | نقاط التعبئة | مثال |
| --- | --- | --- | --- | --- |
| رقم الطلب | نعم | `DEP-NNN` | متسلسل، لا يُعاد استخدامه | `DEP-007` |
| الغرض | نعم | نص | يوضح المشكلة المحلولة، ويُحظر «تسهيل التطوير» | `تحليل إعدادات TOML` |
| تقييم البدائل | نعم | نص | تقييم 1 بديل على الأقل | `جُرِّب toml-js، ولم يُختر لتوقف صيانته` |
| إصدار الإدخال | نعم | إصدار دقيق | لا يجوز استخدام `^` أو `~` | `1.2.3` |
| الإصدار المثبَّت | نعم | إصدار دقيق | مطابق لـ lockfile | `1.2.3` |
| الرخصة | نعم | SPDX ID | مطابقة لصياغة [مواصفة LICENSE](./license-specification.md) | `MIT` |
| حالة الصيانة | نعم | تعداد | نشط / منخفض التكرار / متوقف، مع سند التقدير | `نشط (توجد إيداعات خلال 30 يومًا الأخيرة)` |
| عدد التبعيات المتعدية | نعم | قيمة عددية | عند الكثرة يجب بيان أثر الحجم والمخاطر | `12` |
| الثغرات المعروفة | نعم | نص | يُكتب «لا يوجد» عند عدمها، ولا يُترك فارغًا | `لا يوجد` |
| تاريخ إعادة الفحص | نعم | تاريخ | يجب تعيين تاريخ إعادة فحص للبنود الاستثنائية | `2026-12-31` |

## 5. تعليمات التعبئة

1. **تقييم البناء الداخلي**: تُطرح أولًا مسألة «هل يمكن تحقيقه بالمكتبة القياسية أو بقدرات قائمة»؛ ومن يختار الإدخال رغم إمكان البناء الداخلي يجب أن يبيّن السبب.
2. **الرخصة**: يجب أن تكون SPDX ID؛ و`UNLICENSED` والرخص المخصصة تُحوَّل إلى «تحتاج تأكيدًا قانونيًا»، ولا تُدخَل مباشرة.
3. **حالة الصيانة**: يُستند إلى تاريخ آخر إصدار واستجابة issue، ويُحظر الاكتفاء بأن «يبدو أن أحدًا يصونه».
4. **تثبيت الإصدار**: عند التسليم يجب أن يكون الإصدار في lockfile دقيقًا ومُحلَّلًا؛ ويجوز أن يحتفظ `package.json` بتعبير نطاق، لكن lockfile يجب أن يكون دقيقًا.
5. **إيقاع التحديث**: تُفتح التحديثات الآلية، ويُؤكَّد الدمج بشريًا؛ ويجب أن يجتاز كل تحديث CI وأن تُراجَع تغيرات الرخصة.
6. **معالجة الثغرات**: تُفضَّل الترقية إلى إصدار آمن؛ وعند تعذر الترقية تُكتب إجراءات التخفيف وتاريخ إعادة الفحص، ويُدرَج البند في سجل مخاطر [مواصفة الاستجابة للحوادث](./incident-response-specification.md).
7. **مزامنة القائمة**: بعد إدخال تبعية أو إزالتها تُحدَّث قائمة التبعيات وNOTICE، ويجب أن تتوافق الثلاثة (lockfile والقائمة وNOTICE).

أخطاء شائعة:

| الصياغة الخاطئة | المشكلة | طريقة التصحيح |
| --- | --- | --- |
| «استخدام مكتبة لمعالجة الإعدادات» | لا اسم حزمة ولا غرض محدد | تُكتب اسم الحزمة والإصدار والمشكلة المحلولة |
| كتابة الرخصة «مفتوح المصدر» | لا يمكن الحكم على التوافق | تُكتب SPDX ID |
| عدم إيداع lockfile | البناء غير قابل لإعادة الإنتاج | يُودَع lockfile (يقابل H9) |
| ترك عدد التبعيات المتعدية فارغًا | المخاطر غير مرئية | تُكتب قيمة عددية محددة |
| عدم كتابة إجراء تخفيف للثغرة | المخاطر بلا تتبع | تُضاف الإجراءات وتاريخ إعادة الفحص |

## 6. مثال كامل

```markdown
## طلب إدخال تبعية: remark

- رقم الطلب: DEP-001
- مقدم الطلب: وانغ وو
- الغرض: طبقة تحليل Markdown لدعم حاجة محرك القواعد إلى تحديد مواضع العقد (REQ-001، REQ-004).
- هل يمكن بناؤها داخليًا: لا؛ فالبناء الداخلي لا يغطي حالات GFM الحدّية ضمن سقف الموارد البشرية.
- تقييم البدائل: جُرِّب marked، ولم يُختر لقصوره في تحديد مواضع العقد الصينية.

| الحقل | القيمة |
| --- | --- |
| اسم الحزمة | remark |
| إصدار الإدخال | 15.0.1 |
| الرخصة | MIT |
| توافق الرخصة | متوافق |
| تاريخ آخر إصدار | 2026-11-02 |
| حالة الصيانة | نشط (توجد إيداعات خلال 30 يومًا الأخيرة) |
| التنزيلات الأسبوعية | 4,200,000 |
| عدد التبعيات المتعدية | 18 |
| الثغرات المعروفة | لا يوجد |
| أثر حجم الحزمة | +42 KB |

- القرار: موافَق عليه، ويُنفَّذ مع ADR-0002
- المعتمِد: لي سي
```
