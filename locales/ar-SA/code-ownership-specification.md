# مواصفة ملكية الشيفرة

> المشكلة التي يحلها هذا الملف: يحدد صياغة ملف `.github/CODEOWNERS` وقواعد توزيع الملكية وتوجيه المراجعة، بحيث يُسند كل تغيير تلقائياً إلى مراجع مسؤول.

## 1. مبادئ التصميم

1. **تقابل صريح بين المسار والشخص**: تحدد كل قاعدة من المسؤول عن مسار معيّن، تفادياً لغياب المراجعة أو تكرارها.
2. **أقل عدد لازم من المالكين**: يُضبط عدد مالكي المسار الواحد بين 1 و3، لأن الزيادة تفرّق المسؤولية.
3. **التغطية الافتراضية**: يُعيَّن مالك افتراضي شامل يغطي المسارات غير المطابقة لقاعدة صريحة.
4. **المزامنة مع بنية الفريق**: يُحدَّث الملف عند تغيّر الأعضاء، تفادياً لعرقلة المراجعة بحسابات معطّلة.

## 2. موضع الملف وصياغته

### 2.1 المسار

يجوز وضع ملف `CODEOWNERS` في أي من المواضع التالية، ويُعتمد الأول المتحقق حسب الأولوية:

1. `CODEOWNERS` في جذر المستودع؛
2. `docs/CODEOWNERS`؛
3. `.github/CODEOWNERS` (موصى به).

### 2.2 قواعد الصياغة

```text
# التعليق يبدأ بـ #
<نمط المسار>  <المالك>  [<المالك>...]
```

- سطر واحد لكل قاعدة، ويتبع نمط المسار مالك واحد أو أكثر.
- صيغة المالك `@اسم-المستخدم` أو `@المنظمة/الفريق`.
- عند استخدام بريد إلكتروني كمالك، يجب أن يكون مرتبطاً بحساب GitHub.
- المسار حساس لحالة الأحرف، ويدعم محارف البدل `*` و`**`.

### 2.3 مثال

```text
# المالك الافتراضي
*                       @org/maintainers

# التوزيع حسب المجلد
/src/core/              @org/core-team
/src/api/               @org/api-team @alice
/docs/                  @org/docs-team

# التوزيع حسب نوع الملف
*.md                    @org/docs-team
/.github/workflows/      @org/devops-team
```

## 3. قواعد المطابقة

1. تُطبَّق آخر قاعدة مطابقة فقط، دون تجميع؛ لذلك تُكتب القواعد العامة أولاً والخاصة بعدها.
2. تطابق قاعدة المجلد ذلك المجلد ومجلداته الفرعية، إلا إذا بدأت بـ`/` لتقييد مسار الجذر.
3. ترتيب القواعد يحدد الأولوية، ويجب أن يرتّب من الأوسع إلى الأضيق.
4. يتحمل المالك الافتراضي مسؤولية مراجعة المسارات غير المطابقة لأي قاعدة.

## 4. استراتيجية توزيع الملكية

| البُعد | أساس التوزيع |
| --- | --- |
| المجلد | التوزيع حسب حدود الوحدة أو النظام الفرعي |
| نوع الملف | يجوز توزيع الوثائق والإعداد والاختبارات بحسب النوع توزيعاً موحداً |
| المسارات الحرجة | يحتكر المشرفون الأساسيون ملفات الأمان والإصدار وإعداد CI |
| الأعضاء الجدد | يشاركون أولاً كمراجعين غير إلزاميين، ثم يصبحون مالكين رسميين بعد التمكّن |

## 5. الترابط مع مسار المراجعة

1. عند إنشاء طلب سحب، يطلب GitHub تلقائياً مراجعة مالك المسار المطابق.
2. تُضبط متطلبات المراجعة الإلزامية عبر قواعد حماية الفروع، انظر [مواصفة سير عمل Git والفروع](./git-workflow-and-branching-specification.md).
3. يجب أن يستجيب المالك خلال المدة المتفق عليها، وعند تجاوزها يتحمل المالك الافتراضي المسؤولية.
4. يجب أن يُحدَّث الملف عند تغيّر المالكين، تفادياً لعرقلة المسار بحسابات معطّلة (انظر [مواصفة مراجعة الشيفرة](./code-review-specification.md)).

## 6. متطلبات الصيانة

1. يُراجع الملف مرة بعد كل تغيير في الهيكل التنظيمي أو مسؤوليات الفرق.
2. عند نقل المستودع أو مغادرة عضو، يجب إزالة المالك المقابل فوراً.
3. يجب أن يمر تغيير الملف بمراجعة مالك حالي واحد على الأقل، منعاً لانتشار الصلاحيات ذاتياً.
4. لا يجوز توجيه الملكية إلى حسابات غير نشطة أو حسابات روبوتية (عدا المخصصة للأتمتة).

## 7. الممارسات المحظورة

1. يُمنع استخدام قواعد بدل فضفاضة تجعل الجميع مالكين.
2. يُمنع إسناد المسارات الحساسة (الإصدار، وإعداد المفاتيح) إلى أعضاء لا يملكون قدرة المراجعة.
3. يُمنع كتابة بيانات تواصل شخصية في الملف.
4. يُمنع الإبقاء طويلاً على ملكية أعضاء غادروا المشروع.
