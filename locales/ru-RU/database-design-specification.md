# Спецификация проектирования баз данных

> Какую задачу решает этот файл: определяет правила проектирования структуры таблиц, полей, индексов и миграций базы данных, обеспечивая согласованность, эволюционируемость и прослеживаемость данных.

## 1. Соглашения об именовании

1. Имена таблиц и полей используют единый стиль именования и однозначный смысл.
2. Именование первичных ключей, внешних ключей и индексов подчиняется единым правилам префиксов.
3. Для зарезервированных слов и сокращений должны быть явные соглашения во избежание неоднозначности.

## 2. Проектирование полей

1. Для каждого поля должны быть явно указаны тип, допустимость NULL, значение по умолчанию и смысл.
2. Временные поля используют единый часовой пояс и точность.
3. Поля, чувствительные к точности, например суммы, используют тип с фиксированной точкой, а не плавающую точку.
4. Поля состояния используют явное перечисление с указанием значения каждого варианта.

## 3. Индексы и ограничения

1. Индексы проектируются исходя из сценариев запросов, избыточное индексирование не допускается.
2. Целостность обеспечивается ограничениями, а не проверками на уровне приложения.
3. Правила внешних ключей и каскадных операций должны быть объявлены явно.

## 4. Управление миграциями

1. Изменения структуры управляются скриптами миграции; скрипты версионируются и коммитятся в репозиторий.
2. Миграция должна быть откатываемой; для несовместимых изменений должен быть предусмотрен план миграции данных.
3. Скрипт миграции применяется в промышленной среде после проверки в тестовой среде (см. [спецификацию развёртывания и отката](./deployment-and-rollback-specification.md)).

## 5. Безопасность

1. Конфиденциальные данные должны храниться в зашифрованном или обезличенном виде (см. [спецификацию безопасности и приватности](./security-and-privacy-specification.md)).
2. Строка подключения к базе данных не должна коммититься в репозиторий (соответствует абсолютному правилу H3).
