# Спецификация руководства по миграции

> Какую задачу решает этот файл: определяет структуру, содержательные элементы и сроки выпуска руководства по миграции при обратно несовместимых изменениях, чтобы пользователь мог по шагам плавно перейти со старой версии на новую.

## 1. Условия срабатывания

Руководство по миграции предоставляется при возникновении любого из следующих условий:

1. Сообщение коммита содержит `BREAKING CHANGE:` или `feat!:` / `fix!:` (см. [спецификацию сообщений коммитов](./commit-message-specification.md)).
2. Изменяются имена ключей конфигурации, значения по умолчанию или приоритеты.
3. Изменяются сигнатуры API, структура возвращаемых данных или коды ошибок.
4. Повышается минимальная версия среды выполнения либо прекращается поддержка платформы.
5. Изменяются структура каталогов или именование файлов, что влияет на пути, используемые пользователями.

## 2. Расположение и именование файлов

1. Описание миграции при небольших изменениях вносится в запись соответствующей версии в `CHANGELOG.md`.
2. При крупных изменениях, требующих нескольких шагов, создаётся отдельный файл в каталоге `docs/migration/` с именем по версии, например `docs/migration/v2.md`.
3. Полный путь миграции между мажорными версиями индексируется в `docs/migration/README.md`.
4. README содержит только подсказку о миграции и ссылку, шаги не раскрываются (см. [матрицу документации](./document-matrix.md)).

## 3. Структура документа

Руководство по миграции организуется в следующем порядке:

1. **Заголовок и версии**: указываются исходная и целевая версии, например «переход с v1.x на v2.0».
2. **Обзор влияния**: перечисляются категории изменений и область влияния, указывается, какие пользователи обязаны выполнить миграцию.
3. **Предварительные условия**: подготовка, которую необходимо выполнить до миграции, например резервное копирование, обновление версии окружения.
4. **Перечень изменений**: обратно несовместимые изменения перечисляются по пунктам, каждый пункт содержит «прежнее поведение», «новое поведение», «причину изменения».
5. **Шаги миграции**: пронумерованный перечень выполнимых действий с командами или примерами кода.
6. **Способ проверки**: как убедиться в успехе после миграции, приводятся команды проверки или ожидаемый вывод.
7. **Способ отката**: как вернуться к старой версии при неудачной миграции.
8. **Частые вопросы**: перечень часто встречающихся вопросов и ответов.
9. **Получение помощи**: ссылки на issue, обсуждение или сайт документации.

## 4. Требования к содержанию

### 4.1 Пример сопоставления изменений

```markdown
### Элемент конфигурации `timeout` переименован в `timeoutMs`

- Прежнее поведение: в файле конфигурации используется `timeout: 5000`, единица измерения — секунды.
- Новое поведение: используется `timeoutMs: 5000`, единица измерения — миллисекунды.
- Причина изменения: унификация единиц времени, устранение расхождения с параметрами API.

До миграции:

```yaml
timeout: 5
```

После миграции:

```yaml
timeoutMs: 5000
```

### 4.2 Требования к изложению

1. Для каждого шага приводится напрямую выполнимая команда или код; описание вроде «изменить конфигурацию» недопустимо.
2. Приводится сопоставление до и после миграции для пошаговой сверки.
3. Явно отмечаются шаги, не подлежащие автоматической миграции и требующие ручной обработки.
4. Область влияния должна быть конкретной; расплывчатые формулировки вроде «может затронуть часть пользователей» недопустимы.
5. Команда проверки должна выполняться независимо и содержать ожидаемый вывод.

## 5. Сроки выпуска и связи

1. Руководство по миграции должно выпускаться одновременно с версией, содержащей обратно несовместимые изменения; задержка недопустима.
2. Соответствующая запись `CHANGELOG.md` должна ссылаться на руководство по миграции (см. [спецификацию журнала изменений](./changelog-specification.md)).
3. Блок обратно несовместимых изменений в шаблоне PR должен предлагать указать способ миграции (см. [спецификацию шаблонов Issue и PR](./issue-and-pr-template-specification.md)).
4. Номер версии следует семантическому версионированию, при обратно несовместимом изменении должна повышаться мажорная версия (см. [спецификацию управления версиями](./version-management-specification.md)).
5. README на видном месте предлагает пользователям старых версий ознакомиться с руководством по миграции.

## 6. Политика устаревания и сохранения

1. Руководство по миграции должно сохраняться постоянно; удаление после выпуска новой версии недопустимо.
2. Документацию старых версий допускается помечать как «не поддерживается», но точка входа должна сохраняться.
3. При обновлении через несколько мажорных версий должен предоставляться пошаговый путь; требовать перехода через все изменения за один раз запрещено.

## 7. Запрещённые практики

1. Запрещено ограничиваться формулировкой «есть обратно несовместимые изменения, скорректируйте самостоятельно».
2. Запрещено опускать способ отката.
3. Запрещено использовать в шагах миграции невыполнимый псевдокод.
4. Запрещено удалять руководства по миграции исторических версий.
