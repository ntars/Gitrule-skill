# Спецификация LICENSE

> Какую задачу решает этот файл: определяет SPDX-маркировку лицензии проекта, требования к полному тексту LICENSE, расположение строки авторских прав, механизм распознавания GitHub, размещение файлов при многоуровневом лицензировании и порядок подтверждения, а также правило о недопустимости записи лицензии без подтверждения.

## 1. Основные правила

1. Лицензия проекта должна быть явно указана в README с помощью идентификатора SPDX, и должен быть предоставлен соответствующий файл LICENSE.
2. Файл LICENSE должен содержать официальный полный текст этой лицензии на английском языке; изменять или удалять условия запрещено. Переформулирование, перестановка абзацев или переоформление в Markdown приводят к сбою автоматического распознавания.
3. Строка авторских прав размещается в начале файла или в разделе 19 README, формат см. в [спецификации разделов README](./readme-sections-specification.md).

## 2. Механизм распознавания GitHub

GitHub определяет лицензию репозитория с помощью открытого инструмента licensee. Результат влияет на значок на странице репозитория, поле `license` в API и на то, будет ли репозиторий найден при поиске по ключевому слову `license`. Правила таковы:

1. Проверяются только два места: корень проекта и каталог `LICENSES/` верхнего уровня. Одноимённые файлы внутри `locales/`, `docs/` и других подкаталогов не учитываются.
2. В корне файлы оцениваются по имени, побеждает наибольшая оценка: `LICENSE` — 1.00, `LICENSE.md` — 0.95, `COPYING` — 0.90, формы с суффиксом вроде `LICENSE-MIT` — 0.70.
3. В каталоге `LICENSES/` верхнего уровня имя файла в формате идентификатора SPDX с расширением `.txt`, `.md`, `.markdown` или `.html` даёт 1.00, всё остальное — 0.00.
4. Содержимое должно точно соответствовать официальному полному тексту лицензии. Файл, содержащий лишь указание «этот проект использует лицензию X», не будет распознан, а полученный им результат окажется нестандартным значением.
5. Если распознано несколько различных лицензий, результат на уровне проекта может не возвращать конкретную лицензию, и страница репозитория показывает `View license` или `Other`.
6. Утверждения на естественном языке в README не учитываются. Запись «этот проект распространяется по лицензии MIT» не приводит к распознаванию как MIT.

Следовательно: **утверждение в README и файл LICENSE — два независимых механизма, и нужны оба.** Кроме того, если в корне находится несколько файлов лицензий, то, какой из них будет в итоге указан, зависит одновременно от оценки имени и совпадения содержимого и непредсказуемо; в измерениях репозитории с двойной лицензией сообщали только об одной из двух.

## 3. Размещение файлов при многоуровневом лицензировании

Многоуровневое лицензирование означает, что разные части репозитория подчиняются разным лицензиям, например код — MIT, документация — CC BY 4.0. Размещение определяется в следующем порядке:

| Вариант | Что размещается в корне | Результат распознавания | Условия применения |
| --- | --- | --- | --- |
| Один уровень (по умолчанию) | Один `LICENSE` | Стабильно распознаётся как эта лицензия | Все уровни используют одну лицензию, либо различие не меняет обязанностей пользователей |
| Уровни с пояснением | `LICENSE` содержит основную лицензию, дополнительно `LICENSING.md` | Стабильно распознаётся лицензия из корневого `LICENSE` | Разделение нужно, а значок должен оставаться однозначным |
| Уровни с REUSE | `LICENSES/` верхнего уровня содержит полные тексты каждой лицензии | Может выродиться в нестандартное значение | Только если нижестоящая сторона прямо требует соответствия REUSE |

Компромиссы:

1. Не размещайте в корне несколько файлов лицензий. В измерениях каждый репозиторий с двойной лицензией сообщал только об одной из двух; вторая оставалась невидимой на странице репозитория и в API, что равно публичному объявлению лишь одной лицензии.
2. Размещение REUSE конфликтует с однозначностью значка: несколько лицензий в `LICENSES/` читаются как несколько лицензий, что даёт зелёный `reuse lint` ценой неоднозначного результата распознавания. Одновременно полностью удовлетворить оба требования невозможно; проект должен выбрать.
3. При варианте «уровни с пояснением» имя файла `LICENSING.md` не соответствует ни шаблону `LICENSE`, ни шаблону `COPYING`, поэтому не воспринимается как файл лицензии и не влияет на распознавание корневого `LICENSE`.
4. При любом выбранном размещении раздел 19 README должен указывать выражение SPDX (например `MIT AND CC-BY-4.0`) и область действия каждого уровня. Это единственное место, где сведения сохраняются на уровне человеческого чтения.

## 4. Решение о разделении и порядок подтверждения

Многоуровневое лицензирование имеет юридическое значение. Перед написанием или оптимизацией подтверждайте шаг за шагом; ничего не выдумывайте.

1. Не вводите разделение по собственной инициативе. Если пользователь явно не просил об этом, рассматривайте проект как одноуровневый и указывайте в отчёте: «Если разделение необходимо, возможные варианты и их различия таковы».
2. Любое предложение о разделении должно раскрывать основания: что именно покрывает каждый уровень, лицензии-кандидаты и различие их обязанностей, влияние на нижестоящих пользователей и как изменится результат распознавания.
3. Подтверждайте не менее двух раз до записи: сначала комбинацию (какая лицензия для какого уровня), затем размещение файлов (какая лицензия в корневом файле, создавать ли `LICENSES/`).
4. Подтвердите ещё раз перед пушем. После создания файлов явно сообщите: «Файлы созданы; проверьте и зафиксируйте их самостоятельно» и никогда не выполняйте коммит или пуш вместо пользователя.
5. Неподтверждённые варианты попадают только в отчёт или временный файл; они не должны записываться как `LICENSE`, `LICENSES/` или `LICENSING.md`.
6. Если какую-то часть невозможно отнести ни к одному уровню, помечайте её «【требует подтверждения: отнесение к уровню】» и перечисляйте спорные файлы; не относите её по умолчанию.

## 5. Требования к отказу от ответственности

Тексты лицензий имеют юридическую силу. Шаблоны и инструменты предоставляют только правила определения и размещение файлов и не являются юридической консультацией.

1. Раздел 19 README или файл `LICENSING.md` должен содержать отказ от ответственности с указанием, что выбор лицензии подтверждает сам держатель проекта.
2. Отказ от ответственности должен совпадать с отказом в NOTICE; он не должен присутствовать в одном месте и отсутствовать в другом.
3. Не заявляйте, что «проверка соответствия завершена». Указывайте лишь, что «размещение файлов и маркировка SPDX проверены по правилам на полноту».
4. Юридическая сила многоуровневого лицензирования определяется полным текстом каждой лицензии. Описательный текст внутри репозитория является лишь указателем и не изменяет условия.
