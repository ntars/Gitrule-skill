# Спецификация пуша и публикации

> Какую задачу решает этот файл: определяет перечень действий до, во время и после пуша, правила тегов и релизов, процедуру обработки инцидентов, а также полное руководство по пушу в GitHub и матрицу действий при сбоях.

## 1. Перед пушем

1. `git status` чист, нет неотслеживаемых конфиденциальных файлов.
2. В `git log` нет WIP, нет `fix bug`, нет утечки персональных данных.
3. Подтверждается, что `.gitignore` действует, артефакты и зависимости не отслеживаются.
4. Локально пройдены build, test и lint.
5. Выполняется полное сканирование ключей (включая историю коммитов).
6. Матрица документации укомплектована (см. [матрицу документации](./document-matrix.md)).

## 2. Действия пуша

7. Пуш личной ветки: `git push -u origin feat/xxx`.
8. В основную линию изменения попадают только через PR, прямой push не выполняется.
9. `push --force` запрещён; для перезаписи собственной ветки используется `--force-with-lease`.
10. Rebase/amend для уже отправленных пушем публичных веток запрещены.
11. Файл размером >50MB сначала переводится в LFS, затем отправляется пушем.
12. Перед первым пушем подтверждается видимость репозитория: по умолчанию private, на public переключается только при действительной необходимости публикации.

## 3. Тег и релиз

13. Формат тега `vMAJOR.MINOR.PATCH`, тег должен быть annotated: `git tag -a v1.0.0 -m "release: 1.0.0"`.
14. Тег ставится только после зелёного CI и готовности Release Notes.
15. Несовместимое изменение требует `feat!:` или `BREAKING CHANGE:`, а в CHANGELOG указывается способ миграции.

## 4. Phase 6 · После пуша (Post-Push)

- поставить annotated tag;
- написать Release Notes;
- проверить работоспособность бейджей и ссылок;
- подтвердить зелёный CI;
- подтвердить корректность сведений в блоке About (description / topics / ссылки / social preview).

## 5. Обработка инцидентов

16. **Ключ уже отправлен пушем**: немедленная ротация → очистка через `git filter-repo` → принудительный пуш защищённой ветки требует процедуры администратора → оповещение.
17. **Ошибочный пуш большого файла**: миграция в LFS или перезапись истории; удалять только файл недопустимо.

## 6. Спецификация руководства по пушу в GitHub

Руководство должно содержать следующие семь частей; команды приводятся в полном исполнимом виде.

### 6.1 Предварительная безопасность

1. Перед пушем необходимо полностью резервировать локальный и удалённый репозитории; рекомендуется создать зеркальную резервную копию через `git clone --mirror`.
2. Подтверждается отсутствие соавторов в удалённом репозитории либо их уведомление о приостановке пуша.
3. Подтверждается, что в целевой ветке не включена защита от принудительного пуша.

### 6.2 Локальная подготовка

```bash
git status
git diff --name-status HEAD
git ls-files
```

Сверяются три вывода: изменения, готовые к коммиту, должны совпадать с локальным каталогом, без временных файлов, артефактов сборки и остатков устаревшей документации. `.gitignore` должен покрывать артефакты сборки и локальные файлы конфигурации.

### 6.3 Сверка согласованности

```bash
git fetch origin
git diff --name-status HEAD origin/{{分支名}}
```

Команда выводит различия файлов между удалённым и локальным репозиторием. Файлы, существующие на удалённом репозитории и удалённые локально, требуют локального выполнения `git rm` и коммита, чтобы удаление попало в историю версий.

### 6.4 Коммит и пуш

```bash
git add -A
git commit -m "docs: 重建项目文档（README、README_EN、NOTICE）"
git push --force-with-lease origin {{分支名}}
```

Используется `--force-with-lease` вместо `--force`: при наличии на удалённом репозитории чужих новых коммитов пуш отклоняется, что предотвращает перезапись чужой работы. Удаление удалённого репозитория с последующим воссозданием относится к операциям высокого риска и допускается только для личного репозитория при наличии зеркальной резервной копии; в руководстве риск потери данных должен быть явно отмечен.

### 6.5 Проверка после пуша

```bash
git ls-remote --heads origin
gh repo view --web
```

В веб-интерфейсе постатейно подтверждаются список файлов, отображение README, работоспособность ссылок переключения языка и ссылки NOTICE.

### 6.6 Матрица действий при сбоях

| Тип ошибки | Типичное проявление | Способ устранения | Предупреждение о риске |
| --- | --- | --- | --- |
| Сбой аутентификации | `Authentication failed`, `Permission denied (publickey)` | Перейти с HTTPS на SSH и настроить ключ либо выполнить пуш после `gh auth login` | Нет |
| Обрыв сети | `Failed to connect`, `RPC failed` | Сменить сеть, настроить прокси, выполнить `git config --global http.postBuffer 524288000` | Нет |
| Превышение размера файла | `remote: error: File exceeds 100 MB` | Удалить большой файл из истории коммитов или включить Git LFS | После перезаписи истории необходимо уведомить соавторов о повторном клонировании |
| Конфликт регистра | Несовпадение регистра имён файлов приводит к дублирующимся записям | Исправить через `git mv` и закоммитить | Нет |
| Конфликт истории | `non-fast-forward`, `fetch first` | Предпочтительно `git pull --rebase`; при действительной необходимости перезаписи — `--force-with-lease` | Перезапись чужих коммитов невосстановима |
| Защита ветки | `protected branch hook declined` | Выполнить слияние через процесс PR либо временно скорректировать правила администратором | Корректировка правил должна быть задокументирована |
| Повреждение репозитория | `fatal: not a git repository`, отсутствие объектов | Повторно клонировать и перенести изменения рабочей области | Необходимо предварительно создать резервную копию рабочей области |

### 6.7 Откат

При обнаружении проблемы после завершения пуша используется `git revert` для создания обратного коммита; повторный принудительный пуш с перезаписью уже опубликованной истории запрещён.
