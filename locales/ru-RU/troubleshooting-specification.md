# Спецификация устранения неполадок

> Какую задачу решает этот файл: определяет структуру документации по устранению неполадок (Troubleshooting / FAQ), правила написания записей и механизм сопровождения, чтобы пользователь мог по симптому определить причину и самостоятельно решить типовые проблемы.

## 1. Область применения

Документация по устранению неполадок требуется в следующих случаях:

1. Сбой установки или сборки имеет несколько типовых причин.
2. Между элементами конфигурации существуют конфликты, а сообщение об ошибке недостаточно для указания способа решения.
3. Для определённой платформы или версии существуют известные ограничения.
4. Пользователи многократно задают однотипные вопросы, и ответ можно стандартизировать.

## 2. Расположение и именование файлов

1. При небольшом объёме содержимого оно размещается как раздел README с заголовком «Частые вопросы» или «Устранение неполадок».
2. При значительном объёме создаётся отдельный файл `docs/troubleshooting.md` или `FAQ.md`, а в README сохраняется ссылка для перехода.
3. Вопросы группируются по темам, например «Установка», «Конфигурация», «Запуск», «Производительность», «Сеть».

## 3. Структура документа

1. **Вступительное пояснение**: охват типовых вопросов и применимые версии.
2. **Указатель вопросов**: перечень заголовков вопросов по темам с возможностью быстрого перехода.
3. **Записи вопросов**: последовательное раскрытие по единой структуре.
4. **Всё ещё не решено**: ссылки на issue, обсуждения и другие каналы помощи.

## 4. Структура записи

Каждая запись вопроса должна содержать следующие части:

| Часть | Содержание | Требование |
| --- | --- | --- |
| Симптом | Конкретное проявление, которое видит пользователь | С полным текстом ошибки, запись «ошибка» недопустима |
| Условия возникновения | Когда возникает | С указанием версии, платформы, действия |
| Причина | Корневая причина | С объяснением механизма, а не только выводом |
| Решение | Исполнимые шаги | Нумерованный перечень с командами или конфигурацией |
| Проверка | Как подтвердить исправление | С указанием ожидаемого вывода |
| Связи | Ссылки на связанную документацию или issue | Необязательно |

## 5. Пример записи

```markdown
### При установке возникает `EACCES: permission denied`

**Симптом**: при выполнении `npm install -g <package>` сообщается о недостатке прав.

**Условия возникновения**: установка глобального пакета обычным пользователем в Linux или macOS.

**Причина**: право записи в глобальный каталог установки принадлежит системному администратору, текущий пользователь не имеет права записи.

**Решение**:

```bash
mkdir -p ~/.npm-global
npm config set prefix '~/.npm-global'
export PATH=~/.npm-global/bin:$PATH
npm install -g <package>
```

**Проверка**: успехом считается вывод номера версии при выполнении `<package> --version`.

## 6. Требования к написанию

1. В заголовке вопроса используется формулировка, которую будет искать пользователь, а не внутренний термин.
2. Текст ошибки сохраняется дословно для сопоставления пользователем; конфиденциальные сведения должны обезличиваться (см. [спецификацию безопасности и приватности](./security-and-privacy-specification.md)).
3. В решении приводятся полные команды, наличие настроенных переменных окружения у пользователя не предполагается.
4. Одна запись решает только один вопрос, несколько причин не объединяются.
5. При наличии известного дефекта указываются область влияния и способ обхода; сроки исправления не обещаются.
6. Вопросы, связанные с миграцией, ссылаются на руководство по миграции (см. [спецификацию руководства по миграции](./migration-guide-specification.md)).

## 7. Механизм сопровождения

1. Если один и тот же вопрос задан более трёх раз, запись должна быть добавлена или переписана.
2. После обновления версии все записи пересматриваются, утратившее силу содержимое удаляется.
3. В каждой записи может указываться версия последней проверки для оценки актуальности.
4. Указатель вопросов синхронно обновляется при добавлении и удалении записей.

## 8. Запрещённые практики

1. Запрещается превращать документацию по устранению неполадок в описание функциональности.
2. Запрещается ограничиваться ответами без диагностической ценности вроде «попробуйте перезагрузить».
3. Запрещается опускать текст ошибки и условия возникновения.
4. Запрещается сохранять записи об уже исправленных или утративших силу проблемах.
