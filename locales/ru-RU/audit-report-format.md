# Формат отчёта о проверке

> Какую задачу решает этот файл: определяет единственный формат сдачи отчёта о проверке, требования к полям и примеры заполнения, чтобы отчёт мог быть напрямую исполнен другим агентом.

Отчёт является единственным результатом этапа проверки. Каждый пункт проблемы должен одновременно содержать доказательство, ответственную сторону и действие; выводы, которые невозможно исполнить, не должны попадать в отчёт.

## 1. Структура отчёта

````markdown
# Отчёт о проверке перед пушем · {{仓库名}}

Вывод: {{结论}}
Режим: {{模式}}
Репозиторий: {{仓库名}} · {{可见性}} · {{许可证}} · ветка по умолчанию {{默认分支}}

## I. Состояние контрольных точек
| Контрольная точка | Состояние | Открытые пункты |
| --- | --- | --- |
| A Безопасность | {{门禁状态}} | {{未决项}} |
| B Качество | {{门禁状态}} | {{未决项}} |
| C Главная страница | {{门禁状态}} | {{未决项}} |

## II. Перечень проблем
| Уровень | Измерение | Проблема | Доказательство (путь:строка / вывод команды) | Ответственный агент | Действие |
| --- | --- | --- | --- | --- | --- |
| {{等级}} | {{维度}} | {{问题}} | {{证据}} | {{责任agent}} | {{动作}} |

## III. Состояние матрицы документации
| Файл | Состояние | Отсутствует / требует изменения |
| --- | --- | --- |
| {{文件路径}} | {{状态}} | {{待改项}} |

## IV. Исполнительный список пуша
- [ ] {{推送规则}}

## V. Пояснение о допуске
{{放行说明}}
````

## 2. Определения полей

| Поле | Обязательно | Тип | Ключевые моменты заполнения | Пример |
| --- | --- | --- | --- | --- |
| Имя репозитория | Да | Текст | Дословно совпадает с именем репозитория на GitHub | `markdown-lint-cli` |
| Вывод | Да | Перечисление | Только `ALLOW PUSH` или `BLOCK PUSH`; при ненулевом числе P0 обязателен второй вариант | `BLOCK PUSH` |
| Режим | Да | Перечисление | Для приватных временных скриптовых репозиториев допускается «сокращённая проверка», в остальных случаях — «полная проверка» | `полная проверка` |
| Видимость | Да | Перечисление | `private` / `public`; перед публикацией лицензия проверяется повторно | `private` |
| Лицензия | Да | Идентификатор SPDX | При отсутствии лицензии указывается `NONE`, и тогда вывод должен быть `BLOCK PUSH` | `MIT` |
| Ветка по умолчанию | Да | Текст | Указывается фактическое имя ветки, а не предполагаемое `main` | `main` |
| Состояние контрольной точки | Да | Перечисление ×3 | По одной строке для A/B/C; при `SKIP` причина указывается в «открытых пунктах» | `FAIL` |
| Открытые пункты | Обязательно условно | Текст | Обязательно при состоянии `FAIL` или `SKIP`; перечисляются причины блокировки или пропуска | `D1: обнаружен .env` |
| Уровень | Да | Перечисление | `P0` блокирует / `P1` исправить или зарегистрировать до пуша / `P2` рекомендация | `P0` |
| Измерение | Да | `D1`–`D14` | Номера приведены в [матрице измерений проверки](./review-dimension-matrix.md) | `D1` |
| Проблема | Да | Текст | Одно предложение, констатирующее факт, без предположений и эмоциональных оценок | `в корневом каталоге присутствует .env` |
| Доказательство | Да | Путь:строка или вывод команды | Должно допускать повторную проверку; при невозможности получить доказательство указывается `SKIP + причина` | `.env:3` |
| Ответственный агент | Да | Имя агента | Указывается конкретная исполняющая роль, а не «ответственные лица» | `security-auditor` |
| Действие | Да | Текст | Непосредственно исполнимая операция с указанием целевого файла | `удалить .env, ротировать ключ и очистить историю` |
| Путь к файлу | Да | Текст | Постатейно по перечню из [матрицы документации](./document-matrix.md) | `SECURITY.md` |
| Состояние матрицы документации | Да | Таблица построчно | Для каждого файла отмечается наличие, отсутствие или необходимость изменения | `SECURITY.md отсутствует` |
| Исполнительный список пуша | Да | Список флажков | Постатейно по правилам из [спецификации пуша и релиза](./push-and-release-specification.md) | `- [ ] убедиться, что .gitignore действует` |
| Пояснение о допуске | Да | Текст | При блокировке указываются причина и условия снятия; при допуске — выполненные абсолютные правила | `после снятия P0 возможна повторная проверка` |

## 3. Указания по заполнению

1. **Вывод в первую очередь**: сначала определяется число P0, затем пишется вывод. Пока хотя бы один P0 не снят, выводить `ALLOW PUSH` запрещено.
2. **Обязательность доказательств**: каждая проблема должна иметь `путь:номер строки` или воспроизводимый вывод команды. Вывод без доказательства помечается `SKIP` с указанием причины; писать `PASS` запрещено.
3. **Ответственность на роль**: ответственный агент указывается именем роли из [матрицы измерений проверки](./review-dimension-matrix.md); одна проблема соответствует одной ответственной стороне.
4. **Исполнимость действий**: действие должно указывать целевой файл и тип операции; «обработать позже» и «скорректировать самостоятельно» считаются недействительными.
5. **Согласованность контрольных точек**: состояния трёх строк A/B/C соответствуют перечню проблем; при состоянии `FAIL` любой контрольной точки вывод должен быть `BLOCK PUSH`.
6. **Постатейность матрицы документации**: файлы перечисляются по перечню, ограничиваться записью «документация в основном готова» запрещено.
7. **Развёрнутость перечня**: исполнительный список пуша должен постатейно раскрывать правила; подменять его формулировкой «действовать по спецификации» запрещено.

Частые ошибки:

| Ошибочная формулировка | Проблема | Способ исправления |
| --- | --- | --- |
| В графе доказательств указано «возможно, есть проблема» | Нет пути и вывода, повторная проверка невозможна | Добавить `путь к файлу:номер строки` или вывод команды |
| P0 не снят, но указано `ALLOW PUSH` | Нарушение абсолютных правил | Заменить на `BLOCK PUSH` и перечислить условия снятия |
| Для непроверяемого пункта указано `PASS` | Вымышленный результат | Указать `SKIP` и причину в открытых пунктах |
| Ответственная сторона указана как «ответственные лица» | Отсутствует субъект ответственности | Указать конкретное имя агента |
| Действие указано как «обработать позже» | Неисполнимо | Указать целевой файл и конкретную операцию |
| Ветка по умолчанию указана как `main` без проверки | Расхождение с фактическим состоянием | Ориентироваться на вывод `git branch` |

## 4. Полный пример

Ниже приведён полностью заполненный пример для `BLOCK PUSH`:

````markdown
# Отчёт о проверке перед пушем · markdown-lint-cli

Вывод: BLOCK PUSH
Режим: полная проверка
Репозиторий: markdown-lint-cli · private · NONE · ветка по умолчанию main

## I. Состояние контрольных точек
| Контрольная точка | Состояние | Открытые пункты |
| --- | --- | --- |
| A Безопасность | FAIL | D1 обнаружил .env, D2 без LICENSE |
| B Качество | SKIP | В репозитории не установлены зависимости, сборка и тесты невыполнимы |
| C Главная страница | FAIL | В README отсутствуют раздел установки и минимальный пример |

## II. Перечень проблем
| Уровень | Измерение | Проблема | Доказательство (путь:строка / вывод команды) | Ответственный агент | Действие |
| --- | --- | --- | --- | --- | --- |
| P0 | D1 | В корневом каталоге присутствует .env | `.env:3` содержит DATABASE_URL | security-auditor | Удалить .env, ротировать учётные данные базы данных и очистить историю |
| P0 | D2 | Файл лицензии отсутствует | `ls LICENSE` выводит `No such file or directory` | license-checker | После подтверждения лицензии владельцем репозитория создать LICENSE |
| P1 | D13 | В README отсутствует раздел установки | `README.md:1-28` без заголовка «Установка» | readme-writer | Дописать установку и минимальный пример по стандартному шаблону README |

## III. Состояние матрицы документации
| Файл | Состояние | Отсутствует / требует изменения |
| --- | --- | --- |
| README.md | Требует изменения | Отсутствуют раздел установки и минимальный пример |
| LICENSE | Отсутствует | Тип лицензии ожидает подтверждения владельца |
| SECURITY.md | Отсутствует | Ещё не создан |

## IV. Исполнительный список пуша
- [ ] Убедиться, что git status чист
- [ ] Выполнить полное сканирование ключей (включая историю коммитов)
- [ ] Локально пройти build, test и lint
- [ ] Матрица документации укомплектована

## V. Пояснение о допуске
Причина блокировки: имеются 2 пункта P0 (утечка учётных данных, отсутствие лицензии), а контрольная точка качества не может быть оценена из-за неустановленных зависимостей. Условия снятия: завершить ротацию ключей и очистку истории, определить лицензию, повторно прогнать тесты в окружении, пригодном для сборки и снять P0, после чего провести повторную проверку.
````

При `ALLOW PUSH` в пятом разделе допускается запись: «Выполнены все абсолютные правила, все три уровня контрольных точек имеют состояние PASS, пуш может быть выполнен». Остальные разделы заполняются по фактическому состоянию; опускать доказательства и перечень запрещено.

## 5. Порядок сдачи

1. Полное содержимое языковой навигации корневого README.
2. Полное содержимое README каждого готового языкового каталога с поочерёдным указанием языкового кода и пути к файлу.
3. Содержимое файла NOTICE.
4. Описание варианта LICENSE (если пользователь не указал лицензию, приводятся только кандидаты и их различия без непосредственной генерации).
5. Сводка пунктов, требующих подтверждения.
6. Отчёт о проверке (настоящий отчёт).
7. Инструкция по пушу в GitHub.
