# Спецификация рабочих процессов CI

> Какую задачу решает этот файл: определяет условия запуска, разделение задач, стратегию кэширования и конфигурацию безопасности рабочих процессов непрерывной интеграции `.github/workflows/*.yml`, обеспечивая воспроизводимость и аудируемость сборки, тестов и проверок.

## 1. Принципы проектирования

1. **Единственная ответственность**: каждый рабочий процесс отвечает только за один класс целей (сборка, тесты, релиз, развёртывание документации); смешивать релиз и тесты в одном рабочем процессе запрещено.
2. **Быстрая обратная связь**: лёгкие проверки (lint, форматирование) выполняются раньше, длительные задачи (полная матрица тестов) — позже.
3. **Воспроизводимость**: версии зависимостей фиксируются, используются Actions с фиксированной версией, кэш служит только ускорению и не изменяет результат.
4. **Минимальные полномочия**: полномочия выдаются рабочим процессом по задаче, по умолчанию только чтение, задачи релиза получают повышенные полномочия отдельно (см. [спецификацию безопасности и приватности](./security-and-privacy-specification.md)).

## 2. Структура файла

### 2.1 Именование и путь

- Путь фиксирован: `.github/workflows/*.yml`.
- Имя файла использует строчные буквы и дефисы и отражает ответственность, например `ci.yml`, `release.yml`, `docs.yml`.
- Поле `name` рабочего процесса должно соответствовать семантике имени файла.

### 2.2 Обязательные блоки

| Блок | Назначение | Требование |
| --- | --- | --- |
| `name` | Отображаемое имя рабочего процесса | Краткое, позволяющее понять ответственность |
| `on` | Условия запуска | Явно указать ветки, пути или события |
| `permissions` | Объявление полномочий | Явное объявление, по умолчанию минимальные |
| `jobs` | Набор задач | Разделение по ответственности |

### 2.3 Проектирование условий запуска

| Событие запуска | Применимость | Замечание |
| --- | --- | --- |
| `push` | Основная ветка и ветки релиза | Ограничить набор веток, чтобы избежать запуска во всех ветках |
| `pull_request` | Все PR | Обеспечить проверку перед слиянием |
| `workflow_dispatch` | Ручной запуск | Для контролируемых операций, таких как релиз и откат |
| `schedule` | Задачи по расписанию | Для проверки обновлений зависимостей и ночных сборок |
| `release` | Действия после релиза | Для выгрузки артефактов и анонсов |

## 3. Разделение задач

Рекомендуемый порядок этапов:

1. **Статический анализ**: форматирование, lint, проверка типов.
2. **Сборка**: получение артефактов сборки для повторного использования последующими задачами.
3. **Тесты**: модульные и интеграционные тесты, могут выполняться параллельно по матрице.
4. **Проверка артефактов**: проверка размера, подписи или целостности артефактов сборки.
5. **Релиз**: выполняется только при полностью зелёном CI и выполненных условиях (см. [спецификацию пуша и релиза](./push-and-release-specification.md)).

Зависимости между задачами объявляются через `needs`, что обеспечивает прерывание при сбое; последующие задачи не должны продолжать работу в состоянии сбоя.

## 4. Матричная сборка

Для покрытия нескольких версий и платформ используется `strategy.matrix`:

```yaml
strategy:
  fail-fast: false
  matrix:
    os: [ubuntu-latest, macos-latest, windows-latest]
    node-version: [18, 20, 22]
```

Требования:

- Версии должны покрывать минимальную и последнюю версии, поддерживаемые согласно заявлению проекта (см. [описание совместимости](./readme-sections-specification.md), раздел 14).
- `fail-fast` устанавливается в `false`, чтобы каждая комбинация выполнялась полностью и проблемы совместимости было проще локализовать.
- Число измерений матрицы не должно превышать трёх, чтобы избежать комбинационного взрыва.

## 5. Стратегия кэширования

| Объект кэша | Рекомендуемый ключ | Замечание |
| --- | --- | --- |
| Каталог зависимостей | Хеш файла блокировки менеджера пакетов | При изменении файла блокировки кэш становится недействительным |
| Артефакты сборки | Хеш исходного кода и конфигурации | Соответствует входам сборки |
| Инструментарий | Номер версии | При обновлении версии кэш становится недействительным |

Кэш только ускоряет и не изменяет результат сборки; при попадании в кэш полные тесты всё равно должны выполняться.

## 6. Конфигурация безопасности

1. Секреты внедряются через Secrets репозитория; записывать их в файл рабочего процесса или журналы запрещено.
2. Каждый рабочий процесс явно объявляет `permissions`, по умолчанию `contents: read`.
3. Сторонние Action подключаются с фиксированной версией или хешем коммита; плавающие теги не применяются.
4. При поступлении PR из форка внедрение Secrets запрещено во избежание атак с повышением полномочий.
5. Задачи релиза отделены от основных проверок и запускаются только в защищённых ветках или по тегу.

## 7. Бейджи состояния

Рабочий процесс должен предоставлять для README бейдж состояния в формате:

```markdown
[![CI](https://github.com/{owner}/{repo}/actions/workflows/ci.yml/badge.svg)](https://github.com/{owner}/{repo}/actions/workflows/ci.yml)
```

Параметры и порядок бейджей см. в [спецификации бейджей](./badge-specification.md).

## 8. Запрещённые практики

1. Запрещено жёстко кодировать секреты или внутренние адреса в рабочем процессе.
2. Запрещено использовать `continue-on-error` для сокрытия сбоев тестов.
3. Запрещено настраивать несколько конфликтующих правил запуска для одного условия.
4. Запрещено выполнять релиз при непройденных проверках основной ветки.
