# Спецификация шаблона руководства по разработке

> Какую задачу решает этот файл: определяет каркас руководства по разработке с двумя фазами «написание в облаке — выполнение локально», формат карточек задач, протокол передачи и контрольные точки проверки, чтобы одна и та же идея могла быть переписана облачной моделью в однозначные карточки задач и выполнялась локальной моделью кодирования по частям, эстафетой.

## 1. Назначение и порядок использования

1. Спецификация рассчитана на разделение труда «одна облачная модель рассуждений + одна локальная модель кодирования»: облако отвечает за переписывание расплывчатой идеи в ясный план, локальная сторона — за детерминированное выполнение плана.
2. Порядок использования фиксирован в четыре шага, пропускать их нельзя:
   - Предварительная проверка: проверить, нет ли в идее ошибочных предпосылок, логических скачков или нехватки информации; при нехватке сведений сначала задать вопросы пользователю, додумывать запрещено.
   - Написание в облаке: просканировать открытые решения по правилам раздела 9 и заполнить руководство.
   - Проверка пользователем: в первую очередь проверять команды приёмки, записи реестра принятых решений и запреты.
   - Локальное выполнение: инъецировать соответствующие главы и записи передачи по машиночитаемому индексу и выполнять по частям.
3. В основном тексте руководства запрещены расплывчатые слова вроде «и так далее», «связанное», «уместно», «по возможности», «при необходимости»; в каждом месте даётся либо точное значение, либо правило принятия решения.

## 2. Каркас руководства

Каждое руководство по разработке всегда содержит следующие части, порядок не меняется:

| Часть | Обязанность |
| --- | --- |
| Машиночитаемый индекс | Навигационная таблица путей глав, соответствующих каталогов кода, команд приёмки и отметок фаз |
| Реестр принятых решений | Таблица записей открытой цепочки поставок, единственный источник истины для всего проекта (см. раздел 11) |
| Конституция проекта | Инварианты всего проекта, инъецируются в каждую часть |
| Глоссарий | Сопоставление терминов с доступными объяснениями и соответствующим кодом |
| Главы модулей | По одной главе на модуль, пишутся по структуре раздела 4 |
| Глава выпуска | Спецификация сборки и распространения; действия публикации подтверждаются пользователем |
| Глава текстов сайта | Спецификация текстов для обычных пользователей, в локальную модель не инъецируется |
| Журнал изменений | Дата, глава, изменение и лицо, принявшее решение |

## 3. Конституция проекта

Конституция проекта — инварианты, обязательные для инъекции в каждую локально выполняемую часть; она всегда содержит пять пунктов:

1. Стек технологий и версии: с точностью до номера версии.
2. Соглашение о структуре каталогов: дерево плюс одна фраза об обязанности каждого каталога.
3. Спецификация кодирования: адаптируется по типу проекта; базовая линия — модульность с загрузкой по требованию, минимальный и самый прямой код, не добавлять незапрошенные функции, полные комментарии и пояснение профессиональных понятий доступным языком; проекты с интерфейсом следуют Apple HIG, единицы шрифта — только px или rem, rpx запрещён.
4. Глобальные запреты: то, что делать нельзя никогда, например не подключать зависимости, не внесённые в реестр принятых решений, и не изменять файлы контрактов.
5. Спецификация языка вывода: пояснения, журналы, прогресс и сообщения об ошибках — на упрощённом китайском; код, команды, пути к файлам и имена собственные можно оставлять в оригинале.

## 4. Структура главы модуля

Каждая глава модуля всегда содержит девять разделов, порядок не меняется:

| Раздел | Обязанность |
| --- | --- |
| Обязанности модуля | 1-3 предложения: что делает и чего не делает |
| Используемые открытые решения | Название, назначение, номер записи в реестре принятых решений |
| Список файлов | Пути, действия (создание/изменение/только чтение), обязанности; всего не более 10, сверх этого глава делится |
| Контракт интерфейсов | Сигнатуры, маршруты и поля протокола с точностью до типа, с полными примерами входа и выхода |
| Данные и состояние | Что хранится, где и в каком формате; профессиональные понятия поясняются доступным языком |
| Зависимости | Три списка файлов: что нужно прочитать заранее, что будет вызываться, что нельзя изменять никогда |
| Карточки задач | Части, на которые разбит модуль; каждая карточка выполняется независимо |
| Запреты главы | То, что в данном модуле специально запрещено делать |
| Заметки о проектировании | Основания выбора, отклонённые варианты, различение фактов и предположений; в локальную модель не инъецируются |

## 5. Формат карточки задачи

Одна карточка задачи равна одной локальной сессии и одной команде приёмки; поля фиксированы:

| Поле | Требование |
| --- | --- |
| Цель | Одно предложение, проверяемое машиной |
| Предусловия | Зависимая предыдущая часть и её файлы уже существуют |
| Шаги | Нумерованный список, один детерминированный шаг за раз; выполняется целиком, без прерываний и уточняющих вопросов |
| Команда приёмки | Можно скопировать и выполнить напрямую; если системы приёмки ещё нет, первая карточка обязана сначала её построить |
| Ожидаемый результат | Точный вывод, код выхода или число проверок |
| Обработка сбоев | Меры по каждому типовому ошибочному случаю; после 3 сбоев подряд обязательно остановиться и записать в протокол передачи |
| Требования к передаче | Какие поля обязательно записать в протокол передачи |

Жёсткие ограничения:

1. Если карточка затрагивает более 10 файлов — разделить карточку; если в главе более 6 карточек — разделить главу.
2. В карточках, связанных с самопроверкой поставки, нужно явно перечислить очистку избыточного кода и точки синхронизации README, NOTICE, LICENSE.
3. Действия, удаляющие или перезаписывающие файлы, всегда останавливаются и записываются в поле block протокола передачи до подтверждения пользователем.
4. Задачи, слишком расплывчатые для формулировки команды приёмки, в карточку не заносятся, а отдельно помечаются как «требуется решение пользователя».

## 6. Протокол передачи PROGRESS

Файл протокола передачи PROGRESS.md — единственный источник истины между частями; формат фиксирован:

| Поле | Требование |
| --- | --- |
| done | Достигнута ли цель карточки |
| files | Список фактически изменённых файлов |
| decisions | Решения по ходу работы в формате «выбрано A, потому что B» |
| next | Номер следующей карточки и точка входа; обязательно указать путь к файлу и входную функцию, писать «продолжить доработку» запрещено |
| block | Нерешённые проблемы; если их нет, оставить пустым |

1. По завершении каждой карточки добавляется одна запись; формат изменять нельзя.
2. При локальном выполнении инъецируется только последняя запись, исторические записи не инъецируются.
3. Возобновление с контрольной точки: получив команду «продолжить», сначала прочитать последнюю запись и подтвердить точку останова, затем продолжить с входа, на который указывает next; переделывать выполненные шаги по памяти или догадкам запрещено.

## 7. Бюджет локальной инъекции

harness собирает контекст каждой части по приведённой таблице; общий бюджет не превышает 24K (75% рабочего окна 32K):

| Инъецируемый элемент | Бюджет |
| --- | --- |
| Конституция проекта | 2-3K |
| Глава, к которой относится текущая карточка | 2-5K |
| Последняя запись протокола передачи | около 0.5K |
| Каркас промпта передачи | около 0.3K |
| Код и вывод инструментов | остаток бюджета |

Не инъецируются: полная таблица реестра принятых решений (инъецируются только записи, затрагиваемые карточкой), заметки о проектировании, глава текстов сайта.

## 8. Железные правила промпта передачи

При начале каждой части инъецируется фиксированное вступление; железных правил шесть:

1. Весь вывод — на упрощённом китайском; код, команды, пути и имена собственные можно оставлять в оригинале.
2. Делать только то, что указано в карточке задачи; не добавлять незапрошенные функции, конфигурации или возможности расширения.
3. Ничего не выдумывать и не фантазировать; при неуверенности в сигнатуре API прямо сказать о неуверенности; факты и предположения явно различать.
4. При сбое команды приёмки действовать по обработке сбоев из карточки задачи; самостоятельно менять критерии приёмки запрещено.
5. Действия с удалением или перезаписью файлов всегда останавливаются до подтверждения пользователем.
6. По завершении строго записать протокол передачи согласно требованиям к передаче, затем закончить.

## 9. Правила заполнения в облаке

Перед заполнением руководства облачная модель выполняет две подготовки, затем заполняет главы по очереди:

1. Проверка предпосылок: искать ошибочные предпосылки, логические скачки и нехватку информации; при недостатке сначала спросить пользователя.
2. Сканирование открытых решений: искать готовые решения в открытой экосистеме; сначала сканировать, потом заполнять; при наличии зрелого решения не изобретать велосипед; результаты регистрируются в реестре принятых решений.

При заполнении соблюдать:

1. Уничтожить все расплывчатые слова: в каждом месте давать точное значение или правило принятия решения.
2. Проектные решения записывать в заметки о проектировании, включая основания выбора и отклонённые варианты, для проверки пользователем; в локальную модель они не инъецируются.
3. Инструкции для локальной модели писать исходя из того, что «она не знает контекста проекта»; все предпосылки формулировать явно.
4. Нижняя граница соответствия: при неясной лицензии помечать «требует подтверждения»; для решений с сильным copyleft добавлять напоминание о производных обязательствах; в изменённом открытом коде сохранять исходные авторские права и описание изменений; принятые позиции обязательно синхронизировать с README, README_EN, NOTICE и LICENSE, причём синхронизация является явным шагом и содержанием приёмки соответствующей карточки.
5. Ссылки на спецификации формата документов давать на соответствующие спецификации этого репозитория, не копируя их текст в руководство.

## 10. Статусы фаз и рабочее окно

Каждая глава в машиночитаемом индексе несёт отметку фазы, по которой настраивается локальное рабочее окно:

| Фаза | Признаки | Рабочее окно |
| --- | --- | --- |
| Зелёное поле | Заполнять реализацию по замороженному контракту | 16-24K |
| Рост | Межмодульные функции, уровень по умолчанию | 32K |
| Сопровождение | Рефакторинг и межмодульная диагностика | 48-64K, параллелизм соответственно уменьшается |

Главы периода сопровождения дополнительно снабжаются руководством по диагностике из трёх колонок: симптом, возможное место, команда проверки.

## 11. Реестр принятых решений, выпуск и тексты сайта

1. Поля таблицы реестра принятых решений фиксированы: название, категория, версия, назначение, лицензия, правообладатель, официальный адрес, наличие изменений, описание изменений, способ декларирования, статус принятия; статус принятия делится на три уровня: «можно принять немедленно», «требует оценки», «временно недоступно».
2. Глава выпуска охватывает скрипты сборки, матрицу CI, checksum и шаблоны переменных окружения для подписи; команда приёмки карточки выпуска — проверка артефактов сборки; действия внешней публикации не выполняются локальной моделью, а исполняются после подтверждения пользователем.
3. Глава текстов сайта обращена к обычным пользователям: код, командная строка, технические термины и пустые слова запрещены; структура — позиционирование на первом экране, болевые точки, сильные стороны, доверие, загрузка, истории сценариев, частые вопросы; тон спокойный и сдержанный.

## 12. Межпроектные ссылки и проверка

1. Когда целевой проект ссылается на эту спецификацию, полный текст читается через `gitrule spec`, а каркас руководства копируется как начальный каркас внутрипроектного руководства; эта спецификация не пересматривается вместе с проектом, эволюция внутрипроектного руководства замыкается в репозитории проекта.
2. Для карточек задач, связанных с созданием документации, команда приёмки дополняется `gitrule check`; для многоязычных проектов добавляется `gitrule xcheck`; после изменения глоссария выполняется `gitrule termcheck`.
3. Нарушения документации, найденные `gitrule check`, относятся к автоматически исправимым: можно сначала выполнить `gitrule optimize` и перепроверить; если всё ещё не проходит, записать в поле block протокола передачи.
4. Спецификации Gitrule регулируют только документацию и нормы репозитория; качество кода относится к тестам и проверочным скриптам каждого проекта, одно другое не заменяет.
