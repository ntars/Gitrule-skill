# Спецификация шаблонов Issue и PR

> Какую задачу решает этот файл: определяет проектирование полей, формат и требования к написанию структурированных форм `.github/ISSUE_TEMPLATE/*.yml` и чек-листа самопроверки `.github/PULL_REQUEST_TEMPLATE.md`, обеспечивая исполнимость входных ограничений при отправке сообщений о проблемах и внесении изменений.

## 1. Принципы проектирования

1. **Структура важнее свободного текста**: формы Issue определяются в YAML и направляют заполнение через выпадающие списки, флажки и обязательные поля, сокращая бесполезные сообщения.
2. **Минимизация обязательных полей**: сохраняются только поля, необходимые для локализации проблемы; необязательные поля не должны помечаться как обязательные.
3. **Явная самопроверка**: шаблон PR в виде чек-листа перечисляет отмечаемые пункты самопроверки, чтобы участники не пропускали ключевые шаги.
4. **Единственная ответственность**: форма Issue собирает информацию и не содержит презентации проекта; шаблон PR служит самопроверке и не дублирует описание функциональности (соответствует [матрице документации](./document-matrix.md)).

## 2. Структура формы Issue

### 2.1 Файлы и именование

- Путь фиксирован: `.github/ISSUE_TEMPLATE/*.yml`, один файл на шаблон.
- Имя файла использует строчные буквы и дефисы, например `bug-report.yml`, `feature-request.yml`, `question.yml`.
- Должны быть предоставлены как минимум два типа шаблонов: «сообщение о дефекте» и «запрос функциональности».

### 2.2 Стандартные поля

| Поле | Тип | Обязательно | Назначение |
| --- | --- | --- | --- |
| `name` | Строка | Да | Отображаемое имя шаблона |
| `description` | Строка | Да | Описание назначения шаблона |
| `title` | Префикс строки | Да | Автоматический префикс заголовка проблемы |
| `labels` | Массив | Нет | Автоматически добавляемые метки |
| `body` | Массив | Да | Список полей формы |

Распространённые типы полей в `body`:

| Тип | Сценарий применения | Пример |
| --- | --- | --- |
| `markdown` | Пояснительный текст без ввода | Инструкция по заполнению |
| `textarea` | Описание длинного текста | Шаги воспроизведения проблемы |
| `input` | Короткий текст в одну строку | Номер версии |
| `dropdown` | Ограниченный набор вариантов | Операционная система, серьёзность |
| `checkboxes` | Множественные подтверждения | Проверен ли поиск дубликатов |

### 2.3 Перечень полей сообщения о дефекте

1. Описание проблемы (`textarea`, обязательно): что произошло.
2. Ожидаемое поведение (`textarea`, обязательно): что должно было произойти.
3. Шаги воспроизведения (`textarea`, обязательно): пронумерованы, воспроизводимы независимо.
4. Среда выполнения (`input` или `dropdown`): операционная система, среда выполнения, версия проекта.
5. Журналы или снимки экрана (`textarea`): предоставить сообщение об ошибке, чувствительные сведения должны быть обезличены.
6. Подтверждение проверки дубликатов (`checkboxes`, обязательно): существующие issue проверены.

### 2.4 Перечень полей запроса функциональности

1. Постановка проблемы (`textarea`, обязательно): какой возможности сейчас не хватает.
2. Сценарий использования (`textarea`, обязательно): кому и при каких обстоятельствах это нужно.
3. Желаемое решение (`textarea`): как предполагается реализовать.
4. Альтернативы (`textarea`): другие уже рассмотренные подходы.
5. Влияние на совместимость (`dropdown`): затрагиваются ли несовместимые изменения.

## 3. Структура шаблона PR

### 3.1 Обязательные блоки

`PULL_REQUEST_TEMPLATE.md` должен содержать следующие блоки в фиксированном порядке:

1. Описание изменения: что изменено в этот раз и соответствующий номер issue.
2. Тип изменения: отмечается флажками (функциональность, исправление, документация, рефакторинг, тесты и т. д., типы см. в [спецификации сообщений коммитов](./commit-message-specification.md)).
3. Чек-лист самопроверки: отмечаемые пункты самопроверки.
4. Несовместимые изменения: при отсутствии пишется «нет»; при наличии указывается способ миграции (см. [спецификацию руководства по миграции](./migration-guide-specification.md)).
5. Связанная документация: синхронно ли обновлены README, CHANGELOG, документация API.

### 3.2 Пример чек-листа самопроверки

```markdown
## Чек-лист самопроверки

- [ ] Локальная сборка проходит
- [ ] Соответствующие тесты проходят, для новой функциональности добавлены тесты
- [ ] Сообщение коммита написано согласно [спецификации сообщений коммитов](./commit-message-specification.md)
- [ ] Документация синхронно обновлена или подтверждено, что обновление не требуется
- [ ] Секреты, приватные данные или крупные файлы не добавлены
```

## 4. Готовые к копированию шаблоны

### 4.1 Форма сообщения о дефекте

Сохранить как `.github/ISSUE_TEMPLATE/bug-report.yml`:

```yaml
name: Сообщение о дефекте
description: Сообщить о воспроизводимом функциональном сбое
title: "[Bug]: "
labels: ["bug"]
body:
  - type: markdown
    attributes:
      value: |
        Перед отправкой сначала проверьте существующие issue, чтобы избежать дублирования.
        Не вставляйте секреты, токены или личные приватные данные.
  - type: checkboxes
    id: duplicate-check
    attributes:
      label: Проверка дубликатов
      options:
        - label: Я проверил существующие issue и подтверждаю, что это не повторное сообщение
          required: true
  - type: textarea
    id: description
    attributes:
      label: Описание проблемы
      description: Что произошло на самом деле
      placeholder: После выполнения команды install код выхода программы равен 1
    validations:
      required: true
  - type: textarea
    id: expected
    attributes:
      label: Ожидаемое поведение
      description: Что должно было произойти
    validations:
      required: true
  - type: textarea
    id: steps
    attributes:
      label: Шаги воспроизведения
      description: Перечислите шаги с номерами, чтобы другие могли воспроизвести независимо
      placeholder: |
        1. Выполнить команду
        2. Наблюдать вывод
        3. Возникает сбой
    validations:
      required: true
  - type: input
    id: version
    attributes:
      label: Версия проекта
      placeholder: v1.0.0
    validations:
      required: true
  - type: dropdown
    id: os
    attributes:
      label: Операционная система
      options:
        - macOS
        - Linux
        - Windows
        - Другая
    validations:
      required: true
  - type: textarea
    id: logs
    attributes:
      label: Журналы или снимки экрана
      description: Предоставьте сообщение об ошибке, чувствительные сведения должны быть обезличены
      render: shell
  - type: checkboxes
    id: security
    attributes:
      label: Подтверждение информационной безопасности
      options:
        - label: Подтверждаю, что секреты, токены или личные приватные данные не включены
          required: true
```

### 4.2 Форма запроса функциональности

Сохранить как `.github/ISSUE_TEMPLATE/feature-request.yml`:

```yaml
name: Запрос функциональности
description: Предложить новую возможность или улучшение
title: "[Feature]: "
labels: ["enhancement"]
body:
  - type: textarea
    id: problem
    attributes:
      label: Постановка проблемы
      description: Какой возможности сейчас не хватает
    validations:
      required: true
  - type: textarea
    id: scenario
    attributes:
      label: Сценарий использования
      description: Кому и при каких обстоятельствах нужна эта возможность
    validations:
      required: true
  - type: textarea
    id: proposal
    attributes:
      label: Желаемое решение
      description: Как предполагается реализовать
  - type: textarea
    id: alternatives
    attributes:
      label: Альтернативы
      description: Другие уже рассмотренные подходы
  - type: dropdown
    id: breaking
    attributes:
      label: Затрагиваются ли несовместимые изменения
      options:
        - Нет
        - Да
        - Не уверен
    validations:
      required: true
```

### 4.3 Шаблон PR

Сохранить как `.github/PULL_REQUEST_TEMPLATE.md`:

````markdown
## Описание изменения

{{变更说明}}

## Тип изменения

- [ ] Функциональность (feat)
- [ ] Исправление (fix)
- [ ] Документация (docs)
- [ ] Форматирование (style)
- [ ] Рефакторинг (refactor)
- [ ] Тесты (test)
- [ ] Сборка или инструментарий (build / ci)

## Чек-лист самопроверки

- [ ] Локальная сборка проходит
- [ ] Соответствующие тесты проходят, для новой функциональности добавлены тесты
- [ ] Сообщение коммита написано согласно спецификации сообщений коммитов
- [ ] Документация синхронно обновлена или подтверждено, что обновление не требуется
- [ ] Секреты, приватные данные или крупные файлы не добавлены

## Несовместимые изменения

{{破坏性变更说明}}

## Связанная документация

- [ ] README синхронизирован или обновление не требуется
- [ ] CHANGELOG зарегистрирован
- [ ] Документация API синхронизирована или обновление не требуется
````

### 4.4 Таблица соответствия заполнителей

| Заполнитель | Обязательно | Ключевые моменты заполнения |
| --- | --- | --- |
| `{{变更说明}}` | Да | Одним предложением изложить содержание изменения и приложить номер issue в форме `#число` |
| `{{破坏性变更说明}}` | Да | При отсутствии несовместимых изменений написать «нет»; при наличии указать шаги миграции и ссылку на руководство по миграции |

Поля `name`, `description`, `title`, `labels` формы YAML являются метаданными шаблона и заменяются согласно фактическому состоянию проекта; типы полей и значения `required` в `body` настраиваются согласно перечням полей разделов 2 и 3, сокращать обязательные поля запрещено.

### 4.5 Полный пример заполнения

Пример заполнения сообщения о дефекте:

````markdown
## Описание проблемы

После выполнения `npm run build` процесс завершается с кодом выхода 1.

## Ожидаемое поведение

Сборка завершается успешно и создаёт каталог `dist/`.

## Шаги воспроизведения

1. Переключиться на тег v1.0.0
2. Выполнить `npm ci`
3. Выполнить `npm run build` и наблюдать код выхода 1

## Версия проекта

v1.0.0

## Операционная система

macOS

## Журналы или снимки экрана

```
Error: Cannot find module 'mdlint-core'
```

## Подтверждение информационной безопасности

- [x] Подтверждаю, что секреты, токены или личные приватные данные не включены
````

## 5. Требования к написанию

1. Описания полей используют побудительные или повествовательные предложения и не должны быть разговорными.
2. Для каждого обязательного поля приводится пример заполнения или требование к формату.
3. Подсказка должна объяснять «зачем нужна эта информация», избегая расплывчатых требований.
4. Поля, связанные с приватностью, должны содержать напоминание об обезличивании (см. [спецификацию безопасности и приватности](./security-and-privacy-specification.md)).
5. Шаблоны обновляются по мере развития проекта, устаревшие поля должны удаляться и не накапливаться в течение длительного времени.

## 6. Запрещённые практики

1. Запрещено объединять все типы проблем в один шаблон свободного текста.
2. Запрещено задавать обязательные поля, не связанные с локализацией проблемы.
3. Запрещено включать в шаблоны презентацию проекта или маркетинговый контент.
4. Запрещено, чтобы шаблон PR упускал чек-лист самопроверки и декларацию несовместимых изменений.
