# Спецификация владения кодом

> Какую задачу решает этот файл: определяет синтаксис файла `.github/CODEOWNERS`, распределение прав владения и правила маршрутизации ревью, чтобы каждое изменение автоматически направлялось ответственному ревьюеру.

## 1. Принципы проектирования

1. **Явное сопоставление пути и человека**: каждое правило указывает, кто отвечает за путь, что исключает отсутствие ревью или его дублирование.
2. **Минимально необходимый состав владельцев**: число владельцев одного пути ограничивается 1–3 человеками; избыточное количество размывает ответственность.
3. **Наследование по умолчанию**: задаётся глобальный владелец по умолчанию, покрывающий пути, не попавшие под явные правила.
4. **Синхронизация со структурой команды**: при изменении состава участников файл обновляется своевременно, чтобы недействительные учётные записи не блокировали ревью.

## 2. Расположение файла и синтаксис

### 2.1 Пути

Файл `CODEOWNERS` может размещаться в любом из перечисленных мест; выбирается первое совпадение по приоритету:

1. Корень репозитория `CODEOWNERS`;
2. `docs/CODEOWNERS`;
3. `.github/CODEOWNERS` (рекомендуется).

### 2.2 Правила синтаксиса

```text
# Комментарии начинаются с #
<шаблон пути>  <владелец>  [<владелец>...]
```

- Одна строка — одно правило: за шаблоном пути следует один или несколько владельцев.
- Формат владельца — `@имя_пользователя` или `@организация/команда`.
- Использование адреса электронной почты в качестве владельца требует привязки к учётной записи GitHub.
- Пути чувствительны к регистру, поддерживаются подстановочные знаки `*` и `**`.

### 2.3 Пример

```text
# Владелец по умолчанию
*                       @org/maintainers

# Распределение по каталогам
/src/core/              @org/core-team
/src/api/               @org/api-team @alice
/docs/                  @org/docs-team

# Распределение по типам файлов
*.md                    @org/docs-team
/.github/workflows/      @org/devops-team
```

## 3. Правила сопоставления

1. Действует только последнее совпавшее правило, совпадения не суммируются; поэтому общие правила записываются выше, специальные — ниже.
2. Правило для каталога охватывает этот каталог и его подкаталоги, если только начальный `/` не ограничивает путь корнем.
3. Порядок правил определяет приоритет; правила располагаются от широких к узким.
4. За пути без совпадений ответственность за ревью несёт владелец по умолчанию.

## 4. Стратегия распределения прав владения

| Аспект | Основание распределения |
| --- | --- |
| Каталог | Распределение по границам модулей или подсистем |
| Тип файла | Документация, конфигурация и тесты могут распределяться единообразно по типу |
| Критический путь | Безопасность, релизы и конфигурация CI закрепляются исключительно за ключевыми сопровождающими |
| Новый участник | Сначала участвует как необязательный ревьюер, после освоения становится полноправным владельцем |

## 5. Взаимодействие с процессом ревью

1. При создании PR GitHub автоматически запрашивает ревью у владельцев совпавших путей.
2. Требование обязательного ревью настраивается правилами защиты веток, см. [спецификацию Git-процесса и ветвления](./git-workflow-and-branching-specification.md).
3. Владелец должен ответить в согласованный срок; при превышении срока ответственность переходит к владельцу по умолчанию.
4. Изменение состава владельцев требует синхронного обновления файла, чтобы недействительные учётные записи не блокировали процесс (см. [спецификацию ревью кода](./code-review-specification.md)).

## 6. Требования к сопровождению

1. Проверка выполняется после каждого изменения организационной структуры или зон ответственности команд.
2. При передаче репозитория и уходе участника соответствующий владелец удаляется немедленно.
3. Изменение файла должно пройти ревью как минимум одного действующего владельца, чтобы предотвратить самостоятельное расширение прав.
4. Запрещается указывать в качестве владельцев неактивные учётные записи или учётные записи ботов (кроме случаев, специально предназначенных для автоматизации).

## 7. Запрещённые практики

1. Запрещается использовать слишком широкие подстановочные правила, при которых владельцами становятся все.
2. Запрещается назначать чувствительные пути (релизы, конфигурация секретов) участникам, не способным проводить ревью.
3. Запрещается записывать в файл личные контактные данные.
4. Запрещается надолго сохранять статус владельца за участниками, покинувшими проект.
