# Процесс исполнения

> Какую задачу решает этот файл: определяет полную последовательность этапов от инициации проекта до сдачи, условия входа и результаты каждого этапа, а также правила блокирующих вопросов при недостатке информации.

## 1. Процесс пуша под контролем агента контроля (Phase 0–6)

### Phase 0 · Инициация проекта (Project Init)

Результат: 3 варианта названия проекта + обоснование выбора + вывод проверки на совпадение имён + таблица метаданных репозитория (description / topics / ветка по умолчанию / видимость / license). Правила именования см. в [спецификации именования проектов](./project-naming-specification.md).

### Phase 1 · Инвентаризация (Inventory)

Сканирование репозитория с формированием структурированного перечня:
- технологический стек, входные файлы, менеджер пакетов, lockfile
- имеющаяся документация, отсутствующая документация
- Top10 самых крупных файлов репозитория
- имеющиеся CI / шаблоны / правила защиты
- текущее состояние git: неотслеживаемые файлы, незакоммиченные изменения, подозрительные коммиты в истории

### Phase 2 · Параллельное ревью (Audit)

Согласно [матрице измерений проверки](./review-dimension-matrix.md) измерения распределяются между подагентами для параллельного исполнения; способ распределения см. в [контракте распределения подагентов](./sub-agent-dispatch-contract.md). Каждый подагент возвращает только структурированный вывод, без длинных эссе.

### Phase 3 · Исправление (Fix)

Задачи перечисляются в порядке P0 → P1 → P2 с указанием ответственного агента и предполагаемого действия. При необнулённом P0 переход к Phase 5 не допускается.

### Phase 4 · Создание документации (Docs)

Согласно [матрице документации](./document-matrix.md) каждый файл по отдельности распределяется агенту документации. **Одновременно пишется только один файл; после завершения выполняется проверка, затем берётся следующий.**

### Phase 5 · Пуш (Push)

Исполнение согласно [спецификации пуша и релиза](./push-and-release-specification.md) с построчным отображением результата.

### Phase 6 · После пуша (Post-Push)

Простановка тега, написание Release Notes, проверка доступности бейджей и ссылок, подтверждение зелёного CI, подтверждение корректности сведений в блоке About.

## 2. Процесс создания документации (этапы 0–5)

Продвижение выполняется последовательно по этапам; пока предыдущий этап не завершён, переход к следующему не допускается.

| Этап | Название | Условие входа | Результат |
| --- | --- | --- | --- |
| 0 | Проверка информации | Получены данная спецификация и материалы проекта | Перечень подтверждённой информации, перечень отсутствующей информации |
| 1 | Блокирующие вопросы | Отсутствуют обязательные поля (см. [сбор информации и шаблоны](./information-collection-and-templates.md)) | Структурированный перечень вопросов, сгруппированный по полям |
| 2 | Подтверждение структуры | Обязательные поля заполнены | Оглавление разделов README и тезисный план каждого раздела для подтверждения пользователем |
| 3 | Создание документации | Пользователь подтвердил структуру или явно указал, что подтверждение не требуется | Все сдаваемые материалы |
| 4 | Контрольная точка качества | Создание документации завершено | Результат поэтапной проверки по [контрольной точке качества](./quality-gate.md) |
| 5 | Сдача | Все контрольные точки пройдены либо непройденные пункты помечены | Вывод в порядке [формата отчёта о проверке](./audit-report-format.md) с указаниями по пушу |

## 3. Правила вопросов на этапе 1

1. Вопросы группируются по полям, не более 15 пунктов за один раунд.
2. Каждый вопрос должен пояснять назначение и затрагиваемый раздел, чтобы пользователь мог оценить приоритет.
3. Если пользователь явно указывает, что какой-то пункт предоставить невозможно, в соответствующем месте документа ставится пометка «【ожидает подтверждения: имя поля】», а в конце документа приводится сводка.
4. Если пользователь отвечает «на твоё усмотрение», можно предложить значение, но обязательно с пометкой «【рекомендуемое значение, ожидает подтверждения пользователя】».
