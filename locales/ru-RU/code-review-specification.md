# Спецификация ревью кода

> Какую задачу решает этот файл: определяет шаблон описания pull request, шаблон замечаний ревью, запись ревью, поля и процесс, обеспечивая качество слияния и обмен знаниями.

## 1. Положения спецификации

1. Автор должен указать в описании PR цель изменения, область влияния и результаты самопроверки; шаблон см. в [спецификации Git-процесса и ветвления](./git-workflow-and-branching-specification.md).
2. Ревьюер должен давать конкретные, выполнимые замечания, различая «требуется исправление» и «рекомендация».
3. Перед слиянием требуется одобрение как минимум 1 ревьюера и полностью зелёный CI (соответствует абсолютному правилу H9); автору запрещено самостоятельно одобрять свой PR.
4. При расхождении замечаний вопрос передаётся на решение сопровождающего (см. [спецификацию кодекса поведения](./code-of-conduct-specification.md)).
5. После слияния исходная ветка удаляется, чтобы список веток оставался чистым.

## 2. Контрольный список ревью

Ревьюер должен подтвердить по пунктам:

| № | Измерение | Ключевые моменты проверки | Решение |
| --- | --- | --- | --- |
| 1 | Корректность | Логика верна, граничные случаи и исключения обработаны | Пройдено / Требуется исправление |
| 2 | Тесты | Для изменения есть соответствующие тесты, тесты проходят | Пройдено / Требуется исправление |
| 3 | Стиль | Соответствует [спецификации стиля кода](./code-style-specification.md) | Пройдено / Требуется исправление |
| 4 | Безопасность | Нет чувствительной информации, нет риска инъекций, проверка прав корректна | Пройдено / Требуется исправление |
| 5 | Документация | Изменение интерфейса или поведения синхронизировано с документацией | Пройдено / Требуется исправление |
| 6 | Объём | Изменение сфокусировано, нет посторонних правок | Пройдено / Требуется исправление |
| 7 | Сообщение коммита | Соответствует [спецификации сообщений коммитов](./commit-message-specification.md) | Пройдено / Требуется исправление |
| 8 | Прослеживаемость | Матрица прослеживаемости требований обновлена | Пройдено / Требуется исправление |

## 3. Шаблон замечания ревью

```markdown
### Замечание {{序号}}：{{一句话标题}}

- Уровень: {{必须修改 / 建议 / 提问}}
- Место: {{文件路径:行号}}
- Проблема: {{描述可观察的问题，不评价人}}
- Основание: {{规范条款 / 需求编号 / 风险说明}}
- Рекомендация: {{具体的修改方式或替代方案}}

Пример:
### Замечание 1: Ветка исключения не покрыта
- Уровень: требуется исправление
- Место: `src/rules/spacing.ts:42`
- Проблема: при входных данных с незавершённым Markdown выбрасывается исключение, результат совпадения правила не возвращается.
- Основание: REQ-001, критерий приёмки 2 (граничный путь).
- Рекомендация: перехватить здесь исключение разбора и вернуть совпадение как «разбор не удался», добавить граничный тест.
```

## 4. Шаблон записи ревью

```markdown
## Запись ревью: {{PR 编号}}

Ревьюер: {{姓名}} ｜ Дата ревью: {{YYYY-MM-DD}} ｜ Раунд: {{第 N 轮}}

| Номер замечания | Уровень | Решение по обработке | Исполнитель | Способ проверки |
| --- | --- | --- | --- | --- |
| 1 | Требуется исправление | Исправлено | Автор | см. коммит abc1234 |
| 2 | Рекомендация | Не принято | Автор | Причина: {{说明}} |

Заключение: {{批准 / 需修改后再审 / 拒绝}}
- Условия одобрения: все пункты «требуется исправление» обработаны, CI полностью зелёный.
- Открытые пункты: {{无 / 列出}}
```

## 5. Определение полей

| Поле | Обязательно | Тип | Ключевые моменты заполнения | Пример |
| --- | --- | --- | --- | --- |
| Уровень | Да | Перечисление | Требуется исправление / Рекомендация / Вопрос | `Требуется исправление` |
| Место | Да | `путь:номер строки` | С точностью до строки, указывать только имя файла запрещено | `src/parser.ts:42` |
| Проблема | Да | Текст | Описывать явление, не оценивать автора | `Исключение разбора не перехвачено` |
| Основание | Да | Текст | Пункт спецификации или номер REQ | `REQ-001, критерий приёмки 2` |
| Рекомендация | Да | Текст | Выполнимая, не ограничиваться фразой «оптимизируйте» | `Перехватить исключение и вернуть совпадение` |
| Решение по обработке | Да | Перечисление | Исправлено / Не принято / Отложено | `Исправлено` |
| Способ проверки | Да | Текст | Хеш коммита или способ повторной проверки | `см. коммит abc1234` |
| Заключение | Да | Перечисление | Одобрено / Требуется доработка и повторное ревью / Отклонено | `Одобрено` |

## 6. Указания по заполнению

1. **Различение уровней**: «требуется исправление» обозначает блокирующую слияние проблему (корректность, безопасность, отсутствие тестов); «рекомендация» не влияет на слияние; «вопрос» требует разъяснения от автора, но не требует изменения.
2. **Формулировка замечаний**: описывается наблюдаемая проблема, оценочные выражения вроде «здесь написано очень плохо» запрещены.
3. **Место**: с точностью до номера строки; межфайловые проблемы отмечаются отдельно в каждом замечании.
4. **Основание**: при возможности прослеживается до источника; при отсутствии нормативного основания указываются риск или влияние, фраза «мне так кажется» запрещена.
5. **Решение по обработке**: для «не принято» указывается причина; для «отложено» указывается место дальнейшего отслеживания.
6. **Одобрение**: подтверждается, что все пункты «требуется исправление» закрыты и CI полностью зелёный; автор не должен одобрять свой PR сам.
7. **Расхождения**: при несовпадении мнений ревьюера и автора вопрос передаётся сопровождающему, решение вносится в запись ревью.

Типичные ошибки:

| Ошибочная формулировка | Проблема | Способ исправления |
| --- | --- | --- |
| «Здесь так нельзя» | Нет проблемы, основания и рекомендации | Дополнить три элемента |
| «Рекомендую немного оптимизировать производительность» | Невыполнимо | Дать конкретный способ и критерий оценки |
| Указано только имя файла без номера строки | Затруднена локализация | Указать с точностью до строки |
| Автор одобрил сам | Нарушение правил | Ревью выполняет другой человек |
| «Требуется исправление» применено к личному предпочтению | Злоупотребление уровнем | Понизить до «рекомендации» |

## 7. Полный пример

```markdown
## Запись ревью: #12

Ревьюер: Ли Си ｜ Дата ревью: 2026-11-18 ｜ Раунд: 1-й раунд

| Номер замечания | Уровень | Решение по обработке | Исполнитель | Способ проверки |
| --- | --- | --- | --- | --- |
| 1 | Требуется исправление | Исправлено | Ван У | см. коммит a1b2c3d |
| 2 | Рекомендация | Не принято | Ван У | Причина: текущий QPS не достиг узкого места, избегаем избыточного проектирования |
| 3 | Вопрос | Разъяснено | Ван У | Пояснение добавлено в текст PR |

Заключение: Одобрено
- Условия одобрения: все пункты «требуется исправление» обработаны, CI полностью зелёный (run #128).
- Открытые пункты: нет
```
