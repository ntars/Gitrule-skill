# Спецификация разделов README

> Какую задачу решает этот файл: определяет 20 разделов, которые обязательно должны входить в README каждого языкового каталога, обязательное и недопустимое содержание каждого раздела, а также стандартный формат строки об авторских правах.

## 1. Общие требования к разделам

Все перечисленные ниже 20 разделов должны присутствовать, их порядок фиксирован, языковые версии соответствуют друг другу один к одному.

| № | Раздел | Должен содержать | Не должен содержать |
| --- | --- | --- | --- |
| 1 | Название и позиционирование проекта | Название проекта, описание репозитория (двуязычный объединённый формат `язык страны \| English`), теги (заполнены все 20, только на английском), позиционирование в одну фразу, ссылки переключения языка, текущая версия, статус сопровождения | Расплывчатые прилагательные; описание репозитория длиннее 120 символов; теги со смешанным регистром или с неанглийскими словами |
| 2 | Краткое описание проекта | Предыстория, решаемая проблема, ключевой подход, применимые сценарии, неприменимые сценарии, а также раздельно приведённые преимущества и ограничения (ограничения должны включать область влияния и способ обхода) | Изложение одной фразой; перечисление только преимуществ без ограничений |
| 3 | Ключевые функции | Пункты функций, сгруппированные по модулям, каждый с условием срабатывания и результатом | Только названия функций |
| 4 | Ключевые особенности | Раскрытие по структуре [руководства по описанию особенностей и инженерных компромиссов](./features-and-engineering-tradeoffs-guide.md) | Похвала без подтверждений |
| 5 | Детали проектирования и инженерные компромиссы | Раскрытие по структуре [руководства по описанию особенностей и инженерных компромиссов](./features-and-engineering-tradeoffs-guide.md) | Описание, дублирующее функции |
| 6 | Технологический стек и перечень зависимостей | Среда выполнения, сборка, цепочка инструментов тестирования и ограничения версий; подробности зависимостей указываются в NOTICE | Отсутствие номеров версий |
| 7 | Установка и развёртывание | Требования к среде, шаги установки, команды проверки, способы обновления и удаления, описание контейнеризации | Пропуск шагов или отсутствие проверки |
| 8 | Быстрый старт | Минимальный работоспособный пример с полными командами и ожидаемым выводом | Псевдокод, который невозможно выполнить |
| 9 | Описание конфигурации | Таблица параметров конфигурации (имя ключа, тип, значение по умолчанию, обязательность, диапазон значений, назначение, пример), приоритет конфигурации, поддержка горячего обновления | Отсутствие значений по умолчанию |
| 10 | Описание API или модулей | Сигнатуры интерфейсов, параметры, возвращаемые значения, коды ошибок, примеры вызова, ограничения частоты и квоты | Отсутствие кодов ошибок |
| 11 | Структура каталогов | Древовидная структура и описание обязанностей каждого уровня | Пофайловый перечень без пояснений |
| 12 | Показатели производительности | Среда тестирования, методика тестирования, данные метрик, анализ узких мест, рекомендации по оптимизации | Цифры без условий тестирования |
| 13 | Безопасность и приватность | Сбор и хранение данных, шифрование при передаче, модель прав доступа, канал сообщения об уязвимостях, известные риски | Обещание абсолютной безопасности |
| 14 | Описание совместимости | Матрица версий операционных систем, сред выполнения, браузеров, баз данных с явным указанием неподдерживаемых позиций | Нечёткие формулировки |
| 15 | Известные проблемы и ограничения | Известные проблемы (описание, область влияния, временное решение обхода, ссылка на отслеживание), текущие ограничения, перечень нереализованных функций (функция, причина нереализованности, статус плана) | Сокрытие серьёзных дефектов; описание нереализованных функций как реализованных |
| 16 | Журнал изменений | Структура по Keep a Changelog, номера версий по семантическому версионированию | Пункты без даты |
| 17 | Дальнейшая дорожная карта | Планируемые пункты, статус, целевая версия с пометкой «не обязательство» | Обещание сроков поставки |
| 18 | Участие в разработке | Настройка среды разработки, модель ветвления, правила коммитов, требования к PR, кодекс поведения, шаблон Issue | Только фраза «PR приветствуются» |
| 19 | Авторские права и лицензия | Строка об авторских правах, название лицензии, идентификатор SPDX, место полного текста лицензии | Отсутствие правообладателя |
| 20 | Заявление о соответствии NOTICE | Выжимка по сторонним зависимостям, относительная ссылка на файл NOTICE | Замена NOTICE данным разделом |

## 1.1 Четыре вопроса первого экрана и текст в одну фразу

Первый экран README должен отвечать на четыре вопроса в фиксированном порядке:

1. что делает проект;
2. какую проблему решает проект;
3. какие особенности есть у проекта;
4. минимальный пример hello world.

При этом вопрос 1 соответствует «позиционированию в одну фразу», которое должно одновременно удовлетворять трём условиям: указывать тип проекта, иметь точные определения, допускать прямое воспроизведение. В качестве ориентира можно использовать публичные тексты зрелых проектов:

| Проект | Текст в одну фразу | Разбор структуры |
| --- | --- | --- |
| Angular | One framework. Mobile & desktop. | Категория + охват |
| React | A declarative, efficient, and flexible JavaScript library for building user interfaces. | Три определения + категория + назначение |
| Vue | A progressive, incrementally-adoptable JavaScript framework for building UI on the web. | Две особенности + категория + назначение |

Ограничения формулировки:

- не использовать лишённые информации прилагательные вроде «мощный», «превосходный», «революционный»;
- следует указывать слово категории (библиотека, фреймворк, инструмент, приложение), чтобы читатель сразу относил проект к классу;
- определений особенностей — не более трёх, чтобы избежать нагромождения;
- китайская версия должна укладываться в 60 иероглифов, английская — в 25 слов.

Вопрос 3 «какие особенности» должен одновременно раскрывать неприменимые сценарии. Пример действенной формулировки: указать, что некий брокер сообщений «поддерживает только уровень QoS 0, сценарии, требующие уровня 1, неприменимы»; недейственная формулировка — перечисление только достоинств. Сравнение особенностей должно опираться на проверяемые факты и не должно принижать аналогичные проекты.

Пример hello world из вопроса 4 должен обеспечивать установку и запуск за два шага; проекты со сложной установкой должны предоставлять контейнерный образ или онлайн-демонстрационную среду, чтобы читатель не отказался от проекта после прочтения README.
