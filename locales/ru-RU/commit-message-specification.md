# Спецификация сообщений коммитов

> Какую задачу решает этот файл: определяет поля, формат, указания по заполнению и примеры Conventional Commits, обеспечивая читаемость истории и автоматическую генерацию журнала изменений и номера версии.

## 1. Формат

```text
<тип>[необязательная область][необязательный !]: <описание>

[необязательное тело]

[необязательная сноска]
```

## 2. Типы

Полный набор из десяти типов приведён ниже и охватывает сценарии коммитов типовых открытых проектов:

| Тип | Значение |
| --- | --- |
| `feat` | Новая функциональность |
| `fix` | Исправление дефекта |
| `docs` | Изменение документации |
| `style` | Корректировка форматирования без изменения логики (пробелы, форматирование, отсутствующая точка с запятой и т. п.) |
| `refactor` | Рефакторинг, не добавляющий функциональность и не исправляющий дефекты |
| `perf` | Изменение кода с оптимизацией производительности |
| `test` | Добавление недостающих тестов или исправление существующих |
| `build` | Изменение, затрагивающее систему сборки или внешние зависимости (например, npm, gulp) |
| `ci` | Изменение конфигурации и скриптов непрерывной интеграции (например, GitHub Actions, CircleCI) |
| `chore` | Прочие задачи: сборка, зависимости, инструментальная цепочка |

### 2.1 Сопоставление и выбор командных форматов записи

При разных моделях совместной работы встречаются три типовых формата записи; проект должен выбрать один при инициации и применять его всей командой:

| Формат записи | Формат | Применимость | Ограничение |
| --- | --- | --- | --- |
| Рабочий формат | `[номер задачи] автор: содержание изменения` | Команды, использующие канбан и парное программирование | Зависит от системы номеров задач, без номера не применим |
| Обычный формат | `[категория] компонент (необязательно): содержание изменения` | Команды, которым нужна фильтрация истории по бизнес-модулям | Требует согласованной таблицы категорий, несёт дополнительные издержки |
| Открытый формат | `<type>(<scope>): <subject>` | Открытые библиотеки и приложения с автогенерацией CHANGELOG | Много типов и областей, выше затраты на освоение |

В данном проекте единообразно применяется открытый формат (то есть Conventional Commits) по причине машиночитаемости и возможности автоматической генерации журнала изменений и номера версии. Рабочий и обычный форматы используются только в закрытых командах по договорённости и не должны попадать во внешние репозитории.

## 3. Определение полей

| Поле | Обязательно | Тип | Ключевые моменты заполнения | Пример |
| --- | --- | --- | --- | --- |
| Тип | Да | Перечисление | Один из десяти, самостоятельное изобретение запрещено | `feat` |
| Область | Нет | Текст | Имя модуля, короткое слово в нижнем регистре, без пробелов | `parser` |
| Метка несовместимости | Нет | `!` | Ставится после типа или области, перед двоеточием | `feat!:` |
| Описание | Да | Текст | Повелительное наклонение, начало со строчной буквы, ≤72 символов, без точки в конце | `add TOML config support` |
| Тело | Нет | Текст | Объясняет мотив и реализацию, отделяется от описания пустой строкой | `Allow the parser to read TOML...` |
| Сноска | Нет | Текст | `BREAKING CHANGE:` или `Refs: #N` | `BREAKING CHANGE: ...` |
| Связанное требование | Нет | `REQ-NNN` | Записывается в тело или сноску для прослеживаемости | `Refs: REQ-001` |

## 4. Указания по заполнению

1. **Описание**: используется повелительное наклонение (add, fix, remove), пишется «что сделано», а не «внесены изменения»; в китайском проекте допускается описание на китайском, но оно должно быть единообразным во всём репозитории.
2. **Область**: берётся имя модуля, а не имя файла; для межмодульных изменений область опускается, `all` и `global` не пишутся.
3. **Тело**: пишется только когда описания недостаточно для объяснения мотива; описание не пересказывается, хронология процесса не приводится.
4. **Несовместимое изменение**: `feat!:` / `fix!:` и сноска `BREAKING CHANGE:` применяются по выбору или совместно; при их наличии необходимо одновременно внести запись в [спецификацию журнала изменений](./changelog-specification.md) и [спецификацию руководства по миграции](./migration-guide-specification.md).
5. **Атомарность**: один коммит делает только одно дело; форматирование и изменение логики выполняются двумя коммитами.
6. **Безопасность**: запрещается включать ключи, токены, персональные данные, внутренние адреса; перед коммитом выполняется сверка сканированием ключей (см. [спецификацию безопасности и приватности](./security-and-privacy-specification.md)).
7. **Связь с версией**: `feat` вызывает инкремент минорной версии, `fix` — инкремент патч-версии, `BREAKING CHANGE` — инкремент мажорной версии, подробнее см. [спецификацию управления версиями](./version-management-specification.md).

Типичные ошибки:

| Ошибочная запись | Проблема | Способ исправления |
| --- | --- | --- |
| `wip`, `update`, `fix bug` | Неинформативно, нарушает H10 | Указать объект и действие |
| `feat: Added new feature.` | Не повелительное наклонение, заглавная буква, точка | `feat: add config loader` |
| `feat(全部): 优化` | Область недопустима, описание расплывчато | Указать конкретное имя модуля и суть изменения |
| Один коммит содержит форматирование и изменение функциональности | Нарушает атомарность | Разделить на два коммита `style:` и `feat:` |
| Сообщение коммита содержит внутренний адрес | Утечка информации | Удалить и выполнить сканирование ключей |

## 5. Полный пример

```text
feat(parser): add support for TOML config

Allow the parser to read TOML configuration files in addition to YAML.
Refs: REQ-001

BREAKING CHANGE: the `config` option now accepts a file path instead of an object.
```

Значение полей: `feat` — тип, `parser` — область, после двоеточия — краткое описание; тело объясняет мотив и реализацию, сноска связывает требование; завершающая сноска объявляет несовместимое изменение и указывает направление миграции.

Пример исправления:

```text
fix(spacing): avoid false positives before Chinese punctuation

The spacing rule previously flagged strings such as 「使用Node.js，」 because
the punctuation check ran after whitespace normalization.

Refs: REQ-004, #142
```
