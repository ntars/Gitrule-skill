# Шаблон руководства по участию

> Какую задачу решает этот файл: предлагает готовое к копированию руководство по участию, по которому проект создаёт CONTRIBUTING.md, охватывая способы участия, настройку окружения, модель ветвления, соглашение о коммитах, требования к PR, требования к тестам, кодекс поведения и заявление о лицензии; сопутствующие указания по заполнению описывают адаптацию для проектов разных типов.

## 1. Указания по использованию

1. Скопировать всё содержимое раздела 3 «Текст шаблона» и создать в корне проекта файл `CONTRIBUTING.md`.
2. Заменить заполнители согласно разделу 4; все команды должны быть реальными и выполняться напрямую.
3. Адаптировать по сценариям раздела 5: в проектах типа документации удалить абзац с командами тестов, сохранив процесс Issue и PR.
4. Основания правил см. в [спецификации руководства по участию](./contribution-guide-specification.md); детали ветвления и коммитов — в [спецификации рабочего процесса Git и ветвления](./git-workflow-and-branching-specification.md) и [спецификации сообщений коммитов](./commit-message-specification.md) соответственно.

## 2. Принципы настройки

- **Исполнимость**: в командах указываются полный рабочий каталог и предварительные условия по зависимостям; запрещено писать только «установить зависимости» без конкретной команды.
- **Наличие условия запуска**: для каждого шага указывается, когда он выполняется и какой результат ожидается.
- **Отсутствие общих слов**: запрещено писать только «PR приветствуются» без содержательного процесса, что соответствует проверке управления сообществом в [контрольной точке качества](./quality-gate.md).
- **Ссылка вместо копирования**: правила коммитов и тестов даются ссылкой на соответствующую спецификацию, полный текст в настоящем файле не дублируется.

````markdown

> Настоящий файл описывает, как принять участие в проекте {{项目名称}}, и предназначен для внешних контрибьюторов и тех, кто участвует впервые.

## Модель ветвления

- От ветки {{基准分支}} создаётся личная ветка по формату имени `{{分支命名格式}}` (например, `feat/короткое-описание`).
- Каждый PR решает одну задачу; при слишком большом объёме изменений их следует разделить.
- Прямой коммит в {{受保护分支}} запрещён, слияние выполняется только через PR.

## Соглашение о коммитах

Сообщения коммитов следуют Conventional Commits в формате `type(scope): subject`. Частые типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`. Пример:

```text
feat(cli): add config file support
```

Полные правила см. в [спецификации сообщений коммитов]({{提交规范链接}}).

## Требования к PR

Перед отправкой PR следует выполнить самопроверку:

- [ ] Объём изменений единый, есть соответствующее issue или пояснение.
- [ ] Сообщение коммита соответствует указанному формату.
- [ ] Локальный запуск `{{测试命令}}` проходит полностью.
- [ ] Документация обновлена вместе с кодом.
- [ ] Не добавлены ключи, приватные ключи или чувствительная информация.
- [ ] В описании указаны содержание изменений, причина и способ проверки.

| Статический анализ | `{{lint 命令}}` | Отсутствие ошибок |
| Проверка сборки | `{{构建命令}}` | Успешная сборка |

Порог покрытия: {{覆盖率要求}}.

## Кодекс поведения

Участие в проекте означает согласие соблюдать [кодекс поведения](./CODE_OF_CONDUCT.md).

## Соглашение об Issue

- Перед вопросом следует проверить существующие issue, чтобы избежать дублирования.
- Отчёт о дефекте должен содержать: сведения об окружении, шаги воспроизведения, ожидаемый результат, фактический результат, журнал ошибок.
- Предложение функции должно описывать сценарий использования и альтернативу при отказе от неё.

## Заявление о лицензии

Вклад по умолчанию распространяется по лицензии проекта {{许可证名称及 SPDX 标识符}}, полный текст см. в [LICENSE](./LICENSE). Отправка изменений означает, что вы вправе предоставить свой вклад по этой лицензии.
````

## 5. Указания по заполнению и вариации сценариев

| Сценарий | Обязательные разделы | Разделы, которые можно сократить | Ключевые моменты настройки |
| --- | --- | --- | --- |
| Проект с кодом | Все | Нет | Команды должны фактически выполняться и проходить проверку |
| Проект документации | Способы участия, требования к PR, кодекс поведения, лицензия | Требования к тестам, настройка среды разработки | Удалить таблицу тестов, сохранить самопроверку PR |
| Личный проект | Способы участия, требования к PR, кодекс поведения, лицензия | Настройку окружения можно сократить | Явно указать, принимается ли внешний вклад |
| Корпоративный проект | Все | Нет | Добавить ссылку на соглашение с контрибьюторами (CLA) и юридические требования |

Сопоставление типичных ошибок:

| Ошибочная формулировка | Последствие | Правильная формулировка |
| --- | --- | --- |
| «Любой вклад приветствуется» | Нет конкретного пути, контрибьютор не знает, с чего начать | Привести таблицу способов участия и точек входа |
| «Достаточно запустить тесты» | Неизвестны команда и критерий прохождения | Указать команду, критерий прохождения и порог покрытия |
| Команда указана как `npm install`, хотя проект использует pnpm | Команда не выполняется | Привести в соответствие с фактическим lockfile |

## 6. Полный пример

Ниже приведён заполненный пример абзаца с командами, только как образец формата.

```bash
# Клонирование репозитория
git clone https://github.com/owner/repo.git
cd repo

# Установка зависимостей
pnpm install

# Локальный запуск
pnpm dev
```

Ожидаемый результат: при открытии localhost:3000 отображается главная страница.
