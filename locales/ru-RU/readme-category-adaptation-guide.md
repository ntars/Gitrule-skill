# Руководство по адаптации README к категориям

> Какую задачу решает этот файл: для разных типов проектов — библиотек, приложений, инструментов командной строки, фреймворков, подборок ресурсов — приводит дифференцированные рекомендации по составу разделов README, визуальным акцентам и настройке бейджей, а также объясняет, как каждый тип элементов повышает эстетичность и привлекательность.

Универсальный шаблон применим ко всем проектам, однако у читателей разных типов проектов разные приоритеты. Данный файл поверх общих правил даёт рекомендации по настройке под тип проекта. Читателю следует взять за основу [стандартный шаблон README](./readme-standard-template.md) и урезать его согласно соответствующему типу из данного файла.

## 1. Обзор типов

| Тип | Первоочередной вопрос читателя | Акцент главной страницы | Обязательные разделы | Разделы, которые можно опустить |
| --- | --- | --- | --- | --- |
| Библиотека / SDK | Способ установки и использование API | Версия и лицензия | Установка, быстрый старт, API, совместимость | Развёртывание, скриншоты |
| Приложение | Внешний вид и ключевые функции приложения | Скриншоты и функции | Функции, скриншоты, установка, быстрый старт | Справочник API |
| Инструмент командной строки | Использование команд и производительность | Примеры команд и демонстрация | Установка, использование, сопоставление команд, демонстрация | Архитектура, конфигурация (при малом объёме) |
| Фреймворк | Экосистема и стоимость освоения | Вход в документацию и примеры | Позиционирование, быстрый старт, документация, сообщество | Детали производительности (можно вынести по ссылке) |
| Подборка ресурсов | Что включено, как искать | Классификация каталога и навигация | Каталог, классификация, руководство по вкладу | Установка, API |

## 2. Библиотека / SDK

Типичные представители: HTTP-клиенты вроде axios, библиотеки служебных функций, клиентские SDK.

### 2.1 Состав разделов

- В начале — «одна фраза о позиционировании + версия + лицензия», по ним читатель судит о совместимости.
- «Установка» размещается первой, с командами пакетных менеджеров (npm, pip, cargo и т. п.).
- «Быстрый старт» должен быть полным примером, который можно запустить отдельно.
- «Справочник API» подробно излагается в основном README либо выносится ссылкой в `docs/api.md`; при чрезмерном числе элементов API README содержит только выжимку и ссылку.
- «Совместимость» описывает поддерживаемые версии языка, среду выполнения, платформы.

### 2.2 Визуальные акценты

- Ключевые бейджи: версия, статус сборки, лицензия, число загрузок, размер пакета.
- Изображения используются сдержанно, скриншоты обычно не нужны; небольшой логотип помогает сформировать узнаваемость.
- Параметры API оформляются таблицей для повышения читаемости.

### 2.3 Приёмы повышения эстетичности

1. Бейджи версии и лицензии размещаются вверху и мгновенно формируют доверие.
2. Блок кода быстрого старта располагается рядом с первым экраном, снижая порог пробы.
3. В таблицах API выравниваются ширина столбцов и столбец значений по умолчанию, что уменьшает когнитивную нагрузку.

## 3. Приложение

Типичные представители: редакторы, настольные инструменты, продукты для конечных пользователей.

### 3.1 Состав разделов

- Первый экран должен содержать скриншот продукта или кадр работы: сначала демонстрируется ценность, затем реализация.
- «Ключевые функции» организуются по пользовательским сценариям, а не по техническим модулям.
- «Установка» охватывает установочные пакеты или точки загрузки для каждой платформы.
- «Быстрый старт» даёт кратчайший путь входа.
- Инструкции по сборке из исходного кода могут быть вынесены ссылкой в `CONTRIBUTING.md`.

### 3.2 Визуальные акценты

- Ключевые бейджи: версия, статус сборки, лицензия, число загрузок.
- Скриншот размещается после позиционирования и является ключевым элементом главной страницы.
- Список функций сопровождается иконками или короткими скриншотами, что ускоряет просмотр.

### 3.3 Приёмы повышения эстетичности

1. Качественный скриншот продукта показывается по центру с адаптацией к светлой и тёмной темам.
2. Пункты функций оформляются короткими фразами с иконками, без длинных описаний.
3. Точка загрузки заметна и оформлена ссылкой-кнопкой.

## 4. Инструмент командной строки

Типичные представители: терминальные инструменты вроде fd, ripgrep.

### 4.1 Состав разделов

- После «одной фразы о позиционировании» сразу идёт навигация по разделам для удобных переходов.
- «Установка» перечисляет основные пакетные менеджеры и бинарные сборки для платформ.
- «Использование» ориентировано на задачи и приводит примеры частых команд.
- «Сопоставление команд» или «Сравнение с аналогичными инструментами» — частая потребность.
- «Демонстрация» показывает реальный результат через GIF или запись терминала.
- Данные о производительности должны сопровождаться указанием среды и методики тестирования.

### 4.2 Визуальные акценты

- Ключевые бейджи: версия, статус сборки, поддержка платформ, лицензия.
- Анимированная демонстрация — ключевой визуальный актив, показывающий скорость и удобство работы.
- Команды оформляются блоками кода с языковой разметкой, вывод — блоком `text`.

### 4.3 Приёмы повышения эстетичности

1. Примеры команд размещаются вверху: читатель может скопировать их без прокрутки.
2. Анимированная демонстрация показывает реальную работу терминала и усиливает впечатление «быстроты».
3. Ссылки на языковые версии (например, на китайский или корейский перевод) размещаются рядом со строкой бейджей.

## 5. Фреймворк

Типичные представители: полнофункциональные фреймворки вроде next.js.

### 5.1 Состав разделов

- Первый экран подчёркивает позиционирование, масштаб экосистемы и точку входа в обучение.
- Точка входа в «Документацию» должна быть заметной и обычно ведёт на отдельный сайт документации.
- «Сообщество» описывает площадки обсуждений, каналы мгновенных сообщений и кодекс поведения.
- «Быстрый старт» даёт минимальную команду создания проекта.
- Глубокое содержание (архитектура, API) выносится ссылкой и не раскрывается в README.

### 5.2 Визуальные акценты

- Ключевые бейджи: версия, статус сборки, лицензия, каналы сообщества.
- Брендовый логотип в сочетании с бейджами в стиле `for-the-badge` усиливает главную страницу.
- Для демонстрации экосистемных кейсов можно использовать скриншоты Showcase.

### 5.3 Приёмы повышения эстетичности

1. Логотип по центру и крупные бейджи в едином стиле формируют брендированный первый экран.
2. Точки входа в документацию и сообщество оформляются заметными навигационными блоками.
3. Точки входа для новичков вроде Good First Issues снижают порог вклада.

## 6. Подборка ресурсов

Типичные представители: списки серии awesome.

### 6.1 Состав разделов

- Открывать первый экран логотипом и информацией о спонсорах — распространённая практика.
- Основной текст организует каталог по тематическим категориям и обеспечивает ясную навигацию.
- «Руководство по вкладу» описывает критерии включения и формат подачи.
- Разделы установки, API и развёртывания не нужны.

### 6.2 Визуальные акценты

- Число бейджей можно не ограничивать, но стиль должен быть единым.
- Классификация каталога оформляется заголовками второго уровня и списками, пункты сопровождаются краткими пояснениями.
- Логотипы спонсоров располагаются таблицей или сеткой с сохранением выравнивания.

### 6.3 Приёмы повышения эстетичности

1. Структура каталога ясна, уровни заголовков категорий единообразны.
2. Каждый пункт сопровождается пояснением в одну фразу, а не только ссылкой.
3. Области спонсорства и благодарностей выровнены и аккуратны и не мешают чтению основного текста.

## 7. Общие принципы для всех типов

1. **Приоритет читателя**: первый экран отвечает на самый важный для читателя вопрос; различия типов влияют только на порядок, но не на полноту информации.
2. **Единый стиль**: бейджи, заголовки и блоки кода одного проекта должны быть согласованы.
3. **Воспроизводимые примеры**: любой тип содержит хотя бы один пример, который можно запустить напрямую.
4. **Внешние ссылки**: содержание, выходящее за рамки обязанностей главной страницы, выносится ссылкой в отдельную документацию.
5. **Постоянная синхронизация**: скриншоты, бейджи версий и список функций должны обновляться вместе с версией, чтобы устаревшая информация не подрывала доверие.
