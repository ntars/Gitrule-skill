# Спецификация визуальной вёрстки README

> Какую задачу решает этот файл: определяет уровни вёрстки README, организацию абзацев, сценарии использования и размещения таблиц, скриншотов и GIF, чтобы документация находила баланс между информационной плотностью и визуальной привлекательностью.

Приведённые в данном файле «измеренные» данные получены в результате выборочной статистики README ведущих открытых проектов, проведённой в рамках данного проекта (выборка N=120); эталонные практики взяты из анализа структуры первого экрана нескольких проектов с большим числом звёзд.

## 1. Уровни вёрстки

### 1.1 Уровни заголовков

README должен выстраивать ясную иерархию заголовков, соблюдая следующие ограничения:

1. Во всём тексте сохраняется только один заголовок первого уровня (`#`) — название проекта, в первой строке файла.
2. Заголовки второго уровня (`##`) — основные разделы, их количество целесообразно в пределах 6–12; измеренная медиана — 7.
3. Заголовки третьего уровня (`###`) используются для детализации внутри раздела, только когда содержание заголовка второго уровня велико.
4. Пропуск уровней заголовков не допускается (например, от `#` сразу к `###`).
5. Текст заголовка краток, используется существительное или именная группа, точка в конце не ставится.

### 1.2 Порядок структуры первого экрана

Первый экран — это содержание, видимое читателю без прокрутки; оно организуется в следующем порядке:

1. логотип по центру или баннер проекта (опционально);
2. заголовок первого уровня (название проекта);
3. строка бейджей (подробнее в [спецификации бейджей](./badge-specification.md));
4. позиционирование в одну фразу (что за проект, для кого, какую проблему решает);
5. строка навигационных ссылок по разделам (опционально, для длинных README);
6. краткое изложение ключевых функций или особенностей.

Эталонные примеры: в `fd` и `ripgrep` сразу после позиционирования идёт навигация по разделам; `next.js` и `rust-lang/rust` открываются логотипом по центру и баннером; `vscode` сразу после позиционирования вставляет скриншот продукта.

### 1.3 Абзацы и пробелы

- Каждый абзац укладывается в 1–4 строки, плотные блоки текста не допускаются.
- Между абзацами оставляется пустая строка, чтобы сохранить «воздух» после рендеринга.
- Ключевой вывод ставится вперёд, пояснение — после.
- Между китайским и английским текстом, а также между текстом и цифрами сохраняется один пробел; знаки препинания китайского и английского текста используются по контексту.

## 2. Правила использования таблиц

### 2.1 Сценарии использования

Таблицы подходят для многомерной, сопоставимой информации. По измеренным данным 36.7% выборки используют таблицы; это рекомендуемая форма для описания конфигурации, матрицы совместимости, сопоставления команд. Применимые сценарии включают:

- описание параметров конфигурации (имя ключа, тип, значение по умолчанию, назначение);
- матрицу совместимости платформ и версий;
- сопоставление команд или параметров;
- сравнение функций (данный проект и другие решения);
- дорожную карту и статусы.

### 2.2 Размещение

Таблица идёт сразу после соответствующего заголовка второго уровня, перед ней ставится вводная фраза о назначении таблицы; если после таблицы есть исключения, они дополняются отдельным абзацем.

### 2.3 Требования к оформлению

| Требование | Пояснение |
| --- | --- |
| Контроль числа столбцов | 3–6 столбцов, при превышении 6 столбцов рассматривается разделение |
| Ясный заголовок | Для каждого столбца даётся краткий заголовок-существительное, пустые заголовки не допускаются |
| Единое выравнивание | Способ выравнивания таблиц един во всём тексте |
| Краткое содержание | В ячейке не пишется длинный абзац, при необходимости используются сноски или ссылки |
| Без пустых ячеек | При отсутствии содержания указывается «нет» или «неприменимо» |

## 3. Правила использования блоков кода

### 3.1 Сценарии использования

Блоки кода используются для команд, конфигурации, вызовов API и примеров вывода. По измеренным данным 66.7% выборки содержат блоки кода; это обязательный элемент раздела «Быстрый старт», медиана — 2 блока.

### 3.2 Требования к оформлению

1. Каждый блок кода должен иметь языковую разметку, например `bash`, `json`, `python`, `javascript`, для подсветки синтаксиса.
2. В примере команды приводится полная исполнимая команда, предварительные шаги не опускаются.
3. При необходимости показать результат создаётся отдельный блок кода с разметкой `text`, а в тексте поясняется ожидаемый вывод.
4. Перед блоком кода и после него оставляется по одной пустой строке.
5. Содержание одного блока укладывается в 20 строк; слишком длинный пример разделяется на несколько блоков или переносится в каталог `examples/` со ссылкой.
6. Если в интерактивных командах используется приглашение `$`, это соблюдается единообразно во всём тексте.

Пример оформления:

```bash
npm install <package-name>
```

```text
✓ Installation complete
```

## 4. Правила использования скриншотов и GIF

### 4.1 Сценарии использования и выбор

| Элемент | Применимые сценарии | Замечания |
| --- | --- | --- |
| Статичный скриншот | Интерфейс приложения, результат работы, диаграммы | Измеренная частота использования 63.3%, самый распространённый |
| GIF / анимация | Демонстрация командной строки, интерактивные сценарии, сравнение «до и после» | Большой размер файла, требуется сжатие и контроль длительности |
| Логотип / баннер | Идентификация бренда, первый экран главной страницы | Предоставляются две версии — для светлой и тёмной темы |
| Схема | Архитектура, процессы, потоки данных | Должна обновляться синхронно с версией документа |

По измеренным данным 63.3% выборки содержат изображения. Эталонные примеры: `fd` использует `doc/screencast.svg` в качестве демонстрации, `ripgrep` — скриншот результатов поиска, `vscode` — скриншот работы продукта, `rust` и `next.js` — баннер-логотип с адаптацией к светлой и тёмной теме.

### 4.2 Размещение

1. Логотип / баннер: в самом верху файла, по центру.
2. Скриншот продукта: после позиционирования в одну фразу и до «Быстрого старта», для формирования наглядного представления.
3. GIF-демонстрация: отдельный раздел «Demo / Демонстрация» сразу после «Ключевых функций».
4. Схема архитектуры: в раздел «Архитектура» или «Проектирование» либо в `docs/architecture.md` со ссылкой из README.

### 4.3 Требования к оформлению

- Каждое изображение должно иметь `alt`-текст, описывающий содержание кадра; бессмысленный текст вроде `image` или `скриншот` не допускается.
- Изображения ссылаются на ресурсы репозитория по относительному пути либо по стабильному абсолютному URL; временные ссылки с ограниченным сроком действия следует избегать.
- Для изображений с адаптацией к теме используется HTML `<picture>` вместе с `prefers-color-scheme`, предоставляя две версии — для светлой и тёмной темы.
- Размер изображений контролируется: для скриншотов предпочтительны WebP или оптимизированный PNG, GIF лучше преобразовывать в короткое видео или сжатое анимированное изображение.
- Ширина изображения адаптируется: используется атрибут `width` или ограничение внешнего контейнера, чтобы не разорвать страницу.

## 5. Ссылки и навигация

### 5.1 Навигация по разделам

Если README длиннее 200 строк, на первый экран добавляется строка навигационных ссылок, ведущих к основным разделам:

```markdown
[Установка](#установка) · [Быстрый старт](#быстрый-старт) · [Документация](#документация) · [Участие в разработке](#участие-в-разработке)
```

### 5.2 Приоритет относительных ссылок

Документы, изображения и лицензия внутри репозитория всегда указываются относительным путём, чтобы они оставались доступны при форке и офлайн-чтении. Внешние ссылки должны вести на авторитетные источники (официальная документация, страница пакетного менеджера, страница CI).

## 6. Практический перечень для эстетичности и привлекательности

1. Первый экран содержит логотип или ясный заголовок и передаёт позиционирование проекта за 3 секунды.
2. Бейджи единообразны по стилю, семантической цветовой схеме и умеренны по количеству.
3. Заголовок первого уровня единственный, заголовков второго уровня 6–12, уровни без пропусков.
4. Имеется хотя бы один пример кода, который можно скопировать и запустить.
5. Имеется хотя бы один скриншот или демонстрация, отражающая ценность продукта.
6. Таблицы применяются для сопоставимой информации, число столбцов ограничено, заголовки ясны.
7. Все изображения имеют `alt`, все блоки кода имеют языковую разметку.
8. Длинный документ имеет навигацию по разделам.
9. Изображения и бейджи читаемы в светлой и тёмной темах.
