# Спецификация документов архитектуры

> Какую задачу решает этот файл: определяет шаблоны, поля и правила написания документов архитектуры и записей архитектурных решений (ADR), описывая границы системы, ответственность модулей, атрибуты качества и ключевые компромиссы, а также обеспечивая прослеживаемость решений.

## 1. Положения спецификации

1. Документ архитектуры (`docs/architecture.md`) описывает только структуру и границы и не содержит примеров использования; границы ответственности см. в [матрице документации](./document-matrix.md).
2. Каждое значимое техническое решение должно иметь соответствующий ADR; решение без ADR считается незафиксированным.
3. Нумерация ADR непрерывна и неизменна навсегда; после принятия история не переписывается, изменение статуса фиксируется новым ADR с пометкой «заменено».
4. Описание архитектуры должно соответствовать реализации в коде; при расхождении кода и документации приоритет имеет код, а документация немедленно исправляется.
5. Каждое архитектурное решение должно прослеживаться к одному или нескольким требованиям, прослеживаемость см. в [спецификации матрицы прослеживаемости требований](./requirements-traceability-matrix-specification.md).
6. Для атрибутов качества должны приводиться проверяемые целевые показатели; записывать только «высокая производительность» или «высокая доступность» запрещено.

## 2. Шаблон документа архитектуры

```markdown
# Архитектурное проектирование: {{项目名称}}

Версия документа: {{v1.0}} ｜ Соответствующая версия кода: {{tag}} ｜ Дата последней сверки: {{YYYY-MM-DD}}

## Системный контекст
- Ответственность системы: {{一句话说明系统边界内的责任}}
- Внешние участники: {{用户、上游系统、下游系统}}
- Входы и выходы: {{进入系统的请求与系统产出的结果}}
- За пределами границ: {{明确不由本系统承担的职责}}

## Разделение на модули
| Модуль | Единственная ответственность | Внешний интерфейс | Зависимые модули | Не отвечает за |
| --- | --- | --- | --- | --- |
| {{模块名}} | {{仅一件事}} | {{接口名}} | {{模块名}} | {{明确排除}} |

## Ключевые потоки данных
1. {{触发点}} → {{模块 A}}: {{传递的数据}}
2. {{模块 A}} → {{模块 B}}: {{转换与传递}}
3. {{模块 B}} → {{结果}}: {{最终产出}}

## Выбор технологий
| Область | Выбор | Альтернатива | Основание решения | ADR |
| --- | --- | --- | --- | --- |
| {{语言 / 框架 / 存储}} | {{采用项}} | {{未采用项}} | {{取舍理由}} | {{ADR-000N}} |

## Атрибуты качества
| Атрибут | Целевое значение | Способ проверки | Связанный ADR |
| --- | --- | --- | --- |
| Производительность | {{P95 延迟 < X ms}} | {{压测方式}} | {{ADR-000N}} |
| Доступность | {{月度可用性 ≥ X%}} | {{监控统计}} | {{ADR-000N}} |
| Безопасность | {{敏感数据零明文落盘}} | {{审计方式}} | {{ADR-000N}} |
| Масштабируемость | {{横向扩容至 N 节点无需改代码}} | {{扩容演练}} | {{ADR-000N}} |

## Ограничения и компромиссы
- Технические ограничения: {{语言版本、平台、兼容性}}
- Отклонённые варианты и причины: {{方案 A：原因}}
- Известный технический долг: {{债务项与偿还条件}}
```

## 3. Шаблон ADR

```markdown
# ADR-{{四位序号}}: {{决策标题}}

- Статус: {{提议 / 已采纳 / 已废弃 / 被 ADR-000N 替代}}
- Дата: {{YYYY-MM-DD}}
- Ответственный за решение: {{姓名}}
- Связанные требования: {{REQ-001 / …}}

## Контекст
{{面临的客观问题与约束，须可验证，不写主观偏好}}

## Решение
{{采用的方案，一句话陈述，须明确到可执行的程度}}

## Альтернативные варианты
| Вариант | Преимущества | Недостатки | Причина отклонения |
| --- | --- | --- | --- |
| {{方案 A}} | | | |
| {{方案 B（采用）}} | | | — |

## Последствия
- Положительные: {{获得的能力}}
- Отрицательные: {{引入的成本或限制}}
- Последующие задачи: {{需要跟进的事项}}

## Связанные файлы
- {{架构文档中受影响的章节}}
- {{替代或被引用的 ADR}}
```

## 4. Определение полей

### 4.1 Поля документа архитектуры

| Поле | Обязательно | Тип | Ключевые моменты заполнения | Пример |
| --- | --- | --- | --- | --- |
| Соответствующая версия кода | Да | tag | Совпадает с тегом [спецификации управления версиями](./version-management-specification.md) | `v1.2.0` |
| Дата последней сверки | Да | Дата | Обновляется после каждого изменения кода | `2026-11-18` |
| Единственная ответственность модуля | Да | Текст | Для одного модуля указывается только одно дело | `解析并校验 Markdown 规则` |
| Не отвечает за | Да | Текст | Явные границы предотвращают расползание ответственности | `不负责文本改写` |
| Выбор технологий.Основание решения | Да | Текст | Должен ссылаться на номер ADR | `见 ADR-0002` |
| Атрибуты качества.Целевое значение | Да | Метрика | С единицей и порогом, проверяемое | `P95 < 150ms` |
| Известный технический долг | Нет | Список | С условием запуска погашения | `待 v2 替换解析器` |

### 4.2 Поля ADR

| Поле | Обязательно | Тип | Ключевые моменты заполнения | Пример |
| --- | --- | --- | --- | --- |
| Номер | Да | `ADR-NNNN` | Четырёхзначный порядковый номер, непрерывный и неизменный навсегда | `ADR-0002` |
| Статус | Да | Перечисление | Предложено / Принято / Устарело / Заменено | `已采纳` |
| Связанные требования | Да | Список | Номера REQ из документа инициации проекта | `REQ-001` |
| Контекст | Да | Текст | Изложение объективных ограничений, «мне кажется» запрещено | `需兼容 Node 18` |
| Решение | Да | Текст | Одно предложение, исполнимое | `采用 remark 作为解析器` |
| Альтернативные варианты | Да | Таблица | Не менее 1 отклонённого варианта | См. шаблон |
| Причина отклонения | Да | Текст | Приводится для каждого отклонённого варианта | См. шаблон |
| Последствия | Да | Список | Все три пункта: положительные, отрицательные, последующие задачи | См. шаблон |

## 5. Указания по заполнению

1. **Разделение на модули**: если в «единственной ответственности» строки двумя делами соединяются «и» либо «а также», модуль следует разделить на два.
2. **Потоки данных**: нумеруются в хронологическом порядке с указанием передаваемых данных; запись только имён модулей со стрелками запрещена.
3. **Атрибуты качества**: каждый должен иметь целевое значение, способ проверки и ссылку на ADR; отсутствие любого из них считается неполнотой.
4. **Контекст ADR**: описываются проблема и ограничения, а не само решение; решение появляется только один раз в разделе «Решение».
5. **Альтернативные варианты**: даже при единственном варианте следует указать «рассматривалась собственная реализация, отклонена из-за чрезмерных затрат на сопровождение»; отсутствие альтернатив считается недостаточной аргументацией.
6. **Изменение статуса**: основной текст исходного ADR не изменяется, создаётся новый ADR, а статус исходного меняется на «заменено ADR-000N».
7. **Технический долг**: указывается условие запуска погашения, перечисление только симптомов запрещено.

Типичные ошибки:

| Ошибочная запись | Проблема | Способ исправления |
| --- | --- | --- |
| В документе архитектуры размещены примеры вызова API | Дублирование ответственности с [спецификацией документации API](./api-documentation-specification.md) | Перенести в документацию API, в архитектуре оставить только имена интерфейсов |
| «Система должна быть высокопроизводительной» | Нет порога, непроверяемо | Указать целевой показатель задержки P95 и способ нагрузочного тестирования |
| В ADR только решение без альтернатив | Нет аргументации | Добавить не менее 1 отклонённого варианта и причину |
| Изменён основной текст принятого ADR | История переписана | Создать новый ADR с пометкой об отношении замены |
| Решение не связывается с требованием | Цепочка прослеживаемости разорвана | Добавить связанный номер REQ |

## 6. Полный пример

```markdown
# ADR-0002: принятие remark в качестве слоя разбора Markdown

- Статус: принято
- Дата: 2026-11-18
- Ответственный за решение: Ли Сы
- Связанные требования: REQ-001, REQ-004

## Контекст
Требуется поддержка GFM и позиционирования узлов китайского текста, а зависимости времени выполнения должны быть совместимы с Node 18; предел трудовых ресурсов команды на сопровождение парсера — 0.5 человеко-месяца в квартал.

## Решение
Экосистема remark принимается как единственный слой разбора Markdown, правила реализуются в виде плагинов.

## Альтернативные варианты
| Вариант | Преимущества | Недостатки | Причина отклонения |
| --- | --- | --- | --- |
| Собственный парсер | Полная управляемость | Требует долговременного сопровождения граничных случаев | Превышает предел трудовых ресурсов |
| marked | Лёгкий | Слабое позиционирование узлов китайского текста | Не удовлетворяет REQ-004 |

## Последствия
- Положительные: совместимость с GFM поддерживается вышестоящим проектом, позиционирование узлов удовлетворяет условиям приёмки.
- Отрицательные: изменение API плагинов требует отслеживания версий вышестоящего проекта.
- Последующие задачи: закрепить мажорную версию remark в CI и подписаться на уведомления о его релизах.
```
