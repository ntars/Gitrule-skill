# Спецификация инициации проекта и требований

> Какую задачу решает этот файл: определяет шаблоны и поля формулировки цели, сбора требований и определения границ на этапе инициации проекта, чтобы проект с самого начала имел ясную, проверяемую и прослеживаемую основу.

## 1. Положения спецификации

1. Документ инициации проекта должен отвечать на шесть вопросов: что это, зачем делается, в каком объёме выполняется, для кого не предназначено, кто им пользуется, чем ограничено.
2. Требования должны различаться по трём уровням «должен / следует / может»; соглашения о словоупотреблении см. в [общей спецификации письма](./general-writing-specification.md).
3. Каждое требование должно быть проверяемым: критерии приёмки приводятся в формате Given/When/Then либо указывается измеримый порог, допускающий однозначное решение.
4. Каждое требование должно иметь стабильный номер и источник; пункты требований без номера запрещены.
5. При недостатке информации ставится отметка «【Требует подтверждения: имя поля】», заполнение догадками не допускается; правила см. в [сборе информации и шаблонах](./information-collection-and-templates.md).
6. Границы должны содержать одновременно включаемые и исключаемые пункты; пустой перечень нецелей считается неопределёнными границами.
7. Изменения границ должны фиксировать причину, влияние и принимающего решение, а также вноситься в журнал изменений [спецификации матрицы прослеживаемости требований](./requirements-traceability-matrix-specification.md).

## 3. Шаблон пункта требования

```markdown
### REQ-{{三位序号}}: {{需求标题}}

- Источник: {{工单号 / 访谈 / 竞品 / 推测}}
- Приоритет: {{必须 / 应当 / 可以}}
- Связанная цель: {{G1 / G2 / …}}
- Пользовательская история: как {{角色}}, я хочу {{行为}}, чтобы {{价值}}
- Критерии приёмки:
  1. Given {{前置条件}}
     When {{操作}}
     Then {{预期结果}}
  2. Given {{边界或异常前置条件}}
     When {{操作}}
     Then {{预期结果}}
- Статус: {{待确认 / 已确认 / 已实现 / 已验证 / 已废弃}}
- Прослеживаемость: {{见需求追踪矩阵中的需求 ID}}
```

## 4. Определение полей

### 4.1 Поля документа инициации проекта

| Поле | Обязательно | Тип | Ключевые моменты заполнения | Пример |
| --- | --- | --- | --- | --- |
| Версия документа | Да | Текст | Версия по семантическому версионированию или дата | `v0.1` |
| Статус | Да | Перечисление | Черновик / на ревью / утверждён | `на ревью` |
| Решение принял | Да | Текст | Лицо, обладающее окончательным правом решения по границам и приоритетам | `Чжан Сань` |
| Позиционирование в одной фразе | Да | Текст | Целевые пользователи + ключевая возможность + проблема, ≤60 символов | Предоставить frontend-разработчикам… |
| Основание инициации | Да | Текст | Не менее одной прослеживаемой записи, формулировка «решение команды» запрещена | `ISSUE-142` |
| Цели / нецели | Да | Таблица | Каждая цель сопровождается проверяемым результатом; нецелей не менее одной | `G1: холодный запуск <2s` |
| Критерии успеха | Да | Таблица | Метрика должна иметь базовую линию, порог, способ и время измерения | `частота ошибок <0.1%` |
| Ограничения | Да | Список | Заполняются все четыре категории, при отсутствии пишется «нет» | `должен поддерживать Node 18+` |
| Требует подтверждения | Нет | Список | Используется только формат 【Требует подтверждения: имя поля】 | `【Требует подтверждения: верхняя граница бюджета】` |

### 4.2 Поля пункта требования

| Поле | Обязательно | Тип | Ключевые моменты заполнения | Пример |
| --- | --- | --- | --- | --- |
| Номер | Да | `REQ-NNN` | Трёхзначный порядковый номер, непрерывный, без повторного использования и переупорядочивания | `REQ-007` |
| Источник | Да | Текст | Прослеживается до конкретной записи | `интервью с пользователем #3` |
| Приоритет | Да | Перечисление | должен / следует / может | `должен` |
| Связанная цель | Да | Список | Соответствует номеру G в документе инициации проекта | `G1` |
| Пользовательская история | Да | Текст | Присутствуют все три элемента: роль + действие + ценность | Как…, я хочу…, чтобы… |
| Критерии приёмки | Да | Список | Не менее 1 набора Given/When/Then, обязательны граничный или исключительный случай | См. шаблон |
| Статус | Да | Перечисление | Одно из пяти состояний, только вперёд, без откатов | `подтверждено` |

## 5. Указания по заполнению

1. **Позиционирование в одной фразе**: записывается по трёхчастной формуле «для кого + что предоставляется + что решается»; если после удаления определений предложение теряет смысл, значит, отсутствует содержательная информация.
2. **Критерии успеха**: каждая метрика должна одновременно иметь базовую линию и порог. Формулировки «повысить производительность», «улучшить опыт» признаются непригодными и должны быть заменены на «время запуска P95 снижается с 3s до <1.5s».
3. **Нецели**: указываются явно исключаемые границы и критерий их определения, а не «вернёмся к этому позже»; при отсутствии непустых нецелей границы считаются неопределёнными.
4. **Номер требования**: после присвоения фиксируется навсегда; при отказе от требования статус меняется на «устарело», номер не может быть изъят или использован повторно.
5. **Критерии приёмки**: должны покрывать основной путь и хотя бы один граничный или исключительный путь; условия, не допускающие объективной оценки (например, «красивый интерфейс»), должны быть преобразованы в проверяемую метрику или пункт проверки.
6. **Пункты, требующие подтверждения**: на этапе инициации проекта такие пункты допустимы, но должны быть перечислены полностью с указанием ответственного за подтверждение; до начала разработки их число должно стать нулевым.

Типичные ошибки:

| Ошибочная формулировка | Проблема | Способ исправления |
| --- | --- | --- |
| «Сделать удобный инструмент» | Нет целевых пользователей и проверяемого результата | Дополнить ролью пользователя и пороговой метрикой |
| В нецелях указано «нет» | Границы не определены, объём легко расползается | Перечислить явно исключаемые пункты текущего этапа |
| Требование без номера, описанное прямо в тексте | Невозможно отследить и сослаться | Присвоить `REQ-NNN` и ссылаться на него повсеместно |
| В критериях приёмки указано «функция работает нормально» | Не допускает однозначного решения | Разбить на Given/When/Then |
| Предположение принимается за установленное требование | Источник не прослеживается | Указать источник «предположение» и перевести в пункты, требующие подтверждения |

## 6. Полный пример

```markdown
# Документ инициации проекта: markdown-lint-cli

Версия документа: v0.1 ｜ Статус: на ревью ｜ Решение принял: Ли Сы ｜ Дата: 2026-11-18

## Позиционирование в одной фразе
Предоставить китайскоязычным техническим авторам инструмент командной строки для проверки соответствия Markdown, что решает проблему расхождения стиля документации в разных репозиториях при отсутствии автоматической проверки.

## Предпосылки и мотивация
- Текущее положение: README в 12 репозиториях пишутся вручную разными сопровождающими, стиль не унифицирован.
- Недостатки существующих решений: универсальные англоязычные lint-инструменты не поддерживают правила пробелов между китайским и английским текстом; ручное ревью занимает в среднем 25 минут на документ.
- Окно возможностей: команда унифицирует главные страницы открытых проектов, требуется единовременное внедрение спецификации.
- Основание инициации: ISSUE-142 и протокол ревью документации, датированный 2026-11-10

## Цели и нецели
| Тип | Пункт | Проверяемый результат |
| --- | --- | --- |
| Цель G1 | Автоматическая проверка 8 категорий проблем форматирования | Доля обнаружений на 50 образцах документов ≥95% |
| Цель G2 | Контролируемое время однократной проверки | Проверка документа на 1000 строк <2s |
| Нецель N1 | Не предоставлять литературную правку содержания документа | Выводится только позиция срабатывания правила, текст не переписывается |

## Критерии успеха
| Метрика | Базовая линия | Целевое значение | Способ проверки | Время проверки |
| --- | --- | --- | --- | --- |
| Время ручного ревью | 25 минут на документ | <5 минут на документ | Контрольный эксперимент с 5 сопровождающими | до релиза v1.0 |

### REQ-001: Проверка пробелов в смешанном китайско-английском тексте
- Источник: ISSUE-142
- Приоритет: должен
- Связанная цель: G1
- Пользовательская история: как сопровождающий документации, я хочу, чтобы отсутствующие пробелы между китайским и английским текстом отмечались автоматически, чтобы унифицировать вёрстку.
- Критерии приёмки:
  1. Given документ содержит «使用Node.js开发»
     When выполняется проверка
     Then выводится номер строки и сообщение «между китайским и английским текстом отсутствует пробел»
  2. Given в этом месте документа пробел уже есть
     When выполняется проверка
     Then срабатывание этого правила не выводится
- Статус: подтверждено
```
