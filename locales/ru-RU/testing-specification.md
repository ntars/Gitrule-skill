# Спецификация тестов

> Какую задачу решает этот файл: определяет уровни тестов, шаблоны, поля и методику покрытия тестового плана и тест-кейсов, а также стандарты выполнения, чтобы каждое требование было проверяемым, а каждое изменение — воспроизводимым при регрессии.

## 1. Положения спецификации

1. Тесты делятся на три уровня: модульные, интеграционные и сквозные; для каждого уровня указываются объект тестирования и область, не охваченная тестами, чтобы избежать дублирующего покрытия.
2. Каждое требование уровня «должен» должно соответствовать как минимум одному тест-кейсу; прослеживаемость см. в [спецификации матрицы прослеживаемости требований](./requirements-traceability-matrix-specification.md).
3. При исправлении дефекта сначала добавляется регрессионный тест-кейс, затем изменяется код; регрессионный тест-кейс должен воспроизводить исходный дефект.
4. Порог покрытия задаётся проектом и вносится в CI; он не должен быть ниже установленного порога (соответствует абсолютному правилу H9).
5. Тесты должны быть воспроизводимыми и не зависеть от внешнего состояния; тесты, зависящие от внешних сервисов, должны изолироваться или использовать mock.
6. Именование тестов должно отражать проверяемое поведение и ожидаемый результат; тесты, lint, format и проверка типов должны выполняться в CI автоматически, слияние допускается только при полном зелёном результате (см. [спецификацию ревью кода](./code-review-specification.md)).

## 2. Уровни тестов

| Уровень | Объект тестирования | Что должно покрываться | Что не покрывается | Типичные инструменты |
| --- | --- | --- | --- | --- |
| Модульные тесты | Функции, модули чистой логики | Основная логика, граничные условия, ветки исключений | Межмодульное взаимодействие, внешний I/O | Runner, встроенный в язык |
| Интеграционные тесты | Взаимодействие модулей | Ключевые цепочки вызовов, адаптеры, взаимодействие с хранилищем | Полные пользовательские сценарии | Тестовый контейнер / mock server |
| Сквозные тесты | Полные пользовательские сценарии | Основные пути использования, ключевые бизнес-циклы | Исчерпывающие ветки, нагрузочное тестирование | Драйвер браузера / CLI |

## 3. Шаблон тестового плана

```markdown
# Тестовый план: {{项目名称}} {{版本号}}

Версия: {{v1.0}} ｜ Соответствующая область требований: {{REQ-001 ~ REQ-020}} ｜ Ответственный: {{姓名}}

## Область тестирования
- Включено: {{模块 / 需求编号列表}}
- Исключено: {{不在本期验证的范围及原因}}
- Связанные критерии успеха инициации проекта: {{G1 / G2}}

## Стратегия уровней
| Уровень | Объект тестирования | Цель покрытия | Инструмент | Момент выполнения |
| --- | --- | --- | --- | --- |
| Модульный | {{对象}} | {{覆盖率阈值}} | {{工具}} | Каждый коммит |
| Интеграционный | {{对象}} | {{关键链路清单}} | {{工具}} | Каждое слияние |
| Сквозной | {{场景}} | {{主要路径清单}} | {{工具}} | Каждый релиз |

## Окружение и данные
- Окружение: {{操作系统 / 运行时版本 / 依赖服务版本}}
- Тестовые данные: {{构造方式；禁止使用生产敏感数据}}
- Внешние зависимости: {{需 mock 的服务及隔离方式}}

## Условия входа и выхода
- Вход: {{进入测试的前置条件，如开发自测通过}}
- Выход: {{通过率 100%、无 P0/P1 缺陷、覆盖率达标}}
- Условия приостановки: {{阻塞性问题清单}}

## Риски и компромиссы
- Не охваченная тестами область и причины: {{例如第三方付费接口以 mock 替代}}
- Известные риски: {{例如并发场景仅做 10 路验证}}
```

## 4. Шаблон тест-кейса

```markdown
### TC-{{三位序号}}：{{用例标题}}

- Связанное требование: {{REQ-001}}
- Уровень: {{单元 / 集成 / 端到端}}
- Приоритет: {{P0 / P1 / P2}}
- Тип: {{正常 / 边界 / 异常}}
- Предварительные условия: {{环境与数据准备}}
- Шаги и ожидаемый результат:
  | Шаг | Действие | Ожидаемый результат |
  | --- | --- | --- |
  | 1 | {{操作}} | {{可判定的结果}} |
  | 2 | {{操作}} | {{可判定的结果}} |
- Очистка: {{恢复环境的操作；无则写「无」}}
```

## 5. Определения полей

### 5.1 Поля тестового плана

| Поле | Обязательно | Тип | Ключевые моменты заполнения | Пример |
| --- | --- | --- | --- | --- |
| Соответствующая область требований | Да | Список | Используется интервал номеров REQ | `REQ-001 ~ REQ-020` |
| Исключённая область | Да | Текст | Указывается причина непроведения тестов | `Платный интерфейс не тестируется: нет тестового аккаунта` |
| Цель покрытия | Да | Порог | Покрытие указывается числовым процентом | `Покрытие строк ≥80%` |
| Момент выполнения | Да | Перечисление | Коммит / слияние / релиз | `Каждое слияние` |
| Тестовые данные | Да | Текст | Заявляется способ формирования; реальные чувствительные данные запрещены | `Формируются через fixture` |
| Условия выхода | Да | Текст | Должны быть проверяемыми и включать порог уровня дефектов | `Нет открытых дефектов P0/P1` |

### 5.2 Поля тест-кейса

| Поле | Обязательно | Тип | Ключевые моменты заполнения | Пример |
| --- | --- | --- | --- | --- |
| Номер | Да | `TC-NNN` | Непрерывный, без повторного использования | `TC-007` |
| Связанное требование | Да | Список | Как минимум один номер REQ | `REQ-001` |
| Приоритет | Да | Перечисление | P0 / P1 / P2 | `P0` |
| Тип | Да | Перечисление | Нормальный / граничный / исключительный | `Граничный` |
| Шаги и ожидаемый результат | Да | Таблица | Каждый шаг должен иметь проверяемый ожидаемый результат | см. шаблон |
| Очистка | Да | Текст | При отсутствии очистки пишется «Нет»; пустое значение не допускается | `Нет` |

### 5.3 Методика расчёта покрытия

| Методика | Определение | Применимый уровень | Рекомендуемый порог |
| --- | --- | --- | --- |
| Покрытие строк | Число выполненных операторов / общее число операторов | Модульный | ≥80% |
| Покрытие ветвей | Число выполненных ветвей / общее число ветвей | Модульный | ≥70% |
| Покрытие требований | Число требований уровня «должен» с тест-кейсами / общее число требований уровня «должен» | Все уровни | 100% |
| Покрытие путей | Число проверенных основных путей / общее число выявленных основных путей | Сквозной | 100% |

Пояснение к методике: покрытие служит средством выявления непротестированных областей, а не самоцелью качества; высокое покрытие не заменяет качество утверждений, а утверждения должны проверять поведение, а не только выполнение кода.

## 6. Указания по заполнению

1. **Связанное требование**: должен указываться номер REQ; тест-кейсы, которые невозможно связать, переносятся в записи исследовательского тестирования и не включаются в официальный набор тест-кейсов.
2. **Ожидаемый результат**: должен быть проверяемым. «Возвращает правильный результат» недопустимо; «Возвращает код состояния 200 и непустое поле `name`» допустимо.
3. **Распределение типов**: для каждого требования уровня «должен» требуется как минимум один нормальный тест-кейс и один граничный или исключительный тест-кейс.
4. **Очистка**: тест-кейсы, затрагивающие файлы, базу данных и глобальное состояние, должны содержать шаги очистки; отсутствие очистки считается неполнотой тест-кейса.
5. **Регрессионные тест-кейсы**: при исправлении дефекта имя начинается с номера дефекта, например `TC-007-regression-142`.
6. **Изоляция**: тест-кейсы не должны зависеть от порядка выполнения; при необходимости общего состояния оно восстанавливается в предварительных условиях.

Типичные ошибки:

| Ошибочная формулировка | Проблема | Способ исправления |
| --- | --- | --- |
| В ожидаемом результате указано «функция работает нормально» | Непроверяемо | Указать конкретное возвращаемое значение или состояние |
| Тест-кейс не связан с требованием | Разрыв цепочки прослеживаемости | Дополнить номер REQ |
| Проверяется только нормальный путь | Пропуск граничных дефектов | Дополнить исключительные и граничные тест-кейсы |
| Тест-кейс зависит от результата предыдущего | Невозможно повторное выполнение | Восстановить состояние в предварительных условиях |
| Тестирование на производственных данных | Риск приватности и соответствия требованиям | Перейти на fixture |

## 7. Полный пример

```markdown
# Тестовый план: markdown-lint-cli v1.0

Версия: v1.0 ｜ Соответствующая область требований: REQ-001 ~ REQ-014 ｜ Ответственный: Ван У

## Область тестирования
- Включено: движок правил, разбор аргументов CLI, вывод отчёта (REQ-001 ~ REQ-014)
- Исключено: интеграция с плагином редактора (перенесено на v1.1, соответствующее требование отсутствует)
- Связанные критерии успеха инициации проекта: G1, G2

## Стратегия уровней
| Уровень | Объект тестирования | Цель покрытия | Инструмент | Момент выполнения |
| --- | --- | --- | --- | --- |
| Модульный | Функции правил | Покрытие строк ≥85% | Runner, встроенный в язык | Каждый коммит |
| Интеграционный | CLI → движок правил → отчёт | 3 ключевые цепочки | Тестовый контейнер | Каждое слияние |
| Сквозной | Пакетная проверка реального репозитория | 2 основных пути | Драйвер shell | Каждый релиз |

### TC-001: Обнаружено отсутствие пробела между китайским и английским текстом
- Связанное требование: REQ-001
- Уровень: Модульный
- Приоритет: P0
- Тип: Граничный
- Предварительные условия: загружено правило `spacing`
- Шаги и ожидаемый результат:
  | Шаг | Действие | Ожидаемый результат |
  | --- | --- | --- |
  | 1 | Ввод «使用Node.js开发» | Возвращается 1 совпадение, номер строки 1 |
  | 2 | Ввод «使用 Node.js 开发» | Возвращается 0 совпадений |
- Очистка: нет
```
