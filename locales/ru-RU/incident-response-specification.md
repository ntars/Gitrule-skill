# Спецификация реагирования на инциденты

> Какую задачу решает этот файл: определяет шаблон отчёта об инциденте, запись хронологии, шаблоны коммуникации и поля ретроспективы, обеспечивая управляемость сбоя, синхронизацию информации и накопление опыта.

## 1. Положения спецификации

1. Классификация инцидентов: P0 — ключевая функциональность недоступна или данные повреждены; P1 — серьёзное повреждение функциональности, затрагивающее большинство пользователей; P2 — локальная проблема с ограниченным влиянием.
2. Процесс реагирования: обнаружение → классификация → локализация ущерба → выявление причины → исправление → объявление; локализация ущерба приоритетнее выявления причины.
3. По каждому инциденту P0/P1 проводится ретроспектива с записью хронологии, корневой причины, влияния, действий и пунктов улучшения.
4. Пункты улучшения должны включаться в [спецификацию дорожной карты](./roadmap-specification.md) для отслеживания до закрытия.
5. Ретроспектива сосредоточена на улучшении системы и не предполагает личной ответственности.
6. Утечка секретов: немедленная ротация → очистка истории → объявление; ограничиваться коммитом удаления нельзя (см. [спецификацию безопасности и приватности](./security-and-privacy-specification.md)).
7. Ошибочный пуш больших файлов: миграция на LFS или перезапись истории (см. [спецификацию пуша и релиза](./push-and-release-specification.md)).

## 4. Определение полей

| Поле | Обязательно | Тип | Ключевые моменты заполнения | Пример |
| --- | --- | --- | --- | --- |
| Номер инцидента | Да | `INC-YYYYMMDD-NN` | Порядковый номер за день, сквозной без повторного использования | `INC-20261118-01` |
| Уровень инцидента | Да | Перечисление | P0 / P1 / P2 | `P1` |
| Длительность | Да | Длительность | Число минут от обнаружения до восстановления | `42 минуты` |
| Руководитель | Да | Текст | Единственный, отвечает за решения и синхронизацию | `Ли Си` |
| Доля затронутых пользователей | Да | Текст | Должна содержать основание оценки | `около 8%, по подсчёту логов ошибок` |
| Хронология | Да | Таблица | Каждый узел содержит время и источник | см. шаблон |
| Корневая причина | Да | Текст | Различать непосредственную и корневую причину | `Отсутствие учений по откату` |
| Пункты улучшения. Способ проверки | Да | Текст | Проверяемый, с пороговым значением | `Откат на следующем учении <5 минут` |
| Следующее обновление | Да | Момент времени | Обязательно при обработке, формулировка «обновим по мере необходимости» запрещена | `18:30` |

## 5. Указания по заполнению

1. **Классификация**: уровень присваивается по области влияния и тяжести; при неопределённости уровень завышается, затем корректируется с записью причины.
2. **Приоритет локализации ущерба**: сначала восстанавливается сервис (откат, деградация, ограничение частоты), затем выявляется корневая причина; выявление причины не должно задерживать локализацию ущерба.
3. **Хронология**: записи ведутся в порядке возникновения, источники должны быть проверяемыми (ID алерта, команда, фрагмент лога); дописывание задним числом по памяти запрещено.
4. **Корневая причина**: непосредственная причина — это событие-триггер, корневая причина — дефект системы; заполняются обе.
5. **Коммуникация**: первое уведомление должно содержать время следующего обновления; уведомление о восстановлении должно указывать способ проверки и остаточное влияние.
6. **Пункты улучшения**: не более трёх, включаются в дорожную карту для отслеживания; пункт улучшения без ответственного не может попасть в отчёт.
7. **Ретроспектива**: сосредоточена на улучшении системы и процессов, личность не оценивается; возложение ответственности и формулировки вроде «кто-то по неосторожности» не допускаются.
8. **Особые инциденты**: утечка секретов обрабатывается по H12; ошибочный пуш больших файлов — по процедуре миграции на LFS; в обоих случаях требуется отдельная фиксация.

Типичные ошибки:

| Ошибочная формулировка | Проблема | Способ исправления |
| --- | --- | --- |
| Сначала выявлять корневую причину, затем локализовать ущерб | Удлиняет время сбоя | Сначала восстановить сервис откатом |
| Хронология дописана задним числом | Факты недостоверны | Записывать непосредственно в ходе обработки |
| В корневой причине написано «кто-то по неосторожности» | Персональная ответственность, нет ценности для улучшения | Дойти до уровня процесса или инструментов |
| В уведомлении написано «исправим как можно скорее» | Нет времени следующего обновления | Указать конкретный момент |
| Пункт улучшения без способа проверки | Закрытие невозможно определить | Дополнить порогом и моментом проверки |

## 6. Полный пример

```markdown
# Отчёт об инциденте: INC-20261118-01

- Уровень инцидента: P1
- Время обнаружения: 2026-11-18 10:12
- Время восстановления: 2026-11-18 10:54
- Длительность: 42 минуты
- Руководитель: Ли Си
- Текущий статус: ретроспектива завершена

## Область влияния
| Измерение | Пояснение |
| --- | --- |
| Затронутая функциональность | API проверки правил возвращает 5xx |
| Доля затронутых пользователей | около 8%, по подсчёту логов 5xx |
| Влияние на данные | нет |
| Влияние на бизнес | в течение 42 минут невозможно отправить задачу проверки |

## Корневая причина
- Непосредственная причина: путь загрузки плагина правил был перекрыт новой конфигурацией, что привело к сбою запуска.
- Корневая причина: изменение конфигурации не было включено в предрелизную проверку.

## Пункты улучшения
| Номер | Действие | Ответственный | Срок | Способ проверки | Статус |
| --- | --- | --- | --- | --- | --- |
| A-01 | Включить изменения конфигурации в предрелизный контрольный список | Ван У | 2026-11-25 | В следующих 5 изменениях есть записи о проверке | не начато |
```
